# Conformance

The behaviour of the conformance vectors is the recipe
[`conformance_verification`](../../contracts/fixtures/conformance_verification/conformance_verification.json), which each
of the six implementations runs on MySQL, PostgreSQL and SQLite through its recipe helper
([feature coverage](../../docs/spec/feature-coverage.md) FCV-3). A new behaviour is a new case of that recipe.

What cannot be a recipe step stays here, as a native body in the runner of each implementation:

- the bodies that call generated methods, which a recipe step does not reach; each output compares with the expects of the
  recipe case of the same name;
- the fixed-clock bodies, because `FixClock` is a test entry point of each client ([protocol](../../docs/spec/protocol.md)
  3.3); each output compares with `check/fixed_clock.json`.

`make conformance-check` runs both on the bench databases of its run (`make orm-check` or `make run-databases`), and the
result helpers of the runners.

| file | role |
|---|---|
| `vectors.json` | the vector names and the requirements they test; each name is a recipe case or a fixed-clock body |
| `packages/go/internal/conformance/main.go` | Go runner (generated models in `packages/go/model`) |
| `packages/php/testing/conformance/runner.php` | PHP runner (PDO); also used with the PHP extension loaded for `php-extension` |
| `packages/rust/tests/src/conformance.rs` | Rust runner (models from `polyspec-orm-build`, sqlx) |
| `packages/ts/testing/conformance/runner_typescript.mts` | TypeScript runner (native database drivers) |
| `packages/python/testing/conformance/runner_python.py` | Python runner (models generated by `orm-gen` into the run's Python models directory) |
| `check/recipe_vectors.mts` | runs a body and compares its output; its test also holds each state contract of `contracts/interfaces.json` against its recipe case |
| `check/state.mts` | prints the state digest of a database, which the checks that a test leaves its database as it was read |
