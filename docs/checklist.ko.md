# 프로젝트 체크리스트 (0.0.1 완료)

표기: `[ ]` 대기, `[~]` 진행 중, `[o]` 완료, `[!]` 일시 우회.

## dbspec schema language

- [~] T8 Mermaid schema source를 schema의 source of truth인 neutral schema language dbspec으로 교체한다. 우선순위: 최우선. 원인: Mermaid 방언은 physical schema를 손실 없이 표현하지 못하고, field 이름이 동작을 고르며, 생성된 이름이 변형되고, dialect 기능이 조용히 빠지며, hidden marker로 trigger와 `.sql` source를 복원한다. 완료 기준: T8.0–T8.8이 Go/PHP/Rust/TypeScript에서 conformance와 MySQL/PostgreSQL/SQLite evidence로 완료된다. 작업은 worktree `orm-dbspec-T8`에서 하고, 모든 항목이 통과한 뒤에만 `main`에 merge한다.
- [o] T8.0 MySQL, PostgreSQL, SQLite 사이의 schema 문법과 의미 차이를 모두 기록하고 기능별 neutral 지원 여부를 판정한다(T8 선행). 원인: dbspec은 공통 정의가 하나 있고, 세 DB에서 의미가 같고, introspection으로 복원되는 기능만 지원한다. 이 규칙을 적용하려면 완전한 사실이 필요하다. 완료 기준: `docs/dialects.md`와 한국어 짝 문서가 type, length/precision, null, default, identity, generated column, key, index, FK, CHECK, comment, collation, namespace와 식별자 규칙, 시간 type과 time zone, enum, unsigned, trigger, DDL transaction, catalog 원천을 다룬다. 각 행은 DB별 문법과 의미, neutral 정의와 렌더링 또는 미지원 사유, introspection 원천을 적는다. 각 판정은 `.runtime` DB에 대한 추적되는 공유 `tests/*` case로 검증한다. 증거: `make dialect-facts-check TEST_ENV=<main checkout>/.runtime/servers/env`를 두 번 실행해 실패 없이 probe 239개(MySQL 8.4.11 98개, PostgreSQL 17.11 75개, modernc v1.58.0의 SQLite 3.53.4 66개)가 1.705초와 1.637초에 통과했고 매번 SQLite 파일 이름 case 4개도 통과했다. 각 probe는 자기 database, schema, file을 삭제하고 확인한다. `docs/dialects.md`와 한국어 짝 문서는 기능별로 데이터베이스별 문법과 의미, probe ID, 공식 출처, 중립 rendering 또는 미지원 사유, introspection 출처를 기록하고 client별 SQLite library를 기록한다(Go, PHP, Node 3.53.4, Rust bundled 3.51.3은 probe하지 않음). dbspec은 UTC 연결 규칙을 가진 local `datetime(p)`(시점은 미지원, `timestamptz` 컬럼은 mapping하지 않고 변환)와 `manifestHash`에 속하는 실행기 수정 시각 기록을 지원한다. Audit context 정의는 T8.1 review로 남긴다. 사실과 맞지 않는 결함은 T8.0.1–T8.0.11, T8.0.13, T8.0.14다. `checklist-check`, `docs-rules-check`, `docs-check`, `docs-verify-idempotent`가 통과한다.
- [ ] T8.0.1 PostgreSQL 컬럼 import를 schema별로 복원한다(T8.0 선행). 원인: 컬럼 질의가 `pg_class`를 `relname`만으로 join한다(`internal/ormgen/import.go:589`, `clients/php/src/SchemaImport.php:271`, `clients/rust/orm-build/src/catalog/reader.rs:204`, `clients/typescript/src/tools/introspect.ts:135`). Table 이름은 schema마다만 고유하므로(`postgres.namespace.relname_per_schema`) 다른 schema에 같은 이름의 relation이 있으면 import한 컬럼이 반복된다. PostgreSQL을 사용할 수 없어 import 자체는 실행하지 않았다. 완료 기준: T8.4가 `relnamespace`로 join하고, 두 번째 schema에 같은 이름의 table이 있는 추적 case가 모든 client에서 컬럼 집합 하나를 import한다.
- [ ] T8.0.2 import가 버리거나 거부하는 index 기능을 보고한다(T8.0 선행). 원인: `ormgen import`에서 관찰했다. MySQL functional index와 SQLite 식 index는 `converting NULL to string is unsupported`로 import를 중단한다(`internal/ormgen/import.go:194-196`, `internal/ormgen/migrate.go:285-287`). MySQL prefix index와 SQLite partial index는 전체 index로 import한다(`import.go:187-207`, `migrate.go:263-283`). PostgreSQL reader는 식 key(`indkey` 0)를 `pg_attribute`와 join하며 `indpred`와 `indoption`을 읽지 않는다(`import.go:653-691`, 실행하지 않음). 완료 기준: T8.4가 prefix, partial, 식 index를 위치와 함께 미지원 객체로 보고하며, 해당 데이터베이스의 추적 case가 모든 client에 있다.
- [ ] T8.0.3 생성 컬럼을 일반 컬럼으로 import하지 않고 보고한다(T8.0 선행). 원인: 관찰 결과 MySQL `b int AS (a+1) STORED`는 `GENERATION_EXPRESSION`을 읽지 않아 일반 nullable `int`로 import된다(`internal/ormgen/import.go:130-131`). SQLite `pragma_table_info`는 생성 컬럼을 빼므로 import가 이를 버린다(`internal/ormgen/migrate.go:225`). 완료 기준: T8.4가 세 데이터베이스에서 생성 컬럼을 위치와 함께 미지원으로 보고하며 모든 client에 추적 case가 있다.
- [ ] T8.0.4 식별자 한도를 넘는 이름을 생성하지 않고 거부한다(T8.0 선행). 원인: 관찰 결과 65자 `%% index` 이름은 제한 없이 MySQL `KEY`로 생성되고 MySQL이 DDL을 거부한다(1059)(`internal/ormgen/ddl.go:138`, fulltext `ddl.go:141`). Trigger와 함수 이름은 table 이름에 접미사를 제한 없이 붙여(`internal/ormgen/triggers.go:61-66`, `101-102`, `165-167`) 77자 MySQL trigger 이름과 70자 PostgreSQL trigger 이름을 생성하며 PostgreSQL은 이를 63바이트로 자른다(`postgres.ident.truncated_to_63`). 완료 기준: T8.3이 63바이트를 넘는 선언·생성 이름을 생성 전에 거부하며 모든 client에 추적 case가 있다.
- [ ] T8.0.5 foreign key 동작이 행을 바꿀 때 같은 audit 변경을 기록한다(T8.0 선행). 원인: MySQL은 foreign key 동작으로 바뀐 행에서 trigger를 실행하지 않고(`mysql.fk.cascade_skips_triggers`) PostgreSQL과 SQLite는 실행한다(`postgres.fk.cascade_fires_triggers`, `sqlite.fk.cascade_fires_triggers`). 따라서 `mode=changes` audit trigger(`internal/ormgen/triggers.go:378-437`)는 PostgreSQL과 SQLite에서만 cascade 변경을 기록한다. 완료 기준: T8.3이 `cascade`나 `set_null` foreign key의 자식 table에 대한 audit·immutable setting을 거부하며, 세 데이터베이스의 추적 case가 모든 client에 있다.
- [ ] T8.0.6 일치하는 행이 없는 문장에서 immutable guard를 같게 만든다(T8.0 선행). 원인: PostgreSQL guard는 `FOR EACH STATEMENT` trigger이며(`internal/ormgen/triggers.go:110`, `clients/php/src/SchemaTriggers.php:101`, `clients/rust/orm-schema/src/triggers.rs:112`, `clients/typescript/src/engine/triggers.ts:81`) 일치하는 행이 없는 `UPDATE`나 `DELETE`도 실패시킨다(`postgres.trigger.statement_fires_on_zero_rows`). MySQL과 SQLite row guard는 실행되지 않는다(`mysql.trigger.zero_rows_not_fired`, `sqlite.trigger.zero_rows_not_fired`). `TRUNCATE`도 PostgreSQL에서만 다룬다. 완료 기준: T8.3이 세 데이터베이스에서 row 수준 `UPDATE`·`DELETE` guard를 생성하고, 0행 추적 case가 모든 client의 세 데이터베이스에서 통과한다.
- [ ] T8.0.7 PostgreSQL에서 명시 key 뒤에도 자동 key를 유효하게 유지한다(T8.0 선행). 원인: `GENERATED BY DEFAULT AS IDENTITY`(`internal/ormgen/ddl.go:539`, `clients/php/src/SchemaDdl.php:542`, `clients/rust/orm-schema/src/ddl.rs:230`, `clients/typescript/src/engine/ddl.ts:163`)는 명시 key 뒤로 진행하지 않아 다음 생성 key가 23505로 실패하고(`postgres.identity.by_default_not_advanced`), MySQL과 SQLite는 계속 진행한다(`mysql.auto_increment.explicit_value_advances`, `sqlite.autoincrement.explicit_value_advances`). 완료 기준: 클라이언트가 명시 자동 key를 거부하고, 명시 key를 쓰는 PostgreSQL apply 단계가 identity sequence를 맞추며, 세 데이터베이스의 추적 case가 모든 client에 있다.
- [ ] T8.0.8 MySQL text 컬럼에 binary collation을 생성한다(T8.0 선행). 원인: DDL은 각 MySQL table 끝에 `DEFAULT CHARSET=utf8mb4`를 쓰며(`internal/ormgen/ddl.go:146`, `clients/php/src/SchemaDdl.php:134`, `clients/rust/orm-schema/src/ddl.rs:564`, `clients/typescript/src/engine/ddl.ts:360`) 이는 `utf8mb4_0900_ai_ci`를 선택한다(`mysql.collation.default_accent_case_insensitive`). 따라서 MySQL unique key와 비교는 `a`, `A`, `á`를 같게 보지만 PostgreSQL `C`와 SQLite `BINARY`는 그렇지 않다. 완료 기준: T8.3이 `utf8mb4_0900_bin`과 PostgreSQL `COLLATE "C"`를 생성하며, 세 데이터베이스의 unique key 추적 case가 모든 client에 있다.
- [ ] T8.0.9 `datetime(p)`를 UTC 연결 규칙의 local date-time으로 생성한다(T8.0 선행). 원인: `datetime`은 MySQL `DATETIME`, PostgreSQL `timestamp with time zone`, SQLite 텍스트로 생성되며(`internal/ormgen/ddl.go:487`과 client 포팅) introspection이 복원할 수 없고 이제 `docs/dialects.md`가 거부한다. SQLite `=now` 기본값은 UTC를 쓰지만(`ddl.go:553`, `sqlite.datetime.now_is_utc`) dialect 규칙은 SQLite date-time이 연결 시간대를 쓴다고 기록한다. 완료 기준: T8.3이 MySQL `DATETIME(p)`, PostgreSQL `timestamp(p)`, renderer CHECK를 가진 SQLite 텍스트를 생성하고, 모든 client가 각 연결에 UTC를 설정하며, introspection이 `timestamptz`와 MySQL `TIMESTAMP`를 미지원으로 보고하고, 세 데이터베이스의 추적 case가 모든 client에 있다.
- [ ] T8.0.10 SQLite primary key nullability를 선언대로 import한다(T8.0 선행). 원인: 관찰 결과 `ormgen import`는 `k TEXT PRIMARY KEY`를 NOT NULL로 쓰지만(`internal/ormgen/migrate.go:238`) SQLite는 이 컬럼에 NULL을 받는다(`sqlite.pk.nullable_non_integer`). 완료 기준: T8.4가 `pk`에서 추론하지 않고 `notnull`을 읽으며 모든 client에 SQLite 추적 case가 있다.
- [ ] T8.0.11 import가 다른 정의로 바꾸는 catalog 타입과 동작을 보고한다(T8.0 선행). 원인: PostgreSQL `timestamp`와 `timestamptz`, `time`과 `timetz`, `char(n)`과 `varchar(n)`, `real`과 `double precision`, `json`/`jsonb`와 텍스트를 각각 한 타입으로 import하지만(`internal/ormgen/import.go:845-877`) 저장 값이 다르다(`postgres.char.padded`, `postgres.float.real_single_precision`, `postgres.json.text_jsonb_normalized`). Foreign key update 동작은 읽지 않으며 `RESTRICT`, `NO ACTION`, `SET DEFAULT`는 기본값으로 import한다(`import.go:518-527`, 관찰 결과 MySQL `ON UPDATE CASCADE`가 빠진다). 완료 기준: T8.4가 지원하는 정의는 정확히 복원하고 나머지는 미지원으로 보고하며 모든 client에 추적 case가 있다.
- [o] T8.0.12 PostgreSQL probe 증거를 완성한다(T8.0 선행). 원인: T8.0 진행 중 `TEST_ENV`의 PostgreSQL primary와 replica가 삭제된 경로에 설정된 data directory 때문에 멈췄다. 이후 운영자가 현재 경로에서 서버를 다시 시작했고 `BENCH_SQLITE_DSN`도 현재 경로를 쓴다. 증거: 다시 시작한 서버에서 PostgreSQL probe 75개가 모두 두 번 통과했다. 이전에 실행하지 않은 `postgres.index.varchar_640_four_byte_fits`, `postgres.render.time_of_day_check`, `postgres.collation.c_codepoint`의 `COLLATE "C"` catalog 단계도 포함하며 기록과 다른 PostgreSQL 사실은 없었다.
- [ ] T8.0.13 DSN query를 이름에 포함한 SQLite 파일을 만든 opener를 찾는다(T8.0 선행). 원인: 이전 `.runtime/servers`에 빈 파일 `orm_bench.sqlite?_pragma=busy_timeout(5000)&timezone=%2B00:00`(2026-09-26)이 있었으므로 어떤 프로그램이 query를 파일 이름에 포함한 채 `BENCH_SQLITE_DSN`을 열었다. `TestSQLiteFileNameWithQuery`가 방식을 재현한다. PHP PDO, `node:sqlite`, `sqlite3` shell은 그 이름의 파일을 만들고 `modernc.org/sqlite`는 query를 해석한다. 현재 Go, PHP, TypeScript, Rust 적합성 실행기와 Go, PHP, TypeScript `import` 도구를 같은 DSN 형식으로 bench 파일 사본에 실행했을 때 그런 파일은 생기지 않았으므로 현재 tree에서 해당 경로를 찾지 못했다. 완료 기준: 각 client의 DSN 테스트와 SQLite DSN을 여는 각 도구가 경로만 파일 이름이 됨을 확인하며, 찾은 opener는 추적 RED case와 함께 수정한다.
- [ ] T8.0.14 Go client에서 실패한 MySQL context 초기화를 전달한다(T8.0 선행). 원인: MySQL user variable은 `COMMIT`과 `ROLLBACK` 뒤에도 남고(`mysql.context.user_variable_session_scope`), Go client는 transaction 끝의 ``SET @`orm.<key>` = NULL`` 오류를 버린다(`clients/go/orm/utils.go:152`). 따라서 초기화가 실패하면 audit operation id가 오류 없이 pool 연결에 남는다. PHP, Rust, TypeScript는 오류를 전달한다. 완료 기준: 초기화가 실패하는 추적 Go RED case가 오류를 보고하고 다른 client도 같은 case를 유지한다.
