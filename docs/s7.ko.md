## 공통 완료 조건

S7 항목은 구현·테스트·문서·정적 게시를 모두 완료해야 닫는다. Go·PHP·Rust·TypeScript에서 같은 논리 구조를 사용할 수 없는 기능은 구현하지 않는다.

기본 compiler 경로는 PHP Unix socket, Go in-process, Rust WASM이다. TypeScript는 Connect/Protobuf compiler 경로를 사용한다. 이 경로들은 지원하는 실행 경로다. 네 client는 같은 request, plan, 실행, result, error 자료 구조를 공개한다. Connect/Protobuf는 공통 상호 운용 경로이며, 설정이 지정한 경우 client는 선언된 기본 경로를 사용한다.

## T7.3 마이그레이션 명령

```sh
go run ./cmd/ormgen diff \
  --from old-schema.json \
  --to schema/schema.json \
  --dialect mysql \
  --out migration.sql
```

이 명령은 파괴 옵션 없이 `ADD COLUMN`과 신규 테이블 SQL을 생성한다. 테이블 삭제, 컬럼 삭제, 컬럼 정의 변경이 있으면 실패한다. 파괴 SQL을 검토한 경우에만 `--allow-destructive`를 추가한다.

## T7.7 precompile 명령

```sh
go run ./cmd/ormgen precompile \
  --schema schema/schema.json \
  --dialect mysql \
  --in request.json \
  --out plan.json
```

출력에는 `version`, `schema_hash`, `dialect`, `request_sha256`, `plan`이 포함된다. 클라이언트는 plan을 로드하기 전에 `schema_hash`를 비교한다.

Client는 bundle을 생성한 value-free request와 함께 등록한다. Go는 `db.LoadPlanBundle(bytes, req)`, PHP는 `Orm::transport()->loadPlanBundle($bundle, $req, $kind)`, Rust는 `db.load_plan_bundle(&bytes, &mut req)`, TypeScript는 `db.loadPlanBundle(bundle, request)`를 사용한다. 각 loader는 metadata version, schema hash, dialect, request kind, request hash 존재 여부, plan body를 검사한 뒤 bounded plan cache에 저장한다. 이후 일치하는 request는 compiler를 호출하지 않고 cache의 plan을 사용한다. Schema 또는 dialect가 client와 다르면 bundle은 유효하지 않다.

컴파일러 wire 정의는 `proto/orm/compiler/v1/compiler.proto`다. 전체 request tree, tenant scope parameter, write field, assembly tree, bind metadata, compiler 오류, server metadata를 포함한다. `scripts/proto/generate.sh`는 버전을 고정한 plugin으로 Go·PHP·Rust·TypeScript message type을 생성한다. `ormd -listen 127.0.0.1:8080 -schema schema/schema.json`은 Connect unary 경로에서 binary Protobuf를 처리한다. `make proto-check`는 server를 시작하고 네 `CompilerTransport` 구현이 동일한 metadata와 plan을 반환하는지 검사한다. 네 executor는 plan cache miss에 이 전송을 사용하며 MySQL·PostgreSQL·SQLite 데이터베이스 벡터 63개를 통과한다.

## T7.4 scope 지시문

```text
%% scope battle service_seq
```

지시문은 존재하는 NULL 불가 정수·문자열·enum 컬럼을 요구한다. 생성 클라이언트는 query 객체에만 `scope(value)`를 제공한다. request는 parameter index를 사용자 predicate tree와 분리된 `query.scope_p`에 저장한다.

| 동작 | Scope 처리 |
|---|---|
| root select, update, delete | 전체 사용자 WHERE group 외부에 scope 조건을 추가한다. |
| join | LEFT JOIN을 포함한 JOIN ON에 join entity의 scope를 추가한다. |
| relation | relation query WHERE에 child scope를 추가한다. |
| insert | 선언된 scope 컬럼과 scope parameter를 추가한다. 명시적인 대입은 같은 parameter index를 사용해야 한다. |
| update와 upsert | 선언된 scope 컬럼 대입을 거부한다. |
| raw SQL | compiler가 안전한 삽입 위치를 결정할 수 없으므로 scoped request를 거부한다. |

`%% scope`가 없는 entity에서 `scope(value)`를 호출하면 `IR_INVALID`를 반환한다. update와 delete에는 명시적인 사용자 WHERE group이 계속 필요하다. 단위 테스트는 OR 우선순위, join ON 위치, relation 단계, 쓰기 제한, 잘못된 request를 검사한다. 물리 테스트는 네 클라이언트에서 MySQL·PostgreSQL·SQLite의 tenant 분리를 검사한다.

## T7.6 데이터베이스 행 streaming

`stream(visitor)`는 select 문 하나를 실행하고 결과 collection을 생성하지 않으며 각 행마다 visitor를 한 번 호출한다. 각 행은 자체 값을 소유한다. `false`를 반환하면 순회를 중지하고 `true`를 반환하면 계속한다. 결과는 `state`(`stopped` 또는 `exhausted`)와 `count`를 포함하며 `false`를 반환한 행도 횟수에 포함한다.

| 클라이언트 | 예제 |
|---|---|
| Go | `Battle().Using(ctx, db).Stream(func(row *BattleRow) bool { return handle(row) })` |
| PHP | `Battle::query()->using($db)->stream(fn(BattleRow $row): bool => handle($row))` |
| Rust | `battle::query().using(&db).stream(|row| handle(row)).await?` |
| TypeScript | `await Battle().using(db).stream(async row => handle(row))` |

실행 전에 query를 DB에 지정해야 한다. SQL join은 root 문 하나를 사용하므로 지원한다. 별도 relation 문이 있는 plan은 cursor를 열기 전에 `IR_INVALID`를 반환하며 이 경우 `gets()`를 사용한다. visitor 누락, 잘못된 plan, decode 실패, driver 실패, 언어 런타임의 취소는 기존 오류 분류를 반환한다. callback 예외를 지원하는 언어에서는 visitor 오류를 그대로 반환한다. 모든 종료 경로는 반환 전에 cursor를 닫고 빌린 pool connection을 반환한다. callback의 `false` 반환은 네 언어의 공통 취소 방법이다.

공통 `interface_stream` 벡터는 세 번째 행에서 취소, 네 행 전체 순회, 행 값의 독립성, relation 거부, 실행 문 두 개를 검사한다. Go·PHP·Rust·TypeScript에서 MySQL·PostgreSQL·SQLite를 대상으로 실행한다.

```sh
go run ./tests/conformance/check run
go run ./tests/interfaces/check --results tests/conformance/out
make ts-check rust-check
```

## T7.10 다중 문장 제외

공개 IR과 생성 클라이언트에는 다중 문장 옵션이 없다. `multi_statement`를 포함한 요청은 SQL 실행 전에 `IR_INVALID`를 반환한다. 인터페이스 manifest가 정규화된 심볼 이름을 금지하므로 구조 검사는 모든 생성 클라이언트의 `multi_statement`, `multiStatement`, `MultiStatement` 선언을 거부한다.

| 데이터베이스 | 제약 사항 |
|---|---|
| MySQL | 다중 문장 실행에는 별도 드라이버 옵션과 다중 결과 처리가 필요하다. |
| PostgreSQL | 매개변수를 사용하는 prepared 실행은 한 문장에 여러 명령을 허용하지 않는다. |
| SQLite | 지원 드라이버 API는 한 번에 한 문장을 prepare하고 실행한다. |

relation plan은 순서가 지정된 `steps` 배열을 유지한다. 각 종속 단계는 상위 값이 준비된 뒤 실행한다. 이 구조는 모든 지원 클라이언트와 데이터베이스에서 매개변수 binding, 실패 위치, 문장 수를 동일하게 유지한다. 거부된 요청은 SQL을 실행하지 않고 query 상태와 데이터베이스 상태를 변경하지 않는다.

```sh
go test ./engine ./tests/interfaces/check
go run ./tests/interfaces/check --self-test
```

## T7.11 행 스캔 최적화

Go는 엔티티별 기본 flat projection에 고정 scanner를 생성한다. primitive 필드는 `database/sql.Rows.Scan`에 직접 전달하고 datetime과 codec 출력은 이름이 지정된 임시 값을 사용한다. projection 변경, expression, join, relation, 추가 plan 단계가 있으면 positional assembly 경로를 사용한다. MySQL·PostgreSQL·SQLite 통합 테스트가 두 경로를 검사한다.

PHP는 `PDO::FETCH_NUM` 행을 생성 행의 positional 저장소로 사용한다. PDO에는 Go의 `Rows.Scan`과 같은 typed destination 인터페이스가 없다. `fetch()`로 행마다 객체를 즉시 생성하는 구현은 측정된 100행 시간을 약 425µs에서 511µs로 증가시켜 제거했다. PHP는 `fetchAll(PDO::FETCH_NUM)` 후 생성 행을 구성한다.

기존 Go·PHP native benchmark는 lazy가 아닌 `price`, `ip` 컬럼을 누락했다. 현재 benchmark는 생성 클라이언트와 같은 기본 projection을 사용한다. PHP 기준선은 같은 생성 행 결과도 구성한다. 2026-09-12에 MySQL 8.4에서 세 번 연속 실행한 중앙 비율은 다음과 같다.

| workload | Go client/native | PHP client/native | 제한 |
|---|---:|---:|---:|
| PK 행 | 0.48 | 1.12 | 1.35 |
| 100행 목록 | 1.05 | 0.96 | 1.25 |

제한은 기존 S6 회귀 제한이며 T7.11에서 변경하지 않았다. 이전 S5의 3행 ≤5% 목표는 schema에 컬럼과 codec을 추가한 뒤 서로 다른 작업을 비교했다. 현재 검사는 같은 projection과 typed 결과를 비교한다. PHP는 표본 실행 순서를 교대로 배치하고 Go는 같은 process에서 측정해 시간 편차를 줄인다.

```sh
make perf-check
```

## T7.13 AES 키 로테이션

AES 컬럼이 있는 entity는 NULL 불가 정수 `aes_key_version` 컬럼을 요구한다. 버전 컬럼은 평문 메타데이터이며 인코딩 스타일을 가질 수 없고 기본 projection에서 제외한다. `npm run schema:check`와 schema builder는 잘못된 선언을 거부한다. schema builder는 컬럼 prefix에서 AES style을 추론할 수 있지만, 생성과 회전은 `schema.json`에 확정된 `styles` 목록을 사용한다. 실행 코드는 컬럼 이름 prefix를 검색하지 않는다.

AES entity의 신규 행은 AES 값이 NULL인 경우도 설정된 현재 버전을 저장한다. 한 행의 모든 AES 컬럼은 하나의 버전을 사용한다. AES 데이터를 변경하는 update와 upsert의 duplicate update 분기는 모든 AES 컬럼을 대입해야 한다. 일부만 대입하면 `IR_INVALID`를 반환한다. planner는 전체 대입을 검사한 뒤 현재 버전을 저장한다. 생성 클라이언트는 `aes_key_version` setter를 제공하지 않고, 직접 대입 요청은 `IR_INVALID`를 반환한다. 버전 bind는 일반 설정 메타데이터이며 secret으로 masking하지 않는다.

```toml
[secrets]
aes_version = 2

[secrets.aes_keys]
1 = "old-key"
2 = "current-key"
```

생성 entity API는 각 클라이언트에서 같은 입력과 결과를 사용한다.

| 클라이언트 | 상태 조회 | 회전 |
|---|---|---|
| Go | `Battle().Using(ctx, db).AESStatus(keyring)` | `Battle().Using(ctx, db).RotateAES(keyring)` |
| PHP | `Battle::query()->using($db)->aesStatus($keyring)` | `Battle::query()->using($db)->rotateAES($keyring)` |
| Rust | `battle::query().using(&db).aes_status(&keyring).await?` | `battle::query().using(&db).rotate_aes(&keyring).await?` |
| TypeScript | `Battle().using(db).aesStatus(keyring)` | `Battle().using(db).rotateAES(keyring)` |

상태 조회는 설정된 현재 버전, 전체 행 수, 회전 대상 행 수, 저장 버전별 행 수를 반환한다. 회전은 대상 행만 선택한다. 선언 순서의 모든 primary key 컬럼, 저장 버전, 모든 AES 컬럼을 읽고, 저장 버전의 키로 모든 AES 컬럼을 decode한 뒤 현재 키로 encode하며, 모든 AES 컬럼과 버전을 하나의 transaction에서 update한다. update 조건에 모든 primary key 컬럼과 이전 버전을 포함한다. 동시 변경은 `OPTIMISTIC_LOCK`을 반환한다. 키가 없으면 `CONFIG`, 버전 메타데이터나 암호문이 잘못되면 `CODEC_DECODE`를 반환한다. 오류가 발생하면 transaction을 rollback한다. 회전을 반복 실행하면 변경 행 수 0을 반환한다.

조회는 저장된 `aes_key_version`으로 `secrets.aes_keys`의 key를 선택한다. 회전 전에 저장된 모든 version의 key를 설정한다. 새 version을 write current version으로 지정하고, 상태 조회, 제한된 batch 회전, `pending = 0` 확인, database 검증 순으로 실행한다. PHP는 `batch_size`, TypeScript는 `batchSize`, Rust specification은 `batch_size`, Go는 같은 generated specification field를 사용한다. 기본 batch는 최대 1000행이며 pending 행은 다음 호출에서 다시 선택한다. 보존 기간이 지난 뒤 이전 key를 제거한다.

```sh
go test -tags physical ./clients/go/orm -run TestPhysicalAESRotation -count=1
npm run typescript:check
node tests/typescript/database.mjs
```

물리 테스트는 전용 테이블을 생성하고, 모든 AES 컬럼이 있는 이전 버전 행을 추가하고, 상태를 조회하고, 회전하고, 현재 키로 decode하고, 두 번째 회전의 변경 행 수가 0인지 검사한다. `scripts/db-test.sh`는 `containerctl`로 MySQL과 PostgreSQL 경우를 실행하고 클라이언트 테스트는 SQLite 경우도 실행한다.

## T7.15 마이그레이션 복구

`ormgen recover`는 검토한 구조화 plan 또는 `ormgen migrate`가 기록한 migration ID를
입력으로 받는다. 데이터베이스 마이그레이션 잠금을 획득한 뒤 이력 상태와 실제 schema를
조회한다. 실제 DB가 도착 schema와 일치하면 `applied`, 출발 schema와 일치하면 `retryable`을
기록한다. 그 외 상태는 이력과 파일 로그를 변경하지 않고 `MIGRATION_RECOVERY_UNSAFE`를
반환한다. MySQL·PostgreSQL·SQLite에 같은 상태 전이를 적용한다. 명령 형식과 결과 표는
[usage.ko.md](usage.ko.md)에 있다.

## T7.17 마이그레이션 입력

DDL, diff, plan, migrate, verify, apply, recover는 공통 loader로 schema 입력을 처리한다. 입력은 Mermaid 파일, manifest JSON 파일, ORM 생성 SQL 파일, `db:<dsn>`이다. `ormgen ddl`과 `ormgen diff`가 생성한 SQL은 결정적인 `orm-schema-v1` metadata를 포함한다. loader는 사용 전에 embedded manifest hash를 검사한다. 이 metadata가 없는 SQL은 scope, codec style, named predicate, relation option을 표현할 수 없으므로 `MIGRATION_SOURCE_LOSS`를 반환한다. 구조화 plan은 검증된 정방향·rollback 작업을 포함한다. `ormgen rollback`은 실행 전에 plan, history, 실제 target schema, destructive 위험 승인을 검사하고, 실행 후 source schema와 파일 로그를 검증한다. 명령 행렬과 예제는 [usage.ko.md](usage.ko.md)에 있다.

실제 schema 조회는 `aes_key_version`이 없는 AES column을 거부한다. target MMD·JSON·생성 SQL·live database 검증에는 NULL 불가 정수 version column이 필요하다. Runtime은 이전 ECB 형식의 변환 또는 호환 경로를 제공하지 않는다.
