# 기능 coverage 검증

`contracts/features.json`의 각 기능은 `coverage.kind`, 중복되지 않는 `coverage.cases`, `coverage.owners`, `coverage.dependents`를 선언한다. 데이터베이스를 읽거나 바꾸는 동작에는 `database`, 그 외에는 `independent`를 쓴다. 상태가 `pass` 또는 `partial`인 모든 client는 `packages/<runtime>` 아래에 `part`, `tests`, 필요한 각 데이터베이스(`mysql`, `postgres`, `sqlite`) 또는 `none` 한 칸의 언어별 테스트 명령을 선언한다. 각 사용 부분은 자기 디렉터리에 별도 사례와 테스트를 선언한다. 선언이 빠지거나 선언한 부분 밖의 경로이면 `make feature-check`가 실패한다.

각 데이터베이스 칸에는 `runner`(`node`, `php`, `python`, `go`, `cargo`), `test`(`tests`에 선언된 정확한 경로), 중복되지 않는 `cases`를 가진 명령 객체 배열을 둔다. 선언된 모든 테스트와 사례는 정확히 한 번 있어야 한다. 데이터베이스 명령은 데이터베이스 URI를 담은 필수 환경 변수 이름 `dsn_env`도 지정한다. 검사기는 셸 문자열과 추가 명령 필드를 거부한다. Node, Python 테스트 파일에는 선언된 사례 ID를 인자로 전달하며 테스트는 검증을 통과한 뒤에만 출력한다. 데이터베이스가 없는 항목의 테스트는 `CASE <id> PASS`를 출력하고, 데이터베이스 항목의 테스트 파일은 manifest가 파일에 선언한 데이터베이스마다 한 번 실행되며 사례와 데이터베이스마다 `CASE <id> [<database>] PASS`를 출력한다. 검사기는 각 항목의 데이터베이스 줄만 취하고, 데이터베이스 항목의 줄에 대괄호가 없으면, 데이터베이스가 없는 항목의 줄에 대괄호가 있으면, 같은 `(id, database)` 쌍이 두 번 나오면 거부한다. PHP 테스트 파일은 사례 `<id>`가 method `test_<id>`인 PHPUnit test class다. 검사기는 `vendor-php/bin/phpunit --teamcity`를 `packages/php/phpunit.xml.dist`와 선언된 method의 고정된 filter로 실행하고, 사례를 TeamCity `testStarted`와 `testFinished` event로 관찰한다. `testFailed`나 `testIgnored` event는 실행을 실패시킨다. Python은 `ORM_PYTHON`이 가리키는 interpreter에서 실행하며, 그 interpreter에 설치된 client를 import한다: `make feature-coverage`와 `make owner-check`가 `make install-python`의 venv를 넘기고, `ORM_PYTHON`이 없으면 검사기는 다른 `python`을 실행하지 않고 Python 단위를 실패시킨다. implemented 기능은 Go, PHP, Rust, TypeScript에서 pass이고, Python은 기능마다 지원을 선언하며 Python을 `pass`나 `partial`로 선언한 기능은 Python owner를 선언한다. Go는 고정된 사례 필터로 `go test -json`, Rust는 정확한 사례 필터로 `cargo test`를 실행한다. 검사기는 성공 종료 코드와 각 선언 사례의 관찰된 통과 이벤트를 요구한다. 테스트 출력은 성공 보고서를 제공할 수 없다.
Go와 Rust의 `symbols`는 각 공통 사례 ID를 선언한 소스 파일의 정확한 실제 테스트 이름에 연결한다. 검사기는 누락·추가·중복된 심볼 이름을 거부하고 각 실제 테스트 통과 이벤트를 확인한 뒤 공통 ID를 기록한다. Node, PHP, Python은 공통 ID를 직접 사용한다. 데이터베이스 테스트 파일은 환경에서 데이터베이스를 고르지 않는다. 자기 파일에 manifest가 선언한 데이터베이스와 URI를 모두 `scripts/features/coverage.mts`의 `coverageItems`(`node scripts/features/coverage.mts --items <테스트 파일>`)로 얻으며, 선언된 URI 변수가 비어 있으면 그 이름과 함께 실패한다. Go, PHP, Rust는 그 reader가 아직 resolver를 쓰지 않으므로, 검사기가 항목마다 `ORM_FEATURE_DATABASE`, `ORM_FEATURE_DSN`을 계속 전달한다. URI가 없으면 테스트 시작 전에 실패한다.

데이터베이스 실행마다 검사기는 같은 URI에 대해 테스트 직전과 직후 상태 판독기를 실행한다. 상태 digest는 검사기가 직접 기록하며 테스트 출력은 제공할 수 없다. 각 테스트 묶음은 프로세스마다 10분 제한으로 두 번 실행한다. 두 실행에서 선언된 사례만 관찰하고 결과가 같아야 한다. 데이터베이스 상태는 각 실행 전후와 실행 사이에 같아야 한다. 환경, 테스트 이벤트, 데이터베이스 테이블 또는 상태 판독이 빠지면 실패한다. 검사기는 저장된 보고서를 읽지 않는다.

`scripts/features/coverage.test.mts`의 테스트는 필요한 차원을 하나씩 바꾸고 만들어 낸 JSON 성공, 누락된 소유자, 사용자, 테스트 경로, client, 데이터베이스, 사례, 반복 실행, 상태 비교 또는 선언되지 않은 결과에서 실패를 요구한다. 주장한 모든 동작에 현재 실행 증거가 생길 때까지 `make feature-check`는 실패한다. 검사기 자체 테스트가 성공해도 client 동작의 완료를 주장하지 않는다.
`make feature-coverage`는 `make check`처럼 모든 기능의 coverage를 한 번 실행하고, `make feature-check`는 그것을 모든 검증 명령과 함께 실행한다. `.runtime/servers/env`의 test 환경 아래에서 `node scripts/features/coverage.mts --feature <id>`는 그 기능의 coverage spec만 실행한다: 소유자와 사용자를 데이터베이스마다 두 번. `<id>`는 `scripts/features/check.mts --feature`처럼 `contracts/features.json`의 기능 `id`다. 없는 id는 아무것도 실행하지 않는 대신 고를 수 있는 id 목록과 함께 실패한다. 예를 들어 `node scripts/features/coverage.mts --feature dsn_connection`은 DSN 연결 기능만 실행한다. DSN 기능은 세 데이터베이스에서 다섯 client의 읽기 전용 소유 사례와 Go client와 Rust client 부분의 생성 모델 사용 사례를 실행한다. 선택한 URI는 `ORM_FEATURE_DSN`으로 전달하고 검사기는 두 실행의 전후 데이터베이스 상태를 읽는다.

## Owner 검사 {#owner-checks}

`make owner-check`는 바뀐 file을 소유한 검사를 실행한다. 기본은 `HEAD`와 다른 file과 추적하지 않는 file이고, `PATHS="<paths>"`로 file을 줄 수 있다. `contracts/features.json`의 모든 검증 명령은 `inputs`를 선언하고, 모든 coverage 단위인 owner client(`owner/<language>`)와 사용 부분(`dependent/<id>`)은 `tests`와 선택적 `inputs`를 선언한다. `scripts/features/owners.mts`는 입력에 바뀐 file이 있거나 선언한 fixture data(JSON이나 dbspec file)가 그 file을 적는 명령과 단위를 고른다. 예를 들어 `contracts/fixtures/schema_definition.json`은 `contracts/fixtures/audit.dbs`를, `contracts/symbols/rust.json`은 Rust source를 적는다. 적힌 file이 다시 적는 file은 따라가지 않는다. 고른 명령과 단위마다 그것을 고른 path를 출력하고, 아무것도 고르지 않은 바뀐 path도 출력한다. coverage helper `packages/php/tests/coverage_cases.php`처럼 여러 기능이 쓰는 helper는 `helpers`에 자기 check와 함께 선언하고 어떤 입력에도 넣지 않는다. helper의 변경은 그 check(`scripts/features/check.mts --run --helper <id>`)만 실행하고, helper를 쓰는 모든 기능의 실행은 `make check`가 맡는다. `contracts/features.json`이 바뀌면 `HEAD`와 항목이 다른 기능의 명령과 단위, 그리고 항목이 다른 helper를 고른다. 그 항목 밖의 변경은 `make check`가 모든 기능을 실행하므로 아무것도 고르지 않는다. 고른 명령은 `scripts/features/check.mts --run --feature <id> --command <id>`로, 고른 단위는 `scripts/features/coverage.mts --feature <id> --part <part>`로 실행한다. 각각은 RUN, PASS나 FAIL과 경과 시간을 가진 단계 하나이고, 기한은 단계 안의 case마다 있다. 선언 검사는 입력이 없는 검증 명령, 추적되는 file을 맞추지 않는 입력, 입력으로 쓰인 helper를 실패시킨다. 또 `contracts/check-inputs.json`이 scope `owner`로 선언하고 입력이 바뀐 path를 맞추는 make target을 실행한다. `client-db-check`나 `feature-check`처럼 scope `suite`인 target은 `make check`에서만 실행하고, scope가 없는 target이 있으면 선택이 실패한다. `node scripts/features/owners.mts --list [<paths>]`는 실행하지 않고 고른 것만 출력한다. `scripts/features/owners.test.mts`는 `make feature-unit-check`에서 실행한다.
