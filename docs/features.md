## Current behavior

- `dsn_connection`: Open a database from one URI DSN. The URI scheme selects the driver, every connection reads and writes datetime values in UTC, and the client plans statements in its own process. The PHP client requires no PDO driver extension, so a PHP without pdo_mysql runs it on SQLite. A MySQL DSN connects with TLS through ssl-mode=VERIFY_IDENTITY and an absolute ssl-ca, which checks the server certificate against the CA and the host name; the PHP and TypeScript clients refuse a parameter outside the set of each scheme.
- `model_queries`: Build conditions, joins, relations, columns, subqueries, aggregates, and pages with the generated model methods and read the rows as models and collections.
- `model_writes`: Create, create many, update with optional optimistic locking, save, delete with optional recursive relation deletion, including the duplication assignments of an upsert, and restore a soft-deleted row named by its primary key or one unique key, with new values of its other columns, returning the restored row.
- `transactions`: Run a callback in a transaction shared by the current execution flow, with savepoints for nested calls, deadlock retry, isolation, read-only mode, timeoutMs, row locks, named locks, and transaction-local values. A SQLite write transaction takes the write lock at its start and waits for it up to busy_timeout. A test entry point of each client arms a rollback fault: the next rollback of a transaction whose callback failed runs and is reported as FAULT, so the transaction returns ROLLBACK.
- `statement_events`: Publish an event for every statement the client sends to the subscribers registered on the connection: the statement, its masked binds, its kind by origin, the tables it names, its elapsed time, the number of its transaction on the connection, and its error. Subscribers run synchronously after the statement and before the operation continues; a failing subscriber fails the operation with SUBSCRIBER. Every client sends the same transaction control statements.
- `model_generation`: Generate the models from the dbspec document set with the generator of each language. Go and Rust scan the sources and generate the chain methods they call; PHP resolves chains at run time and TypeScript types the scanned chains. With `--check`, the Go, PHP, and TypeScript generators compare the models with the output directory without writing.
- `schema_definition`: Parse and emit dbspec documents, compute the manifest and schema hashes of a document set, render the DDL of each dialect, introspect a database into a document, diff two schemas into plans and apply them with verification and recovery, and export and import Mermaid diagrams. The TypeScript declarations of apply and introspection name their connections with types of their own, so code that calls them type-checks without the pg, mysql2 or node:sqlite types.
- `schema_install`: Install a dbspec document set through a connection: every client renders the statements of its dialect, creates every table when no table of the set exists, changes nothing when every table exists, and fails with CONFIG when only some exist; it then compares the tables of the set in the database with the set and fails with CONFIG naming each difference. Registering a set on a connection, with utils().schema().register or the connect helper of generated code, reads and writes nothing in the database; install and addTablesAndColumns verify the database. A process loads the generated code of several document sets, and one connection serves all of them, each request with the model of its manifest hash. addTablesAndColumns upgrades an installed document set by the tables the database lacks and the missing columns of the existing tables that are null or have a default with the plan steps of the dialect, which create each table with its indexes, foreign keys, checks and triggers and replace the audit triggers of each changed table; it leaves the tables of other sets unchanged and returns SCHEMA_DIFFERS before any change for every other difference. A set that uses external documents of another set owns only its own tables: install and addTablesAndColumns require the used external tables in the database as declared and fail with CONFIG otherwise, and never create or change them.
- `planner`: Validate a value-free request against the manifest and render the dialect SQL, bind slots, assembly metadata, and the tables each statement names in the client process. The four planners produce identical statements.
- `composite_keys`: Preserve every declared primary and foreign key component in identity, writes, relations, tuple conditions, and pages.
- `authenticated_encryption`: Encode authenticated versioned AES values and blind indexes, read mixed key versions, and rotate every encrypted column of a table in batches.
- `parameter_chunking`: Pad relation key lists to size classes, split relation keys and oversized root IN lists at the driver bind limit, merge the results, and reject root shapes that a merge would change.
- `constraints_and_relations`: Keep CHECK constraints, indexes, internal and external foreign keys, soft delete, immutable tables, and relation delete actions in the planner and the migration system.
- `audit_triggers`: The audit setting of a table names its audit column and the audit record table that the column refers to through a declared restrict foreign key, and installs row triggers that copy every inserted and updated row into the declared history table; the setting records every column, or only the columns that an exclude or include list selects, and the history table holds exactly the recorded columns. The connection configuration takes an audit source, a function that returns the audit values of the current request, and a transaction with audit values calls it once and inserts one audit record from its values and the transaction's into the table that the audited tables reference, before the callback; every audited insert, update, soft delete and restore in the transaction writes the record's key, on every transaction entry point: Go Transaction, PHP transaction and TypeScript transaction through the connection or its context or signal handle, and Rust transaction, transaction_send and transaction_once. A nested transaction keeps the outer audit.
- `interface_contract`: Every client exposes the public symbols declared in contracts/interfaces.json. Each language extracts its declarations from real syntax trees without running model code, and the comparator fails when a symbol, field, return, or error differs from the common interface.
- `performance_gate`: The Go and PHP clients keep hot-path latency within a measured ratio of the raw driver on the seeded MySQL bench database, and make perf-check fails when a workload exceeds its recorded bound. The Rust bench harness measures without an enforced bound, and the TypeScript standard is not built.
- `conformance_verification`: Run the same model chains in Go, PHP, Rust, and TypeScript on MySQL, PostgreSQL, and SQLite and compare the statements and results with the recorded vectors.
- `catalog_connection`: With the live-db feature, orm-build opens a catalog connection from one DSN, reads table metadata and bounded table pages, runs dialect-parsed read-only queries, and inserts, updates and deletes rows with verified snapshots. Only the Rust client provides it.

Run make feature-check to validate paths and execute every verification command declared for non-planned features. An implemented feature requires tests and paired documentation; partial and planned are incomplete.
