# Codecs — reading and writing column styles (S2)

- **COD-1** Go database value conversion returns `CODEC_DECODE` for malformed, null, overflowing, non-finite, or unsupported values. In every client, host encoding and the blind index return `CODEC_ENCODE` for an empty host stage list or a value other than text or bytes: a host stage takes the UTF-8 of a text or the bytes given, and binds a value by its kind, so an integer, a float or a bool is no plaintext (the case `host_values_by_kind` of `tests/codec/codec.json`). SQL NULL passes the host stages as SQL NULL; a style other than `aes`, `hex` and `ip`, a codec style such as `serialize` among them, returns `CODEC_UNSUPPORTED` before the value or the cell is read; a `hex` cell that is not hex and an `aes` cell shorter than its header, nonce and tag return `CODEC_DECODE` (the case `host_stage_errors`). A model column whose read value the generated model cannot convert into its type fails with the code of the conversion and a message that names the entity and the column before the message of the conversion, as the same text in every client: `<CODE>: <entity>.<column>: <message>`, the form of COD-41. The message of the conversion is one text per column type in every client, which names no host type and no value: `i16 cell is not an exact integer in its range` (and `i32`, `i64`), `f64 cell is not a finite number`, `bool cell is not boolean`, `decimal cell is not a decimal of its precision and scale`, `date cell is not a date` (and `datetime`, `time`), `varchar cell is not text` (and `text`, `uuid`) for a cell that is no text and `text is not valid UTF-8` for one whose bytes are not UTF-8 (COD-69), `bytes cell is not bytes`, and `non-null column received SQL NULL`; such as `CODEC_DECODE: typed_value.wide: i64 cell is not an exact integer in its range`. Row assembly returns the error to the caller, and insert validates assigned fields before writing. An empty byte slice remains distinct from SQL NULL. Scalar aggregate conversion accepts a valid decimal as its nearest finite binary64 value.

- **COD-2** The `polyspec-orm` Python package registers PyMySQL `DECIMAL`/`NEWDECIMAL` and psycopg `NUMERIC` cells as their exact decimal text before ORM decoding. A generated `decimal(P,S)` field accepts a decimal string and returns a decimal string with exactly `S` fractional digits on MySQL, PostgreSQL, and SQLite. `P` is from 1 through 18 and `S` is from 0 through `P`; every schema builder rejects other declarations. The value has at most `P` digits in total, including exactly `S` fractional digits after zero padding. A binary floating-point value is not a decimal field input. An invalid decimal, excess precision or scale, and a database value that cannot be decoded exactly fail with `CODEC_ENCODE` on write or `CODEC_DECODE` on read. The `CODEC_ENCODE` text is `decimal: <reason>`, with the reason `invalid precision or scale`, `invalid text`, `fraction exceeds scale`, `value exceeds precision` or `value exceeds the scaled integer range`, and a read cell is the COD-1 refusal `decimal cell is not a decimal of its precision and scale`; neither names the value (INT-163). SQL NULL remains distinct. This exact field rule does not change the finite binary64 result rule for scalar `sum` and `avg`.

- **COD-3** Column styles are stored in the manifest `styles: [...]` in **write order** (`gz_*` → `['serialize','gz']`: serialize, then compress). Reading applies the reverse order. `aes`, `hex`, and `ip` are host stages; the remaining stages are executor codecs. Go, PHP, Rust, TypeScript, and Python use the same authenticated AES v2 format and produce the same normalized values. Deterministic encodings are byte-identical in every client.

### Blind index

- **COD-4** `%% blind_index <table> <aes_column> <index_column>` declares the equality-search column for an AES column. The target must be nullable-matched, declared as a single-column index, and use `char(64)`/`string` or `bytes` storage. Multiple AES columns may declare the same target. When a request assigns the target explicitly, that assignment supplies it; otherwise, exactly one assigned AES source may derive it, and assigning distinct sources that derive the same target is `IR_INVALID`, regardless of their values. The rule applies independently to insert `set` and `on_duplicate`. On insert and update, the runtime writes lowercase HMAC-SHA256(plaintext, `secrets.blind_index`) to the target. Equality and `IN` predicates on the AES column use that target and never compare ciphertext. The blind-index key is independent from AES key versions and is required when the schema declares this directive.

### AES v2

- **COD-5** `aes` writes `ORM-AES2\0 || nonce || ciphertext || tag`. The nonce is 12 random bytes, the tag is the AES-256-GCM authentication tag, and the associated data is `ORM-AES2\0`. The AES key is SHA-256(`polyspec/orm/aes-256-gcm/v2\0` || configured key bytes). `aes_hex` applies AES first and uppercase hex second.

- **COD-6** Every AES column has a non-null integer `aes_key_version` column in the same entity. New writes use `secrets.aes_version`. Reads use the stored row version to select `secrets.aes_keys[version]`. Each node of a read, the root and each joined row, reads the version stored in its own row, so a joined row stored under another version than its parent decrypts with its own key. Missing versions and authentication failures stop the operation; the codes of these failures are set by COD-44 and COD-47 to COD-60. The runtime does not decode the previous ECB format.

### Encrypted JSON value

- **COD-7** A blob column with the stages `ordered_json aes` stores a JSON value encrypted with AES v2. The `ordered_json` stage writes the ordered-json text, and `aes` encrypts that text; a read decrypts the cell and returns the ordered-json value of the text, as for every `ordered_json` stage (see [Value model](#value-model)). The value keeps the member order, the number text, and an empty object apart from an empty array, so `1.50` reads back as `1.50`. The entity declares the non-null integer `aes_key_version` column.

```text
dbspec 1 example

table service_config {
  seq i64 identity
  aes_key_version i32
  config bytes
  primary key (seq)
  settings {
    codec config ordered_json aes
    aes_version aes_key_version
  }
}
```

- **COD-8** The keys come from the connection configuration: `AESKey`, `AESVersion`, and `AESKeys` in Go `orm.Config`; `aesKey`, `aesVersion`, and `aesKeys` in PHP `Config`, the TypeScript connection options and the Python connection options; and `aes_key`, `aes_version`, and `aes_keys` in Rust `polyspec_orm::Config`. A write encrypts with the key of the current version, `AESKeys[AESVersion]`, and records the version in `aes_key_version`; `AESKey` is that key and may be omitted when the key list holds it, and an `AESKey` that differs from it fails the connection with `CONFIG`. A current version that is not positive, a key list that lacks the current version, and a key list with a version that is not positive or with an empty key fail the connection with `CONFIG` too, and none of these failures opens a database; the zero value of Go `AESVersion` is the absent version and selects 1. Their texts name no version (INT-163): a key that differs from the list is `aes key differs from the key list at the current version`, a current version that is not positive or that the list lacks is `aes current version is not declared`, and a bad list is `aes key list holds an invalid version or an empty key` (COD-44). A read selects the key of the stored version. `utils().aes().rotate(model, keyring)` re-encrypts every row whose version differs from the keyring's current version. A `jsontext` column takes only the `ordered_json` stage, so an encrypted JSON value is always a blob column. Audit change rows record an AES column as `{"redacted": true, "present": true}`, never as its plaintext or ciphertext. An empty AES key fails with `CONFIG` on encode and on decode, and an empty blind-index key fails with `CONFIG` when the index is computed, in every client; invalid ciphertext fails with `CODEC_DECODE`, and no other key is tried.

- **COD-9** `ordered_json` — write (value → stored bytes): ordered-json text from the common value model; read (stored bytes → value): ordered-json parse; reference: ordered-json `0.0.9` of its tag `v0.0.9`; Go uses the module `github.com/polyspec/ordered-json/packages/go` at the version packages/go/go.mod requires (`v0.0.9`), Rust the package of `packages/rust/Cargo.toml` at the tag, and PHP and TypeScript the version `0.0.9`, which the root composer.json and package.json of the repository take from the Composer zip and npm archive of the GitHub release `v0.0.9`
- **COD-10** `serialize` — write (value → stored bytes): PHP serialize; read (stored bytes → value): PHP unserialize; reference: `serialize` / `unserialize`
- **COD-11** `base64` — write (value → stored bytes): base64 of the bytes of the stage before it; read (stored bytes → value): base64_decode; reference: `base64_encode` / `base64_decode`
- **COD-12** `gz` — write (value → stored bytes): zlib of the bytes of the stage before it, level 9; read (stored bytes → value): zlib inflate of any zlib stream of RFC 1950 whose method is deflate (RFC 1951), whatever its compression level flag (`78 01`, `78 5e`, `78 9c`, `78 da`) and its block types (stored, fixed Huffman, dynamic Huffman); reference: `gzcompress(…, 9)` / `gzuncompress`
- **COD-13** `yaml` — write (value → stored bytes): YAML 1.2 document; read (stored bytes → value): YAML 1.2 parse; reference: single document and common value model

### Stage lists {#stage-lists}

- **COD-14** Only a value stage (`ordered_json`, `serialize`, `yaml`) turns a value into bytes; `base64` and `gz` only transform the bytes of the stage before them, so the style `gz_*` is the list `['serialize','gz']` and serializes because it names `serialize`. A list that starts with `base64` or `gz`, such as `['base64']` or `['gz']`, serializes nothing in any client: the value is a string, the stage writes its UTF-8 text, and any other value fails with `CODEC_ENCODE`; SQL NULL stays SQL NULL. A read of such a list gives the text of the bytes, and bytes that are not valid UTF-8 fail with `CODEC_DECODE`. An empty stage list writes a string as it is and reads a cell as its text: any other value fails with `CODEC_ENCODE`, and bytes that are not valid UTF-8 fail with `CODEC_DECODE` (the case `empty_stage_list`). An empty cell fails with `CODEC_DECODE`, except under a last `base64` stage and under an empty stage list: their encoders write an empty cell for empty text, so `""` stored with `['base64']` or `[]` reads back as `""`, while `['serialize','base64']` refuses the empty cell in its `serialize` stage. An `ordered_json` cell is JSON text, which RFC 8259 (8.1) requires to be UTF-8, so a cell that is not valid UTF-8 fails with `CODEC_DECODE` (the case `ordered_json_text_is_utf8`). The cases `base64_text_*`, `gz_text_*`, `decode_base64_text_*` and `decode_gz_text_*` of `tests/codec/codec.json` give these cases.

## Value model
- **COD-15** An `ordered_json` stage stores its text in a `jsontext` column, which is text on the three databases, so the stored text is read back as written. The stages `json aes` store the encrypted text in a blob column (see [Encrypted JSON value](#encrypted-json-value)). Data queried inside the database is modeled as columns or a child table; the ORM has no JSON path conditions and no JSON indexes.

- **COD-16** Styled columns use JSON-like values: null, bool, integer (i64), finite float (f64), string, list, and string-keyed map; a non-finite float, such as the serialize `d:NAN;`, `d:INF;` and `d:-INF;`, is not a value and returns `CODEC_DECODE`. An `ordered_json` stage reads as the ordered-json value of every client, which preserves the object member order and the number text and distinguishes an empty object from an empty array. A write takes that value and stores its text unchanged. An ordered-json value is written by a first `ordered_json` stage only: under another first stage (`serialize`, `yaml`, `gz`, `base64`) it returns `CODEC_ENCODE` in every client (the case `ordered_json_value_stages` of `tests/codec/codec.json`). The JSON output of a model writes each ordered-json value inside the tagged styled column value as its stored text, with the member order and number text unchanged, in every client. When the language's JSON encoder cannot write stored text, the client writes the output with its own method and the encoder fails: PHP `json_encode` of a row that holds an ordered-json value fails with `CODEC_ENCODE` and `toJson()` writes the output. TypeScript `toJSON` rebuilds the value in its stored member order with each scalar as `JSON.rawJSON` of its stored text; it fails with `CODEC_ENCODE` when JavaScript would reorder a member key, such as `"1"`, or when a stored key text differs from `JSON.stringify` of the key, and `toJSONText()` writes the exact text in every case. Rust serde serialization writes the output as a serde_json raw value, which a serde_json serializer writes unchanged. Python `json.dumps` cannot encode a model and fails with `TypeError`; `to_json_text()` of a model and of a `Collection` writes the output, with the members in the row order of `to_array()`, each other value as `JSON.stringify` writes it, and the same text as TypeScript `toJSONText()` for the same row; a value that JSON cannot write, such as `bytes` or a non-finite number, fails with `CODEC_ENCODE`. The array output is listed in the table. The other styles use the common value model.
- **COD-62** Go holds an integer above the i64 range as a uint64, and Rust as a serde_json u64, and TypeScript as a bigint, and Python as an int; a write of such an integer under `serialize` or `yaml` returns `CODEC_ENCODE`, since the common value model holds an integer of i64 only (COD-16). The integer of PHP and of the PHP extension is i64, and PHP reads an integer literal above it as a float, so no PHP value holds such an integer and the rule has no PHP case. The recipe `tests/codec/codec-integer-beyond-i64.json` holds its cases.
- **COD-63** Go holds bytes as a `[]byte`, and PHP and the PHP extension as a `Bytes`, and TypeScript as a `Uint8Array`, and Python as `bytes`; bytes are no value of the common value model (COD-16), so a write of a bytes value, or of a list or a map that holds one, under `ordered_json`, `serialize` or `yaml`, under a first `gz` or `base64` stage, or under an empty stage list, returns `CODEC_ENCODE`. The value of a Rust codec write is a serde_json value, which holds no bytes, so the rule has no Rust case. The recipe `tests/codec/codec-bytes-value.json` holds its cases.
- **COD-64** Go holds a text that is not valid UTF-8 as a `string`, and PHP and the PHP extension as a `string`, and TypeScript a text with a lone surrogate as a `string`, and Python as a `str`; such a text is no sequence of Unicode scalar values, which JSON text is (RFC 8259, 8.1), so a write of it under `ordered_json` returns `CODEC_ENCODE: json: the text is not a sequence of Unicode scalar values`, the rule `text-unicode` of COD-70. The value of a Rust `ordered_json` write is a serde_json value, whose strings are Rust `String`s and so valid UTF-8, or an ordered-json value, whose text the write stores unchanged (COD-16), so the rule has no Rust case. A Go, PHP or PHP extension string whose bytes are not UTF-8 is the `text_hex` wrapper of FCV-4, so the recipe `tests/codec/codec-raw-text.json`, which Go, PHP and the PHP extension run, holds those cases, under each first stage and under the host stages and the blind index (`text-unicode` and `host-input-unicode` of COD-70). A TypeScript or Python string with a lone surrogate is the `text_code_points` wrapper of FCV-4, so the recipe `tests/codec/codec-lone-surrogate.json`, which TypeScript and Python run, holds those cases in the same places.
- **COD-65** A float writes under `serialize` as `d:` followed by its value, and an integral float writes as its digits with no fraction and no exponent, so the float `4.0` writes `d:4;` in every client, and a `serialize` integer is an `i:` value (the case `serialize_integral_float`). The float notation of a finite value is the shortest digits that read back as the same value, in fixed notation when the decimal exponent is from -4 to 16 and in the exponent form `1.0E+25` otherwise, with a mantissa of one digit followed by `.0`; a negative zero writes `d:-0;` (the case `serialize_float_notation`).
- **COD-66** `yaml` writes a float with no fraction and no exponent with one fraction digit, so the float `2.0` writes `2.0`, and a string that holds a character outside c-printable (YAML 1.2.2, 5.1), or a byte order mark, is written double-quoted with each such character as its escape `\xHH`, `\uHHHH` or `\UHHHHHHHH` (YAML 1.2.2, 5.7); a key that holds U+2028 is written as an explicit key, `? key`, which every client reads (the case `yaml_writes_what_it_reads`). A `yaml` read refuses a character outside c-printable and a byte order mark anywhere except at the start of the stream with `CODEC_DECODE`, and strips one byte order mark at the start of the stream (YAML 1.2.2, 5.2) (the case `yaml_refused_forms`).
- **COD-67** A `serialize` array key that is an integer in the i64 range, written as `0`, `-` followed by a nonzero digit, or a nonzero digit followed by digits, is written as an integer key `i:N;`, and any other key, such as `07`, is a string key `s:` with its UTF-8 length (the case `serialize_keys_and_floats`), in every client; a read of an integer key outside i64 returns `CODEC_DECODE`.

- **COD-17** The `github.com/polyspec/orm/packages/go` Go JSON codec returns `orm.StyledValue` from `Decode`, with `*orderedjson.Value` in its value variant, and `Encode` accepts `orm.StyledValue`. `orm.SqlNull()` selects SQL NULL; `orm.Value(v)` selects a stored value, including `v == nil`. `Kind()` reports `sql-null` or `value`, and `Data()` returns the stored value only for the value variant. Generated setters return `(*Model, error)` and validate the value before changing the model; getters return `(orm.StyledValue, error)` and fail with `COLUMN_UNSELECTED` for an absent column. The codec does not use Go's `encoding/json` for user values. Portable scalar/list/map values, named scalar types, and Go structs with `json` field tags are converted to ordered-json explicitly; parsed ordered-json values retain their original order and node kinds. `jsontext.Value` and `json.RawMessage` are accepted only as already-encoded raw JSON values and are parsed immediately into ordered-json. Unsupported Go kinds, non-string map keys, `[]byte`, and non-finite numbers return `CODEC_ENCODE`.

- **COD-18** The TypeScript codec returns `StyledValue<T>` from `decode`. Its `kind` is `sql-null` or `value`; `StyledValue.sqlNull()` and `StyledValue.value(v)` build the two variants, and `payload()` returns the value of the value variant and fails with `CODEC_DECODE` for SQL NULL. An `ordered_json` value is an ordered-json `Value`, and `toJSON()` writes the tagged form `{"kind":"sql-null"}` or `{"kind":"value","value":...}`.

- **COD-19** The Python codec returns `polyspec.orm.StyledValue` from `decode`. Its `kind` is `sql-null` or `value`; `StyledValue.sql_null()` and `StyledValue.value(v)` build the two variants, and `payload()` returns the stored value and raises `CODEC_DECODE` for SQL NULL. `to_json()` writes the same tagged form as TypeScript.

- **COD-20** A styled value column (`ordered_json`, `serialize`, or `yaml`) distinguishes SQL NULL from a stored null value. SQL NULL has no encoded value; JSON literal null stores `null`, PHP serialized null stores `N;`, and YAML null stores a YAML null document. Every styled-column setter takes `StyledValue<T>` and every getter returns `StyledValue<T>`: `SqlNull` writes or reports SQL NULL, while `Value(v)` writes or reports the encoded value, including a null value. A nullable column accepts both variants; a non-null column rejects `SqlNull` with `CODEC_ENCODE`. A plain language null is not a styled-column setter input. A read returns SQL NULL of a nullable styled value column as `SqlNull` in the root row, a joined row and a related row, so a value read from a row is a setter input that writes the same state back; Python `StyledValue.sql_null()` and `StyledValue.value(v)` of `polyspec.orm` are the two variants. A rejected setter fails at the call: Go setters return `(*Model, error)` and getters return `(orm.StyledValue, error)`; Rust setters return `Result<Self>` and getters return `Result<StyledValue<T>>`; PHP, Python and TypeScript throw the coded error. A column excluded from a row selection has neither value: requesting it returns `COLUMN_UNSELECTED`. Empty JSON stored text is invalid and returns `CODEC_DECODE`. Model JSON output and row-array output wrap every selected styled value column as `{"kind":"sql-null"}` for SQL NULL or `{"kind":"value","value":<decoded value>}` for an encoded value. The wrapper is outside the value, so a JSON document such as `{"kind":"sql-null"}` remains `{"kind":"value","value":{"kind":"sql-null"}}`. No output is constructed for an unselected requested column. `contracts/fixtures/styled_column_states.json` defines the requirement inputs, results, stored values, outputs, and errors for Go, PHP, PHP extension, TypeScript, Python, and Rust on three databases; it does not claim that native codec coverage is complete.

- **COD-21** The `@polyspec/orm` TypeScript client checks a styled value by the rules of COD-70 when a setter takes it (COD-73) and again when the value is encoded: an undefined member is `json-undefined`; a missing array index, a symbol member or an object member that JSON would omit is a value outside the JSON value model (`json-value`, `serialize-value`, `yaml-value`); a number that is not finite is `json-non-finite`, `serialize-non-finite-write` or `yaml-non-finite-write`; each fails with its one text. The encode of the write holds a value whose input object changed after assignment. `payload()` checks nothing but SQL NULL (COD-73).

- **COD-22** The `github.com/polyspec/orm/packages/go` Go module encodes values implementing `json.Marshaler` through `MarshalJSON`, then parses them immediately into ordered-json. The returned bytes must be valid JSON; custom marshalers therefore remain in the ordered-json model and cannot bypass node-kind validation.

- **COD-23** The `github.com/polyspec/orm/packages/go` Go module rejects `[]byte` as a common JSON value with `CODEC_ENCODE`; it does not silently convert it to Go's base64 JSON string representation. Decode bytes into the common value model before assigning a JSON column.
- **COD-24** getter for an `ordered_json` column — Go: `orm.StyledValue` containing `*orderedjson.Value`; Rust: `StyledValue<polyspec_orm::ordered_json::Value>`; PHP: `Polyspec\Orm\StyledValue` containing `Polyspec\OrderedJson\Value`; TypeScript: `StyledValue<Value>` of `ordered-json`; Python: `polyspec.orm.StyledValue` containing `polyspec.ordered_json.Value`
- **COD-25** setter input for a styled column — Go: `orm.StyledValue` containing a portable value or ordered-json value; Rust: `StyledValue<T>`; `T` is the style value; PHP: `Polyspec\Orm\StyledValue` containing the style value; TypeScript: `StyledValue<T>`; `T` is the style value; Python: `polyspec.orm.StyledValue` containing the style value
- **COD-26** model JSON output — Go: `json.Marshal(model)`: the tagged styled column value with its stored document text; Rust: `to_json()` and serde serialization: the tagged styled column value with its stored document text; PHP: `toJson()`: the tagged styled column value; `json_encode` fails with `CODEC_ENCODE`; TypeScript: `JSON.stringify(model)` and `toJSONText()`: the tagged styled column value; Python: `to_json_text()`: the tagged styled column value with its stored document text; `json.dumps` fails with `TypeError`. JSON has no bytes, so in every runtime, including the PHP extension, the JSON output refuses a bytes column whose value is its stored bytes, which is one without a codec stage, with the same text: `CODEC_ENCODE: <entity>.<column>: JSON output cannot write bytes`, such as `CODEC_ENCODE: byte_cell.body: JSON output cannot write bytes`, and in Go `json.Marshal` returns it inside the `*json.MarshalerError` of `encoding/json`, whose `Unwrap` is that orm error; a SQL NULL is `null`, and a column whose codec stage decodes its bytes into a value writes that value; the array form holds the bytes (COD-27)
- **COD-68** The `polyspec-orm` Python package's `to_json_text()` keeps the place of a member that JavaScript would reorder, writes a collection as the array of the texts of its rows, an empty one as `[]`, and a related row under its relation name; it writes other values as `JSON.stringify` writes them and fails with `CODEC_ENCODE` on a value that JSON cannot write, and `json.dumps` of a model fails with `TypeError`.
- **COD-27** The array form of a model holds the same values in every runtime: Go `ToArray()`, Rust `to_array()`, PHP and the PHP extension `toArray()`, TypeScript `toArray()` and Python `to_array()` return the tagged styled column value, a styled document with its member order and number text, such as `1e400`, a non-finite float as itself, a `date`, `time(p)` or `datetime(p)` column as its one text of PRT-69, with exactly p fraction digits, and a bytes column without a codec stage as its bytes: Go a `[]byte`, Rust an `ArrayValue::Bytes`, PHP and the PHP extension a `Bytes`, TypeScript a `Uint8Array` and Python `bytes`. The Rust `to_array()` returns an `ArrayValue`, which holds each of these values, and so do the `to_array()` of a Rust collection, group row and group rows. The array form of a group row holds the value of a bytes column without a codec stage as the same bytes value in each runtime, and its JSON output refuses it (INT-162).

- **COD-28** PHP arrays are ordered maps. An array with exactly the keys `0..n-1` is read as a list; other keys are read as a map. Serialize-family codecs preserve the key representation. The `json` style is `ordered_json`, which writes the members of an object in their order (COD-16), so its encoding is the same bytes in every client.

- **COD-29** `yaml` stores one YAML 1.2 document. Output values use the common value model. Mapping keys are strings; integral YAML keys, in every integer form of the core schema (`7`, `07`, `+7`, `0o7`, `0x7`), are converted to decimal strings for compatibility with PHP arrays, and two keys of one decimal string are duplicates. A stream that is not UTF-8 returns `CODEC_DECODE`, and a byte order mark may start it (YAML 1.2, 5.2); a plain integer outside i64 is not a value (COD-16) and returns `CODEC_DECODE`. Duplicate keys, multiple documents, aliases, anchors (with or without an alias), explicit tags (the core tags such as `!!str` and `!!int` included), non-finite numbers, collection keys, and plain boolean, null, or floating-point keys return `CODEC_DECODE`. `<<` is an ordinary key, since YAML 1.2 has no merge key (the merge key is a type of YAML 1.1): a read takes `<<: 1` as the key `<<`, and a client writes the key `<<` so that it reads back as that key (the case `yaml_merge_key_is_a_key`). A text without a document, empty or holding only comments, is not a YAML value and returns `CODEC_DECODE`; SQL NULL is a separate state, and a null value is stored as a null document such as `null` or `---`. A read takes any single YAML 1.2 document of the core schema that holds the value, so the text a client writes may differ from another client's in the forms that YAML allows: with or without a final line break, with or without the document end marker `...`, a block sequence indented by any number of spaces, a mapping item of a sequence on the line of its dash or on the next line, and a scalar or key plain, single-quoted or double-quoted; a client reads every one of them as the same value. A float that a client writes keeps a fraction or an exponent, so that it reads back as a float and not as an integer; TypeScript holds an integer as a bigint and a float as a number, so it writes the float `2.0` as `2.0`.

## Cases
- **COD-30** Ordered-json distinguishes an empty object from an empty list. `{}` remains an object and `[]` remains an array through parse, encode, and repeated round trips in every client.
- **COD-31** Rust reads SQL NULL as `Val::Null` and empty text as `Val::Str("")`. Decoding empty text with an `ordered_json` stage returns `CODEC_DECODE`.
- **COD-32** SQL NULL, JSON literal null, and an unselected styled value column remain distinct in storage, getters, row arrays, and model JSON output. Requesting the unselected column returns `COLUMN_UNSELECTED`.
- **COD-33** `ordered_json` preserves `[]`, `{}`, `0`, and `""`. A parse failure returns `CODEC_DECODE`.
- **COD-34** A serialize-family format failure returns `CODEC_DECODE`. `O:`, `C:`, `R:`, and `r:` return `CODEC_UNSUPPORTED`.
- **COD-35** A YAML parse or value-model failure returns `CODEC_DECODE`. A YAML encode failure returns `CODEC_ENCODE`. A value stage (`ordered_json`, `serialize`, `yaml`) outside the first position returns `CODEC_UNSUPPORTED`, and so does a style that no stage of COD-3 names, in every client, on a write and on a read, before the value or the cell is read; the case `encode_style_errors` of `tests/codec/codec.json` holds both.
- **COD-36** String lengths use byte length. The `gz` bytes of one value can differ by implementation within the zlib streams of COD-12, so `gz` guarantees equal round-trip values, and every client reads the stream of every other.

## Decoding is exact {#decoding-is-exact}
- **COD-37** A stored cell is the output of the encoder, so a read decodes a cell only in the form the encoder writes, in every client and on every database. The encoder writes `base64` as the padded standard alphabet with zero padding bits and no white space or line breaks, and `hex` as upper-case hex digits only; it never writes characters around them. A `base64` or `hex` stage therefore fails with `CODEC_DECODE` on any other form: surrounding or embedded white space of any kind (space, line break, form feed, NUL, an information separator such as U+001C, a byte order mark), a missing padding character, non-zero padding bits, or a character outside the alphabet. No client trims or skips characters before decoding. The reasons are these:

  - A value that decodes from more than one stored form does not round-trip: re-encoding it writes different bytes, so the read hides that the stored cell differs from what the ORM writes.
  - Each language's trimming removes a different set of characters (for example Go and Python strip a form feed, PHP strips NUL, and JavaScript strips a byte order mark), so a lenient read accepts different cells in different clients; an exact read is the one rule that every client implements alike.
  - The rule holds on every database because the client decodes every `hex` cell: MySQL `UNHEX` takes odd-length text and yields NULL for a cell with white space, so no dialect reads `hex` in SQL. No dialect writes `hex` in SQL either: the client encoder writes the upper-case text on every database, and every dialect reads the cell as stored for the host decode.

- **COD-38** The `ip` encoder holds to the same rule on the write side: it packs only the exact text of an address and fails with `CODEC_ENCODE` on any white space around or inside it (space, tab, line break, form feed, NUL, a no-break space), in every client. A condition value of an `ip` column is refused the same way when the condition is built, since a dialect that encodes it in SQL would read it as NULL. No client trims the input, since two inputs would then store the same bytes and the stored value would not read back as the input; the cases `ip_*` of `tests/codec/codec.json` give these cases. A zone, such as `%eth0`, is no part of an address and fails with `CODEC_ENCODE`. `ip` packs an IPv4 address as its 4 bytes and an IPv6 address as its 16 bytes, an IPv4-mapped address (`::ffff:a.b.c.d`) included, as MySQL `INET6_ATON` packs it (MySQL 8.4 packs `::ffff:10.0.5.9` as the 16 bytes `00000000000000000000FFFF0A000509`), and a read returns the RFC 5952 canonical text of those bytes, which writes an IPv4-mapped address as `::ffff:` and its dotted decimal (section 5), as `INET6_NTOA` does; a cell of any other length is `CODEC_DECODE` (the cases `ip_packs_and_reads` and `decode_ip_*`).

- **COD-69** A `varchar` or `text` column of a model reads its cell as text only when the cell is valid UTF-8, in every client and on every database: a stored text that is not valid UTF-8 fails with `CODEC_DECODE` and the message `CODEC_DECODE: <entity>.<column>: text is not valid UTF-8`, and no client returns its bytes or replaces them. Returned, such a text would not read alike across runtimes, since a string holds bytes in some runtimes and Unicode scalar values only in others (COD-64). SQLite stores such a text, and flowmark answers it as `{"text": base64}` (PRT-67), so each client reads its bytes there: Python and Rust read a SQLite text that is not UTF-8 as its bytes, and TypeScript, whose node:sqlite replaces each invalid sequence with U+FFFD, reads a statement whose text holds U+FFFD again with each text cast to a BLOB and takes the whole answer from that read, as the catalog read does (INT-153). A MySQL `utf8mb4` column refuses the write in strict mode (`Incorrect string value`) and a PostgreSQL `UTF8` database refuses it (`invalid byte sequence for encoding "UTF8"`), so they store no such text. The case `text_not_utf8_refused` of the recipe `conformance_verification` gives these cases. The host decode of COD-1 refuses no plaintext for its bytes: it returns a plaintext that is UTF-8 as its text and any other as its bytes, which a Go or a PHP string holds, so that the column conversion reads it, and a `varchar` or `text` column refuses it as above (the case `host_refusals` of `tests/codec/codec.json`).

- **COD-39** `hex` is upper-case hex digits only: every encoder writes upper case, so a lower-case letter is `CODEC_DECODE`. A `hex` cell of an odd length or with any byte outside the upper-case hex digits fails with the one message `hex: odd length or non-hex input` in every client. Go exports the host decode as `orm.HostDecode(raw, styles, aesKey)`, as the other clients export theirs (PHP `Codec::hostDecode`, TypeScript `hostDecode`, Rust `codec::host_decode`, Python `host_decode`); a list without `aes` needs no key.

## Vectors (`tests/codec`)
- **COD-40** `tests/codec/codec.json` is the codec recipe (docs/spec/feature-coverage.md FCV-2), reviewed data held by hand like every recipe, and every client runs it through its recipe helper. Its encode cases encode a value, decode the cell back to the value, and compare the cell with the bytes the spec fixes where the encoding of the styles is deterministic; its decode cases give fixed cells, one for each form that the spec allows a writer (the zlib streams of COD-12, the YAML forms of COD-29, the float texts of serialize), and every client must decode each to its value or error, so that what one client writes, every client reads. Database round trips are checked by `codec_roundtrip` in `tests/conformance`. The PHP extension `polyspec_orm` declares `Polyspec\\Orm\\Codec` itself and implements it in C (`packages/php-ext/src/codec.c`, a port of the PHP client's `Codec.php`), so its lane runs the recipe through the extension's codec, not through the PHP client.

## Generated code
- **COD-41** Read: the executor decodes each cell immediately after reading positional rows according to `assemble.columns[].styles`. A cell that a stage refuses fails the read with `CODEC_DECODE`, whose message names the entity of the node that reads the cell, a joined node included, and the column before the message of the stage, as the same text in every client: `CODEC_DECODE: <entity>.<column>: <message>`, such as `CODEC_DECODE: author.aes_hex_email: hex: odd length or non-hex input` (the case `a_refused_row_ends_the_read_and_keeps_the_connection` of `contracts/fixtures/model_queries/model_queries.json`). A failure of another code, such as `CONFIG` for a missing key, keeps its own message. The message of a stage, on read and on write, names no value and no text of the library that the stage reads or writes with (INT-163): a stream or a value that the library refuses is the stage's own text, `gz: bad zlib stream`, `base64: bad input`, `json: the cell is not JSON` and `yaml: the stream does not parse` on read and `gz: the compression failed`, `json: the value has no JSON text`, `yaml: the value has no YAML text` and `aes: the encryption failed` on write, a text that is not an address is `ip: the text is not an address` and a cell of another length `ip: the cell is not 4 or 16 packed bytes`; a rule of the stage states the rule by its one text of COD-70, which names no position, and the error keeps the failure of the library as its cause (COD-71).
- **COD-42** Write: `set<Col>(v)` uses the declared style, calls runtime `setStyled`, and binds the encoded bytes.
- **COD-43** A predicate on a styled column compares by equality (`eq`, `not_eq`, `in`, `not_in`) exactly when what it compares is a deterministic function of the value, so that the parameter equals what is stored. A predicate value passes through the host stages of its column only (`aes`, `hex`, `ip`, COD-3), never the executor codecs, which encode a written value alone. So a column whose every stage is a host stage compares by equality: `hex` and `ip` compare the stored cell, and a column with an `aes` stage compares its blind index ([COD-4](#blind-index)), the HMAC of the value itself whatever the position of `aes` in the chain, never its random-nonce ciphertext; such a column without a declared blind index fails the equality with `IR_INVALID`. A column with any executor codec, such as `ordered_json aes`, takes only `isNull` and `isNotNull`: its stored form and its blind index come from the encoded text, which a predicate value is not. Every validator applies this one rule (`ir.OpAllowed` and its counterparts; planner cases `planner_ip_hex_eq`, `planner_hex_eq`, `planner_aes_hex_eq`, `planner_hex_aes_eq` and `planner_ordered_json_aes_eq`).
- **COD-44** The read path has one shared error requirement for the six declared implementations—Go, PHP, PHP extension, TypeScript, Python, and Rust—for a key version and a stored version: an undeclared, empty or otherwise invalid key version is `CONFIG`, and a stored version that is not a positive i32 integer is `CODEC_DECODE`, never coerced to 0 or NaN. A keyring checks its key list before its current version, and its texts name no version (INT-163): a version below 1 or an empty key is `aes key list holds an invalid version or an empty key`, a current version that the list lacks is `aes current version is not declared`, a version that a read or a rotation needs and the list lacks is `aes version is not declared`, and a stored version outside the positive i32 integers is `aes version is not a positive 32-bit integer`. The requirement does not assert that native PHP extension codec coverage is complete.
- **COD-45** TypeScript reads an integer of an added column (INT-160) as a JavaScript number only when it is a safe integer, of magnitude at most 2^53 - 1, so that it is exact; a bigint, or a text of exactly its digits, is converted under the same bound. A fraction, a non-finite number, a boolean, an empty or non-numeric text, and a larger value fail with `CODEC_DECODE`; SQL NULL stays null.
- **COD-46** A conformance vector that fails reports its error with the original error as its cause, and a write vector runs its body inside the transaction that the runner gives it.
- **COD-47** Any implemented rotation path uses the key-version and stored-version error codes and texts of COD-44; a stored version that a rotation refuses is `CODEC_DECODE: aes version is not a positive 32-bit integer`, with no entity and column, since a rotation reads no model row, while a read names them (COD-41); a cell that a stage refuses in a rotation is likewise the message of the stage alone, such as `CODEC_DECODE: hex: odd length or non-hex input`. This rule does not claim that each implementation currently exposes rotation.
- **COD-48** A read row that lacks its version cell is `INTERNAL`, a broken invariant of the client, not stored bytes.
- **COD-49** A stored version written as text that is not an integer is `CODEC_DECODE` on the read path, and it is never coerced.
- **COD-50** A stored version of zero is `CODEC_DECODE` on the read path; zero is not a key version.
- **COD-51** A stored version above the i32 range is `CODEC_DECODE` on the read path; the accepted stored versions are the positive i32 integers.
- **COD-52** A stored version that is an undeclared integer is `CONFIG`, a missing secret of the connection.
- **COD-53** A stored version written as text that is a positive integer, with or without leading zeros, decodes to that version.
- **COD-54** On the rotation path a stored version of zero is `CODEC_DECODE`, as on the read path.
- **COD-55** A rotation row that lacks an AES column the client selected is `INTERNAL`, a broken invariant of the client.
- **COD-56** A read plan whose AES column has no version column fails with `INTERNAL`; no version is assumed.
- **COD-57** A keyring that lacks the stored version is `CONFIG`, not the single key.
- **COD-58** A NULL stored version of a non-NULL AES value is `CODEC_DECODE`.
- **COD-59** A NULL AES value with a NULL version is NULL on the read path: its version is neither read nor checked, and no error is raised.

## Stage refusals {#stage-refusals}

- **COD-70** A codec stage, a host stage and the blind index refuse an input by the rules of the table below, each with its code and its one text, which are the same in Go, TypeScript, Python, PHP, the PHP extension and Rust (INT-163). A text names no value: no value of the cell or of the caller, no digit, tag or kind that the input holds, no host type and no position; a line, a column or an offset that a library reports stays in the cause that COD-71 keeps, never in the text. A text names a style only where the rule is about the declared list of styles, as COD-41 names the entity and the column. The error reads `<code>: <text>`, and a read of a model row writes the entity and the column before the text (COD-41). Where several rules apply to one input, the first that the stage meets is the error: the list of styles before the value or the cell, the stream rules of `yaml` (`yaml-utf8` and `yaml-printable`) before its parse, and the nodes and bytes of a value, a cell or a stream in their order, each document before the next. A node is met where it starts, before any node that it holds: first its anchor and its tag, in their written order, then the nesting rule of its level, then the rules of the node itself. So a map key that is a sequence or a map is `yaml-key-collection` before the nodes inside it, `[.inf]: c` and `[*y]: c` included, since the key starts before `.inf` and `*y` do, and a list or a map at level 257 is its nesting rule before the nodes inside it. A key is met before its value, and a repeated key is met at the key that repeats an earlier one (`yaml-duplicate`, `serialize-duplicate`). An alias is met where it stands, whether its anchor is in the stream or not: a runtime whose YAML library resolves aliases while it parses still reports the rule of each node before the alias, such as an earlier tag, a repeated key or a float that is not finite, and not `yaml-alias` (the case `yaml_rules_before_an_undefined_alias` of `tests/codec/codec.json`). The nesting rules (`json-depth`, `json-depth-read`, `serialize-depth`, `serialize-depth-write`, `yaml-depth` and `yaml-depth-write`) count the lists and maps of a path from the outermost one, which is level 1, a YAML sequence or mapping, block or flow, and a serialize `a` field each one level: 256 nested lists, and a scalar inside 256 nested lists, are 256 levels, which every stage reads and writes, and a list or a map at level 257 is refused. No runtime refuses fewer levels, and no failure of a stack, a recursion limit or a library at more levels leaves a stage as another error (COD-71). A rule holds in every runtime; the last column states the runtimes whose values cannot reach it and why, and a rule that no input reaches is still the error that the runtime returns there. Each rule that a recipe value can reach has a case that holds the whole text, in `tests/codec/codec.json`, which every runtime runs, or in the recipe of the runtimes whose values hold its input: `tests/codec/codec-bytes-value.json` (COD-63), `tests/codec/codec-integer-beyond-i64.json` (COD-62), `tests/codec/codec-non-finite-value.json` (a float that is not finite, the `f64` wrapper of FCV-4, in Go, TypeScript, Python, PHP and the PHP extension), `tests/codec/codec-raw-text.json` (a string whose bytes are not UTF-8, the `text_hex` wrapper, in Go, PHP and the PHP extension, COD-64), `tests/codec/codec-lone-surrogate.json` (a string with a lone surrogate, the `text_code_points` wrapper, in TypeScript and Python, COD-64), `tests/codec/codec-map-keys.json` (a map whose keys are not strings, the `map_entries` wrapper, in Go and Python), `tests/codec/codec-styled-unset.json` (the styled value that is neither SQL NULL nor a value, the `styled_unset` wrapper, in Go and Python), `tests/codec/codec-undefined-member.json` (a member that is undefined, the `undefined` wrapper, in TypeScript) and `tests/codec/codec-json-depth.json` (the nesting rules of each value stage, encode and decode, in every runtime). No rule leaves the recipes for want of a value form: a value that one runtime holds and JSON does not is a wrapper of FCV-4 that only the runtimes holding it run.

- **COD-71** A failure of a library or of the host that a rule of COD-70 meets is the orm error of that rule, with the failure of the library kept as its cause: Go `Cause` (`errors.Unwrap`), TypeScript the `cause` of `ErrorOptions`, Python `raise ... from` (`__cause__`), PHP and the PHP extension `getPrevious()`, and Rust `source()`. The rules whose failure is a library's in every runtime are `gz-stream`, `gz-compress`, `json-cell` of a cell that is UTF-8, `json-depth-read`, `json-text`, `yaml-parse`, `yaml-text`, `yaml-read-back` (whose cause is the failure of the read), `aes-encrypt` and `aes-auth`, and each recipe step of them states `library_cause: true` (FCV-4). A library call that reports its failure only as a result, such as PHP `gzuncompress` and `openssl_decrypt` returning `false`, keeps as the cause an exception that holds what the library reports beside the result, the warning of the call, the message of zlib or the queue of OpenSSL errors, or the name of the call where the library reports nothing more. `base64-input`, `json-cell` of a cell that is not UTF-8, `text-utf8`, `serialize-string-utf8`, `serialize-int`, `serialize-float`, `serialize-string-length`, `serialize-array-length` and `yaml-depth` keep a cause where a runtime finds them with a library call; a runtime that finds them by a check of its own, as TypeScript, Python and PHP check the form of `base64-input`, has no failure to keep, so their recipe steps state no cause. No exception of a library or of the host leaves a codec call: a `UnicodeDecodeError`, a `TypeError`, a Node `crypto` error or a Rust panic on a path of COD-70 is that rule's error. A Go value whose struct field a rule refuses is the error of that rule, which names no field.
- **COD-72** A guard of a codec stage that stands behind a rule of COD-70 which always fires first is reached by no input and is removed: the decode guard `style <style> after a decoded value` of Go, TypeScript, Python and Rust stands behind `style-first`, since only a value stage turns the cell into a value and `style-first` puts it first in the list, which a decode applies last; the TypeScript check that the written text of an encode is UTF-8 (`the text is not valid UTF-8`) stands behind `text-unicode`, since the writer encodes only strings that `text-unicode` passed, and the UTF-8 of Unicode scalar values is valid UTF-8; and the PHP extension guard `ip: the packed address is not valid` stands behind `ip-cell`, since `inet_ntop` writes the text of any 4 or 16 bytes.
