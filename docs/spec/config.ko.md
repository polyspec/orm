# 런타임 연결

클라이언트는 연결 값을 인자로 받으며 환경 변수나 비밀 저장소를 스스로 읽지 않는다. 클라이언트는 설정 파일을 읽지 않는다.

DSN URI만 데이터베이스를 선택한다.

```text
mysql://user:password@host:3306/orm_example
mysql://user@localhost/orm_example?socket=/tmp/mysql.sock
postgres://user:password@host:5432/orm_example?sslmode=disable
postgres:///orm_example?host=/tmp
sqlite:///var/lib/orm_example.sqlite?_pragma=busy_timeout(5000)
markdown://127.0.0.1:4100/tracker?token=0123456789abcdef0123456789abcdef
```

- **CFG-1** scheme이 MySQL, PostgreSQL, SQLite 중 하나를 선택한다. 클라이언트는 해당 네이티브 드라이버를 만들고 연결 풀을 연다. 스키마 로딩과 해시 검사는 내부에서 처리한다. scheme `markdown`은 flowmark server가 제공하는 markdown corpus에서 SQLite dialect를 선택한다. 그 DSN과 server 연결은 [프로토콜](protocol.ko.md#_5-markdown-connections)에, corpus가 SQLite에 더하는 것은 [dialects](dialects.ko.md#markdown-corpus)에 있다. 서버가 거부한 연결은 `max_user_connections` 초과처럼 모든 클라이언트에서 `DRIVER`로 실패하며, 서버의 메시지를 담고 네이티브 오류를 cause로 둔다. TLS 실패(CFG-16), SQLite 파일, 서버가 모르는 time zone은 `CONFIG`다. 모든 클라이언트가 이를 구현한다. Python 클라이언트는 이 연결에 server 연결 하나를 유지한다.
- **CFG-2** 모든 연결은 서버 시간대와 상관없이 datetime 값을 UTC로 읽고 쓴다([dialects](dialects.ko.md#date-and-time)). MySQL 연결은 `time_zone = '+00:00'`을, PostgreSQL 연결은 `TimeZone`을 `UTC`로 설정하고, SQLite 값과 ORM 값 함수는 클라이언트에서 UTC를 쓴다. offset이 있는 값은 UTC wall clock으로 쓰고 UTC로 다시 읽는다. 선택 매개변수 `timezone`은 `UTC`나 `+00:00`만 받으며, 다른 값은 `CONFIG`를 반환한다. 다른 값은 decode한 값을 INT-187대로 quote한 `CONFIG: dsn timezone <value>: every connection reads and writes datetime values in UTC`이다.
- **CFG-3** 모든 MySQL 연결은 열릴 때 드라이버 자체 설정 뒤에 세션 `sql_mode`를 `STRICT_ALL_TABLES,ONLY_FULL_GROUP_BY,NO_ZERO_DATE,NO_ZERO_IN_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`로 정한다. 그래서 변환, 잘림, grouping 결과가 서버의 `sql_mode`에 따르지 않고, 드라이버가 더한 mode(sqlx의 `PIPES_AS_CONCAT`, client flag의 `IGNORE_SPACE`)는 대체된다. 연결은 `@@SESSION.sql_mode`를 `ONLY_FULL_GROUP_BY,STRICT_ALL_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`로 읽는다(`mysql.session.sql_mode_set`, `contracts/fixtures/dsn_connection`의 case `mysql_session_settings`).
- **CFG-4** 연결 설정은 최대 연결 수 `poolSize`를 받는다. Go는 `orm.Config{PoolSize: n}`, PHP는 `new Config(poolSize: n)`, TypeScript는 `{ poolSize: n }`, Rust는 `Db::connect(dsn, n, config)`, Python은 `connect(dsn, {"poolSize": n})`이다. 0이거나 지정하지 않으면 풀을 유지하는 클라이언트는 최대 10개의 연결을 열고, 음수는 `CONFIG`를 반환한다. 풀은 최대값보다 많은 연결을 열지 않으며, 모든 연결이 사용 중일 때 연결이 필요한 문이나 트랜잭션은 연결이 반환될 때까지 기다린다. TypeScript의 SQLite 드라이버는 연결 하나를 유지한다. PHP는 요청마다 연결을 연다. 각 `Db`가 연결 하나를 열고 그 연결은 `Db`와 함께 닫히며, 요청보다 오래 남는 연결은 없다. PHP의 풀은 PgBouncer나 ProxySQL이 맡는다([연결 pooler](#connection-poolers)). PHP 클라이언트는 자기 풀을 가지지 않는다. php-fpm worker는 한 번에 요청 하나를 처리하고 다음 요청과 상태를 공유하지 않으며, 요청을 넘어 유지한 연결은 한 요청의 세션 상태를 다음 요청에 넘기고 서버 연결 수를 worker 수만큼 늘린다. 풀러는 대신 적은 서버 연결을 모든 worker가 나누어 쓰게 한다. 클라이언트가 무시하는 설정은 호출자가 연결이 풀링된다고 믿게 하므로, 0이 아닌 n의 `new Config(poolSize: n)`은 `CONFIG`를 반환한다. `stats()`는 `Db`의 연결 하나인 1을 `maxOpenConnections`로 보고한다.
- **CFG-5** 연결 설정은 풀의 최대 유휴 연결 수 `poolIdleSize`와 풀 연결의 수명(밀리초) `poolLifetimeMs`를 받는다. Go는 `orm.Config{PoolIdleSize: n, PoolLifetimeMs: ms}`, TypeScript는 `{ poolIdleSize: n, poolLifetimeMs: ms }`, Rust는 `Config { pool_idle_size: n, pool_lifetime_ms: ms, ..Default::default() }`, Python은 `connect(dsn, {"poolIdleSize": n, "poolLifetimeMs": ms})`이며, PHP는 풀이 없어 이 항목의 끝처럼 이 값을 거부한다. 풀이 이미 `poolIdleSize`개의 유휴 연결을 유지하는 동안 반환된 연결은 닫힌다. 수명이 지난 연결은 유휴 상태일 때 또는 반환될 때 닫힌다. `poolIdleSize`가 0이거나 지정하지 않으면 풀 크기까지 유휴 연결을 유지한다. `poolLifetimeMs`가 0이거나 지정하지 않으면 Rust를 뺀, 풀이 있는 모든 클라이언트는 수명 없이 연결을 유지하고, Rust는 풀의 30분 수명을 유지한다. 음수나 풀 크기보다 큰 유휴 연결 수는 `CONFIG`를 반환하며, Rust의 필드는 부호 없는 정수다. TypeScript의 SQLite 드라이버는 연결 하나를 유지하며 이 값을 사용하지 않는다. PHP에는 풀이 없으므로 0이 아닌 `poolIdleSize`나 `poolLifetimeMs`에 `CONFIG`를 반환한다.
- **CFG-5a** Go와 Rust와 TypeScript와 Python은 MySQL과 PostgreSQL에서 connection pool을 유지하고 `stats()`가 그 pool을 보고한다. transaction은 그 기간 동안 pool의 connection 하나를 차지하므로 pool 크기를 넘는 transaction은 기다리고, 열린 connection 수는 pool 크기를 넘지 않으며, `poolIdleSize`를 넘어 반납된 connection은 닫힌다. PHP와 PHP extension에는 pool이 없고(CFG-4) SQLite의 pool은 runtime마다 다르므로, recipe `connection_pool`은 이 동작을 두 서버에서 명시한다.
- **CFG-5b** PHP와 PHP extension은 pool을 유지하지 않으므로 0이 아닌 `poolSize`, `poolIdleSize`, `poolLifetimeMs`에 `CONFIG`를 반환하고, message는 PgBouncer와 ProxySQL을 이름 짓는다(CFG-4, CFG-5). recipe `dsn_reject_php_pool`이 이를 시험한다.
- **CFG-6** 연결 설정은 연결의 모든 문을 제한하는 `statementTimeoutMs`를 받는다. Go는 `orm.Config{StatementTimeoutMs: n}`, PHP는 `new Config(statementTimeoutMs: n)`, TypeScript는 `{ statementTimeoutMs: n }`, Rust는 `Config { statement_timeout_ms: n, ..Default::default() }`, Python은 `connect(dsn, {"statementTimeoutMs": n})`이다. 0이거나 지정하지 않으면 서버 기본값을 쓰고, 음수는 `CONFIG`를 반환한다. PostgreSQL은 `statement_timeout`으로 모든 문을 제한하며, 모든 클라이언트는 이 값을 각 서버 연결의 startup 매개변수로 전달한다. MySQL은 `max_execution_time`으로 SELECT 문을 제한하며, 쓰기는 이 값이 아니라 서버 잠금 대기 시간(`innodb_lock_wait_timeout`)이 제한한다. MariaDB는 `max_statement_time`으로 모든 문을 제한하며, 각 연결은 그 서버의 변수를 설정한다(DIA-208). SQLite에는 세션 시간 제한이 없으므로 DSN의 `busy_timeout`이 그 한계다. 제한에 걸려 중단된 문은 `CANCELED`를 반환한다. MySQL 잠금 대기 시간 초과(오류 1205)는 그 쓰기 한계가 끝난 것이므로 모든 클라이언트에서 `CANCELED`를 반환한다.
- **CFG-6a** PHP-extension package `polyspec/orm-php-ext`는 실패한 native 문장의 cursor를 닫고, 같은 연결로 다음 문장을 실행한다.
- **CFG-7** PHP와 Python 클라이언트는 연결이 열릴 때 세션 설정을 정한다. PostgreSQL은 time zone과 `statement_timeout`을 startup 매개변수로 받고, MySQL은 `SET NAMES utf8mb4, time_zone = '+00:00', sql_mode = '<declared modes>'`를 init command 하나로 실행한다. statement timeout은 연결이 열린 뒤 읽는 server의 변수이므로(DIA-208), 첫 연결은 `SELECT VERSION()` 뒤에 따로 statement 하나로 설정하고, 같은 `Db`를 위해 다시 여는 연결은 init command에 담는다. `exit`나 fatal error로 트랜잭션 안에서 끝난 PHP 요청은 그 연결도 함께 끝내며, 서버가 트랜잭션을 rollback하고 연결의 named lock과 세션 값을 푼다.
- **CFG-8** 연결 설정은 현재 요청의 audit 값, 곧 계정이나 요청 id처럼 audit 기록 테이블의 컬럼 이름에서 값으로 가는 map을 돌려주는 함수 `auditSource`를 받는다. Go는 `orm.Config{AuditSource: func(ctx context.Context) (map[string]any, error)}`(트랜잭션의 context로 부른다), PHP는 `new Config(auditSource: fn (): array => [...])`, TypeScript는 `{ auditSource: () => ({...}) }`, Rust는 `Config { audit_source: Some(Arc::new(|| Ok(vec![...]))), .. }`, Python은 `connect(dsn, {"auditSource": lambda: {...}})`다. audit 값을 가진 트랜잭션은 이 함수를 한 번 부르고 그 값과 자기 값으로 audit 기록을 삽입한다([사용법](../operations/usage.ko.md#audited-writes)). ORM은 자기 audit 값을 쓰지 않으며, 함수의 오류는 트랜잭션을 실패시킨다.
- **CFG-8a** Go는 트랜잭션의 context로 audit source를 부르므로, `WithContext` 핸들의 트랜잭션은 자기 context를 source에 넘긴다.
- **CFG-9** 흐름은 자기 언어의 취소 수단을 연결 핸들에 적용해 문을 취소한다. Go의 `db.WithContext(ctx)`와 TypeScript의 `db.withSignal(signal)`은 같은 연결을 가리키는 핸들이다. 모델은 연결에 연결하듯 핸들에 연결하고, 핸들에서 시작한 트랜잭션도 같은 취소를 따르며, 컨텍스트나 시그널을 취소하면 실행 중인 문이 `CANCELED`로 끝나고 연결은 계속 쓸 수 있다. Python의 `db.with_future(future)`는 제공한 `asyncio.Future`가 취소될 때 MySQL, PostgreSQL, SQLite 연결에서 실행 중인 문을 취소하는 핸들을 돌려준다. Python SQL은 동기 실행이므로 이벤트 루프가 취소를 처리하도록 `asyncio.to_thread`에서 실행한다. transaction 정리는 취소하지 않으며 rollback 뒤 root 연결을 다시 쓸 수 있다. Rust는 문의 future를 버리면 문이 취소되고 풀로 돌아가기 전에 대여한 연결을 닫는다. PostgreSQL은 실행 중인 문을 취소하고 MySQL은 실행 중인 질의를 종료하며, TypeScript의 SQLite 드라이버는 문 하나를 중간에 양보하지 않고 실행하므로 시그널은 실행 중인 문이 아니라 다음 문에 적용된다. PHP `$db->withCancellation($source)`는 같은 논리 connection의 handle을 반환한다. `$source->cancel()`은 그 source에 연결된 handle에서 시작한 모든 진행 중 statement를 `CANCELED`로 끝반환한다. SQLite는 progress handler로 virtual machine을 interrupt하고 MySQL은 control connection이 해당 source의 active server connection을 종료하며, transaction rollback 뒤 root handle은 다음 statement 전에 다시 연결한다. PostgreSQL에서는 PHP가 `pdo_pgsql`과 `ext-pgsql`을 모두 필요로 하며, 같은 물리 연결에서 protocol cancel request를 보내고 중단된 transaction을 rollback한 뒤 root 연결을 다시 사용한다. transaction 정리는 취소하지 않는다. markdown 연결에서는 모든 클라이언트가 연결을 닫아 실행 중인 문을 끝내며, server는 그 트랜잭션을 rollback한다(PRT-71). 체인에는 취소 연산이 없고 연결 핸들이 그 역할을 맡는다. 핸들은 별도의 값이므로 Go의 `db.Root()`, Python의 `db.root()`, TypeScript의 `db.root()`는 파생의 기준이 된 연결을 돌려주며, 한 연결에서 파생한 핸들들은 같은 연결로 비교된다.
- **CFG-10** MySQL `socket` 매개변수는 Unix 소켓으로 연결한다. 클라이언트는 낙관적 갱신에 필요한 found-rows 개수를 켠다. 비밀번호 로그인은 모든 클라이언트에서 소켓으로도 성공한다. MySQL은 소켓을 안전한 전송으로 여겨 `caching_sha2_password`의 전체 인증에서 평문 비밀번호를 읽고, 모든 클라이언트가 그곳에 평문 비밀번호를 전송한다. recipe model_socket의 case `socket_update_finds_its_row`는 pooler lane에서 비밀번호로 로그인한다. MySQL DSN은 모든 클라이언트에서 host와 database를 적고, 그렇지 않으면 `mysql DSN must include host and database`이다. `socket`이 있으면 host는 MySQL이 로컬 server에 주는 이름인 `localhost`이다. socket 연결은 host를 읽지 않으므로 다른 host는 `mysql DSN socket needs the host localhost, which names the local server`이다. PostgreSQL DSN은 host를 URL이나 `host` 매개변수 중 하나에 적는다. 둘 다 없으면 `postgres DSN must include host and database`이고, 둘이 다르면 클라이언트가 하나를 버리게 되므로 각각 INT-187대로 quote한 `postgres DSN names two hosts, <url host> in the URL and <host> in the host parameter`이다. 이것은 CFG-20의 host 단계이며, host가 있는지, 그 안의 `%`, 그리고 socket이나 두 host를 차례로 검사한다. database 단계는 database가 있는지, 그 escape, 그리고 `;`와 NUL을 차례로 검사하고, 빠진 database도 같은 `must include host and database` 텍스트이다. database는 DSN path의 첫 `/` 뒤를 쓴 그대로 읽은 것이다. dot segment를 지우지 않고 다른 `/`도 버리지 않으므로 `mysql://h//orm`의 database는 `/orm`이다. 첫 `/` 뒤에 아무것도 없는 path에는 database가 없다.
- **CFG-11** SQLite 경로는 절대 경로여야 한다. 클라이언트는 파일을 열기 전에 경로를 UTF-8로 percent-decode한다: `sqlite:///var/lib/my%20data.sqlite`는 `/var/lib/my data.sqlite`를 열고, `%25`, `%23`, `%3F`는 글자 그대로의 `%`, `#`, `?`가 된다. 뒤에 hexadecimal 두 자리가 없는 `%`와 UTF-8이 아닌 decode 결과는 `CONFIG: sqlite DSN path "<path as written>" is not percent-encoded UTF-8`이고, 그다음 decode한 NUL byte는 `CONFIG: sqlite DSN path "<path as written>" holds a NUL byte, which a file name cannot hold`이며, 경로는 각각 INT-187대로 quote한다. 경로는 DSN에 쓴 그대로 읽고 dot segment를 지우지 않으므로, `sqlite:///tmp/../a.sqlite`는 file system이 푸는 대로 `/tmp/../a.sqlite`를 연다. 이것은 CFG-20의 database 단계이며 매개변수 값보다 먼저이다. recipe `dsn_connection`의 사례 `sqlite_path_opens_the_percent_decoded_file`와 `sqlite_invalid_path_is_config_and_creates_no_file`이 이를 담으며 모든 클라이언트가 이를 실행한다. 클라이언트는 외래 키를 켠다. 쓰기 트랜잭션은 `BEGIN IMMEDIATE`로 시작해 시작 시점부터 데이터베이스의 쓰기 잠금을 가진다. 따라서 두 쓰기 트랜잭션은 차례로 실행되고, 읽은 뒤에 쓰는 트랜잭션도 실패하지 않는다. `readOnly` 옵션을 쓴 트랜잭션은 `BEGIN`으로 시작하고 쓰기 잠금을 얻지 않는다. 시작 문은 클라이언트가 정하며, `_txlock`이 있는 DSN은 `CONFIG`를 반환한다.
- **CFG-12** SQLite 연결은 다른 연결이 가진 잠금을 최대 5000밀리초 기다린다. Go, PHP, PHP extension, TypeScript, Python, Rust 여섯 configured implementation은 DSN 매개변수 `_pragma=busy_timeout(ms)`로 다른 시간을 정한다. 예를 들어 `sqlite:///var/lib/orm_example.sqlite?_pragma=busy_timeout(10000)`이며, `busy_timeout(0)`은 기다리지 않는다. SQLite는 더 큰 수를 0으로 읽어 전혀 기다리지 않게 되므로, SQLite의 C `int`가 담는 가장 긴 대기인 0부터 2147483647까지의 십진 정수가 아닌 `busy_timeout` 값은 SQLite와 markdown에서 `CONFIG: <scheme> DSN _pragma "<value>" is invalid`이다. 대기가 끝날 때까지 다른 연결이 잠금을 놓지 않으면 `CANCELED`를 반환한다. `DEADLOCK`만 재시도하므로 이 트랜잭션은 다시 실행하지 않는다. 모든 `_pragma=name(value)` 매개변수는 연결에서 `PRAGMA name = value`를 실행한다. name은 `a`부터 `z`와 `_`가 하나 이상이고, value는 ASCII 글자, 숫자, `_`가 하나 이상이다. 그 밖의 `_pragma`는 decode한 값을 INT-187대로 quote한 `CONFIG: sqlite DSN _pragma <pragma> is invalid`이다. `CONFIG`를 반환하는 DSN은 파일을 만들지 않는다.
- **CFG-13** SQLite 읽기는 다른 연결이 쓰기 트랜잭션을 연 동안에도 실행되며, 그 전에 커밋된 행을 반환한다. 클라이언트는 데이터베이스 파일의 저널 모드를 그대로 두며 WAL을 요구하지 않는다. 기본 롤백 저널에서는 쓰기의 커밋 중에 시작한 읽기가 `busy_timeout` 안에서 커밋을 기다린다. `_pragma=journal_mode(WAL)`은 파일을 WAL로 바꾸며, WAL에서는 읽기가 커밋을 기다리지 않는다. 이 모드는 파일에 남는다.
- **CFG-14** `@polyspec/orm`의 SQLite 드라이버(TypeScript)는 잠금을 동기적으로 기다리므로 기다리는 동안 이벤트 루프가 멈춘다. 따라서 TypeScript 프로세스는 SQLite 파일 하나에 `Db` 하나를 연다. 그 `Db`의 트랜잭션은 차례로 실행되고, 여러 프로세스는 잠금 대기로 파일을 함께 쓴다.

데이터베이스 자격 증명과 AES 키는 커밋하거나 런타임 파일에 기록하거나 로그에 남기지 않는다. 배포 비밀 저장소에서 값을 읽은 뒤 클라이언트 연결 옵션으로 전달한다.

## 연결 끊김 {#lost-connections}

관리자가 세션을 끝낼 때(`pg_terminate_backend`, `KILL`), 서버가 다시 시작할 때, 연결이 한도보다 오래 유휴일 때(PostgreSQL `idle_session_timeout`, transaction 안에서는 `idle_in_transaction_session_timeout`, MySQL `wait_timeout`) 서버는 연결을 끝내고, 네트워크 장애는 연결을 끊는다. 그 연결의 다음 문은 실패하며, 모든 클라이언트는 드라이버와 그 메시지와 상관없이 그 실패를 `CONNECTION_LOST` 코드로 보고한다. MySQL 오류 2006, 2013, 4031, PostgreSQL SQLSTATE class 08과 25P03, 57P01, 57P02, 57P05, 그리고 더 이상 열려 있지 않은 연결에 대한 드라이버의 오류다(PHP pdo_pgsql은 backend process id가 0인 연결에서 서버 SQLSTATE 없이 보고한다. go-sql-driver `ErrInvalidConn`, `driver.ErrBadConn`, Rust의 끊긴 socket, mysql2의 fatal 오류, 연결 오류를 알린 node-postgres 연결, 닫힌 연결의 PyMySQL `InterfaceError`, psycopg가 닫힌 것으로 표시한 연결에서 서버 SQLSTATE 없이 온 psycopg 오류). SQLite에는 서버 연결이 없다.

- **CFG-15** 모든 클라이언트는 그렇게 실패한 문에 `CONNECTION_LOST`를 반환하고 그 문을 다시 전송하지 않는다. 연결의 트랜잭션이나 세션 상태가 사라졌기 때문이다.
- **CFG-38** PHP와 PHP extension은 connection에 session 하나를 둔다. 따라서 첫 statement 전에 server가 그 session을 끝내면 그 statement는 `CONNECTION_LOST`로 실패하고, 한 번만 전송된다.
- **CFG-39** Go: callback 도중 context가 취소된 transaction은 `CANCELED`만 돌려주고, connection은 그 transaction의 named lock, user variable, SQLite mode를 유지하지 않는다.
- **CFG-40** Go: `DriverFromDSN`은 DSN URI의 scheme으로 데이터베이스를 이름하고, URI가 아닌 DSN에는 `CONFIG`를 돌려준다.
- **CFG-41** transaction pooler의 server connection을 거치는 catalog session은, 그 connection의 다른 client가 같은 text의 prepared statement를 아직 쥔 동안 column type이 바뀐 table을 읽는다.
- **CFG-42** Go와 PHP와 PHP extension과 TypeScript와 Python과 Rust: 한 SQLite 파일을 여는 여러 process는 읽고 쓰는 transaction의 모든 쓰기를 transaction 재시도 없이 commit한다. 그들 사이의 잠금은 CFG-12가 기다리는 파일 잠금이기 때문이다. 각 쓰기는 CFG-12의 busy timeout만큼 기다린다. SQLite는 기다리는 쪽에 차례대로 잠금을 주지 않으므로, 이 요구의 시험은 파일을 `_pragma=busy_timeout(60000)`으로 열고, runner의 부하가 대기를 끝내지 않는다.
- **CFG-43** `github.com/polyspec/orm/packages/go` 모듈: SQLite 파일의 쓰기 transaction 안에서 끝나는 process는 잠금 보유자를 남기지 않는다. 운영체제가 process와 함께 잠금을 풀고, 잠금을 기다리지 않는 연결은 곧바로 쓰며, commit되지 않은 쓰기는 rollback된다.

## DSN 매개변수와 TLS

MySQL DSN과 PostgreSQL DSN은 각각 모든 클라이언트가 구현하는 한 가지 모드로 TLS 연결한다.

```text
mysql://user:password@db.example:3306/orm_example?ssl-mode=VERIFY_IDENTITY&ssl-ca=/etc/orm/mysql-ca.pem
postgres://user:password@db.example:5432/orm_example?sslmode=verify-full&sslrootcert=/etc/orm/postgres-ca.pem
```

- **CFG-16** `ssl-mode=VERIFY_IDENTITY`와 인증 기관의 PEM file 절대 경로인 `ssl-ca`는 server 인증서를 그 인증 기관으로, DSN의 host를 인증서로 검사하는 TLS로 연결한다. 다른 인증 기관이 서명했거나 다른 host를 이름한 인증서는 `CONFIG`로 연결을 실패시키고, 메시지는 `TLS connection failed`를 담는다. 그러면 password는 TLS 안에서만 전달되며, 클라이언트는 server의 RSA 공개 키를 요청하지 않는다.
- **CFG-17** host는 server 인증서가 이름하는 host 이름이며 IP 주소가 아니다. TypeScript driver가 주소 host를 이름 `localhost`로 검사하기 때문이며, 모든 클라이언트는 `ssl-mode`와 함께 쓴 주소에 `CONFIG`를 반환한다. 이 모드는 TCP로 연결하며 `socket`을 받지 않는다.
- **CFG-18** `VERIFY_CA`나 `REQUIRED` 같은 `ssl-mode`의 다른 값, `ssl-ca` 없는 `ssl-mode`, `ssl-mode` 없는 `ssl-ca`, 상대 `ssl-ca` 경로, 읽을 수 없는 CA file은 모든 클라이언트에서 `CONFIG`를 반환한다. 텍스트는 `mysql DSN ssl-mode <mode> is not supported; the TLS mode is ssl-mode=VERIFY_IDENTITY with ssl-ca`(mode가 없으면 `""`), `mysql DSN ssl-mode=VERIFY_IDENTITY needs ssl-ca, the absolute path of the CA file`, `mysql DSN ssl-ca <path> is not an absolute path`, platform의 오류를 붙인(INT-187) `mysql DSN ssl-ca <path> is not a readable file: <error>`이며, mode와 path는 INT-187대로 quote한다.
- **CFG-44** `ssl-mode`가 없는 MySQL DSN은 모든 클라이언트에서 TLS 없이 연결한다. server가 TLS를 내놓아도 그렇다. PyMySQL과 sqlx는 그렇지 않으면 server가 TLS를 내놓을 때마다 인증서를 확인하지 않은 채 TLS를 쓰므로, DSN이 `ssl-mode`를 적지 않으면 Python 클라이언트는 `ssl_disabled`를, Rust 클라이언트는 `ssl-mode=DISABLED`를 넘긴다. Go, TypeScript, PHP driver는 그런 DSN에 TLS를 보내지 않는다. recipe dsn_connection의 case `plain_dsn_connects_without_tls`가 MySQL과 MariaDB에서 session의 `Ssl_version`이 비어 있음을 읽는다.
- **CFG-45** `sslmode=verify-full`과 인증 기관 PEM 파일의 절대 경로인 `sslrootcert`는 PostgreSQL DSN을 TLS로 연결한다. 이 TLS는 server 인증서를 그 인증 기관 하나로만 확인하고 DSN의 host를 인증서와 대조한다. 어떤 클라이언트도 `~/.postgresql/root.crt`나 platform 저장소 같은 기본 인증 기관을 읽지 않는다. 다른 인증 기관이 서명했거나 다른 host를 적은 인증서는 연결을 `CONFIG`로 실패시키고, message는 `TLS connection failed`를 담는다. 이 mode는 TCP로 연결한다. socket 디렉터리를 적은 `host` 매개변수, 곧 `/`로 시작하는 값은 `CONFIG: postgres DSN sslmode=verify-full connects over TCP and does not accept a socket directory as host`이다.
- **CFG-46** `require`나 `verify-ca` 같은 `sslmode`의 다른 값, `sslrootcert` 없는 `sslmode=verify-full`, `sslmode=verify-full` 없는 `sslrootcert`, 상대 `sslrootcert` 경로, 읽을 수 없는 인증 기관 파일은 모든 클라이언트에서 `CONFIG`를 돌려준다. 각각 `postgres DSN sslmode <mode> is not supported; it accepts disable, or verify-full with sslrootcert`, `postgres DSN sslmode=verify-full needs sslrootcert, the absolute path of the CA file`, `postgres DSN sslrootcert needs sslmode=verify-full`, `postgres DSN sslrootcert <path> is not an absolute path`, `postgres DSN sslrootcert <path> is not a readable file: <error>`이다. error는 platform의 error이고(INT-187), mode와 path는 INT-187대로 quote한다. 이것들은 CFG-20의 값 단계이고 순서는 `sslmode`의 값, mode 없는 `sslrootcert`, `sslrootcert` 없는 mode, 경로, CFG-45의 socket 디렉터리이다. 파일을 읽을 수 있는지는 클라이언트가 첫 연결을 열 때 검사한다.
- **CFG-47** `sslmode`가 없거나 `sslmode=disable`인 PostgreSQL DSN은 CFG-44가 MySQL에 대해 말하는 것처럼 모든 클라이언트에서 TLS 없이 연결한다. server가 TLS를 내놓아도 그렇다. libpq와 그것을 따르는 driver는 그렇지 않으면 인증서를 확인하지 않는 TLS를 우선한다. recipe dsn_connection의 case `postgres_plain_dsn_connects_without_tls`가 session이 TLS를 쓰지 않음을 읽는다.
- **CFG-19** 모든 클라이언트는 다음 매개변수만 받는다. MySQL은 `timezone`, `socket`, `ssl-mode`, `ssl-ca`, PostgreSQL은 `timezone`, `host`, `sslmode`, `sslrootcert`(CFG-45부터 CFG-47), SQLite는 `timezone`, `_pragma`, 그리고 그 자체가 `CONFIG`를 돌려주는 `_txlock`, markdown은 `token`, `timezone`, `_pragma`이다(PRT-63). `token`이 없는 markdown DSN은 `CONFIG: markdown DSN is missing the parameter "token"`이다. 다른 매개변수는 `CONFIG: <scheme> DSN has the unknown parameter <name>; it accepts <names>`이고, names는 위 순서로 적은 그 scheme의 이름이다.
- **CFG-20** 모든 클라이언트는 연결을 열기 전, 그리고 값을 decode하기 전에 DSN의 query를 같은 규칙으로 읽는다. query는 `&`에서 쌍으로 나뉘고 각 쌍은 첫 `=`에서 나뉜다. 빈 query에는 쌍이 없고, `?&a=1`이나 `?a=1&`의 빈 쌍은 이름이 `""`이며 어떤 scheme도 그 이름을 받지 않는다. 이름과 값은 HTML form처럼 decode한다. `+`는 공백이고, `%` 뒤의 16진수 두 자리는 그 byte이다. 이름은 대소문자까지 정확히 비교한다. percent-encoded UTF-8이 아닌 이름은 scheme이 받지 않는 이름이며, message는 그 이름을 쓴 그대로 적는다. 다음은 각각 `CONFIG`이고, 쌍마다 적힌 순서로 이 순서대로 검사한다. 먼저 scheme이 받지 않는 이름(CFG-19)이며, 그 값을 decode하기 전에 검사한다. 다음은 앞선 쌍이 이미 준 이름이면 `<scheme> DSN repeats the parameter <name>`이다. 그다음은 16진수 두 자리가 뒤따르지 않는 `%`나 UTF-8이 아닌 decode 결과로 `<scheme> DSN parameter <name> is not percent-encoded UTF-8`이다. 이어서 빈 값이나 `=` 없는 쌍으로 `<scheme> DSN parameter <name> is empty`이다. 마지막은 `;`나 NUL을 담은 `socket`, `host`, `sslrootcert`의 값으로, PHP의 PDO DSN이 담을 수 없으므로 `<scheme> DSN parameter <name> holds a character that a connection string cannot hold`이다. MySQL이나 PostgreSQL DSN의 database 이름(path를 percent-decode한 것)에 `;`나 NUL이 있으면 INT-187대로 quote한 `<scheme> DSN database <database> holds a character that a connection string cannot hold`이다. path가 percent-encoded UTF-8이 아닌 database 이름은 path를 적힌 그대로 쓴 `<scheme> DSN database <path> is not percent-encoded UTF-8`이다. `%`를 담은 host는 `<scheme> DSN host <host> holds a percent escape, which no host name needs`이고, fragment(`#`)가 있는 DSN은 `<scheme> DSN has a fragment, which no connection reads`이므로, DSN의 어떤 부분도 읽히지 않고 버려지지 않는다. DSN은 RFC 3986 URI인지, fragment, 위 규칙의 query, host, database 이름, 그리고 매개변수의 값의 순서로 검사한다. 값은 `timezone`(CFG-2) 다음에 나머지를 CFG-19가 적은 순서로 검사하므로, SQLite에서는 `_pragma`(CFG-12)가 `_txlock`보다 먼저이고 MySQL에서는 `ssl-mode`와 `ssl-ca`(CFG-16부터 CFG-18), PostgreSQL에서는 `sslmode`와 `sslrootcert`(CFG-46)이다. 이 순서로 검사하고 첫 오류로 거부한다. `<name>`은 INT-187대로 quote한다. `_pragma`만 반복할 수 있고, 쌍마다 pragma 하나이다. 클라이언트는 이 page가 정한 값만 driver에 넘기고 query를 그대로 넘기지 않으므로, DSN은 모든 클라이언트에서 같은 연결을 뜻한다.

## Primary와 replica

ORM은 문을 서버 사이에서 분배하지 않는다. replica에서 읽을 때는 서버마다 연결을 하나씩 쓴다. primary에 하나, replica마다 하나를 열고, 문이 쓸 연결을 `connect`로 모델이나 행에 전달한다.

| 언어 | 연결 | replica로 읽기 | primary로 쓰기 |
|---|---|---|---|
| PHP | `$master = \Polyspec\Orm\Tests\Model\connect($primaryDsn, $config);` `$slave1 = \Polyspec\Orm\Tests\Model\connect($replicaDsn, $config);` | `(new User)($slave1)->name($name)->get()` | `$row->connect($master)->setName($new)->update()` |
| Go | `master, err := model.Connect(primaryDSN, cfg)` `slave1, err := model.Connect(replicaDSN, cfg)` | `model.User().Connect(slave1).Name(name).Get()` | `row.Connect(master).SetName(next).Update()` |
| Rust | `let master = model::connect(&primary_dsn, n, cfg.clone()).await?;` `let slave1 = model::connect(&replica_dsn, n, cfg).await?;` | `User::new().connect(&slave1).name(name).get().await?` | `row.connect(&master).set_name(next).update(false).await?` |
| TypeScript | `const master = await connect(primaryDsn, options);` `const slave1 = await connect(replicaDsn, options);` | `new User().connect(slave1).name(name).get()` | `row.connect(master).setName(next).update()` |
| Python | `master = model.connect(primary_dsn, **options)` `slave1 = model.connect(replica_dsn, **options)` | `model.User().connect(slave1).name(name).get()` | `row.connect(master).set_name(new).update()` |

- **CFG-21** 모델이나 읽어 온 행은 자신이 연결된 연결만 사용한다. `master`의 트랜잭션 안에서 `slave1`에 연결한 모델은 트랜잭션 밖에서 `slave1`로 실행되고, `connect`가 없는 모델은 트랜잭션 안에서 실행된다.
- **CFG-22** 연결마다 풀, prepared statement, 세션 설정이 따로 있다.
- **CFG-22a** Go와 Rust와 TypeScript와 Python: MySQL과 PostgreSQL에서 연결의 `stats()`는 자기 pool의 connection만 집계한다(CFG-5a).
- **CFG-23** replica는 primary가 commit한 변경을 그 뒤에 적용한다. 같은 요청의 쓰기를 읽어야 하는 읽기는 primary 연결을 사용하며, orm은 연결을 스스로 고르지 않는다.
- **CFG-24** replica는 쓰기를 거부한다. PostgreSQL은 SQLSTATE 25006을, `super_read_only`인 MySQL replica는 오류 1290을 반환한다. 클라이언트는 읽기 전용 트랜잭션의 쓰기와 읽기 전용으로 열린 SQLite 데이터베이스에 대한 쓰기와 마찬가지로 드라이버 메시지와 함께 `READ_ONLY`를 반환한다.
- **CFG-25** 스키마 도구와 `utils().schema().install`은 primary에서 실행하고, replica는 복제로 스키마를 적용한다.
- **CFG-26** SQLite는 단일 노드 전용이다. SQLite 데이터베이스는 절대 경로로 지정한 로컬 파일이며, ORM은 SQLite replica를 지원하지 않는다.

`make orm-test-servers`는 MySQL primary의 replica와 PostgreSQL primary의 standby를 시작한다. 이 규칙은 Go, PHP, PHP extension, TypeScript, Python, Rust 여섯 configured implementation에 적용되며 PHP extension의 전체 database verification은 아직 남아 있다. PostgreSQL standby는 physical replication slot `orm_replica`로 stream하므로, standby가 멈춘 동안에도 primary는 standby가 아직 받지 않은 WAL을 보존한다.

## 연결 pooler {#connection-poolers}

연결 pooler는 클라이언트와 데이터베이스 서버 하나 사이에서 적은 수의 서버 연결을 많은 클라이언트 연결이 나누어 쓰게 한다. Go, PHP, PHP extension, TypeScript, Python, Rust 여섯 configured implementation에 공통 pooler 규칙이 적용된다. 클라이언트는 PostgreSQL에서 transaction 모드의 PgBouncer, MySQL에서 ProxySQL을 통해 동작하며, 둘은 pooler로만 쓴다. 클라이언트는 해당 서버의 DSN으로 pooler에 연결하고, pooler는 어떤 문도 다른 서버로 보내지 않는다. `make client-pooler-check`는 선언된 database case를 실행하며, PHP extension database coverage가 완료됐음을 뜻하지 않는다.

PgBouncer 설정:

- **CFG-27** `pool_mode`: `transaction`. 서버 연결 하나가 한 번에 클라이언트 트랜잭션 하나 또는 트랜잭션 밖의 문 하나를 처리한다.
- **CFG-28** `max_prepared_statements`: 0보다 큰 값(PgBouncer 기본값 200). Go 클라이언트, Rust 클라이언트, TypeScript 클라이언트, Python 클라이언트(`prepare_threshold=0`인 psycopg)는 문을 프로토콜 수준의 이름 있는 prepared statement로 실행하고, PHP 클라이언트는 PostgreSQL 문을 bind와 함께 unnamed statement로 실행한다. 0이면 한 서버 연결에서 준비한 문이 다음 서버 연결에 없어서 PgBouncer가 `prepared statement … already exists` 또는 `does not exist`를 반환한다. PgBouncer는 이름 있는 문을 그 text로 서버 연결에 유지하며, 서버 연결이 이미 가진 text의 Parse는 서버에 닿지 않는다. 그래서 설계상 schema 변경 뒤에 실행되는 catalog session(SCH-6a)은 문에 이름을 붙이는 모든 클라이언트에서 `BEGIN` 직후 `DEALLOCATE ALL`을 실행한다. transaction이 session 동안 서버 연결을 잡고, session의 모든 문은 그 시점 뒤에 서버가 parse하며, PgBouncer는 다른 클라이언트가 아직 쓰는 문을 그 서버 연결에 다시 준비한다. PgBouncer를 거치는 `DEALLOCATE ALL`은 1.22 이상이 필요하다. 클라이언트 연결이나 그 text를 가진 서버 연결에 있는 schema 변경 이전의 문은 직접 연결에서도 PgBouncer를 거쳐도 똑같이 실패한다. 결과 타입이 바뀌었거나(`0A000`, `cached plan must not change result type`), parameter가 새 컬럼에 대해 옛 타입을 유지하거나(`42883`, `42804`), 값을 그 옛 타입으로 읽는다(`22P02`, `22003`, `22007`, `22008`). 트랜잭션 밖에서 실패한 문은 아무것도 바꾸지 않았으므로, 이 중 하나로 실패한 문은 `DEALLOCATE ALL`로 시작하는 트랜잭션 하나 안에서 서버 연결 하나로 한 번 더 실행된다. 다시 실행되는 문은 서버가 지금 추론하는 매개변수 타입을 받고, 타입이 바뀐 매개변수는 Rust를 뺀 모든 클라이언트가 보내는 그 text에서 PostgreSQL이 읽는 값이다. driver가 모든 값을 binary로 bind하는 Rust 클라이언트는 같은 transaction 안에서 그 text를 서버가 추론한 타입으로 읽게 하므로, 그 타입이 읽지 않는 text는 모든 클라이언트에서 PostgreSQL의 `DRIVER` 오류로 실패한다(DIA-219). recipe `parameter_chunking`의 case `model_text_parameter_refused_after_schema_change`, `model_decimal_text_parameter_after_schema_change`, `model_numeric_text_parameter_refused_after_schema_change`가 정수, 날짜, numeric 타입으로 바뀐 column에 text를 쓴다. 다른 이유로 실패한 문은 같은 방식으로 다시 실패하고 그 오류가 호출자에게 전달된다. 호출자의 트랜잭션 안에서는 서버가 트랜잭션을 중단했으므로 오류는 `DRIVER`로 호출자에게 전달된다. PHP 클라이언트는 문에 이름을 붙이지 않으므로 이 경우가 없다.
- **CFG-29** `track_extra_parameters`: `statement_timeout`. 연결이 `statementTimeoutMs`를 설정할 때 필요하다. 클라이언트는 `statement_timeout`을 startup 매개변수로 전달한다. PgBouncer는 추적하지 않는 startup 매개변수를 거부하고, 추적하는 매개변수는 그 클라이언트 연결에 배정하는 모든 서버 연결에만 설정한다.

- **CFG-30** 클라이언트가 트랜잭션 밖에서 정하는 PostgreSQL 세션 상태는 시간대뿐이다. 모든 클라이언트는 시간대를 startup 매개변수 `TimeZone=UTC`로 보내며, PgBouncer는 `TimeZone`을 기본으로 추적한다. 트랜잭션 옵션(`SET TRANSACTION`, `SET LOCAL statement_timeout`), `utils().setLocal`(`set_config(…, true)`), `utils().lock`(`pg_advisory_xact_lock`)은 트랜잭션과 함께 끝난다.
- **CFG-31** 문 취소는 PgBouncer를 거치면 best effort이며 보장되지 않는다. PgBouncer는 클라이언트 연결의 프로토콜 취소 요청을 그 문을 실행하는 서버 연결로 전달하지만, 이 경로는 신뢰할 수 없다. PgBouncer의 취소 경쟁(BUG #14891)은 1.18에서만 고쳐졌고 그 수정에는 hang 부작용이 있으며, 다중 프로세스 구성에서는 peering이 1.19에서 들어오기 전까지 취소 요청이 유실되었다. SQLx 0.9에는 CancelRequest API가 없어 Rust 클라이언트에는 PgBouncer를 거치는 지원되는 취소 경로가 없다. TypeScript는 연결의 process id와 secret key로 그 요청을 전송하고, PHP는 PostgreSQL 연결에서 `ext-pgsql`로 protocol cancel request를 전송한다. 유실된 취소는 문을 계속 실행 상태로 두므로, 호출자는 취소가 서버에 닿는다고 의존해서는 안 된다.
- **CFG-32** `polyspec-orm` crate, 곧 Rust 클라이언트는 startup 매개변수 `extra_float_digits`를 보내지 않는다. PostgreSQL 12 이상은 서버 기본값으로 float8 값을 정확히 출력한다.
- **CFG-33** 위반된 foreign key, check 또는 unique key는 `FOREIGN_KEY`, `CONSTRAINT` 또는 `DUPLICATE_KEY`로 보고되며, 각 database의 native code는 [errors.yaml](errors.yaml)이 나열한 것이고, statement는 어떤 row도 바꾸지 않는다. 이는 CFG-6의 `1205` 규칙 옆의 대응이다.
- **CFG-36** 모든 클라이언트는 CFG-18과 CFG-46이 나열하는 각 형태에 대해 연결을 열기 전에 `CONFIG`를 돌려준다. Go, PHP, PHP extension, TypeScript, Python은 음수인 `poolSize`, `poolIdleSize`, `poolLifetimeMs`, `statementTimeoutMs`에 대해서도 그렇게 하고, Rust의 설정은 이 값들을 부호 없는 타입으로 담는다.
- **CFG-37** 모든 클라이언트는 CFG-19가 정하지 않은 매개변수와 CFG-20의 각 형태에 대해 `CONFIG`를 돌려준다. 어떤 클라이언트도 매개변수를 driver에 넘기지 않는다.

ProxySQL 설정:

- **CFG-34** `mysql-threshold_resultset_size`: 기본값 4 MiB가 아니라 `65536`. 이 크기 아래에서 ProxySQL은 결과를 클라이언트에 전달하기 전에 buffer에 담고, 이 크기의 8배를 담으면 backend 읽기를 멈춘다. ProxySQL의 worker thread는 이 둘 중 하나가 멈출 때까지 결과의 행 읽기에 머문다. 그래서 기본값에서는 짧은 행의 결과가 thread의 heartbeat 기록을 막고, watchdog은 heartbeat를 `restart_on_missing_heartbeats`(기본값 10)번 놓치면 프로세스 전체를 중단하여 모든 클라이언트의 연결이 끊어진다. 이 크기는 두 기능의 범위도 정한다. 이보다 큰 결과는 query cache에 저장되지 않고, 결과가 클라이언트에 닿기 시작한 문은 실패해도 재시도되지 않는다.
- **CFG-35** `mysql-kill_backend_connection_when_disconnect`: 기본값 `true`. 예산으로 멈춘 catalog 읽기(INT-115)는 결과의 나머지를 읽지 않고 반환하며 연결을 닫는다. 행을 전달하던 문은 어느 값에서나 닫힌 backend와 함께 끝난다. 긴 scan이나 `SLEEP`처럼 아무것도 전달하지 않는 문은 `false`에서는 끝까지 실행되고 `true`에서는 즉시 kill된다. 중단된 읽기의 socket을 닫을 수 있는 runtime은 kill이 실패하거나 kill이 없을 때 기다리지 않고 닫는다. catalog가 닫은 연결은 서버가 그 thread를 끝낼 때까지 `max_user_connections`의 자리를 차지하며 서버는 이를 아무에게도 알리지 않으므로, 그 닫기로부터 2초 안에 한도가 거부한 재연결은 그 2초가 끝날 때까지 다시 시도한다(알림이 없어 쓰는 timer이며, 측정값은 40 ms 이내). 그 catalog의 닫기 뒤가 아닌 연결은 곧바로 실패한다. 연결을 닫은 budget 중단은 rollback을 시도하지 않으며 오류는 `CATALOG_LIMIT` 하나다.

ProxySQL은 기본 multiplexing으로 실행한다. ProxySQL은 클라이언트 연결마다 `time_zone`, `sql_mode`, `max_execution_time`(MariaDB에서는 `max_statement_time`)을 기억하고 그 연결에 쓰는 모든 서버 연결에 적용한다. 사용자 변수, `GET_LOCK`, `CREATE TEMPORARY TABLE`을 포함한 문이 실행되면 ProxySQL은 그 클라이언트 연결이 끊어질 때까지 서버 연결 하나에 고정한다. MySQL에서 `utils().setLocal`은 사용자 변수 `` @`orm.<key>` ``를, `utils().lock`은 `GET_LOCK`을 쓰므로 이들을 사용한 연결은 더 이상 multiplexing되지 않는다. 결과는 달라지지 않는다.

migration plan 적용은 pooler를 거치지 않고 primary에 직접 연결한다. 적용이 세션 범위의 MySQL `GET_LOCK`이나 PostgreSQL advisory lock을 잡기 때문이다([plans](plans.md#apply)).
