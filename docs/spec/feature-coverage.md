# Feature coverage verification

- **FCV-1** Each feature in `contracts/features.json` declares `coverage.kind`, distinct `coverage.cases`, `coverage.owners`, and `coverage.dependents`. Use `database` when behavior reads or changes a database and `independent` otherwise. Every `pass` or `partial` client declares an owner under `packages/<runtime>` with `part`, `tests`, and native test commands for each required database (`mysql`, `postgres`, `sqlite`) or the single `none` slot. Each dependent part declares separate cases and tests in its own directory. Missing declarations and paths outside the declared part fail `make feature-check`.

- **FCV-2** One spec holds every orm test. A behaviour that more than one runtime has is tested by the cases of a recipe, which every runtime runs; a runtime keeps a native test only for a behaviour that no other runtime has, such as its binding and packaging surface, a compile-fail fixture or the loading of the PHP extension, or for an input that no recipe value can hold, such as a text that is not a sequence of Unicode scalar values, which a JSON recipe cannot write; such native tests of one behaviour are one parity unit, bound in each runtime that can hold the input. The harness tests of P32 are not parity units. A recipe is a JSON file of a parity suite (`suites` of `config/parity.json`) whose `$schema` names `scripts/features/schema/recipe.schema.json` by its path relative to the recipe, which is how a recipe is told from the other files of the suites, and that schema closes its keys: `requirements`, `fixture` (a `dbspec-set.json` document set, absent from a recipe without a database), `seed` and `cases`, and `schema` (the `.dbs` manifest that `ir.validate` steps check against, FCV-4), each case with a distinct `id`, its `requirements`, an optional `seed` and its `steps`. `scripts/features/recipes.test.mts` validates every recipe against the schema with ajv 8.20.0 through `checkJson` of `scripts/json/schema.mts`, and a recipe that the schema refuses fails that test, which runs in `make feature-unit-check`. Until every feature is a recipe, the verification commands and coverage owners of `contracts/features.json` run as FCV-1, FCV-5 and FCV-6 state.
  - `generator-takes-the-documents-only-from-the-set-file` (ORES-21, DBS-5, DBS-98) stays native in every runtime, as an FCV-2 runtime-specific generator entry: the generator has no entry point that all six runtimes share. Go `generator.Generate(Options)` takes a runtime model; Rust `Builder::set(path).try_generate()` takes the set file; PHP `OrmGen::main` and `OrmGen::run`, the TypeScript `generateTypeScript(Manifest, ...)` and the Python `generate_models(RuntimeModel, ...)` take a model or the command line. Each runtime keeps its own test of the rule: Go `TestGoGenerationCommandRefusesTheRemovedDocumentFlags`, PHP `OrmGenCliTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, php-extension `OrmGenCliTestExtensionTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, TypeScript `generate`, Python `test_the_removed_document_flags_are_usage_errors`, Rust `the_builder_takes_the_documents_only_from_the_set_file`.
  - The command line of the generator stays native in every runtime, as an FCV-2 runtime-specific generator entry, for the reason of the unit above: `generator.generate` maps to the call that takes a schema, and the set file, its diagnostics and the comparison belong to the entries around it. These are `generator-set-errors-print-every-error-and-write-nothing` (DBS-27), `generator-rejects-a-document-without-the-signature` (DBS-4, DBS-155), `generator-check-compares-without-writing` and `coverage-model-generation-model-generation-check` (DBS-175).
  - What a generated member is typed as stays native in every runtime, as an FCV-2 compile fixture: a type is spelled in its language, and the compiler of that language is what proves it, so no recipe value can state it. These are `generated-field-types-follow-runtime-model`, `generated-field-types-follow-runtime-model-dbs-112`, `generated-decimal-field-uses-exact-text`, `generator-time-setter-takes-the-text-form`, `generated-typed-getter-public-column-api` and `generated-nonnull-styled-setter-rejects-sql-null`.
  - `dbspec-set-bench` (SCH-1) stays native in every runtime, for the reason of `generator-takes-the-documents-only-from-the-set-file`: it reads the bench set through the set file and the generated output of the language, and `generator.generate` takes a schema.
  - `generated-external-model-reads-its-table` (DBS-110, DBS-173) stays native in every runtime: the generated schema value that carries the external text is source of the language, so only the generated module of that language, loaded or compiled and connected, shows that the model of a used external table reads its table.
  - `generated-manifest-text-and-hash-match` (DBS-104, DBS-111, DBS-120) stays native in every runtime: it loads the generated module of the language and refuses one that its manifest contradicts. The case `generated-code-carries-the-manifest-hash` of the `generator` recipe holds the hash of DBS-103 in every runtime.

The code of a refused text is the recipe `tests/dbspec/load-set.json`, and what all runtimes share is `tests/dbspec/runtime-model.json`.
  - `dbspec-encoding-and-limit-natives` (DBS-144) stays native in every runtime: the line form of a JSON recipe cannot write an empty text, a text without a final line feed or one that is not a sequence of Unicode scalar values (Go, PHP, the extension, TypeScript and Python hold such a text; Rust binds the case `bare-cr` of `dbspec-rules`, since its `&str` cannot hold one), and the peak memory of the limit document in PHP has no op. - **FCV-3** A recipe with a fixture is one suite unit per database, `<recipe>-mysql`, `<recipe>-postgres` and `<recipe>-sqlite`, on the one recipe file, with the cases `$.cases[*].id`; a recipe without a database is one suite unit. Each runtime binds each unit to one entry of its ecosystem test pattern: Go `TestRecipe<Recipe><Database>` in a `*_test.go` file, PHP `test<Database>` in a `*Test.php` class, Rust a libtest-mimic trial `<recipe>_<database>`, Node `<recipe>-<database>.test.mjs` and Python `test_<recipe>_<database>.py`. The entry calls the shared recipe helper of its runtime with the recipe and the database; the helper is a module of the tests with no command line, no output format of its own and no main. For each case the helper creates a database with the case-database factory of its runtime, builds the Schema of the fixture set at run time through the public dbspec API of its runtime (the parse and the manifest of the documents of the set) and installs it with `utils().schema().install`, connects the live catalog to the database (Rust `CatalogConnection::connect`, Go `ConnectCatalog`, PHP `Catalog::connect`, TypeScript `connectCatalog`, Python `connect_catalog`) and reads its current namespace, inserts the seed rows of the recipe and then of the case with `insert_row` of that catalog and the metadata that `describe_table` reads, runs the steps in order and closes the catalog; a seed row that fails fails the case. A step that fails fails the case and names the recipe, the case, the index of the step and the database. A recipe without a database binds its unit with the database part `None`: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs` and `test_<recipe>_none.py`. A recipe whose `fixture` is `"none"` instead of a `dbspec-set.json` has one suite unit per database, as a recipe with a fixture does (`<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`); its cases run on an empty case database and install no fixture, and the helper reads that field and never infers the empty database from the first op. A recipe whose cases need MySQL alone (the socket case of CFG-10) has the one suite unit `<recipe>-mysql`, bound in each runtime that runs MySQL; each case of that unit runs on each of its bindings, and its steps have no `expect`, since an `expect` of FCV-4 has the three database keys.
- **FCV-4** A step is `{"op": <name>, ...}`. Its op names one call of the public API that all six runtimes (Go, PHP, PHP extension, TypeScript, Python, Rust) have, its other fields are the arguments of that call, and the helper maps the op to that call and to nothing else; a runtime that maps no call to an op fails the case with `OP_UNKNOWN <op>`; before any case runs, the loader of each runtime refuses, by name, a file, case or step key and an op that the key table of the recipe schema (`scripts/features/schema/recipe-keys.json`, beside the schema that the recipe names in `$schema`) does not hold for it, and a recipe without `$schema`. A step may bind its result with `"as": <name>`, and a later field of the same case reads it with `{"ref": "<name>"}` or `{"ref": "<name>.<path>"}`. A path is its segments joined by `.`, each a member name or, for an array, a decimal index from 0. A step whose op compares its result has `expect`, whose keys are exactly `mysql`, `postgres` and `sqlite` in a recipe with a fixture and exactly `none` in a recipe without a database; each value is `{"value": <value>}`, `{"error": <code>}` with a code of `docs/spec/errors.yaml` and, on an op that declares it, a `message_suffix` that the message of the error ends with, a `message_holds` that it holds, for a message that the driver wraps, and `driver_cause: true`, for an error that keeps the error of the driver as its cause, or the fields that its op declares below. A field that holds SQL is a string or an object with exactly the keys `mysql`, `postgres` and `sqlite`, and so is an argument value whose form the database decides, such as a time of the default precision of the database. Values, in a step, an expect or a seed row, are recipe wrappers: `{"int": "<decimal>"}` for a signed or unsigned 64-bit integer, `{"text": ...}`, `{"date": ...}`, `{"time": ...}` and `{"datetime": ...}` in the forms of INT-103 and DBS-121, `{"decimal": ...}` in the form of INT-97, `{"bytes_hex": ...}` with two lowercase hex digits per byte, `{"bool": true}` or `{"bool": false}`, `{"null": <type>}`, SQL NULL with its parameter type, and, for the values of the common value model of COD-16 that a styled codec reads and writes, `{"nil": true}` for its null, which is not SQL NULL (COD-20), `{"float": "<number>"}` for a binary64 number in decimal or exponent text, `{"array": [<value>, ...]}` and `{"object": [["<key>", <value>], ...]}` with its members as key and value pairs, and `{"sequence": {"from": <integer>, "count": <integer>}}` with `count` at least 1 for the list of the integers `from`, `from + 1`, ..., `from + count - 1`, each an `int` wrapper, which a helper expands to the list of its argument, so that a long list such as the values of an IN list need not be written out in full; an item of an `array` value that is a `sequence` adds its integers in place. Two floats are equal when their texts name the same binary64 value; an `ordered_json` value compares its numbers by their text and its object members in order (COD-16), and every other style compares an object as the set of its pairs, since no other style defines a member order. A cell that an encode op writes is compared by its bytes, a text cell by its UTF-8 bytes, so its expect is `{"value": {"bytes_hex": ...}}`. The ops are:
  - `model.connect {pool_size, dsn?}` connects the generated model of the fixture to the case database, or with `dsn` to the database that the DSN names (Rust `model::connect`, Go `Connect`, PHP `Orm::connect`, TypeScript and Python the generated `connect`), and binds the connection with `as`; its step has no `expect`. `dsn` is `"case"`, `"case-socket"` or the DSN text of the step. `"case-socket"` is the MySQL DSN of the case database with the Unix socket `ORM_TEST_MYSQL_SOCKET` as its `socket` parameter (CFG-10, CFG-19); a recipe that uses it has the one suite unit `<recipe>-mysql` (FCV-3). A MySQL connection through a socket enables the found-rows count (CFG-10), so a revision-guarded `model.update` of the row that its own connection wrote finds that row.
  - `codec.decode {styles, raw}` decodes a stored value through its codec styles (Rust `codec::decode`, Go `Decode`, PHP `Codec::decode`, TypeScript and Python `decode`); its expect is `{"value": ...}` or `{"error": ...}`.
  - `codec.encode {styles, value}` encodes a value through the executor stages of its styles (Rust `codec::encode`, Go `Encode`, PHP `Codec::encode`, TypeScript and Python `encode`) and may bind the cell with `as`; its value may also be `{"ordered_json": <value>}`, the ordered-json value of that value whatever the stages, so that a recipe writes an ordered-json value under a stage that is not `ordered_json` (COD-16); its expect, when the spec makes the encoding of those styles deterministic, is the cell, and otherwise the step has none and a later `codec.decode` of the bound cell checks the round trip; an encode that fails expects `{"error": ...}`.
  - `codec.host_encode {styles, value, key}` and `codec.host_decode {styles, raw, key}` run the host stages `aes`, `hex` and `ip` of COD-3 with the AES key text `key` (Rust `codec::host_encode` and `codec::host_decode`, Go `HostEncode` and `HostDecode`, PHP `Codec::hostEncode` and `Codec::hostDecode`, TypeScript `hostEncode` and `hostDecode`, Python `host_encode` and `host_decode`); `host_encode` may bind the cell with `as`, and each expects `{"value": ...}` or `{"error": ...}`, `host_encode` none when its output is not deterministic (the nonce of `aes`, COD-5).
  - `collection.key {keys, expect}` takes each value of `keys` through the public key of a collection (INT-11, INT-63, PRT-35; Rust `Key::of`, Go `KeyOf` and `Key.Value`, PHP `Collection::keyOf` and `Collection::identityOf`, TypeScript and Python `Collection.put`, `get` and `keys`). An entry of `keys` is `{"type": ..., "value": ...}`, or `{"type": "bytes", "hex": ...}`, or `{"type": "null"}`. Its expect per database is `{"groups": [...], "types": [...]}`, for each key the index of the first key equal to it and its native type, or `{"error": ..., "message": ...}`. A key that returns another value than it took fails the step.
  - `codec.blind_index {value, key}` derives the blind index of a text with the AES key text `key` (COD-4; Rust `codec::blind_index`, Go `BlindIndex`, PHP `Codec::blindIndex`, TypeScript `blindIndex`, Python `blind_index`); its expect is `{"value": {"text": ...}}` or `{"error": ...}`.
  - `ir.validate {request}` checks one request of the IR (docs/spec/protocol.md) against the manifest of the recipe's `schema`, a root key that names the `.dbs` file relative to the recipe; the helper adds `manifest_hash` and builds the request as the runtime's request type holds it, so a shape that the typed request refuses expects `{"error": "IR_INVALID"}` (Rust `engine::validate`, Go `validate`, PHP `Validator`, TypeScript `validate`, Python `validate`); its expect is `{"value": {"bool": true}}` for an accepted request and `{"error": <code>}` otherwise.
  - `ir.answer {chain, answer | answers, expect}` runs the chain of tests/markdown/cases.json that `chain` names (tests/markdown/README.md) on a connection whose listener answers connect with `{"ok": true}` and the chain's one request with `answer`, or, for a transaction chain, answers each control message and each request by the key of `answers` that its op or kind names (docs/spec/protocol.md section 5, Read; the values of tests/ir/answers.json); it needs no database. Its expect is `{"value": <result>}`, the result of the chain in the plain JSON form of tests/markdown/README.md (a row, a list, a count, a value, `{"error": CODE}` or `{"error", "runs"}`), compared as JSON values, in each runtime with the chain that its markdown conformance runs. An expect of `{"none": {"params": [...]}}` instead names the `params` of the one request that the listener received (PRT-66 and PRT-67: the wire values in the JSON form of PRT-67, compared as JSON values, the `now` of the message not compared), so the case observes the request text that the chain's statement sends without a database; a case has the one form or the other.
  - `planner.compile {schema, input}` compiles one request of the IR (docs/spec/protocol.md) with the engine of each of the three dialects, the public call Engine.compile of client-engine (config/parity.json, Go `Engine.Compile`, PHP and PHP extension `Engine::compile`, TypeScript `Engine#compile`, Python `Engine.compile`, Rust `engine::compile`); `schema` names the `.dbs` manifest relative to the recipe, and the step adds its manifest_hash to `input`. Its expect is `{"value": {"mysql": [<statement>, ...], "postgres": [...], "sqlite": [...]}}`, one plan per dialect, or `{"error": <code>}`; the helper compares the plans of the three dialects as the planner fixture writes them, an audit slot with `name` the audit record table (PRT-32), and with `assemble_types: true` each statement also with `assemble_types`, the type of each output column by name. It needs no database.
  - `generator.generate {schema, options?}` runs the generator of the runtime on the `.dbs` manifest `schema`, which names its file relative to the recipe as `planner.compile` does, and on the scanned sources of `options`, through the public generate entry of each runtime: Go `generator.Generate(Options)`, Rust `Builder::try_generate`, PHP `OrmGen::run`, TypeScript `generateTypeScript` and Python `generate_models`. These calls take a schema, so one op covers the five generators (DSL-44, DSL-151, DSL-152); the API unit is `client-model-generation` (INT-100) of config/parity.json, which binds no runtime yet, so the five calls are named by the ruling of 2026-11-02. `options` is `{"used": [<.dbs relative to the recipe>, ...], "before": {"schema": <.dbs relative to the recipe>, "output": <directory>, "scan": <directory>}, "sources": {<language>: {<path relative to the scanned root>: <source text>}}}`, where `<language>` is `go`, `php`, `typescript`, `python` or `rust`; for each case and runtime, the helper makes one fresh temporary directory as the scan root, writes every file of `sources` for its own language under that root at its path, and calls the generator with that root as the scan input; `before` generates another set first, its schema into its output with the scan of one source directory, so that the sources can use the output of another set (imported-set); `schema_replace {from, to}` replaces a text of the document of `schema` before the generation, so that one document holds the column names that the generator refuses; the set of `schema` goes to the directory `model`, and PHP takes the namespace `Example\\<Directory>` of each output; php-extension reads the `php` sources. Its expect is `{"value": {"includes": [<"table.name">, ...], "excludes": [<"table.name">, ...]}}`, where `includes` lists the methods that the generated code must contain and `excludes` the methods it must not contain, each in schema terms, where Python, which resolves a chain at call time and declares no chain method (DSL-37), also reads the calls that its scan attributes to the class; a name without a method, `"table"`, says that the table has a model, and `text {includes, excludes}` lists texts that the generated files of the set hold together or do not hold; the lists are not the full method set, since a case states only what its natives assert (the public call returns only an error, so the Go helper parses the generated `.go` files with go/parser and lists their method identifiers; every helper reads names from the generated code and checks both lists against them), or `{"error": <code>, "message"?: <text>, "position"?: {"line", "column"?}}`, where `message` is a text that the error contains and `position` is the source position that DSL-152 requires for a file that does not parse (its line, and its column only where the parser gives one; the expect omits it for every other error). A name is never a language's method spelling: `table` is the entity's table name in the `.dbs` manifest, and `name` is the snake_case identifier of the generated method without its language prefix (`get`, `alias`, `new`), so the getter `getGhost` (Go `GetGhost`, Python `get_ghost`) of `user` is `user.ghost`, and the chain method `gtReadCount` of `author` is `author.gt_read_count`. The helper of each runtime maps its own spelling back to that identifier, since the generator defines that mapping; the refusals have the codes `GENERATOR_SCAN_PARSE`, `GENERATOR_SCAN_UNATTACHED` and, for a name that the chain rules or the column name rules refuse (DSL-37, DSL-116, DSL-127, DSL-129, DSL-130, PLN-22), `CONFIG` of docs/spec/errors.yaml, which the Rust helper reads from the start of the message. It needs no database.
  - `dbspec.parse {lines, as}` parses the schema text whose lines are `lines` (docs/spec/dbspec.md). Its public call is Parse of client-dbspec-document (config/parity.json), which all six runtimes have: Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Parse`, PHP and PHP extension `Dbspec::parse`, TypeScript `parseDbspec`, Python `parse_dbspec` and Rust `polyspec_orm_schema::dbspec::parse`; `as` binds the document. Its expect is `{"none": {"diagnostics": [[rule, line, column, message], ...]}}`, the diagnostics in order, whose message is the text of rule `plan` and null for every other rule.
  - `dbspec.parse_plan {lines, as}` parses the plan text whose lines are `lines` (docs/spec/plans.md). Its public call is ParsePlan, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-document): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `ParsePlan`, PHP and PHP extension `Dbspec::parsePlan`, TypeScript `parsePlan`, Python `parse_plan` and Rust `parse_plan`; `as` binds the plan. Its expect is the diagnostics of `dbspec.parse`.
  - `dbspec.diff {source, plan}` diffs the plan against the document that `source` binds (null is the empty schema). Its public call is Diff, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-manifest-set): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Diff`, PHP and PHP extension `Dbspec::diff`, TypeScript `diffPlan`, Python `diff_plan` and Rust `diff`. Its expect is `{"none": {"changes": [[kind, table, name], ...]}}` for a diff without diagnostics, or `{"none": {"messages": [...]}}`, the messages of its diagnostics, each of rule `plan`.
  - `dbspec.chain {plans}` orders the plans that `plans` binds into one chain. Its public call is Chain, which all six runtimes have (config/parity.json, client-dbspec-plan): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Chain`, PHP and PHP extension `Dbspec::chain`, TypeScript `chainPlans`, Python `chain_plans` and Rust `chain`. Its expect is `{"none": {"order": [<plan name>, ...]}}` for a chain without diagnostics, or `{"none": {"messages": [...]}}`, the messages of its diagnostics, each of rule `chain`.
  - `dbspec.compare {source, target}` compares the two documents that `source` and `target` bind, without a plan. Its public call is CompareSchemas, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-manifest-set): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `CompareSchemas`, PHP and PHP extension `Dbspec::compareSchemas`, TypeScript `compareSchemas`, Python `compare_schemas` and Rust `compare_schemas`. Its expect is `{"none": {"differences": [[kind, table, name], ...], "diagnostics": [[rule, line, column, message], ...]}}`, whose messages are those of every rule.

- **FCV-5** The test cases under `scripts/features/coverage.test.mts` change one required dimension at a time and require failure for invented JSON success, an absent owner, dependent part, test path, client, database, case, repeated run, state comparison, or an undeclared result. `make feature-check` fails until every claimed behavior has current execution evidence. A successful checker self-test does not assert that client behavior is complete.
- **FCV-6** `make feature-coverage` runs the coverage of every feature once, as `make orm-check` does, and `make feature-check` runs it with every verification command. `node scripts/features/coverage.mts --feature <id>`, under the test environment of `.runtime/servers/env`, runs the coverage specs of that feature only: its owners and dependent parts on each database, twice. `<id>` is a feature `id` of `contracts/features.json`, as for `scripts/features/check.mts --feature`; an unknown id fails with the list of valid ids instead of running nothing. For example, `node scripts/features/coverage.mts --feature dsn_connection` executes only the DSN connection feature. The DSN feature requires read-only owner cases for all six configured implementations (Go, PHP, PHP extension, TypeScript, Python and Rust); the current owner cases do not yet cover PHP extension behavior. Generated-model dependent cases currently run in Go and Rust; required evidence for PHP, PHP extension, TypeScript, Python and Rust remains scoped by the feature manifest, so missing owner coverage leaves the feature partial. The selected URI is supplied through `ORM_FEATURE_DSN`; the checker reads database state before and after both runs.


## Database features as recipes

- **FCV-8** A database feature becomes a recipe in its own commit. The commit adds the recipe file with its `fixture` (a `dbspec-set.json` that names its `.dbs` documents), its `seed` and its `cases`; adds each op that its steps use to the list of FCV-4, to `scripts/features/schema/recipe.schema.json` and to the recipe helper of each of the six runtimes; adds the three suite units of FCV-3 to `config/parity.json`, each bound in the six runtimes; points the owners of the feature in `contracts/features.json` at the recipe; and removes the hand-written coverage tests of that feature, so that no behaviour of it is tested twice. A make target that runs a recipe declares its databases as a need in `contracts/check-inputs.json`, with scope `owner`, `needs` that name its runtime and `databases`, and `inputs` that match the recipe, as `catalog-connection-check/<runtime>` does. `catalog_connection` (`contracts/fixtures/catalog_connection/catalog_connection.json`) is the precedent.
- **FCV-9** A recipe gets its databases from its run and never from a feature variable. The target declares `databases` among its `needs`, so `scripts/check/run.mts` creates the databases of its run and passes that run's environment file as `TEST_ENV` (`make run-databases TARGETS=...`). The recipe helper reads the server DSNs `ORM_TEST_MYSQL_DSN` and `ORM_TEST_POSTGRES_DSN` from that environment, and uses them only as admin connections. For each case it creates a database on the server, or a SQLite file of its own, with the case-database factory of its runtime (Go `testdb.New`, TypeScript `case-database.mjs`, Python `case_database`, PHP `with_case_database`, Rust `CaseDatabase::create` of `packages/rust/case-database`), installs the fixture into it and drops it when the case ends. A recipe never reads `ORM_FEATURE_DATABASE` or `ORM_FEATURE_DSN`, which name the bench database of the hand-written tests that FCV-8 removes.
- **FCV-10** A database feature runs on all three databases, `mysql`, `postgres` and `sqlite`. A recipe with a fixture has one suite unit per database (FCV-3), and every expect has exactly those three keys (FCV-4), so a database on which a case is expected to fail says so with its `{"error": <code>}` and does not drop out. The recipe format has no exclusion key: `scripts/features/schema/recipe.schema.json` closes the keys of a recipe, and no recipe declares an exclusion. An exclusion would be a schema change with a declared reason; until one exists, a difference between databases is written as the outcome of each database.
- **FCV-11** A missing DSN fails the case and names the variable; it never skips. Each factory of FCV-9 fails with `<VARIABLE> is required; database tests never skip`: Go `testdb.New`, TypeScript `case-database.mjs`, Rust `packages/rust/case-database` and PHP `case_database.php` do so today. Python `case_database` names the variable too, but its message (`is required for the <dialect> statement fault cases`, from `required_dsn` of `statement_fault.py`) is not the FCV-11 wording, and it is a defect to be aligned. A factory that fails without naming the variable, or that skips, is a defect of FCV-11, not an accepted skip. The same failure happens for a recipe run outside its make target when `ORM_TEST_MYSQL_DSN` or `ORM_TEST_POSTGRES_DSN` is unset.
- **FCV-12** The feature checker reads each runtime's result from the case results of the recipe run by name and does not run the recipe a second time. Each binding of a suite unit names its cases by `$.cases[*].id` (FCV-3), so a case result is identified by the unit (recipe and database) and the case id. Today `catalog-connection-check/<runtime>` runs each runtime's test entries and reads their exit status; it records no per-case result for the feature checker. Giving the checker per-case results extends that path, and the recipe rows of T334-3 add the extension when the checker first reads a recipe.
- **FCV-13** The seed data of a recipe belongs to its recipe file and is installed per case, never per run and never in a shared database. For each case the helper installs the fixture set into the case database, then inserts the file-level `seed` and then the case's own `seed` with `insert_row`, in the order of the recipe, through the metadata that `describe_table` reads (Go `insertSeed`, and the same order in TypeScript, Python, PHP and Rust). A seed row that fails fails the case.
- **FCV-14** A runtime keeps a native test for a database behaviour only where FCV-2 names the behaviour as runtime-unique, and the test's file states that reason. A database behaviour that another runtime has is a recipe case, and the native test of it is removed in the commit that adds the recipe. Whether a native test states a valid reason is a judgement at review, not a check.
- **FCV-15** Each runtime has one recipe runner: Go `packages/go/internal/recipe`, TypeScript `packages/ts/tests/recipe.mjs`, Python `packages/python/tests/recipe.py`, PHP `packages/php/tests/Recipe.php`, which the PHP extension runs, and Rust `packages/rust/tests/src/recipe.rs`, whose trial binaries add the dispatcher of the generated models of their fixture, since the runner cannot name those models. The binding of a recipe suite unit hands its file to the runner of its runtime and implements no op. A runner dispatches an op by its full name from a list it names and refuses an op it does not name with `OP_UNKNOWN`. Every op of the recipe schema is the op of a step of a recipe, so a runtime that lacks an op fails that recipe. `make recipe-runners-check` enforces this.

## Owner checks

- **FCV-7** `make owner-check` runs the checks that own the changed files: by default the files that differ from `HEAD` and the untracked files, or the files given as `PATHS="<paths>"`. Every verification command of `contracts/features.json` declares its `inputs`, and every coverage part, an owner client (`owner/<language>`) or a dependent part (`dependent/<id>`), declares its `tests` and optional `inputs`. `scripts/features/owners.mts` selects the commands and parts whose inputs contain a changed file or whose declared fixture data (a JSON or dbspec file) names one, as `contracts/fixtures/schema_definition.json` names `contracts/fixtures/audit.dbs` and `contracts/symbols/rust.json` names the Rust sources; a file named by a named file is not followed. It prints each selected command and part with the paths that selected it, and each changed path that selects nothing. A helper that several features use, such as the coverage helper `packages/php/tests/coverage_cases.php`, is declared under `helpers` with its own check and is an input of nothing: its change runs only that check (`scripts/features/check.mts --run --helper <id>`), and `make orm-check` runs every feature that uses it. A change to `contracts/features.json` selects the commands and parts of every feature whose entry differs from `HEAD`, and every helper whose entry differs; a change outside these entries selects none, as `make orm-check` runs every feature. The selected commands run as `scripts/features/check.mts --run --feature <id> --command <id>` and the selected parts as `scripts/features/coverage.mts --feature <id> --part <part>`, each as one step with RUN, PASS or FAIL and its elapsed time; the deadlines are those of the cases inside the step. The declaration check fails on a verification command without inputs, an input that matches no tracked file and a helper declared as an input. It also runs the make targets that `contracts/check-inputs.json` declares with scope `owner` and whose inputs match a changed path; a target with scope `suite`, such as `client-db-check` or `feature-check`, runs only in `make orm-check`, and a target without a scope fails the selection. `node scripts/features/owners.mts --list [<paths>]` prints the selection without running it. `scripts/features/owners.test.mts` runs in `make feature-unit-check`.

## Catalog connection exclusions {#catalog-connection-exclusions}

The recipe `contracts/fixtures/catalog_connection/catalog_connection.json` covers the catalog behavior that the six runtimes share (SCH-6a, INT-117). A native test stays only for a behavior that FCV-2 leaves to one runtime, or that the recipe cannot express. Each kept behavior is listed here with its reason.

- **Surface and packaging (FCV-2).** The class and method surface of `Catalog` and `Model` in PHP and the PHP extension, the loading of the extension, the Rust library surface of the build crate, and the fault-injection doubles of commit, rollback, metadata and cleanup failures, descriptor changes and trigger visibility. The recipe cannot inject a failure.
- **Excluded from the recipe.** The TypeScript `precisionCase` is covered by the recipe case `declared_temporal_cells`, so it has no native test.
- **PHP cause form (INT-109).** The recipe case `descriptor_column_name` holds the code and the message of a descriptor with an invalid column name in every runtime. The `previous` exception of that failure is a form that PHP and the PHP extension alone have, so `CatalogPageValidationTest` and `CatalogConnectionSurfaceTest` assert it. Whether the library `Catalog` is a PHP class is the same surface, and `CatalogPageValidationTest` asserts it.
- **Codec.** No recipe case decodes empty `ordered_json` text, so its native check stays until a codec recipe case asserts it.
