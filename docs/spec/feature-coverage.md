# Feature coverage verification

- **FCV-1** Each feature in `contracts/features.json` declares `coverage.kind`, distinct `coverage.cases`, `coverage.owners`, and `coverage.dependents`. Use `database` when behavior reads or changes a database and `independent` otherwise. Every `pass` or `partial` client declares an owner under `packages/<runtime>` with `part`, `tests`, and native test commands for each required database (`mysql`, `postgres`, `sqlite`) or the single `none` slot. Each dependent part declares separate cases and tests in its own directory. Missing declarations and paths outside the declared part fail `make feature-check`.

- **FCV-2** One spec holds every orm test. A behaviour that more than one runtime has is tested by the cases of a recipe, which every runtime runs; a runtime keeps a native test only for a behaviour that no other runtime has, such as its binding and packaging surface, a compile-fail fixture or the loading of the PHP extension, or for an input that no recipe value can hold, such as a text that is not a sequence of Unicode scalar values, which a JSON recipe cannot write; such native tests of one behaviour are one parity unit, bound in each runtime that can hold the input. The harness tests of P32 are not parity units. A recipe is a JSON file of a parity suite (`suites` of `config/parity.json`) whose `$schema` names `scripts/features/schema/recipe.schema.json` by its path relative to the recipe, which is how a recipe is told from the other files of the suites, and that schema closes its keys: `requirements`, `fixture` (a `dbspec-set.json` document set, absent from a recipe without a database), `seed` and `cases`, and `schema` (the `.dbs` manifest that `ir.validate` steps check against, FCV-4), each case with a distinct `id`, its `requirements`, an optional `seed` and its `steps`. `scripts/features/recipes.test.mts` validates every recipe against the schema with ajv 8.20.0 through `checkJson` of `scripts/json/schema.mts`, and a recipe that the schema refuses fails that test, which runs in `make feature-unit-check`. Until every feature is a recipe, the verification commands and coverage owners of `contracts/features.json` run as FCV-1, FCV-5 and FCV-6 state.
  - `generator-takes-the-documents-only-from-the-set-file` (ORES-21, DBS-5, DBS-98) stays native in every runtime, as an FCV-2 runtime-specific generator entry: the generator has no entry point that all six runtimes share. Go `generator.Generate(Options)` takes a runtime model; Rust `Builder::set(path).try_generate()` takes the set file; PHP `OrmGen::main` and `OrmGen::run`, the TypeScript `generateTypeScript(Manifest, ...)` and the Python `generate_models(RuntimeModel, ...)` take a model or the command line. Each runtime keeps its own test of the rule: Go `TestGoGenerationCommandRefusesTheRemovedDocumentFlags`, PHP `OrmGenCliTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, php-extension `OrmGenCliTestExtensionTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, TypeScript `generate`, Python `test_the_removed_document_flags_are_usage_errors`, Rust `the_builder_takes_the_documents_only_from_the_set_file`.
- **FCV-3** A recipe with a fixture is one suite unit per database, `<recipe>-mysql`, `<recipe>-postgres` and `<recipe>-sqlite`, on the one recipe file, with the cases `$.cases[*].id`; a recipe without a database is one suite unit. Each runtime binds each unit to one entry of its ecosystem test pattern: Go `TestRecipe<Recipe><Database>` in a `*_test.go` file, PHP `test<Database>` in a `*Test.php` class, Rust a libtest-mimic trial `<recipe>_<database>`, Node `<recipe>-<database>.test.mjs` and Python `test_<recipe>_<database>.py`. The entry calls the shared recipe helper of its runtime with the recipe and the database; the helper is a module of the tests with no command line, no output format of its own and no main. For each case the helper creates a database with the case-database factory of its runtime, builds the Schema of the fixture set at run time through the public dbspec API of its runtime (the parse and the manifest of the documents of the set) and installs it with `utils().schema().install`, connects the live catalog to the database (Rust `CatalogConnection::connect`, Go `ConnectCatalog`, PHP `Catalog::connect`, TypeScript `connectCatalog`, Python `connect_catalog`) and reads its current namespace, inserts the seed rows of the recipe and then of the case with `insert_row` of that catalog and the metadata that `describe_table` reads, runs the steps in order and closes the catalog; a seed row that fails fails the case. A step that fails fails the case and names the recipe, the case, the index of the step and the database. A recipe without a database binds its unit with the database part `None`: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs` and `test_<recipe>_none.py`. A recipe whose `fixture` is `"none"` instead of a `dbspec-set.json` has one suite unit per database, as a recipe with a fixture does (`<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`); its cases run on an empty case database and install no fixture, and the helper reads that field and never infers the empty database from the first op.
- **FCV-4** A step is `{"op": <name>, ...}`. Its op names one call of the public API that all six runtimes (Go, PHP, PHP extension, TypeScript, Python, Rust) have, its other fields are the arguments of that call, and the helper maps the op to that call and to nothing else; a runtime that maps no call to an op fails the case with `OP_UNKNOWN <op>`. A step may bind its result with `"as": <name>`, and a later field of the same case reads it with `{"ref": "<name>"}` or `{"ref": "<name>.<path>"}`. A step whose op compares its result has `expect`, whose keys are exactly `mysql`, `postgres` and `sqlite` in a recipe with a fixture and exactly `none` in a recipe without a database; each value is `{"value": <value>}`, `{"error": <code>}` with a code of `docs/spec/errors.yaml`, or the fields that its op declares below. A field that holds SQL is a string or an object with exactly the keys `mysql`, `postgres` and `sqlite`, and so is an argument value whose form the database decides, such as a time of the default precision of the database. Values, in a step, an expect or a seed row, are recipe wrappers: `{"int": "<decimal>"}` for a signed or unsigned 64-bit integer, `{"text": ...}`, `{"date": ...}`, `{"time": ...}` and `{"datetime": ...}` in the forms of INT-103 and DBS-121, `{"decimal": ...}` in the form of INT-97, `{"bytes_hex": ...}` with two lowercase hex digits per byte, `{"bool": true}` or `{"bool": false}`, `{"null": <type>}`, SQL NULL with its parameter type, and, for the values of the common value model of COD-16 that a styled codec reads and writes, `{"nil": true}` for its null, which is not SQL NULL (COD-20), `{"float": "<number>"}` for a binary64 number in decimal or exponent text, `{"array": [<value>, ...]}` and `{"object": [["<key>", <value>], ...]}` with its members as key and value pairs. Two floats are equal when their texts name the same binary64 value; an `ordered_json` value compares its numbers by their text and its object members in order (COD-16), and every other style compares an object as the set of its pairs, since no other style defines a member order. A cell that an encode op writes is compared by its bytes, a text cell by its UTF-8 bytes, so its expect is `{"value": {"bytes_hex": ...}}`. The ops are:
  - `model.connect {pool_size}` connects the generated model of the fixture to the case database (Rust `model::connect`, Go `Connect`, PHP `Orm::connect`, TypeScript and Python the generated `connect`) and binds the connection with `as`; its step has no `expect`.
  - `codec.decode {styles, raw}` decodes a stored value through its codec styles (Rust `codec::decode`, Go `Decode`, PHP `Codec::decode`, TypeScript and Python `decode`); its expect is `{"value": ...}` or `{"error": ...}`.
  - `codec.encode {styles, value}` encodes a value through the executor stages of its styles (Rust `codec::encode`, Go `Encode`, PHP `Codec::encode`, TypeScript and Python `encode`) and may bind the cell with `as`; its value may also be `{"ordered_json": <value>}`, the ordered-json value of that value whatever the stages, so that a recipe writes an ordered-json value under a stage that is not `ordered_json` (COD-16); its expect, when the spec makes the encoding of those styles deterministic, is the cell, and otherwise the step has none and a later `codec.decode` of the bound cell checks the round trip; an encode that fails expects `{"error": ...}`.
  - `codec.host_encode {styles, value, key}` and `codec.host_decode {styles, raw, key}` run the host stages `aes`, `hex` and `ip` of COD-3 with the AES key text `key` (Rust `codec::host_encode` and `codec::host_decode`, Go `HostEncode` and `HostDecode`, PHP `Codec::hostEncode` and `Codec::hostDecode`, TypeScript `hostEncode` and `hostDecode`, Python `host_encode` and `host_decode`); `host_encode` may bind the cell with `as`, and each expects `{"value": ...}` or `{"error": ...}`, `host_encode` none when its output is not deterministic (the nonce of `aes`, COD-5).
  - `codec.blind_index {value, key}` derives the blind index of a text with the AES key text `key` (COD-4; Rust `codec::blind_index`, Go `BlindIndex`, PHP `Codec::blindIndex`, TypeScript `blindIndex`, Python `blind_index`); its expect is `{"value": {"text": ...}}` or `{"error": ...}`.
  - `ir.validate {request}` checks one request of the IR (docs/spec/protocol.md) against the manifest of the recipe's `schema`, a root key that names the `.dbs` file relative to the recipe; the helper adds `manifest_hash` and builds the request as the runtime's request type holds it, so a shape that the typed request refuses expects `{"error": "IR_INVALID"}` (Rust `engine::validate`, Go `validate`, PHP `Validator`, TypeScript `validate`, Python `validate`); its expect is `{"value": {"bool": true}}` for an accepted request and `{"error": <code>}` otherwise.
  - `ir.answer {chain, answer | answers, expect}` runs the chain of tests/markdown/cases.json that `chain` names (tests/markdown/README.md) on a connection whose listener answers connect with `{"ok": true}` and the chain's one request with `answer`, or, for a transaction chain, answers each control message and each request by the key of `answers` that its op or kind names (docs/spec/protocol.md section 5, Read; the values of tests/ir/answers.json); it needs no database. Its expect is `{"value": <result>}`, the result of the chain in the plain JSON form of tests/markdown/README.md (a row, a list, a count, a value, `{"error": CODE}` or `{"error", "runs"}`), compared as JSON values, in each runtime with the chain that its markdown conformance runs. An expect of `{"none": {"params": [...]}}` instead names the `params` of the one request that the listener received (PRT-66 and PRT-67: the wire values in the JSON form of PRT-67, compared as JSON values, the `now` of the message not compared), so the case observes the request text that the chain's statement sends without a database; a case has the one form or the other. A step with the bind field `bind {column, value}` (T334-3-15-3c, PRT-67) names the chain `slot` instead: the `column` is a time or datetime column of tests/bind/slots.dbs (its type and precision come from that column), and the `value` is the client value as text; the slot model of tests/bind/slots.dbs takes the value through its generated setter, the public calls of the generated-model-query-chain and client-model-terminal-write API units, and sends the insert, so the expect `{"none": {"params": [...]}}` gives the wire values of that insert, and a value the slot rejects is `{"none": {"value": {"error": CODE}}}` (CODEC_ENCODE), before any statement.
  - `planner.compile {schema, input}` compiles one request of the IR (docs/spec/protocol.md) with the engine of each of the three dialects, the public call Engine.compile of client-engine (config/parity.json, Go `Engine.Compile`, PHP and PHP extension `Engine::compile`, TypeScript `Engine#compile`, Python `Engine.compile`, Rust `engine::compile`); `schema` names the `.dbs` manifest relative to the recipe, and the step adds its manifest_hash to `input`. Its expect is `{"value": {"mysql": [<statement>, ...], "postgres": [...], "sqlite": [...]}}`, one plan per dialect, or `{"error": <code>}`; the helper compares the plans of the three dialects as the planner fixture writes them. It needs no database.
  - `dbspec.parse {lines, as}` parses the schema text whose lines are `lines` (docs/spec/dbspec.md). Its public call is Parse of client-dbspec-document (config/parity.json), which all six runtimes have: Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Parse`, PHP and PHP extension `Dbspec::parse`, TypeScript `parseDbspec`, Python `parse_dbspec` and Rust `polyspec_orm_schema::dbspec::parse`; `as` binds the document. Its expect is `{"none": {"diagnostics": [[rule, line, column, message], ...]}}`, the diagnostics in order, whose message is the text of rule `plan` and null for every other rule.
  - `dbspec.parse_plan {lines, as}` parses the plan text whose lines are `lines` (docs/spec/plans.md). Its public call is ParsePlan, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-document): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `ParsePlan`, PHP and PHP extension `Dbspec::parsePlan`, TypeScript `parsePlan`, Python `parse_plan` and Rust `parse_plan`; `as` binds the plan. Its expect is the diagnostics of `dbspec.parse`.
  - `dbspec.diff {source, plan}` diffs the plan against the document that `source` binds (null is the empty schema). Its public call is Diff, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-manifest-set): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Diff`, PHP and PHP extension `Dbspec::diff`, TypeScript `diffPlan`, Python `diff_plan` and Rust `diff`. Its expect is `{"none": {"changes": [[kind, table, name], ...]}}` for a diff without diagnostics, or `{"none": {"messages": [...]}}`, the messages of its diagnostics, each of rule `plan`.
  - `dbspec.chain {plans}` orders the plans that `plans` binds into one chain. Its public call is Chain, which all six runtimes have (config/parity.json, client-dbspec-plan): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `Chain`, PHP and PHP extension `Dbspec::chain`, TypeScript `chainPlans`, Python `chain_plans` and Rust `chain`. Its expect is `{"none": {"order": [<plan name>, ...]}}` for a chain without diagnostics, or `{"none": {"messages": [...]}}`, the messages of its diagnostics, each of rule `chain`.
  - `dbspec.compare {source, target}` compares the two documents that `source` and `target` bind, without a plan. Its public call is CompareSchemas, which all six runtimes have (config/parity.json, client-dbspec-plan and client-dbspec-manifest-set): Go, PHP, PHP extension, TypeScript, Python and Rust. The functions are Go `CompareSchemas`, PHP and PHP extension `Dbspec::compareSchemas`, TypeScript `compareSchemas`, Python `compare_schemas` and Rust `compare_schemas`. Its expect is `{"none": {"differences": [[kind, table, name], ...], "diagnostics": [[rule, line, column, message], ...]}}`, whose messages are those of every rule.
  - `dbspec.emit_plan {plan}` writes the plan that `plan` binds as the text of docs/spec/plans.md. Its public call is EmitPlan of client-dbspec-document and client-dbspec-plan (config/parity.json), which all six runtimes have: Go `EmitPlan`, PHP and PHP extension `Dbspec::emitPlan`, TypeScript `emitPlan`, Python `emit_plan` and Rust `emit_plan`. Its expect is `{"none": {"text": <plan text>}}`, the lines of the plan, each ended by a newline.
  - `dbspec.plan_steps {source, plan, dialect}` computes the steps of the plan that `plan` binds against the document that `source` binds (null is the empty schema), for the dialect `dialect` (docs/spec/plans.md, Steps). Its public call is PlanSteps of client-dbspec-plan, which all six runtimes have: Go `PlanSteps`, PHP and PHP extension `Dbspec::planSteps`, TypeScript `planSteps`, Python `plan_steps` and Rust `plan_steps`. Its expect is `{"none": {"steps": [<step>, ...]}}`, the steps in order, each the object of docs/spec/plans.md. Each dialect is one step, so a case that checks three dialects has three steps.
  - `dbspec.parse_emit {documents}` parses each document of `documents` (`.dbs` paths relative to the recipe file, parsed with the set of the documents' headers) and emits it (client-dbspec-document, `parse` and `emit`, public in all six runtimes); its expect is `{"identical": <bool>}`, true when the emitted text of every document is its file's bytes (DBS-123).
  - `dbspec.manifest {documents}` builds the manifest of the document set (client-dbspec-manifest-set, `manifest`, public in all six runtimes); its expect is `{"manifest_hash": "sha256:<hex>"}` (DBS-103).
  - `dbspec.render {documents}` renders the document set for each dialect (client-dbspec-introspection-render, `render`, public in all six runtimes); its expect is `{"mysql": [<statement>, ...], "postgres": [<statement>, ...], "sqlite": [<statement>, ...]}`, each list in the order of the render, non-empty (DBS-99).
  - `dbspec.analyze {document}` analyzes one document (client-dbspec-document, `analyze`) and checks that the analysis holds the result of `parse` unchanged; its expect is `{"tokens": [[<line>, <start>, <end>, <class>], ...]}` (DBS-134, DBS-135).
  - `dbspec.parse_positions {document}` parses one document (client-dbspec-document, `parse`) and returns the positions of its declarations; its expect is `{"positions": [{"kind": <kind>, "path": [<name>, ...], "line": <n>, "column": <n>}, ...]}` (DBS-142).
  - `dbspec.format {text}` formats the document text, an array of lines joined with LF and a final LF (client-dbspec-document, `format`); its expect is `{"text": [<line>, ...]}` for a text that formats, and the formatted text formats to itself, or `{"diagnostics": [{"rule": <rule>, "line": <n>, "column": <n>}, ...]}` for a text that the format refuses, with no text (DBS-141, ORES-14).
  - `dbspec.format {text, set?, crlf?, mixed?}` is the inline form of the same op, with the other documents of the case: `set` is `{<name>: [<line>, ...]}`, each parsed with the set of the documents' headers; `crlf` joins the lines of `text` and of every document of `set` with CRLF, and `mixed` joins line i to line i-1 with CRLF when i is odd and LF when i is even, with no final line ending (client-dbspec-document, `parse`, `emit` and `format`, public in all six runtimes; DBS-2, DBS-123, DBS-141, ORES-19). Its expect is `{"text": [<line>, ...]}` when the text parses and emits to itself, the emission of the parse with the set equals the expected text, that text formats to itself, and format returns it; or `{"diagnostics": [{"rule": <rule>, "line": <n>, "column": <n>}, ...]}` when `parse` refuses the text with exactly those diagnostics and `format` returns no text.
  - `dbspec.analyze {text, set?, crlf?, mixed?}` is the inline form of `dbspec.analyze`: it analyzes the text with the same join rules (client-dbspec-document, `analyze`, public in all six runtimes; DBS-134, DBS-135, ORES-1). Its expect is `{"tokens": [[<line>, <start>, <end>, <class>], ...]}` and checks the tokens only, so the text may be an invalid document.
  - `dbspec.parse_positions {text, set?, crlf?, mixed?}` is the inline form of `dbspec.parse_positions` (client-dbspec-document, `parse`; DBS-142, ORES-72), with the same expect.
  - `dbspec.parse_set {owned, external}` parses the set of the texts `owned` and `external` (client-dbspec-manifest-set, `parseSet`, public in all six runtimes; DBS-2, DBS-28, DBS-29, DBS-30, DBS-31, DBS-156, DBS-168, DBS-171); its expect is `{"documents": [{"name": <name>, "external": <bool>, "parsed": <bool>, "diagnostics": [{"rule": <rule>, "line": <n>, "column": <n>, "message": <message, optional>}, ...]}, ...]}`, in the order of the set.
  - `dbspec.read_file {path}` reads the document file at `path`, relative to the recipe file, with `readDbspecFile` (client-dbspec-document, `readFile`, public in all six runtimes; DBS-4, DBS-155, DBS-171), and `dbspec.read_bytes {path}` reads the bytes of that file and checks them with `readDbspecBytes` under the name `path` (client-dbspec-document, `readBytes`). Their expect is `{"errors": [{"line": <n>, "column": <n>, "rule": <rule>}, ...]}`, where each message is the name followed by " is not a dbspec document" for the signature rule or " is not valid UTF-8" for the encoding rule; an empty list means no diagnostic, and then the text equals the file bytes and its emission is unchanged.
  - `dbspec.set {owned, external?, parsing?}` parses the set of the texts `owned` and `external` (LF-joined, each with the other texts as its set and `parsing` as well; `external` texts are marked external) and builds its manifest (client-dbspec-manifest-set, `parseSet` and `manifest`, public in all six runtimes; DBS-30, DBS-99, DBS-103, DBS-105). Its expect is `{"diagnostics": [{"rule": <rule>, "line": <n>, "column": <n>}, ...]}` when the manifest is refused (an empty list when it is built), or `{"manifest": {"manifest_text": <text>, "schema_text": <text>, "manifest_hash": "sha256:<hex>", "schema_hash": "sha256:<hex>", "external_text"?: <text>}, "created"?: [<table>, ...]}` when it is built. The hash form is that of `dbspec.manifest` (T334-3-18-1, commit 164f49ddc). A built manifest also holds: its manifest and external texts parse back as a set without diagnostics; the manifest of the reversed `owned` order is the same; each dialect of `render` gives the refusal's diagnostics, and a built set renders non-empty statements, with `created` creating exactly those tables (client-dbspec-introspection-render, `render`; DBS-99).
  - `catalog.current_namespace {}` reads the namespace that the case catalog selected (`current_namespace`, docs/spec/interfaces.md, Qualified catalog table metadata); its expect is `{"value": ...}`: the name of the case database on MySQL, which the helper binds as `database` before the first step and the expect reads with `{"ref": "database"}`, the schema `public` on PostgreSQL and `main` on SQLite.
  - `catalog.describe_table {table}` reads the metadata of the table named `table` in the namespace of the case (`describe_table`); its expect is `{"columns": [<name>, ...], "primary_key": [<name>, ...], "reliable_row_identity": <bool>}`, and `as` binds the metadata.
  - `catalog.table_page {table, limit, offset, columns}` reads a page of that table (`table_page`); its expect is `{"columns": [<name>, ...], "order_by": [<name>, ...], "has_more": <bool>, "rows": [[<value>, ...], ...]}`, whose `columns` names every column of the page in physical order (INT-114) and whose rows hold the cells of the columns that `columns` names, in that order, and `as` binds the page.
  - `catalog.read_only_query {sql, max_rows, max_bytes}` runs a read through `read_only_query`; its expect is `{"rows": [[<value>, ...], ...]}` or `{"error": ...}`. `max_rows` and `max_bytes` are optional; an absent one is the default of the runtime.
  - `catalog.read_only_grid_query {sql, max_rows, max_bytes}` runs a read through `read_only_grid_query`; its expect is `{"columns": [<name>, ...], "rows": [[<value>, ...], ...]}`, whose `columns` is optional, or `{"error": ...}`.
  - `catalog.row_snapshot {page, index}` builds the snapshot of the row `index` of a bound page through the from-page constructor of the runtime (Rust `RowSnapshot::from_page`, Go `CatalogSnapshotFromPage`, PHP, TypeScript and Python `rowSnapshotFromPage` or `row_snapshot_from_page` of the catalog); `as` binds it, and its step has no `expect`.
  - `catalog.insert_row {metadata, values}` inserts a row with the bound metadata and the values of `values`, an object of column names (`insert_row`); its expect is `{"rows": [[<value>, ...], ...]}` or `{"error": ...}`.
  - `catalog.update_row {snapshot, set}` updates the row of a bound snapshot with the values of `set` (`update_row`); its expect is `{"rows": [[<value>, ...], ...]}` or `{"error": ...}`.
  - `catalog.delete_row {snapshot}` deletes the row of a bound snapshot (`delete_row`); its expect is `{"value": {"int": ...}}`, the count of deleted rows, or `{"error": ...}`.
  - `sql.exec {sql, reason}` runs DDL that a `.dbs` cannot declare, such as a generated column (DBS-42) or a native type outside dbspec, through the native driver of the runtime; `reason` states why the fixture cannot declare it, and its step has no `expect`.
  - `dsn.connect {dsn}` opens the DSN of the case database (`"case"`) or the DSN text of the step with `Connect` of the public API (Go `orm.Connect`, PHP `Orm::connect`, TypeScript `Db.connect`, Python `Db.connect`, Rust `Db::connect`, public in all six runtimes); its expect is `{"value": {"text": <driver>}}` or `{"error": <code>}`, and the connection is closed.

  A model op uses the `connection` that `model.connect` binds (its `as` name, such as `db` or `conn`) and names a generated-model call of the fixture set; the helper resolves the model by name from the fixture's generated models (the `models.txt` entries of `packages/go` and the generated test models of the other runtimes), so no op carries model code. Each model op takes `connection` and `model`, the model name as the generator spells it, such as `CompositeAccount` or `EventProbe` (the table `event_probe`). A bound row is named by `row`, which is the `as` name of a `model.get_by`.
  - `model.create {connection, model, values}` calls `Create` on a model set from `values`, an object of column names and their values (the terminal Create of client-model-terminal-write, INT-34); `as` binds the created model; its expect is `{"error": <code>}` or absent.
  - `model.creates {connection, model, rows, batch}` calls `Creates` with the rows of `rows` and batch size `batch`; its expect is `{"value": {"int": <count>}}` or `{"error": <code>}`.
  - `model.save {connection, model, values}` calls `Save` on a model set from `values`, which dispatches INSERT or UPDATE by its key (DSL-109); its expect is `{"error": <code>}` or absent.
  - `model.duplicate_create {connection, model, values, duplication}` calls `Create` with the `Duplication` assignments of `duplication`, an object of column names and values; its expect is `{"error": <code>}` or absent.
  - `model.update {connection, model, key, set}` or `{row, set}` loads the row whose key columns hold `key`, or the bound row `row`, writes the assignments of `set` through its entity and calls `Update` (the terminal Update of client-model-terminal-write, INT-35); its expect is `{"error": <code>}` or absent.
  - `model.arithmetic {connection, model, key, column, operation, amount}` loads the row of `key`, applies `operation` (`plus` or `minus`, PLN-26) to `column` by `amount` and calls `Update`; its expect is `{"error": <code>}` or absent.
  - `model.delete {connection, model, where}` or `{row}` loads the rows whose columns equal `where`, or the bound row `row`, and calls `Delete` on each (the terminal Delete of client-model-terminal-write, INT-37); its expect is `{"error": <code>}` or absent.
  - `model.count {connection, model, where?}` calls `GetCount` with the equalities of `where`; with no `where` it counts every row of the model (client-model-terminal-read); its expect is `{"value": {"int": <count>}}`.
  - `model.get_by {connection, model, key | where, columns?}` takes exactly one of `key`, which calls the key lookup `GetBy` of the key columns, or `where`, which calls `Where` and the terminal `Get` (the Where of generated-model-query-chain and the terminal Get of client-model-terminal-read, INT-29). ## Database features as recipes

- **FCV-8** A database feature becomes a recipe in its own commit. The commit adds the recipe file with its `fixture` (a `dbspec-set.json` that names its `.dbs` documents), its `seed` and its `cases`; adds each op that its steps use to the list of FCV-4, to `scripts/features/schema/recipe.schema.json` and to the recipe helper of each of the six runtimes; adds the three suite units of FCV-3 to `config/parity.json`, each bound in the six runtimes; points the owners of the feature in `contracts/features.json` at the recipe; and removes the hand-written coverage tests of that feature, so that no behaviour of it is tested twice. A make target that runs a recipe declares its databases as a need in `contracts/check-inputs.json`, with scope `owner`, `needs` that name its runtime and `databases`, and `inputs` that match the recipe, as `catalog-connection-check/<runtime>` does. `catalog_connection` (`contracts/fixtures/catalog_connection/catalog_connection.json`) is the precedent.
- **FCV-9** A recipe gets its databases from its run and never from a feature variable. The target declares `databases` among its `needs`, so `scripts/check/run.mts` creates the databases of its run and passes that run's environment file as `TEST_ENV` (`make run-databases TARGETS=...`). The recipe helper reads the server DSNs `ORM_TEST_MYSQL_DSN` and `ORM_TEST_POSTGRES_DSN` from that environment, and uses them only as admin connections. For each case it creates a database on the server, or a SQLite file of its own, with the case-database factory of its runtime (Go `testdb.New`, TypeScript `case-database.mjs`, Python `case_database`, PHP `with_case_database`, Rust `CaseDatabase::create` of `packages/rust/case-database`), installs the fixture into it and drops it when the case ends. A recipe never reads `ORM_FEATURE_DATABASE` or `ORM_FEATURE_DSN`, which name the bench database of the hand-written tests that FCV-8 removes.
- **FCV-10** A database feature runs on all three databases, `mysql`, `postgres` and `sqlite`. A recipe with a fixture has one suite unit per database (FCV-3), and every expect has exactly those three keys (FCV-4), so a database on which a case is expected to fail says so with its `{"error": <code>}` and does not drop out. The recipe format has no exclusion key: `scripts/features/schema/recipe.schema.json` closes the keys of a recipe, and no recipe declares an exclusion. An exclusion would be a schema change with a declared reason; until one exists, a difference between databases is written as the outcome of each database.
- **FCV-11** A missing DSN fails the case and names the variable; it never skips. Each factory of FCV-9 fails with `<VARIABLE> is required; database tests never skip`: Go `testdb.New`, TypeScript `case-database.mjs`, Rust `packages/rust/case-database` and PHP `case_database.php` do so today. Python `case_database` names the variable too, but its message (`is required for the <dialect> statement fault cases`, from `required_dsn` of `statement_fault.py`) is not the FCV-11 wording, and it is a defect to be aligned. A factory that fails without naming the variable, or that skips, is a defect of FCV-11, not an accepted skip. The same failure happens for a recipe run outside its make target when `ORM_TEST_MYSQL_DSN` or `ORM_TEST_POSTGRES_DSN` is unset.
- **FCV-12** The feature checker reads each runtime's result from the case results of the recipe run by name and does not run the recipe a second time. Each binding of a suite unit names its cases by `$.cases[*].id` (FCV-3), so a case result is identified by the unit (recipe and database) and the case id. Today `catalog-connection-check/<runtime>` runs each runtime's test entries and reads their exit status; it records no per-case result for the feature checker. Giving the checker per-case results extends that path, and the recipe rows of T334-3 add the extension when the checker first reads a recipe.
- **FCV-13** The seed data of a recipe belongs to its recipe file and is installed per case, never per run and never in a shared database. For each case the helper installs the fixture set into the case database, then inserts the file-level `seed` and then the case's own `seed` with `insert_row`, in the order of the recipe, through the metadata that `describe_table` reads (Go `insertSeed`, and the same order in TypeScript, Python, PHP and Rust). A seed row that fails fails the case.
- **FCV-14** A runtime keeps a native test for a database behaviour only where FCV-2 names the behaviour as runtime-unique, and the test's file states that reason. A database behaviour that another runtime has is a recipe case, and the native test of it is removed in the commit that adds the recipe. Whether a native test states a valid reason is a judgement at review, not a check.

## Owner checks

- **FCV-7** `make owner-check` runs the checks that own the changed files: by default the files that differ from `HEAD` and the untracked files, or the files given as `PATHS="<paths>"`. Every verification command of `contracts/features.json` declares its `inputs`, and every coverage part, an owner client (`owner/<language>`) or a dependent part (`dependent/<id>`), declares its `tests` and optional `inputs`. `scripts/features/owners.mts` selects the commands and parts whose inputs contain a changed file or whose declared fixture data (a JSON or dbspec file) names one, as `contracts/fixtures/schema_definition.json` names `contracts/fixtures/audit.dbs` and `contracts/symbols/rust.json` names the Rust sources; a file named by a named file is not followed. It prints each selected command and part with the paths that selected it, and each changed path that selects nothing. A helper that several features use, such as the coverage helper `packages/php/tests/coverage_cases.php`, is declared under `helpers` with its own check and is an input of nothing: its change runs only that check (`scripts/features/check.mts --run --helper <id>`), and `make orm-check` runs every feature that uses it. A change to `contracts/features.json` selects the commands and parts of every feature whose entry differs from `HEAD`, and every helper whose entry differs; a change outside these entries selects none, as `make orm-check` runs every feature. The selected commands run as `scripts/features/check.mts --run --feature <id> --command <id>` and the selected parts as `scripts/features/coverage.mts --feature <id> --part <part>`, each as one step with RUN, PASS or FAIL and its elapsed time; the deadlines are those of the cases inside the step. The declaration check fails on a verification command without inputs, an input that matches no tracked file and a helper declared as an input. It also runs the make targets that `contracts/check-inputs.json` declares with scope `owner` and whose inputs match a changed path; a target with scope `suite`, such as `client-db-check` or `feature-check`, runs only in `make orm-check`, and a target without a scope fails the selection. `node scripts/features/owners.mts --list [<paths>]` prints the selection without running it. `scripts/features/owners.test.mts` runs in `make feature-unit-check`.
