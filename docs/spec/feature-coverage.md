# Feature coverage verification

- **FCV-1** Each feature in `contracts/features.json` declares `coverage.kind`, distinct `coverage.cases`, `coverage.owners`, and `coverage.dependents`. Use `database` when behavior reads or changes a database and `independent` otherwise. Every `pass` or `partial` client declares an owner under `packages/<runtime>` with `part`, `tests`, and native test commands for each required database (`mysql`, `postgres`, `sqlite`) or the single `none` slot. Each dependent part declares separate cases and tests in its own directory. Missing declarations and paths outside the declared part fail `make feature-check`.

- **FCV-2** One spec holds every orm test. A behaviour that more than one runtime has is tested by the cases of a recipe, which every runtime runs; a runtime keeps a native test only for a behaviour that no other runtime has, such as its binding and packaging surface, a compile-fail fixture or the loading of the PHP extension, or for an input that no recipe value can hold, such as a text that is not a sequence of Unicode scalar values, which a JSON recipe cannot write; such native tests of one behaviour are one parity unit, bound in each runtime that can hold the input. The harness tests of P32 are not parity units. A recipe is a JSON file of a parity suite (`suites` of `config/parity.json`) whose `$schema` names `scripts/features/schema/recipe.schema.json` by its path relative to the recipe, which is how a recipe is told from the other files of the suites, and that schema closes its keys: `requirements`, `fixture` (a `dbspec-set.json` document set, absent from a recipe without a database), `seed` and `cases`, and `schema` (the `.dbs` manifest that `ir.validate` steps check against, FCV-4), each case with a distinct `id`, its `requirements`, an optional `seed` and its `steps`. `scripts/features/recipes.test.mts` validates every recipe against the schema with ajv 8.20.0 through `checkJson` of `scripts/json/schema.mts`, and a recipe that the schema refuses fails that test, which runs in `make feature-unit-check`. Until every feature is a recipe, the verification commands and coverage owners of `contracts/features.json` run as FCV-1, FCV-5 and FCV-6 state.

- **FCV-3** A recipe with a fixture is one suite unit per database, `<recipe>-mysql`, `<recipe>-postgres` and `<recipe>-sqlite`, on the one recipe file, with the cases `$.cases[*].id`; a recipe without a database is one suite unit. Each runtime binds each unit to one entry of its ecosystem test pattern: Go `TestRecipe<Recipe><Database>` in a `*_test.go` file, PHP `test<Database>` in a `*Test.php` class, Rust a libtest-mimic trial `<recipe>_<database>`, Node `<recipe>-<database>.test.mjs` and Python `test_<recipe>_<database>.py`. The entry calls the shared recipe helper of its runtime with the recipe and the database; the helper is a module of the tests with no command line, no output format of its own and no main. For each case the helper creates a database with the case-database factory of its runtime, builds the Schema of the fixture set at run time through the public dbspec API of its runtime (the parse and the manifest of the documents of the set) and installs it with `utils().schema().install`, connects the live catalog to the database (Rust `CatalogConnection::connect`, Go `ConnectCatalog`, PHP `Catalog::connect`, TypeScript `connectCatalog`, Python `connect_catalog`) and reads its current namespace, inserts the seed rows of the recipe and then of the case with `insert_row` of that catalog and the metadata that `describe_table` reads, runs the steps in order and closes the catalog; a seed row that fails fails the case. A step that fails fails the case and names the recipe, the case, the index of the step and the database. A recipe without a database binds its unit with the database part `None`: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs` and `test_<recipe>_none.py`. A recipe whose `fixture` is `"none"` instead of a `dbspec-set.json` has one suite unit per database, as a recipe with a fixture does (`<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`); its cases run on an empty case database and install no fixture, and the helper reads that field and never infers the empty database from the first op. A recipe whose cases need MySQL alone (the socket case of CFG-10) has the one suite unit `<recipe>-mysql`, bound in each runtime that runs MySQL; each case of that unit runs on each of its bindings, and its steps have no `expect`, since an `expect` of FCV-4 has the three database keys.
- **FCV-4** A step is `{"op": <name>, ...}`. Its op names one call of the public API that all six runtimes (Go, PHP, PHP extension, TypeScript, Python, Rust) have, its other fields are the arguments of that call, and the helper maps the op to that call and to nothing else; a runtime that maps no call to an op fails the case with `OP_UNKNOWN <op>`; before any case runs, the loader of each runtime refuses, by name, a file, case or step key and an op that the key table of the recipe schema (`scripts/features/schema/recipe-keys.json`, beside the schema that the recipe names in `$schema`) does not hold for it, and a recipe without `$schema`. A step may bind its result with `"as": <name>`, and a later field of the same case reads it with `{"ref": "<name>"}` or `{"ref": "<name>.<path>"}`. A path is its segments joined by `.`, each a member name or, for an array, a decimal index from 0. A step whose op compares its result has `expect`, whose keys are exactly the databases that run the step in a recipe with a fixture (`mysql`, `postgres` and `sqlite`, or those that the `only` of the step, else of its case, names; FCV-10) and exactly `none` in a recipe without a database; each value is `{"value": <value>}`, `{"error": <code>}` with a code of `docs/spec/errors.yaml` and, on an op that declares it, a `message_suffix` that the message of the error ends with, a `message_holds` that it holds, for a message that the driver wraps, `driver_cause: true`, for an error that keeps the error of the driver as its cause, and `keeps_callback: true`, for a ROLLBACK error that keeps the error of the callback, or the fields that its op declares below. A field that holds SQL is a string or an object with exactly the keys `mysql`, `postgres` and `sqlite`, and so is an argument value whose form the database decides, such as a time of the default precision of the database. Values, in a step, an expect or a seed row, are recipe wrappers: `{"int": "<decimal>"}` for a signed or unsigned 64-bit integer, `{"text": ...}`, `{"date": ...}`, `{"time": ...}` and `{"datetime": ...}` in the forms of INT-103 and DBS-121, `{"decimal": ...}` in the form of INT-97, `{"bytes_hex": ...}` with two lowercase hex digits per byte, `{"bool": true}` or `{"bool": false}`, `{"null": <type>}`, SQL NULL with its parameter type, and, for the values of the common value model of COD-16 that a styled codec reads and writes, `{"nil": true}` for its null, which is not SQL NULL (COD-20), `{"float": "<number>"}` for a binary64 number in decimal or exponent text, `{"array": [<value>, ...]}` and `{"object": [["<key>", <value>], ...]}` with its members as key and value pairs, and `{"sequence": {"from": <integer>, "count": <integer>}}` with `count` at least 1 for the list of the integers `from`, `from + 1`, ..., `from + count - 1`, each an `int` wrapper, which a helper expands to the list of its argument, so that a long list such as the values of an IN list need not be written out in full; an item of an `array` value that is a `sequence` adds its integers in place.   - `model.query {connection, model, where, order, columns, lock}` with `expect_unnamed`: the PHP client and the PHP extension name no statement (CFG-28), so a step that a named statement fails holds the outcome of `expect_unnamed` in those two and of `expect` in Go, Rust, TypeScript and Python.
  - `model.query {connection, model, where, order, columns, lock}` calls `Gets` with the equalities of `where`, ordered ascending by the columns of `order` when it is present, and reads `columns`; `lock`, when present, is one of `update`, `share`, `update_nowait` and `share_nowait`, which takes the row lock of `ForUpdate`, `ForShare`, `ForUpdateNoWait` or `ForShareNoWait` (Rust `Core::lock`); its expect is `{"rows": [[<value>, ...], ...]}`. API units `client-model-terminal-read`, `client-query-base` and `generated-model-query-chain`.
  - `transaction {connection, isolation, read_only, fail, steps}` runs `steps`, the ops of this list in order, in the callback of `Db.transaction` on `connection`, with the options `isolation` (a level name of `IsolationLevel`, absent for the default), `read_only` (`ReadOnly` when true) and `fail`, which makes the callback return an error after its steps so that the transaction rolls back; a `transaction` step inside another one is a savepoint (DSL-119). Its expect is `{"value": {"bool": true}}` when the transaction commits, `{"value": {"bool": false}}` when it rolls back by `fail`, or `{"error": <code>}` when the step is refused, such as a nested option (CONFIG). API unit `client-db-transaction`.
  - `model.assign {model, column, value}` sets the column of a new row of the generated model `model` (the bind fixture `slots`) through its public setter of `column` (the Go `Set<Column>`, TypeScript and PHP `set<Column>`, Python `set_<column>`, Rust `set_<column>`), and builds the insert statement of that row, the encode step, without a database; no database runs, and the first message of the markdown listener of `markdown.send` is the statement. Its `value` is a recipe wrapper, and its expect is `{"message": <json>}`, the JSON of the one parameter of the statement, or `{"error": <code>}` for the error that the setter or the encode returns before it sends a message (public API: `client-model-terminal-write`, INT-34 to INT-39, and `generated-model-field-access`, which all six runtimes have). A typed setter that takes no null refuses the nil wrapper before it is called, so a nil assigned into a not-null slot is a native test of the runtime that holds it (tests/bind/messages-python-null.json, FCV-2).

  The Rust mutations also take a cancellation flag, a publisher of the phases and a commit permit; the Rust helper passes a flag that is not set, a publisher that keeps nothing and a permit that allows. The helper of each runtime turns the values that its calls return into recipe wrappers before it compares them.

  - `schema.install {schema}` or `{connection}`, `schema.register {schema}` and `schema.connect {schema}` call `utils().schema().install`, `utils().schema().register` and the connect of a schema value (Go `Install`, `Register` and `ConnectSchema`) on the case database (API units `client-schema-utils-install`, `client-schema-utils-register` and `client-db-connectschema`); `schema.add_tables_and_columns {schema}` calls `addTablesAndColumns` (`client-schema-utils-add-tables-and-columns`) and its expect is `{"value": {"array": [<name>, ...]}}`, the created tables and then the added `table.column` names. The `schema` argument is `{"documents": [<file>, ...], "external": [<file>, ...], "manifest_replace": {"from": <text>, "to": <text>}}`: the file names are relative to the recipe, `external` names the documents of the other sets that the set uses, and `manifest_replace` replaces the text of the manifest of the built schema and keeps its hash, so that the text no longer hashes to it. A `message_contains` on `schema.add_tables_and_columns` is a text that the message of the refusal holds. Each of these three expects `{"value": {"bool": true}}` for a call that returns without error, or `{"error": <code>}`. The `{connection}` form installs the fixture of the recipe on that connection (client-schema-utils-install, INT-55) and has no expect; a case with `"install": false` gets no fixture from the helper before its steps (FCV-9), so its steps install it with this op, and the statement_events cases do so on their own connection before they subscribe, because the SQLite row-lock table is created once per open database handle.
  - `statements.count {steps}` runs its nested steps, each with its own expect, and counts the statements that the database sends while they run (the statement event of `client-statement-event`: Go `Subscribe` of the case connection, PHP `subscribe`, TypeScript and Python `subscribe`, Rust the statement subscription of the connection); its expect is `{"count": <int>}`, and the count is compared as an integer.
  - `transaction {connection?, steps, fail?}` runs its nested steps inside one transaction (`client-db-transaction`: Go `Transaction`, and each runtime's transaction of the case connection); a nested step that fails its own expect fails the transaction, and each nested step keeps its per-database expect. Its expect is `{"value": {"bool": true}}` when the nested steps pass and the transaction commits, or `{"error": <code>}` when the transaction fails. `connection` names the connection that `model.connect` binds and defaults to the case connection (DB.Transaction, INT-72); with `fail: true` the callback returns its own error after its steps, and the expect is `{"error": "CALLBACK"}`, the sentinel that the helper of each runtime returns for a callback's own error. `CALLBACK` is not an orm error code.
  - `query.search {connection, model, columns, text}` searches the text `text` in the columns `columns` of the model `model` (named as the model ops name it) through the public query API of the runtime: the helper normalizes the text with the public bind-check transform fulltext_boolean (DIA-6; Go `plan.FulltextBoolean`, TypeScript `fulltextBoolean`, PHP `Transform::fulltextBoolean`, Python `fulltext_boolean`, Rust `value::fulltext_boolean`; API units client-engine, client-value-function and client-query-ir), builds the predicate as the IR of PRT-75 and compiles it with the public Engine.Compile of client-engine on the dialect of `connection`. Its expect on MySQL and PostgreSQL is `{"sql": <text>, "params": [<value>, ...]}`: the text is the compiled statement with its placeholders as the compiler emits them, and the params are the bound values after the transform, so the normalization of DIA-6 is in the params and the text is not changed. A text with no term is run on the case connection, and the real bind check refuses it: `{"error": "IR_INVALID"}` (DIA-6). On SQLite the predicate is refused at compile (DIA-187): `{"error": "OPERATOR_NOT_ALLOWED"}`. Each expect has the keys of FCV-10.
  - `query.search_chain {connection, model, mode, text}` reads the statement of the generated fulltext method of the mode through the public getQuery on `connection`: `fulltext_boolean` calls `fulltextBooleanNameWithDescription` and `fulltext` calls `fulltextNameWithDescription`, in the spelling of each runtime (DSL-32, DSL-33). Its expect on MySQL and PostgreSQL is `{"sql": <text>, "params": [<value>, ...]}`, and on SQLite `{"error": "OPERATOR_NOT_ALLOWED"}` (DIA-187).

  A row that moves a feature into recipes adds the ops it needs to this list, to the schema and to the helper of every runtime in one commit.

- **FCV-5** The test cases under `scripts/features/coverage.test.mts` change one required dimension at a time and require failure for invented JSON success, an absent owner, dependent part, test path, client, database, case, repeated run, state comparison, or an undeclared result. `make feature-check` fails until every claimed behavior has current execution evidence. A successful checker self-test does not assert that client behavior is complete.
- **FCV-6** `make feature-coverage` runs the coverage of every feature once, as `make orm-check` does, and `make feature-check` runs it with every verification command. `node scripts/features/coverage.mts --feature <id>`, under the test environment of `.runtime/servers/env`, runs the coverage specs of that feature only: its owners and dependent parts on each database, twice. `<id>` is a feature `id` of `contracts/features.json`, as for `scripts/features/check.mts --feature`; an unknown id fails with the list of valid ids instead of running nothing. For example, `node scripts/features/coverage.mts --feature dsn_connection` executes only the DSN connection feature. The DSN feature requires read-only owner cases for all six configured implementations (Go, PHP, PHP extension, TypeScript, Python and Rust); the current owner cases do not yet cover PHP extension behavior. Generated-model dependent cases currently run in Go and Rust; required evidence for PHP, PHP extension, TypeScript, Python and Rust remains scoped by the feature manifest, so missing owner coverage leaves the feature partial. The selected URI is supplied through `ORM_FEATURE_DSN`; the checker reads database state before and after both runs.


## Database features as recipes

- **FCV-8** A database feature becomes a recipe in its own commit. The commit adds the recipe file with its `fixture` (a `dbspec-set.json` that names its `.dbs` documents), its `seed` and its `cases`; adds each op that its steps use to the list of FCV-4, to `scripts/features/schema/recipe.schema.json` and to the recipe helper of each of the six runtimes; adds the three suite units of FCV-3 to `config/parity.json`, each bound in the six runtimes; points the owners of the feature in `contracts/features.json` at the recipe; and removes the hand-written coverage tests of that feature, so that no behaviour of it is tested twice. A make target that runs a recipe declares its databases as a need in `contracts/check-inputs.json`, with scope `owner`, `needs` that name its runtime and `databases`, and `inputs` that match the recipe, as `catalog-connection-check/<runtime>` does. `catalog_connection` (`contracts/fixtures/catalog_connection/catalog_connection.json`) is the precedent.
- **FCV-9** A recipe gets its databases from its run and never from a feature variable. The target declares `databases` among its `needs`, so `scripts/check/run.mts` creates the databases of its run and passes that run's environment file as `TEST_ENV` (`make run-databases TARGETS=...`). The recipe helper reads the server DSNs `ORM_TEST_MYSQL_DSN` and `ORM_TEST_POSTGRES_DSN` from that environment, and uses them only as admin connections. For each case it creates a database on the server, or a SQLite file of its own, with the case-database factory of its runtime (Go `testdb.New`, TypeScript `case-database.mjs`, Python `case_database`, PHP `with_case_database`, Rust `CaseDatabase::create` of `packages/rust/case-database`), installs the fixture into it and drops it when the case ends. A recipe never reads `ORM_FEATURE_DATABASE` or `ORM_FEATURE_DSN`, which name the bench database of the hand-written tests that FCV-8 removes.
- **FCV-10** A database feature runs on all three databases, `mysql`, `postgres` and `sqlite`. A recipe with a fixture has one suite unit per database (FCV-3), and every expect names exactly the databases that run its step (FCV-4), so a database on which a case is expected to fail says so with its `{"error": <code>}` and does not drop out. `only`, on a step or a case, names the databases that run it, for a statement or a call that exists only there, such as the notification of PostgreSQL (INT-91), or a behavior that only they have; a call that a database refuses is written as that refusal, not left out with `only`. An expect names no database that does not run its step, because a recipe states nothing that never runs, and `scripts/features/recipes.test.mts` refuses any other set of names; without an `only` and its reason, a difference between databases is written as the outcome of each database.
- **FCV-11** A missing DSN fails the case and names the variable; it never skips. Each factory of FCV-9 fails with `<VARIABLE> is required; database tests never skip`: Go `testdb.New`, TypeScript `case-database.mjs`, Rust `packages/rust/case-database` and PHP `case_database.php` do so today. Python `case_database` names the variable too, but its message (`is required for the <dialect> statement fault cases`, from `required_dsn` of `statement_fault.py`) is not the FCV-11 wording, and it is a defect to be aligned. A factory that fails without naming the variable, or that skips, is a defect of FCV-11, not an accepted skip. The same failure happens for a recipe run outside its make target when `ORM_TEST_MYSQL_DSN` or `ORM_TEST_POSTGRES_DSN` is unset.
- **FCV-12** The feature checker reads each runtime's result from the case results of the recipe by name. An owner of a recipe names it in its command: `{"runner", "test", "recipe"}`, with `symbol` for the test method of Go and PHP. The recipe is the list of its owners: the manifest holds no copy, reading it (`scripts/features/manifest.mts`) takes the cases of the recipe on that database, a case with `only` left out on the others, and the schema of the manifest refuses a written copy; when every owner of a feature is a recipe owner, its `coverage.cases` comes from the recipe the same way, and `make feature-unit-check`'s `scripts/features/recipes.test.mts` refuses a written copy of that list. The checker runs the entry once with the test runner of its runtime and sets `ORM_RECIPE_RESULTS` to a file; each recipe runner of FCV-15 appends `CASE <id> [<database>] PASS` to that file when a case has passed, or `CASE <id> PASS` for a recipe without a database, and writes nothing when the variable is unset. The result is the exit status of the entry and those lines, read by one reader for all six runtimes: a case without a line did not pass. An owner of an independent feature whose behaviour is a case of a recipe with a database names that one database as `database`. A recipe owner names no `dsn_env`, and the checker reads no database state for it, since each case has a database of its own (FCV-9).
- **FCV-13** The seed data of a recipe belongs to its recipe file and is installed per case, never per run and never in a shared database. For each case the helper installs the fixture set into the case database, then inserts the file-level `seed` and then the case's own `seed` with `insert_row`, in the order of the recipe, through the metadata that `describe_table` reads (Go `insertSeed`, and the same order in TypeScript, Python, PHP and Rust). A seed row that fails fails the case. `seed.after` is one `sql.exec` step that runs once the rows of the seed are written, for what those rows leave behind, such as a PostgreSQL identity sequence that an explicit row does not move.
- **FCV-14** A runtime keeps a native test for a database behaviour only where FCV-2 names the behaviour as runtime-unique, and the test's file states that reason. A database behaviour that another runtime has is a recipe case, and the native test of it is removed in the commit that adds the recipe. Whether a native test states a valid reason is a judgement at review, not a check. Such a test takes a case database of its own as a recipe does (FCV-9): its command states `"case_database": true` in place of `dsn_env`, and `dsn_env` beside it is refused: the checker gives the item no bench database, reads no state around it and still runs it twice.
- **FCV-15** Each runtime has one recipe runner: Go `packages/go/internal/recipe`, TypeScript `packages/ts/tests/recipe.mjs`, Python `packages/python/tests/recipe.py`, PHP `packages/php/tests/Recipe.php`, which the PHP extension runs, and Rust `packages/rust/tests/src/recipe.rs`, whose trial binaries add the dispatcher of the generated models of their fixture, since the runner cannot name those models. The binding of a recipe suite unit hands its file to the runner of its runtime and implements no op. A runner dispatches an op by its full name from a list it names and refuses an op it does not name with `OP_UNKNOWN`. Every op of the recipe schema is the op of a step of a recipe, so a runtime that lacks an op fails that recipe. `make recipe-runners-check` enforces this.

## Owner checks

- **FCV-7** `make owner-check` runs the checks that own the changed files: by default the files that differ from `HEAD` and the untracked files, or the files given as `PATHS="<paths>"`. Every verification command of `contracts/features.json` declares its `inputs`, and every coverage part, an owner client (`owner/<language>`) or a dependent part (`dependent/<id>`), declares its `tests` and optional `inputs`. `scripts/features/owners.mts` selects the commands and parts whose inputs contain a changed file or whose declared fixture data (a JSON or dbspec file) names one, as `contracts/fixtures/schema_definition.json` names `contracts/fixtures/audit.dbs` and `contracts/symbols/rust.json` names the Rust sources; a file named by a named file is not followed. It prints each selected command and part with the paths that selected it, and each changed path that selects nothing. A helper that several features use, such as the coverage helper `packages/php/tests/coverage_cases.php`, is declared under `helpers` with its own check and is an input of nothing: its change runs only that check (`scripts/features/check.mts --run --helper <id>`), and `make orm-check` runs every feature that uses it. A change to `contracts/features.json` selects the commands and parts of every feature whose entry differs from `HEAD`, and every helper whose entry differs; a change outside these entries selects none, as `make orm-check` runs every feature. The selected commands run as `scripts/features/check.mts --run --feature <id> --command <id>` and the selected parts as `scripts/features/coverage.mts --feature <id> --part <part>`, each as one step with RUN, PASS or FAIL and its elapsed time; the deadlines are those of the cases inside the step. The declaration check fails on a verification command without inputs, an input that matches no tracked file and a helper declared as an input. It also runs the make targets that `contracts/check-inputs.json` declares with scope `owner` and whose inputs match a changed path; a target with scope `suite`, such as `client-db-check` or `feature-check`, runs only in `make orm-check`, and a target without a scope fails the selection. `node scripts/features/owners.mts --list [<paths>]` prints the selection without running it. `scripts/features/owners.test.mts` runs in `make feature-unit-check`.

## Catalog connection exclusions {#catalog-connection-exclusions}

The recipe `contracts/fixtures/catalog_connection/catalog_connection.json` covers the catalog behavior that the six runtimes share (SCH-6a, INT-117). A native test stays only for a behavior that FCV-2 leaves to one runtime, or that the recipe cannot express. Each kept behavior is listed here with its reason.

- **Surface and packaging (FCV-2).** The class and method surface of `Catalog` and `Model` in PHP and the PHP extension, the loading of the extension, the Rust library surface of the build crate, and the fault-injection doubles of commit, rollback, metadata and cleanup failures, descriptor changes and trigger visibility. The recipe cannot inject a failure.
- **Excluded from the recipe.** The TypeScript `precisionCase` is covered by the recipe case `declared_temporal_cells`, so it has no native test.
- **PHP cause form (INT-109).** The recipe case `descriptor_column_name` holds the code and the message of a descriptor with an invalid column name in every runtime. The `previous` exception of that failure is a form that PHP and the PHP extension alone have, so `CatalogPageValidationTest` and `CatalogConnectionSurfaceTest` assert it. Whether the library `Catalog` is a PHP class is the same surface, and `CatalogPageValidationTest` asserts it.
- **Codec.** No recipe case decodes empty `ordered_json` text, so its native check stays until a codec recipe case asserts it.
