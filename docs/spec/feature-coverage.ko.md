# 기능 coverage 검증

- **FCV-1** `contracts/features.json`의 각 기능은 `coverage.kind`, 중복되지 않는 `coverage.cases`, `coverage.owners`, `coverage.dependents`를 선언한다. 데이터베이스를 읽거나 바꾸는 동작에는 `database`, 그 외에는 `independent`를 쓴다. 상태가 `pass` 또는 `partial`인 모든 client는 `packages/<runtime>` 아래에 `part`, `tests`, 필요한 각 데이터베이스(`mysql`, `postgres`, `sqlite`) 또는 `none` 한 칸의 언어별 테스트 명령을 선언한다. 각 사용 부분은 자기 디렉터리에 별도 사례와 테스트를 선언한다. 선언이 빠지거나 선언한 부분 밖의 경로이면 `make feature-check`가 실패한다.

- **FCV-2** 모든 orm 테스트는 하나의 spec에 있다. 둘 이상의 runtime이 가진 동작은 모든 runtime이 실행하는 recipe의 사례로 테스트한다. runtime은 다른 runtime에 없는 동작, 예를 들어 자기 binding과 packaging 표면, compile-fail fixture, PHP extension 적재에 대해서만 실제 테스트를 유지하며, P32의 harness 테스트는 parity unit이 아니다. recipe는 `$schema`가 recipe에서의 상대 경로로 `scripts/features/schema/recipe.schema.json`을 가리키는 parity suite(`config/parity.json`의 `suites`)의 JSON 파일이며, recipe는 이것으로 suite의 다른 파일과 구별되고, 그 schema가 key를 닫는다: `requirements`, `fixture`(`.dbs` 파일, 데이터베이스가 없는 recipe에는 없다), `seed`, `cases`이며, 각 사례는 중복되지 않는 `id`, 자기 `requirements`, 선택적인 `seed`, 자기 `steps`를 가진다. `scripts/features/recipes.test.mts`는 `scripts/json/schema.mts`의 `checkJson`으로 ajv 8.20.0을 써서 모든 recipe를 schema로 검증하며, schema가 거부하는 recipe는 `make feature-unit-check`에서 실행되는 그 테스트를 실패시킨다. 모든 기능이 recipe가 되기 전까지 `contracts/features.json`의 검증 명령과 coverage 소유자는 FCV-1, FCV-5, FCV-6이 적은 대로 실행된다.
- **FCV-3** fixture가 있는 recipe는 데이터베이스마다 suite unit 하나, 즉 recipe 파일 하나 위의 `<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`이고, 사례는 `$.cases[*].id`이다. 데이터베이스가 없는 recipe는 suite unit 하나이다. 각 runtime은 각 unit을 자기 ecosystem 테스트 pattern의 entry 하나에 묶는다: Go는 `*_test.go` 파일의 `TestRecipe<Recipe><Database>`, PHP는 `*Test.php` class의 `test<Database>`, Rust는 libtest-mimic trial `<recipe>_<database>`, Node는 `<recipe>-<database>.test.mjs`, Python은 `test_<recipe>_<database>.py`이며, 데이터베이스가 없는 recipe는 데이터베이스 부분을 None으로 하여 unit을 묶는다: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs`, `test_<recipe>_none.py`. entry는 recipe와 데이터베이스를 주어 자기 runtime의 공유 recipe helper를 호출한다. helper는 command line, 자기 출력 형식, main이 없는 테스트 module이다. helper는 사례마다 자기 runtime의 case-database factory로 데이터베이스를 만들고, 자기 runtime의 installer(Rust `Db::connect_schema`, Go `ConnectSchema`, PHP `SchemaUtils::install`, TypeScript `applyPlans`, Python `apply_plan`)로 fixture를 설치하고, orm-gen이 fixture로 생성하는 fixture set의 generated model create로 recipe의 seed 행과 이어서 사례의 seed 행을 넣고, step을 차례로 실행한다. 실패한 step은 사례를 실패시키며 recipe, 사례, step 순번, 데이터베이스를 적는다.
- **FCV-4** step은 `{"op": <name>, ...}`이다. op는 여섯 runtime(Go, PHP, PHP extension, TypeScript, Python, Rust) 모두가 가진 public API 호출 하나를 가리키고, 나머지 field는 그 호출의 인자이며, helper는 op를 그 호출에만 대응시킨다. op에 대응하는 호출이 없는 runtime은 `OP_UNKNOWN <op>`로 사례를 실패시킨다. step은 `"as": <name>`으로 결과를 묶을 수 있고, 같은 사례의 뒤 field는 `{"ref": "<name>"}` 또는 `{"ref": "<name>.<path>"}`로 그것을 읽는다. 결과를 비교하는 op의 step은 `expect`를 가지며, 그 key는 fixture가 있는 recipe에서 정확히 `mysql`, `postgres`, `sqlite`이고 데이터베이스가 없는 recipe에서 정확히 `none`이다. 각 값은 `{"value": <value>}`, `docs/spec/errors.yaml`의 code를 가진 `{"error": <code>}`, 또는 아래에서 op가 선언하는 field이다. SQL을 담는 field는 문자열이거나 정확히 key `mysql`, `postgres`, `sqlite`를 가진 object이다. step, expect, seed 행의 값은 recipe wrapper이다: 부호 있는 또는 부호 없는 64-bit 정수는 `{"int": "<decimal>"}`, `{"text": ...}`, INT-103과 DBS-121 형식의 `{"date": ...}`, `{"time": ...}`, `{"datetime": ...}`, INT-97 형식의 `{"decimal": ...}`, byte마다 소문자 hex 두 자리인 `{"bytes_hex": ...}`, `{"bool": true}` 또는 `{"bool": false}`, parameter type을 가진 SQL NULL인 `{"null": <type>}`, 그리고 styled codec이 읽고 쓰는 COD-16의 공통 값 모델의 값으로서 SQL NULL이 아닌 그 null인 `{"nil": true}`(COD-20), 10진 또는 지수 text의 binary64 수인 `{"float": "<number>"}`, `{"array": [<value>, ...]}`, 그리고 member를 key와 value의 쌍으로 가진 `{"object": [["<key>", <value>], ...]}`이다. 두 float는 그 text가 같은 binary64 값을 가리킬 때 같다. `ordered_json` 값은 수를 그 text로, object member를 순서대로 비교하고(COD-16), 다른 style은 member 순서를 정의하지 않으므로 object를 그 쌍의 집합으로 비교한다. encode op가 쓴 cell은 그 byte로 비교하고 text cell은 UTF-8 byte로 비교하므로, 그 expect는 `{"value": {"bytes_hex": ...}}`이다. op는 다음과 같다:
  - `model.connect {pool_size}`는 fixture의 generated model을 case 데이터베이스에 연결하고(Rust `model::connect`, Go `Connect`, PHP `Orm::connect`, TypeScript와 Python은 generated `connect`), `as`로 그 연결을 묶으며, 그 step은 `expect`가 없다.
  - `codec.decode {styles, raw}`는 저장된 값을 그 codec style로 decode한다(Rust `codec::decode`, Go `Decode`, PHP `Codec::decode`, TypeScript와 Python `decode`). expect는 `{"value": ...}` 또는 `{"error": ...}`이다.
  - `codec.encode {styles, value}`는 값을 그 style의 executor stage로 encode하고(Rust `codec::encode`, Go `Encode`, PHP `Codec::encode`, TypeScript와 Python `encode`), `as`로 cell을 묶을 수 있다. spec이 그 style의 encoding을 결정적으로 정하면 expect는 그 cell이고, 그렇지 않으면 step은 expect가 없으며 묶인 cell을 읽는 뒤의 `codec.decode`가 round trip을 확인한다. 실패하는 encode는 `{"error": ...}`를 기대한다.
  - `codec.host_encode {styles, value, key}`와 `codec.host_decode {styles, raw, key}`는 COD-3의 host stage `aes`, `hex`, `ip`를 AES key text `key`로 실행한다(Rust `codec::host_encode`와 `codec::host_decode`, Go `HostEncode`와 `HostDecode`, PHP `Codec::hostEncode`와 `Codec::hostDecode`, TypeScript `hostEncode`와 `hostDecode`, Python `host_encode`와 `host_decode`). `host_encode`는 `as`로 cell을 묶을 수 있고, 각각 `{"value": ...}` 또는 `{"error": ...}`를 기대하며, 출력이 결정적이지 않을 때(`aes`의 nonce, COD-5) `host_encode`는 expect가 없다.
  - `codec.blind_index {value, key}`는 text의 blind index를 AES key text `key`로 만든다(COD-4; Rust `codec::blind_index`, Go `BlindIndex`, PHP `Codec::blindIndex`, TypeScript `blindIndex`, Python `blind_index`). expect는 `{"value": {"text": ...}}` 또는 `{"error": ...}`이다.
  - `sql.exec {sql, reason}`은 `.dbs`가 선언할 수 없는 DDL, 예를 들어 generated column(DBS-42)이나 dbspec 밖의 native type을 runtime의 native driver로 실행한다. `reason`은 fixture가 그것을 선언할 수 없는 이유를 적고, 그 step은 `expect`가 없다.

  기능을 recipe로 옮기는 row는 필요한 op를 한 commit에서 이 목록, schema, 모든 runtime의 helper에 더한다.

- **FCV-5** `scripts/features/coverage.test.mts`의 테스트는 필요한 차원을 하나씩 바꾸고 만들어 낸 JSON 성공, 누락된 소유자, 사용자, 테스트 경로, client, 데이터베이스, 사례, 반복 실행, 상태 비교 또는 선언되지 않은 결과에서 실패를 요구한다. 주장한 모든 동작에 현재 실행 증거가 생길 때까지 `make feature-check`는 실패한다. 검사기 자체 테스트가 성공해도 client 동작의 완료를 주장하지 않는다.
- **FCV-6** `make feature-coverage`는 `make orm-check`처럼 모든 기능의 coverage를 한 번 실행하고, `make feature-check`는 그것을 모든 검증 명령과 함께 실행한다. `.runtime/servers/env`의 test 환경 아래에서 `node scripts/features/coverage.mts --feature <id>`는 그 기능의 coverage spec만 실행한다: 소유자와 사용자를 데이터베이스마다 두 번. `<id>`는 `scripts/features/check.mts --feature`처럼 `contracts/features.json`의 기능 `id`다. 없는 id는 아무것도 실행하지 않는 대신 고를 수 있는 id 목록과 함께 실패한다. 예를 들어 `node scripts/features/coverage.mts --feature dsn_connection`은 DSN 연결 기능만 실행한다. DSN 기능은 세 데이터베이스에서 다섯 client의 읽기 전용 소유 사례와 Go client와 Rust client 부분의 생성 모델 사용 사례를 실행한다. 선택한 URI는 `ORM_FEATURE_DSN`으로 전달하고 검사기는 두 실행의 전후 데이터베이스 상태를 읽는다.

## Owner 검사 {#owner-checks}

- **FCV-7** `make owner-check`는 바뀐 file을 소유한 검사를 실행한다. 기본은 `HEAD`와 다른 file과 추적하지 않는 file이고, `PATHS="<paths>"`로 file을 줄 수 있다. `contracts/features.json`의 모든 검증 명령은 `inputs`를 선언하고, 모든 coverage 단위인 owner client(`owner/<language>`)와 사용 부분(`dependent/<id>`)은 `tests`와 선택적 `inputs`를 선언한다. `scripts/features/owners.mts`는 입력에 바뀐 file이 있거나 선언한 fixture data(JSON이나 dbspec file)가 그 file을 적는 명령과 단위를 고른다. 예를 들어 `contracts/fixtures/schema_definition.json`은 `contracts/fixtures/audit.dbs`를, `contracts/symbols/rust.json`은 Rust source를 적는다. 적힌 file이 다시 적는 file은 따라가지 않는다. 고른 명령과 단위마다 그것을 고른 path를 출력하고, 아무것도 고르지 않은 바뀐 path도 출력한다. coverage helper `packages/php/tests/coverage_cases.php`처럼 여러 기능이 쓰는 helper는 `helpers`에 자기 check와 함께 선언하고 어떤 입력에도 넣지 않는다. helper의 변경은 그 check(`scripts/features/check.mts --run --helper <id>`)만 실행하고, helper를 쓰는 모든 기능의 실행은 `make orm-check`가 맡는다. `contracts/features.json`이 바뀌면 `HEAD`와 항목이 다른 기능의 명령과 단위, 그리고 항목이 다른 helper를 고른다. 그 항목 밖의 변경은 `make orm-check`가 모든 기능을 실행하므로 아무것도 고르지 않는다. 고른 명령은 `scripts/features/check.mts --run --feature <id> --command <id>`로, 고른 단위는 `scripts/features/coverage.mts --feature <id> --part <part>`로 실행한다. 각각은 RUN, PASS나 FAIL과 경과 시간을 가진 단계 하나이고, 기한은 단계 안의 case마다 있다. 선언 검사는 입력이 없는 검증 명령, 추적되는 file을 맞추지 않는 입력, 입력으로 쓰인 helper를 실패시킨다. 또 `contracts/check-inputs.json`이 scope `owner`로 선언하고 입력이 바뀐 path를 맞추는 make target을 실행한다. `client-db-check`나 `feature-check`처럼 scope `suite`인 target은 `make orm-check`에서만 실행하고, scope가 없는 target이 있으면 선택이 실패한다. `node scripts/features/owners.mts --list [<paths>]`는 실행하지 않고 고른 것만 출력한다. `scripts/features/owners.test.mts`는 `make feature-unit-check`에서 실행한다.
