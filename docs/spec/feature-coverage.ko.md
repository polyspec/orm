# 기능 coverage 검증

- **FCV-1** `contracts/features.json`의 각 기능은 `coverage.kind`, 중복되지 않는 `coverage.cases`, `coverage.owners`, `coverage.dependents`를 선언한다. 데이터베이스를 읽거나 바꾸는 동작에는 `database`, 그 외에는 `independent`를 쓴다. 상태가 `pass` 또는 `partial`인 모든 client는 `packages/<runtime>` 아래에 `part`, `tests`, 필요한 각 데이터베이스(`mysql`, `postgres`, `sqlite`) 또는 `none` 한 칸의 언어별 테스트 명령을 선언한다. 각 사용 부분은 자기 디렉터리에 별도 사례와 테스트를 선언한다. 선언이 빠지거나 선언한 부분 밖의 경로이면 `make feature-check`가 실패한다.

- **FCV-2** 모든 orm 테스트는 하나의 spec에 있다. 둘 이상의 runtime이 가진 동작은 모든 runtime이 실행하는 recipe의 사례로 테스트한다. runtime은 다른 runtime에 없는 동작, 예를 들어 자기 binding과 packaging 표면, compile-fail fixture, PHP extension 적재에 대해서만, 또는 recipe 값이 담을 수 없는 입력, 예를 들어 JSON recipe가 쓸 수 없는 Unicode scalar 값의 열이 아닌 text에 대해서만 실제 테스트를 유지한다; 한 동작의 그런 실제 테스트는 하나의 parity unit이며, 그 입력을 담을 수 있는 각 runtime에 bind한다. P32의 harness 테스트는 parity unit이 아니다. recipe는 `$schema`가 recipe에서의 상대 경로로 `scripts/features/schema/recipe.schema.json`을 가리키는 parity suite(`config/parity.json`의 `suites`)의 JSON 파일이며, recipe는 이것으로 suite의 다른 파일과 구별되고, 그 schema가 key를 닫는다: `requirements`, `fixture`(`dbspec-set.json` document set, 데이터베이스가 없는 recipe에는 없다), `seed`, `cases`, 그리고 `schema`(`ir.validate` step이 검사하는 `.dbs` manifest, FCV-4)이며, 각 사례는 중복되지 않는 `id`, 자기 `requirements`, 선택적인 `seed`, 자기 `steps`를 가진다. `scripts/features/recipes.test.mts`는 `scripts/json/schema.mts`의 `checkJson`으로 ajv 8.20.0을 써서 모든 recipe를 schema로 검증하며, schema가 거부하는 recipe는 `make feature-unit-check`에서 실행되는 그 테스트를 실패시킨다. 모든 기능이 recipe가 되기 전까지 `contracts/features.json`의 검증 명령과 coverage 소유자는 FCV-1, FCV-5, FCV-6이 적은 대로 실행된다.
  - `generator-takes-the-documents-only-from-the-set-file`(ORES-21, DBS-5, DBS-98)은 모든 runtime에서 native로 남는다. FCV-2의 runtime별 generator 진입점이며, generator에는 여섯 runtime이 공유하는 진입점이 없기 때문이다. Go `generator.Generate(Options)`는 runtime model을 받고, Rust `Builder::set(path).try_generate()`는 set file을 받으며, PHP `OrmGen::main`과 `OrmGen::run`, TypeScript `generateTypeScript(Manifest, ...)`, Python `generate_models(RuntimeModel, ...)`는 model 또는 명령줄을 받는다. 각 runtime은 이 규칙의 자기 test를 유지한다. Go `TestGoGenerationCommandRefusesTheRemovedDocumentFlags`, PHP `OrmGenCliTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, php-extension `OrmGenCliTestExtensionTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, TypeScript `generate`, Python `test_the_removed_document_flags_are_usage_errors`, Rust `the_builder_takes_the_documents_only_from_the_set_file`.

- **FCV-3** fixture가 있는 recipe는 데이터베이스마다 suite unit 하나, 즉 recipe 파일 하나 위의 `<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`이고, 사례는 `$.cases[*].id`이다. 데이터베이스가 없는 recipe는 suite unit 하나이다. 각 runtime은 각 unit을 자기 ecosystem 테스트 pattern의 entry 하나에 묶는다: Go는 `*_test.go` 파일의 `TestRecipe<Recipe><Database>`, PHP는 `*Test.php` class의 `test<Database>`, Rust는 libtest-mimic trial `<recipe>_<database>`, Node는 `<recipe>-<database>.test.mjs`, Python은 `test_<recipe>_<database>.py`이다. entry는 recipe와 데이터베이스를 주어 자기 runtime의 공유 recipe helper를 호출한다. helper는 command line, 자기 출력 형식, main이 없는 테스트 module이다. helper는 사례마다 자기 runtime의 case-database factory로 데이터베이스를 만들고, 자기 runtime의 public dbspec API(set 문서의 parse와 manifest)로 실행 시점에 fixture set의 Schema를 만들어 `utils().schema().install`로 설치하고, live catalog를 데이터베이스에 연결하고(Rust `CatalogConnection::connect`, Go `ConnectCatalog`, PHP `Catalog::connect`, TypeScript `connectCatalog`, Python `connect_catalog`) 그 current namespace를 읽고, `describe_table`이 읽은 metadata와 그 catalog의 `insert_row`로 recipe의 seed 행과 이어서 사례의 seed 행을 넣고, step을 차례로 실행하고, catalog를 닫는다. 실패한 seed 행은 사례를 실패시킨다. 실패한 step은 사례를 실패시키며 recipe, 사례, step 순번, 데이터베이스를 적는다. 데이터베이스가 없는 recipe는 데이터베이스 부분을 `None`으로 하여 unit을 묶는다: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs`, `test_<recipe>_none.py`이다. `fixture`가 `dbspec-set.json`이 아니라 `"none"`인 recipe는 fixture가 있는 recipe와 같이 database마다 suite unit 하나(`<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`)를 가지며, 그 사례는 빈 사례 database에서 실행되고 fixture를 설치하지 않는다. helper는 그 field를 읽고, 첫 op로 빈 database를 추정하지 않는다. MySQL만 필요한 사례를 가진 recipe(CFG-10의 소켓 사례)는 suite unit `<recipe>-mysql` 하나만 가지며, 그 unit은 MySQL을 실행하는 각 runtime에 bind한다. 그 unit의 각 사례는 그 bind마다 실행되고, FCV-4의 `expect`는 세 database key를 가지므로 그 step은 `expect`가 없다.
- **FCV-4** step은 `{"op": <name>, ...}`이다. op는 여섯 runtime(Go, PHP, PHP extension, TypeScript, Python, Rust) 모두가 가진 public API 호출 하나를 가리키고, 나머지 field는 그 호출의 인자이며, helper는 op를 그 호출에만 대응시킨다. op에 대응하는 호출이 없는 runtime은 `OP_UNKNOWN <op>`로 사례를 실패시킨다. 각 runtime의 loader는 어떤 사례도 실행하기 전에, recipe schema의 key table(recipe가 `$schema`로 지정하는 schema 옆의 `scripts/features/schema/recipe-keys.json`)이 담지 않은 file, case, step key와 op, 그리고 `$schema`가 없는 recipe를 그 이름과 함께 거부한다. step은 `"as": <name>`으로 결과를 묶을 수 있고, 같은 사례의 뒤 field는 `{"ref": "<name>"}` 또는 `{"ref": "<name>.<path>"}`로 그것을 읽는다. 경로(path)는 그 segment들을 `.`으로 이은 것이며, 각 segment는 member 이름이거나, array이면 0부터 세는 10진 index이다. 결과를 비교하는 op의 step은 `expect`를 가지며, 그 key는 fixture가 있는 recipe에서 정확히 `mysql`, `postgres`, `sqlite`이고 데이터베이스가 없는 recipe에서 정확히 `none`이다. 각 값은 `{"value": <value>}`, `docs/spec/errors.yaml`의 code를 가진 `{"error": <code>}`(그것을 선언한 op에서는 error 메시지가 끝나는 `message_suffix`, driver가 감싼 메시지가 담는 `message_holds`, driver의 error를 원인으로 지니는 error의 `driver_cause: true`를 더한다), 또는 아래에서 op가 선언하는 field이다. SQL을 담는 field는 문자열이거나 정확히 key `mysql`, `postgres`, `sqlite`를 가진 object이며, 데이터베이스의 기본 precision을 가진 시간처럼 데이터베이스가 형식을 정하는 인자 값도 그렇다. step, expect, seed 행의 값은 recipe wrapper이다: 부호 있는 또는 부호 없는 64-bit 정수는 `{"int": "<decimal>"}`, `{"text": ...}`, INT-103과 DBS-121 형식의 `{"date": ...}`, `{"time": ...}`, `{"datetime": ...}`, INT-97 형식의 `{"decimal": ...}`, byte마다 소문자 hex 두 자리인 `{"bytes_hex": ...}`, `{"bool": true}` 또는 `{"bool": false}`, parameter type을 가진 SQL NULL인 `{"null": <type>}`, 그리고 styled codec이 읽고 쓰는 COD-16의 공통 값 모델의 값으로서 SQL NULL이 아닌 그 null인 `{"nil": true}`(COD-20), 10진 또는 지수 text의 binary64 수인 `{"float": "<number>"}`, `{"array": [<value>, ...]}`, 그리고 member를 key와 value의 쌍으로 가진 `{"object": [["<key>", <value>], ...]}`이다. `{"sequence": {"from": <integer>, "count": <integer>}}`(`count`는 1 이상)는 `from`, `from + 1`, ..., `from + count - 1`의 정수 목록이며 각 값은 `int` wrapper이다. helper는 이를 인자의 목록으로 펼치므로, IN 목록 같은 긴 목록을 전부 적지 않아도 된다. array 값의 항목이 `sequence`이면 그 정수들을 그 위치에 펼쳐 넣는다. 두 float는 그 text가 같은 binary64 값을 가리킬 때 같다. `ordered_json` 값은 수를 그 text로, object member를 순서대로 비교하고(COD-16), 다른 style은 member 순서를 정의하지 않으므로 object를 그 쌍의 집합으로 비교한다. encode op가 쓴 cell은 그 byte로 비교하고 text cell은 UTF-8 byte로 비교하므로, 그 expect는 `{"value": {"bytes_hex": ...}}`이다. op는 다음과 같다:
  - `model.connect {pool_size, dsn?}`는 fixture의 generated model을 case 데이터베이스에 연결하고(Rust `model::connect`, Go `Connect`, PHP `Orm::connect`, TypeScript와 Python은 generated `connect`), `dsn`이 있으면 그 DSN이 이름한 데이터베이스에 연결하며, `as`로 그 연결을 묶는다. 그 step은 `expect`가 없다. `dsn`은 `"case"`, `"case-socket"` 또는 step의 DSN 문자열이다. `"case-socket"`은 case 데이터베이스의 MySQL DSN에 Unix 소켓 `ORM_TEST_MYSQL_SOCKET`을 `socket` 매개변수로 붙인 것이다(CFG-10, CFG-19). 이 DSN을 쓰는 recipe는 suite unit `<recipe>-mysql` 하나뿐이다(FCV-3). 소켓 연결은 found-rows 개수를 켜므로(CFG-10), 자기 연결이 쓴 행을 가리키는 revision 보호 `model.update`는 그 행을 찾는다.
  - `codec.decode {styles, raw}`는 저장된 값을 그 codec style로 decode한다(Rust `codec::decode`, Go `Decode`, PHP `Codec::decode`, TypeScript와 Python `decode`). expect는 `{"value": ...}` 또는 `{"error": ...}`이다.
  - `codec.encode {styles, value}`는 값을 그 style의 executor stage로 encode하고(Rust `codec::encode`, Go `Encode`, PHP `Codec::encode`, TypeScript와 Python `encode`), `as`로 cell을 묶을 수 있다. 값은 `{"ordered_json": <value>}`일 수도 있으며, 이는 stage와 관계없이 그 값의 ordered-json 값이므로 recipe는 `ordered_json`이 아닌 stage 아래에서도 ordered-json 값을 쓴다(COD-16). spec이 그 style의 encoding을 결정적으로 정하면 expect는 그 cell이고, 그렇지 않으면 step은 expect가 없으며 묶인 cell을 읽는 뒤의 `codec.decode`가 round trip을 확인한다. 실패하는 encode는 `{"error": ...}`를 기대한다.
  - `codec.host_encode {styles, value, key}`와 `codec.host_decode {styles, raw, key}`는 COD-3의 host stage `aes`, `hex`, `ip`를 AES key text `key`로 실행한다(Rust `codec::host_encode`와 `codec::host_decode`, Go `HostEncode`와 `HostDecode`, PHP `Codec::hostEncode`와 `Codec::hostDecode`, TypeScript `hostEncode`와 `hostDecode`, Python `host_encode`와 `host_decode`). `host_encode`는 `as`로 cell을 묶을 수 있고, 각각 `{"value": ...}` 또는 `{"error": ...}`를 기대하며, 출력이 결정적이지 않을 때(`aes`의 nonce, COD-5) `host_encode`는 expect가 없다.
  - `collection.key {keys, expect}`는 `keys`의 각 값을 collection의 public key에 통과시킵니다(INT-11, INT-63, PRT-35; Rust `Key::of`, Go `KeyOf`와 `Key.Value`, PHP `Collection::keyOf`와 `Collection::identityOf`, TypeScript와 Python `Collection.put`, `get`, `keys`). `keys`의 항목은 `{"type": ..., "value": ...}`, `{"type": "bytes", "hex": ...}` 또는 `{"type": "null"}`입니다. database별 expect는 `{"groups": [...], "types": [...]}`로 각 key에 대해 그와 같은 첫 key의 index와 native type이거나, `{"error": ..., "message": ...}`입니다. key가 받은 값과 다른 값을 돌려주면 step이 실패합니다.
  - `codec.blind_index {value, key}`는 text의 blind index를 AES key text `key`로 만든다(COD-4; Rust `codec::blind_index`, Go `BlindIndex`, PHP `Codec::blindIndex`, TypeScript `blindIndex`, Python `blind_index`). expect는 `{"value": {"text": ...}}` 또는 `{"error": ...}`이다.
  - `ir.validate {request}`는 IR 요청 하나를 recipe의 `schema` key가 가리키는 `.dbs` manifest에 대해 검증한다(docs/spec/protocol.md). `schema`는 recipe 파일 기준 상대 경로다. helper는 `manifest_hash`를 더하고 요청을 그 runtime의 요청 타입이 담는 대로 만들므로, 타입이 거부하는 형태는 `{"error": "IR_INVALID"}`를 기대한다(Rust `engine::validate`, Go `validate`, PHP `Validator`, TypeScript `validate`, Python `validate`). expect는 허용된 요청이면 `{"value": {"bool": true}}`, 아니면 `{"error": <code>}`다.
  - `ir.validate` step은 `manifest_hash`를 둘 수 있다. 요청이 recipe `schema`의 hash 대신 담는 hash로, 다른 manifest의 요청을 뜻한다(PRT-1).
  - `ir.param_uses {schema, input}`는 `planner.compile`처럼 만든 요청을 검증하고 각 parameter의 쓰임을 확인한다(DIA-31, PRT-67). expect는 `{"value": {"uses": [[<use>, ...], ...]}}`이고 parameter마다 목록 하나다. use는 열이 타입을 정하지 않는 값이면 `{"type"}`, 아니면 `{"type", "column", "length", "null", "precision", "scale"}`이며, 열에 대입되는 값에는 `"assign": true`가 붙는다.
  - `planner.columns {schema, input, names}`는 `planner.compile`처럼 만든 요청을 dialect마다 compile하고 첫 statement에서 `names`가 고른 출력 열을 확인한다. expect는 `{"value": [{"name", "type", "hidden"}, ...]}`이고 `names` 순서이며, plan이 그 이름을 고른 횟수만큼 항목이 있다(PRT-69, DIA-33).
  - `ir.answer {chain, answer | answers, expect}`는 `chain`이 이름 붙인 tests/markdown/cases.json의 chain을 tests/markdown/README.md대로 실행한다. 연결의 listener는 connect에 `{"ok": true}`를 돌려주고, chain의 요청 하나에는 `answer`를 돌려준다. transaction chain이면 제어 메시지와 요청마다 op 또는 kind에 해당하는 `answers`의 값을 돌려준다(docs/spec/protocol.md 5절 Read, tests/ir/answers.json의 값). database를 쓰지 않는다. expect는 `{"value": <결과>}`이며, 결과는 tests/markdown/README.md의 평면 JSON 형식(row, list, count, value, `{"error": CODE}` 또는 `{"error", "runs"}`)이고 JSON 값으로 비교한다. `{"none": {"params": [...]}}` expect는 대신 listener가 받은 요청 하나의 `params`(PRT-66, PRT-67: PRT-67의 JSON 형식인 wire 값을 JSON 값으로 비교하며, 메시지의 `now`는 비교하지 않는다)를 지정한다. 그래서 chain의 문장이 보내는 요청 텍스트를 database 없이 관측하며, 한 case는 둘 중 하나의 형식만 가진다.
  - `planner.compile {schema, input}`는 세 dialect 각각의 엔진으로 IR 요청 하나(docs/spec/protocol.md)를 컴파일한다. 공개 호출은 client-engine(config/parity.json)의 Engine.compile이다(Go `Engine.Compile`, PHP와 PHP 확장 `Engine::compile`, TypeScript `Engine#compile`, Python `Engine.compile`, Rust `engine::compile`). `schema`는 recipe 파일 기준의 `.dbs` manifest이고, step은 그 manifest_hash를 `input`에 더한다. expect는 `{"value": {"mysql": [<statement>, ...], "postgres": [...], "sqlite": [...]}}`(dialect별 plan) 또는 `{"error": <code>}`이며, helper는 세 dialect의 plan을 planner fixture가 쓰는 형식으로 비교한다. 데이터베이스는 필요 없다.
  - `generator.generate {schema, options?}`는 `schema`인 `.dbs` manifest(파일은 `planner.compile`처럼 recipe 기준으로 적는다)와 `options`의 scan source에 대해 각 runtime의 generator를 공개 generate 진입점으로 실행한다: Go `generator.Generate(Options)`, Rust `Builder::try_generate`, PHP `OrmGen::run`, TypeScript `generateTypeScript`, Python `generate_models`. 이 호출들은 schema를 받으므로 op 하나가 다섯 generator를 덮는다(DSL-44, DSL-151, DSL-152). 공개 API unit은 config/parity.json의 `client-model-generation`(INT-100)이고 아직 runtime을 묶지 않으므로, 다섯 호출은 2026-11-02 판정으로 명시한다. `options`는 `{"used": [<recipe 기준 .dbs>, ...], "before": {"schema": <recipe 기준 .dbs>, "output": <디렉터리>, "scan": <디렉터리>}, "sources": {<language>: {<scan 루트 기준 경로>: <source text>}}}`이며, `<language>`는 `go`, `php`, `typescript`, `python`, `rust` 중 하나이다. 각 case와 runtime마다 helper는 임시 디렉터리 하나를 새로 만들어 scan 루트로 삼고, 자기 language의 `sources` 파일을 모두 그 아래 경로대로 쓴 뒤 그 루트를 scan 입력으로 하여 generator를 호출한다. `before`는 다른 set을 먼저 생성한다. 그 schema를 그 output에 source 디렉터리 하나의 scan으로 생성하므로 source가 다른 set의 출력을 쓸 수 있다(imported-set). `schema_replace {from, to}`는 생성 전에 `schema` 문서의 text를 바꾸므로, 문서 하나가 생성기가 거부하는 컬럼 이름을 담는다. `schema`의 set은 디렉터리 `model`에 생성되고, PHP는 각 출력에 namespace `Example\\<Directory>`를 쓴다. php-extension은 `php` source를 읽는다. expect는 `{"value": {"includes": [<"table.name">, ...], "excludes": [<"table.name">, ...]}}`(`includes`는 생성된 code가 담아야 하는 method, `excludes`는 담지 않아야 하는 method를 schema 용어로 적는다. chain을 호출 시점에 풀어 chain method를 선언하지 않는 Python(DSL-37)은 scan이 그 class에 귀속한 호출도 읽는다; method가 없는 이름 `"table"`은 그 table에 model이 있음을 뜻하고, `text {includes, excludes}`는 set의 생성 파일 전체가 담거나 담지 않는 text를 적는다; 목록은 전체 method 집합이 아니며, 사례는 자기 native가 검사하는 것만 적는다. 공개 호출은 error만 돌려주므로 Go helper는 생성된 `.go` 파일을 go/parser로 읽어 method 식별자를 나열하며, 모든 helper는 두 목록을 생성된 code에 대해 검사한다) 또는 `{"error": <code>, "message"?: <text>, "position"?: {"line", "column"?}}`이며, `message`는 오류가 담는 text이고 `position`은 DSL-152가 요구하는 파싱되지 않는 파일의 source 위치다(line, column은 parser가 주는 경우에만; 다른 모든 오류에서 expect는 이를 생략한다). name은 언어의 method 표기가 아니다: `table`은 `.dbs` manifest의 entity table 이름이고, `name`은 언어 접두(`get`, `alias`, `new`)를 뺀 생성 method의 snake_case 식별자다(`user`의 getter `getGhost`(Go `GetGhost`, Python `get_ghost`)는 `user.ghost`, `author`의 chain method `gtReadCount`는 `author.gt_read_count`). 각 runtime의 helper는 자기 표기를 이 식별자로 되돌리며, 그 대응은 generator가 정한다; 거부의 code는 docs/spec/errors.yaml의 `GENERATOR_SCAN_PARSE`, `GENERATOR_SCAN_UNATTACHED`, 그리고 chain 규칙이나 컬럼 이름 규칙이 거부하는 이름(DSL-37, DSL-116, DSL-127, DSL-129, DSL-130, PLN-22)의 `CONFIG`이며, Rust helper는 message 앞에서 읽는다. 데이터베이스는 필요 없다.
  - `dbspec.parse {lines, as}`는 줄이 `lines`인 schema text를 파싱한다(docs/spec/dbspec.md). 공개 호출은 Parse이며, 여섯 runtime이 모두 가진다: Go, PHP, PHP extension, TypeScript, Python, Rust. 함수는 Go `Parse`, PHP와 PHP extension `Dbspec::parse`, TypeScript `parseDbspec`, Python `parse_dbspec`, Rust `polyspec_orm_schema::dbspec::parse`이다. `as`는 document를 묶는다. expect는 `{"none": {"diagnostics": [[rule, line, column, message], ...]}}`이며, message는 rule `plan`의 텍스트이고 다른 rule은 null이다.
  - `dbspec.parse_plan {lines, as}`는 줄이 `lines`인 plan text를 파싱한다(docs/spec/plans.md). 공개 호출은 ParsePlan이며, 여섯 runtime이 모두 가진다: Go, PHP, PHP extension, TypeScript, Python, Rust. 함수는 Go `ParsePlan`, PHP와 PHP extension `Dbspec::parsePlan`, TypeScript `parsePlan`, Python `parse_plan`, Rust `parse_plan`이다. `as`는 plan을 묶는다. expect는 `dbspec.parse`의 diagnostics와 같다.
  - `dbspec.diff {source, plan}`은 plan을 `source`가 묶은 document와 비교한다(null은 빈 schema). 공개 호출은 Diff이며, 여섯 runtime이 모두 가진다: Go, PHP, PHP extension, TypeScript, Python, Rust. 함수는 Go `Diff`, PHP와 PHP extension `Dbspec::diff`, TypeScript `diffPlan`, Python `diff_plan`, Rust `diff`이다. expect는 diagnostics가 없는 diff에 `{"none": {"changes": [[kind, table, name], ...]}}`, 아니면 `{"none": {"messages": [...]}}`이며, 각 message는 rule `plan`이다.
  - `dbspec.chain {plans}`는 `plans`가 묶은 plan들을 chain 하나로 순서 짓는다. 공개 호출은 Chain이며, 여섯 runtime이 모두 가진다: Go, PHP, PHP extension, TypeScript, Python, Rust. 함수는 Go `Chain`, PHP와 PHP extension `Dbspec::chain`, TypeScript `chainPlans`, Python `chain_plans`, Rust `chain`이다. expect는 diagnostics가 없는 chain에 `{"none": {"order": [<plan name>, ...]}}`, 아니면 `{"none": {"messages": [...]}}`이며, 각 message는 rule `chain`이다.
  - `dbspec.compare {source, target}`은 `source`와 `target`이 묶은 두 document를 plan 없이 비교한다. 공개 호출은 CompareSchemas이며, 여섯 runtime이 모두 가진다: Go, PHP, PHP extension, TypeScript, Python, Rust. 함수는 Go `CompareSchemas`, PHP와 PHP extension `Dbspec::compareSchemas`, TypeScript `compareSchemas`, Python `compare_schemas`, Rust `compare_schemas`이다. expect는 `{"none": {"differences": [[kind, table, name], ...], "diagnostics": [[rule, line, column, message], ...]}}`이며, message는 모든 rule의 것이다.
  - `dbspec.emit_plan {plan}`는 `plan`이 묶은 plan을 docs/spec/plans.md의 텍스트로 쓴다. 공개 호출은 client-dbspec-document와 client-dbspec-plan(config/parity.json)의 EmitPlan이며, 여섯 runtime이 모두 가진다: Go `EmitPlan`, PHP와 PHP extension `Dbspec::emitPlan`, TypeScript `emitPlan`, Python `emit_plan`, Rust `emit_plan`. expect는 `{"none": {"text": <plan text>}}`이며, plan의 각 줄이 newline으로 끝난 텍스트다.
  - `dbspec.plan_steps {source, plan, dialect}`는 `plan`이 묶은 plan의 step을 `source`가 묶은 document(null은 빈 schema)에 대해, dialect `dialect`별로 계산한다(docs/spec/plans.md, Steps). 공개 호출은 client-dbspec-plan의 PlanSteps이며, 여섯 runtime이 모두 가진다: Go `PlanSteps`, PHP와 PHP extension `Dbspec::planSteps`, TypeScript `planSteps`, Python `plan_steps`, Rust `plan_steps`. expect는 `{"none": {"steps": [<step>, ...]}}`이며, step은 순서대로이고 각각 docs/spec/plans.md의 객체다. dialect마다 한 번 호출하므로, 세 dialect를 확인하는 case는 호출이 세 번이다. 세 dialect가 아닌 이름의 expect는 `{"none": {"refused": <name>}}`이다. 호출은 DBS-174의 자기 형식(Go는 panic, PHP와 PHP extension은 `InvalidArgumentException`, TypeScript와 Python은 `TypeError`)으로 거부하고 그 메시지에 이름을 담는다. Rust는 dialect를 enum 타입으로 받으므로 그런 호출이 없다.
  - `dbspec.add_tables_steps {source, target, dialect}`는 `source`가 묶은 설치된 document에서 `target`이 묶은 더 새 document로 가는 추가 전용 step을 unsupported 항목 없이 계산한다(docs/spec/schema.md). 공개 호출은 여섯 runtime 모두에 있는 `Dbspec.addTablesAndColumnsSteps`이다. expect는 `{"none": {"added": [<name>, ...], "statements": [<statement>, ...], "differences": [<difference>, ...]}}`이다.

    - `{"action": "scope", "kinds": K, "column": C, "value": V, "nested": B}`는 종류가 K에 있는 요청의 where에 `C = V`를 AND로 덧붙인다. V는 parameter로 바인딩한다. `nested: true`이면 그 요청의 모든 relation query에도 덧붙인다.
    - `{"action": "assign", "kinds": K, "column": C, "value": V}`는 일치하는 insert(단일과 묶음 모두)의 Set에 `C = V`를 덧붙인다. V는 parameter로 바인딩한다.
    - `{"action": "assign_first", "kinds": K, "column": C, "value": V}`는 일치하는 요청의 Set 맨 앞에 `C = V`를 넣는다. V는 parameter로 바인딩한다.
    - `{"action": "rewrite", "kinds": K, "column": C, "value": V}`는 일치하는 요청의 Set에서 C의 각 대입에 V를 새 parameter로 바인딩한다.
    - `{"action": "invalid_param", "kinds": K, "column": C}`는 요청의 parameter를 다섯 칸 넘는 parameter 번호로 `C = `를 where에 AND로 덧붙인다. `ir.Validate`가 이를 거부한다(PRT-65).
    - `{"action": "record", "kinds": K}`는 일치하는 요청마다 `{"kind": <kind>, "entity": <table>}`을 기록한다.
    - `{"action": "record_param", "kinds": K, "column": C}`는 일치하는 요청의 Set에서 C의 각 대입마다 `{"kind": <kind>, "entity": <table>, "param": <value>}`를 기록한다. `param`은 hook이 읽은 바인딩 값이다(INT-78).
    - `{"action": "fail", "kinds": K, "error": CODE}`는 일치하는 요청을 오류 코드 CODE로 실패시킨다.
    K는 요청 종류의 목록(`one`, `all`, `count`, `group_count`, `sum`, `avg`, `paginate`, `insert`, `update`, `delete`, `restore`)이거나 이름 `reads`(앞의 일곱), `reads+restore`(같은 것과 `restore`), `every` 중 하나이다.
  - `hook.records {}`는 field가 없다. expect는 실행된 순서대로 `kind`와 `entity`, `record_param` action이면 `param`도 가진 객체의 `{"value": [<record>, ...]}`, 또는 entity별 기록 수 `{"counts": {<entity>: <정수>}}`이다.
  - `model.restore {connection, model, values, columns?}`는 `values`로 설정한 모델(키가 가리키는 soft delete된 행)에 `Restore`를 호출한다(INT-38). expect는 없거나 `{"error": <code>}`이고, `columns`가 있으면 `Restore`가 돌려준 행의 해당 컬럼인 `{"rows": [[<value>, ...]]}`이다.
  - 표 모델의 `model.update {connection, model, key, set}`는 읽기 없이 새 모델에 키와 대입을 설정하고 `Update`를 호출하므로, 어떤 행도 가리키지 않는 키는 일치하는 행이 없는 update다. `model.connect`는 `audit_source`를 받는다. `{"values": {<column>: <value>}}`는 이 값을 돌려주는 source이고, `{"fail": true}`는 자기 오류로 트랜잭션을 실패시키는 source이며 expect는 이를 `CALLBACK`으로 적는다(CFG-8). 없으면 연결에 audit source가 없다.
  - `model.connect {pool_size, as, aes_keyring}`는 AES 키링 `aes_keyring`, `{"current": <정수>, "versions": {"<version>": "<key text>"}}`로 연결을 연다. 연결은 `current`로 쓰고 `versions`의 모든 버전을 복호화한다(API unit `aes-keyring`, INT-130, `aes-utils`, INT-131). 공개 생성자가 거부하는 키링(빈 키, 또는 선언되지 않은 `current`)은 생성자가 돌려주는 코드(CONFIG)로 그 step을 실패시키며, step은 이를 `{"error": <code>}`로 기대한다.
  - `utils.aes_rotate {connection, model, keyring}`는 공개 생성자가 `keyring`(`model.connect`의 객체)으로 만든 키링으로 연결의 AES 유틸리티의 `Rotate`를 호출한다(API unit `aes-utils-rotate`, INT-60). 목표 버전은 `current`다. expect는 없음, `{"value": {"int": <rotated>}}` 또는 `{"error": <code>}`다. 회전된 행의 저장 버전은 COD-47과 COD-54(docs/spec/codec.md)가 읽는다.
  - conformance_verification recipe(contracts/fixtures/conformance_verification, T334-3-5)는 tests/conformance/vectors.json, vectors.postgres.json, vectors.sqlite.json의 conformance vector를 case로 담는다. vector의 데이터베이스별 기대 text, bind, 결과가 case의 expect이고, 구현에서 기록한 expect는 없다. seed는 migration 전에 recipe에 명시한다. 162행이고 그중 54행이 `author`이며, 값은 vector가 지정한 sequence 번호에서 benchmarks/sql/seed.*.sql의 공식을 따른다. 자체 fixture set(conformance_verification.dbs, conformance_reader.dbs, 외부 conformance_shared.dbs)은 모델을 생성하지 않으므로 case는 아래 table 경로에서 실행한다. recipe는 공개 builder만 구동하고, 생성된 각 메서드는 native 본문을 유지한다(T334-3-5-1). 생성 메서드를 이름 문자열로 호출하는 recipe는 타입 API가 아니라 이름 dispatcher를 검증하기 때문이다.
  - op당 경로는 하나다. fixture contracts/fixtures/bench/dbspec-set.json은 모델을 생성한다. 이 fixture를 쓰는 recipe의 model op는 그 모델의 생성된 타입 메서드를 호출한다(composite_keys, constraints_and_relations, fulltext_search, model_queries, model_socket, model_writes, performance_gate, transactions). 다른 fixture의 model op는 table 경로에서 실행한다. op는 fixture 테이블의 entity에 대해 공개 builder를 호출하며, 예를 들어 `HookItem`은 테이블 `hook_item`이다. 둘은 서로 다른 호출이고 한 호출의 두 interpreter가 아니다. 앞은 생성 API를, 뒤는 그 아래 builder를 검증한다. 경로는 fixture가 정하고 recipe는 경로를 지정하지 않는다.
  - table 경로 필드. `where`는 `{"chain": [[<connector>, <predicate>], [<connector>], ...]}`(명시적 연결자, 단독 `[<connector>]`는 DSL-14의 별도 연결자)와 `{"placed": <join as>}`(그 `as`로 묶은 join의 DSL-17 group)도 받는다. join은 `match`(열 쌍), `alias`, `where`를 받고(DSL-91~DSL-95), relation은 `many`와 `alias`를 받으며 `as`는 선택이다(DSL-80, DSL-81, DSL-83). `columns` 항목은 `{"expr", "as"}`일 수 있고, `add_columns`와 `remove_columns`는 DSL-72~DSL-75의 호출이며, `order` 항목은 `{"fn", "dir"}`일 수 있고(DSL-135), `limit`은 정수 또는 `limit` 객체이고, `aggregate`는 DSL-61~DSL-63의 종결 호출이고, `pick`은 결과 행에서 비교할 필드를 제한하며, `compile: true`는 getQuery로 쿼리를 읽는다(DSL-65). `set` 값은 `{"arith": {"operation", "amount"}}`일 수 있다(DSL-102). `model.creates`는 크기를 명시하는 batch 한도 case를 위해 `rows` 대신 `rows_sequence {column, from, count, values}`를 받는다.
  - `{"json": <plain JSON>}`은 table 경로 결과의 expect다. 행은 쿼리 순서의 객체이고 scalar는 그 값 자체다. `{"error": <code>, "message_suffix": <text>}`는 오류 message의 끝도 요구하며, code만으로 한 case의 거부를 구분할 수 없을 때 쓴다. 객체는 member를 기록된 순서로 비교한다.
  - `model.chain {connection, model, as, ...}`은 실행하지 않고 쿼리를 만들고, 뒤의 `model.query`나 `model.count`가 `from`으로 이어 간다(DSL-69). `utils.lock`, `utils.set_local`, `utils.local {connection, name, ...}`은 transaction 안에서 같은 이름의 공개 유틸리티를 호출한다. `transaction`의 빈 `steps`는 문장을 보내지 않는 transaction이다.
  - `utils.was_inserted {connection, table, sequence, expect}`는 연결의 유틸리티에서 `wasInserted(table, sequence)`를 호출하고(INT-52), `utils.backend_waiting_for_lock {connection, expect}`는 `backendWaitingForLock()`을 호출하며(INT-53), `utils.groups {connection, expect}`는 런타임이 가진 유틸리티 그룹을 이름 `aes`, `privileges`, `schema`, `stats`의 순서로 돌려준다(INT-61, INT-73, INT-134). recipe는 `utils`(`contracts/fixtures/utils/utils.json`)다.
  - `events.captured`의 `masks`는 `{<database>: [{"event", "bind", "value", "reason"}]}`이다. 그 위치의 bind는 `value`에 적힌 표식으로 비교하며, 표식은 `$AES`(AES 값의 임의 nonce), `$TS`(`updated_ts`에서 읽은 시각), `$NOW`(시계) 중 하나다. mask는 recipe가 고정할 수 없는 값만 가리고 vector가 고정한 값은 가리지 않으며, `reason`에 그 이유를 적는다.
  - `model.query`와 `model.count`의 `where`에 있는 array 값은 IN 목록(DSL-46; suite conformance-mysql, conformance-postgres, conformance-sqlite의 API unit)이며 client가 bind 한도에서 나눈다(PRT-76). `model.query`는 `page: true`를 받으며, 이때 `limit`과 `offset`으로 `GetsPage`를 호출하고 `{"rows": [...], "total": <정수>}`를 반환한다. `page`가 false인 `limit`은 statement의 공개 `Limit`이므로, 나뉜 목록에 건 limit은 `IR_INVALID`로 실패한다(PRT-76). 그 `relation`은 `many`를 받으며, true이면 부모마다 자식 각각에, false이면 부모마다 첫 자식에 한 행을 만든다.

  model op와 `transaction` op는 `connection`을 받는다. 이것은 `model.connect`가 묶은 connection이다. model op는 fixture set의 generated model 호출 하나를 가리키고, helper는 fixture의 generated model에서 그 model을 `model` 필드의 값으로 찾으므로 op는 model 코드를 싣지 않는다. 각 model op는 `connection`과 `model`을 받으며, `model`은 generator가 쓰는 model 이름이다(예: `CompositeAccount`).
  - `model.create {connection, model, values}`는 `values`(column 이름과 값의 object)로 만든 model set에 `Create`를 호출한다. `as`는 만들어진 model을 묶고, expect는 `{"error": <code>}` 또는 없음이다. API unit `client-model-terminal-write`.
  - `model.count {connection, model, where}`는 `where`의 같음 조건으로 `GetCount`를 호출한다. expect는 `{"value": {"int": <count>}}`다. API unit `client-model-terminal-read`.
  - `expect_unnamed`가 있는 `model.query {connection, model, where, order, columns, lock}`: PHP 클라이언트와 PHP extension은 문에 이름을 붙이지 않으므로(CFG-28), 이름 있는 문이 실패하는 step은 이 둘에서 `expect_unnamed`의 결과를, Go, Rust, TypeScript, Python에서 `expect`의 결과를 유지한다.
  - `model.query {connection, model, where, order, columns, lock}`는 `where`의 같음 조건으로 `Gets`를 호출하고, `order`가 있으면 그 column들의 오름차순으로 정렬하며, `columns`를 읽는다. `lock`이 있으면 `update`, `share`, `update_nowait`, `share_nowait` 중 하나이며, 각각 `ForUpdate`, `ForShare`, `ForUpdateNoWait`, `ForShareNoWait`의 행 잠금을 건다(Rust는 `Core::lock`). expect는 `{"rows": [[<value>, ...], ...]}`다. API unit `client-model-terminal-read`, `client-query-base`, `generated-model-query-chain`.
  - `transaction {connection, isolation, read_only, fail, steps}`는 이 목록의 op인 `steps`를 순서대로 `connection`의 `Db.transaction` callback에서 실행한다. 옵션은 `isolation`(`IsolationLevel`의 level 이름, 없으면 기본값), `read_only`(참이면 `ReadOnly`), `fail`이다. `fail`은 steps 뒤에 callback이 error를 돌려주게 해서 transaction을 rollback시킨다. 다른 transaction 안의 `transaction` step은 savepoint다(DSL-119). expect는 commit되면 `{"value": {"bool": true}}`, `fail`로 rollback되면 `{"value": {"bool": false}}`, 옵션 중첩 같은 이유로 step이 거부되면 `{"error": <code>}`다. API unit `client-db-transaction`.
  - `model.assign {model, column, value}`은 생성된 model `model`(bind fixture `slots`)의 새 row에 `column`의 public setter(Go `Set<Column>`, TypeScript와 PHP `set<Column>`, Python `set_<column>`, Rust `set_<column>`)로 값을 넣고, database 없이 그 row의 insert 문장, 즉 encode 단계를 만든다. database는 돌지 않으며, `markdown.send`의 markdown listener가 받는 첫 message가 그 문장이다. `value`는 recipe wrapper이고, expect는 `{"message": <json>}`(문장의 parameter 하나의 JSON)이며, setter나 encode가 message를 보내기 전에 돌려주는 error는 `{"error": <code>}`다(public API: `client-model-terminal-write`, INT-34부터 INT-39까지, 그리고 여섯 runtime이 모두 가진 `generated-model-field-access`). null을 받지 않는 typed setter는 nil wrapper를 호출 전에 거부하므로, not-null slot에 대입한 nil은 그것을 담는 runtime의 native 시험이다(tests/bind/messages-python-null.json, FCV-2).

  Rust의 mutation은 cancellation flag, phase publisher, commit permit도 받는다. Rust helper는 설정되지 않은 flag, 아무것도 남기지 않는 publisher, 허용하는 permit을 넘긴다. 각 runtime의 helper는 호출이 돌려준 값을 비교하기 전에 recipe wrapper로 바꾼다.

  - `schema.install {schema}` 또는 `{connection}`, `schema.register {schema}`, `schema.connect {schema}`는 case database에서 schema 값의 `utils().schema().install`, `utils().schema().register`와 connect를 호출한다(Go `Install`, `Register`, `ConnectSchema`; API unit `client-schema-utils-install`, `client-schema-utils-register`, `client-db-connectschema`). `schema.add_tables_and_columns {schema}`는 `addTablesAndColumns`를 호출한다(`client-schema-utils-add-tables-and-columns`). expect는 `{"value": {"array": [<name>, ...]}}`로, 만들어진 table과 그다음 추가된 `table.column` 이름이다. `schema` 인자는 `{"documents": [<file>, ...], "external": [<file>, ...], "manifest_replace": {"from": <text>, "to": <text>}}`이다. file 이름은 recipe에 상대적이고, `external`은 그 set이 쓰는 다른 set의 document 이름이며, `manifest_replace`는 만들어진 schema의 manifest text를 바꾸되 hash는 그대로 두어 text가 그 hash와 맞지 않게 한다. `schema.add_tables_and_columns`의 `message_contains`는 거부 message에 들어 있는 text이다. 세 op의 expect는 오류 없이 돌아온 호출에는 `{"value": {"bool": true}}`, 아니면 `{"error": <code>}`이다. `{connection}` 형태는 그 connection에 recipe의 fixture를 설치하며(client-schema-utils-install, INT-55), expect는 없다. `"install": false`인 case는 step 전에 helper에서 fixture를 받지 않으므로(FCV-9) step이 이 op로 설치하고, statement_events case는 subscribe 전에 자기 connection에서 설치한다. SQLite의 row-lock table은 열린 database handle마다 한 번 만들어지기 때문이다.
  - `statements.count {steps}`는 중첩 step을 각자의 expect로 실행하고, 그동안 database가 보내는 statement를 집계한다(statement event API unit `client-statement-event`: Go `Subscribe`, PHP `subscribe`, TypeScript와 Python `subscribe`, Rust connection의 statement subscription). expect는 `{"count": <int>}`이고 count는 정수로 비교한다.
  - `transaction {connection?, steps, fail?}`는 중첩 step을 한 transaction 안에서 실행한다(`client-db-transaction`: Go `Transaction`과 각 runtime의 case connection transaction). 실패한 중첩 step은 transaction을 실패시키고, 각 중첩 step은 자기 database별 expect를 유지한다. expect는 중첩 step이 통과하고 commit되면 `{"value": {"bool": true}}`, transaction이 실패하면 `{"error": <code>}`이다. `connection`은 `model.connect`가 묶는 connection이며 기본값은 case connection이다(DB.Transaction, INT-72). `fail: true`이면 callback이 중첩 step 뒤에 자기 error를 반환하고, expect는 `{"error": "CALLBACK"}`이다. `CALLBACK`은 각 runtime의 helper가 callback 자체의 error에 반환하는 sentinel이며, orm error code가 아니다.
  - `query.search {connection, model, columns, text}`는 `model` 모델(모델 연산이 부르는 이름)의 `columns` 컬럼에서 텍스트 `text`를 런타임의 공개 쿼리 API로 검색한다. 헬퍼는 공개 bind-check 변환 fulltext_boolean(DIA-6; Go `plan.FulltextBoolean`, TypeScript `fulltextBoolean`, PHP `Transform::fulltextBoolean`, Python `fulltext_boolean`, Rust `value::fulltext_boolean`; API unit client-engine, client-value-function, client-query-ir)으로 텍스트를 정규화하고, PRT-75의 IR로 술어를 만든 뒤 `connection`의 dialect에서 client-engine의 공개 Engine.Compile로 컴파일한다. MySQL과 PostgreSQL에서의 expect는 `{"sql": <text>, "params": [<value>, ...]}`다. text는 컴파일러가 내보내는 placeholder 그대로의 컴파일 문장이고, params는 변환 뒤의 bind 값이라 DIA-6 정규화는 params에 드러나며 text는 바뀌지 않는다. 용어가 없는 텍스트는 case connection에서 실행되고 실제 bind 검사가 거부하므로 `{"error": "IR_INVALID"}`다(DIA-6). SQLite에서는 술어가 컴파일 단계에서 거부되므로 `{"error": "OPERATOR_NOT_ALLOWED"}`다(DIA-187). 각 expect는 FCV-10의 키를 가진다.
  - `query.search_chain {connection, model, mode, text}`는 `connection`에서 공개 getQuery로 mode의 생성된 fulltext method가 만드는 statement를 읽는다. `fulltext_boolean`은 `fulltextBooleanNameWithDescription`을, `fulltext`는 `fulltextNameWithDescription`을 각 런타임의 표기로 호출한다(DSL-32, DSL-33). expect는 MySQL과 PostgreSQL에서 `{"sql": <text>, "params": [<value>, ...]}`, SQLite에서 `{"error": "OPERATOR_NOT_ALLOWED"}`다(DIA-187).

  기능을 recipe로 옮기는 row는 필요한 op를 한 commit에서 이 목록, schema, 모든 runtime의 helper에 더한다.

- **FCV-5** `scripts/features/coverage.test.mts`의 테스트는 필요한 차원을 하나씩 바꾸고 만들어 낸 JSON 성공, 누락된 소유자, 사용자, 테스트 경로, client, 데이터베이스, 사례, 반복 실행, 상태 비교 또는 선언되지 않은 결과에서 실패를 요구한다. 주장한 모든 동작에 현재 실행 증거가 생길 때까지 `make feature-check`는 실패한다. 검사기 자체 테스트가 성공해도 client 동작의 완료를 주장하지 않는다.
- **FCV-6** `make feature-coverage`는 `make orm-check`처럼 모든 기능의 coverage를 한 번 실행하고, `make feature-check`는 그것을 모든 검증 명령과 함께 실행한다. `.runtime/servers/env`의 test 환경 아래에서 `node scripts/features/coverage.mts --feature <id>`는 그 기능의 coverage spec만 실행한다: 소유자와 사용자를 데이터베이스마다 두 번. `<id>`는 `scripts/features/check.mts --feature`처럼 `contracts/features.json`의 기능 `id`다. 없는 id는 아무것도 실행하지 않는 대신 고를 수 있는 id 목록과 함께 실패한다. 예를 들어 `node scripts/features/coverage.mts --feature dsn_connection`은 DSN 연결 기능만 실행한다. DSN 기능은 세 데이터베이스에서 다섯 client의 읽기 전용 소유 사례와 Go client와 Rust client 부분의 생성 모델 사용 사례를 실행한다. 선택한 URI는 `ORM_FEATURE_DSN`으로 전달하고 검사기는 두 실행의 전후 데이터베이스 상태를 읽는다.


## Database 기능의 recipe화 {#database-recipes}

- **FCV-8** database 기능은 자기 commit에서 recipe가 된다. 그 commit은 recipe 파일을 `fixture`(`.dbs` 문서를 적는 `dbspec-set.json`), `seed`, `cases`와 함께 추가하고, 그 step들이 쓰는 op 각각을 FCV-4 목록, `scripts/features/schema/recipe.schema.json`, 여섯 runtime 각각의 recipe helper에 추가하며, FCV-3의 suite unit 세 개를 `config/parity.json`에 추가하여 여섯 runtime 모두 bind하고, `contracts/features.json`의 그 기능 소유자를 recipe로 향하게 하며, 그 기능의 손으로 쓴 coverage 테스트를 지워 어떤 동작도 두 번 테스트되지 않게 한다. recipe를 실행하는 make target은 `contracts/check-inputs.json`에 scope `owner`, runtime과 `databases`를 `needs`로, `inputs`에는 recipe에 맞는 경로를 적는다. `catalog-connection-check/<runtime>`이 그렇다. 선례는 `catalog_connection`(`contracts/fixtures/catalog_connection/catalog_connection.json`)이다.
- **FCV-9** recipe는 database를 feature 변수가 아니라 자기 run에서 받는다. target은 `databases`를 `needs`에 선언하므로 `scripts/check/run.mts`가 그 run의 database를 만들고, 그 run의 environment 파일을 `TEST_ENV`로 넘긴다(`make run-databases TARGETS=...`). recipe helper는 그 environment에서 서버 DSN `ORM_TEST_MYSQL_DSN`과 `ORM_TEST_POSTGRES_DSN`을 읽고, 관리 연결로만 쓴다. 사례마다 helper는 자기 runtime의 case-database factory(Go `testdb.New`, TypeScript `case-database.mjs`, Python `case_database`, PHP `with_case_database`, Rust `CaseDatabase::create`와 `packages/rust/case-database`)로 서버에 database 하나를 만들거나(SQLite는 자기 파일 하나), fixture를 설치하고, 사례가 끝나면 그것을 지운다. recipe는 `ORM_FEATURE_DATABASE`나 `ORM_FEATURE_DSN`을 절대 읽지 않는다. 이 둘은 FCV-8이 지우는 손으로 쓴 테스트의 bench database를 지정한다.
- **FCV-10** database 기능은 `mysql`, `postgres`, `sqlite` 세 database 모두에서 실행된다. fixture가 있는 recipe는 database마다 suite unit 하나(FCV-3)를 가지며, 모든 expect는 정확히 그 세 key를 가진다(FCV-4). 그래서 사례가 실패하도록 기대된 database는 `{"error": <code>}`로 그렇다고 적고, 빠지지 않는다. recipe 형식에는 제외 key가 없다. `scripts/features/schema/recipe.schema.json`이 recipe의 key를 닫으며, 제외를 선언한 recipe는 없다. 제외는 선언된 이유가 있는 schema 변경일 것이며, 그것이 생기기 전까지 database 간 차이는 database마다의 결과로 적는다.
- **FCV-11** DSN이 없으면 사례는 실패하고 변수 이름을 밝히며, 건너뛰지 않는다. FCV-9의 각 factory는 `<VARIABLE> is required; database tests never skip`으로 실패한다. Go `testdb.New`, TypeScript `case-database.mjs`, Rust `packages/rust/case-database`, PHP `case_database.php`는 지금 그렇게 실패한다. Python `case_database`도 변수 이름을 밝히지만, 그 메시지(`statement_fault.py`의 `required_dsn`이 내는 `is required for the <dialect> statement fault cases`)는 FCV-11 문구가 아니므로 맞출 결함이다. 변수 이름을 밝히지 않거나 skip하는 factory는 FCV-11 결함이며 받아들일 skip이 아니다. make target 밖에서 recipe를 실행할 때 `ORM_TEST_MYSQL_DSN`이나 `ORM_TEST_POSTGRES_DSN`이 없어도 같은 실패가 난다.
- **FCV-12** feature 검사기는 각 runtime의 결과를 recipe의 사례 결과에서 사례 id로 읽는다. recipe의 owner는 자기 명령에 그것을 적는다: `{"runner", "test", "recipe", "cases"}`이고, Go와 PHP는 test method를 `symbol`로 적는다. `cases`는 그 database에서의 recipe 목록이며 `only`가 있는 사례는 다른 database에서 빠진다. `make feature-unit-check`의 `scripts/features/recipes.test.mts`가 다른 목록을 거부하고, feature의 모든 owner가 recipe owner이면 `coverage.cases`도 recipe의 목록이다. 검사기는 그 runtime의 test runner로 entry를 한 번 실행하고 `ORM_RECIPE_RESULTS`에 파일 하나를 지정한다. FCV-15의 각 recipe runner는 사례가 통과하면 그 파일에 `CASE <id> [<database>] PASS`를, database 없는 recipe면 `CASE <id> PASS`를 덧붙이고, 변수가 없으면 아무것도 쓰지 않는다. 결과는 entry의 종료 상태와 그 줄들이며, 여섯 runtime 모두 reader 하나로 읽는다. 줄이 없는 사례는 통과하지 않은 것이다. recipe owner는 `dsn_env`를 적지 않고, 사례마다 자기 database를 가지므로(FCV-9) 검사기는 그 database 상태를 읽지 않는다.
- **FCV-13** recipe의 seed 데이터는 recipe 파일에 속하며, run마다가 아니라 사례마다 설치되고, 공유 database에 담지 않는다. 사례마다 helper는 fixture set을 사례 database에 설치한 뒤, 파일 수준의 `seed`와 그다음 사례 자신의 `seed`를 recipe의 순서대로 `describe_table`이 읽는 metadata를 거쳐 `insert_row`로 넣는다(Go `insertSeed`, 그리고 TypeScript, Python, PHP, Rust도 같은 순서). seed 행 하나가 실패하면 사례가 실패한다.
- **FCV-14** runtime은 database 동작의 네이티브 테스트를, FCV-2가 그 동작을 runtime 고유로 적은 곳에서만 유지하고, 그 테스트 파일이 그 이유를 적는다. 다른 runtime이 가진 database 동작은 recipe 사례이며, 그 네이티브 테스트는 recipe를 더하는 commit에서 지운다. 네이티브 테스트가 유효한 이유를 가졌는지는 검토의 판단이며 검사가 아니다.
- **FCV-15** 각 runtime의 recipe runner는 하나다. Go `packages/go/internal/recipe`, TypeScript `packages/ts/tests/recipe.mjs`, Python `packages/python/tests/recipe.py`, PHP `packages/php/tests/Recipe.php`(PHP extension도 이것을 실행), Rust `packages/rust/tests/src/recipe.rs`이며, Rust의 trial binary는 runner가 이름을 알 수 없는 fixture의 생성 model을 위해 그 model의 dispatcher를 더한다. recipe suite unit의 binding은 그 파일을 자기 runtime의 runner에 넘기고 op를 구현하지 않는다. runner는 자기 목록의 전체 op 이름과 맞추어 dispatch하고, 목록에 없는 op는 `OP_UNKNOWN`으로 거부한다. recipe schema의 모든 op는 어떤 recipe의 step이므로, op가 없는 runtime은 그 recipe에서 실패한다. `make recipe-runners-check`가 이를 강제한다.

## Owner 검사 {#owner-checks}

- **FCV-7** `make owner-check`는 바뀐 file을 소유한 검사를 실행한다. 기본은 `HEAD`와 다른 file과 추적하지 않는 file이고, `PATHS="<paths>"`로 file을 줄 수 있다. `contracts/features.json`의 모든 검증 명령은 `inputs`를 선언하고, 모든 coverage 단위인 owner client(`owner/<language>`)와 사용 부분(`dependent/<id>`)은 `tests`와 선택적 `inputs`를 선언한다. `scripts/features/owners.mts`는 입력에 바뀐 file이 있거나 선언한 fixture data(JSON이나 dbspec file)가 그 file을 적는 명령과 단위를 고른다. 예를 들어 `contracts/fixtures/schema_definition.json`은 `contracts/fixtures/audit.dbs`를, `contracts/symbols/rust.json`은 Rust source를 적는다. 적힌 file이 다시 적는 file은 따라가지 않는다. 고른 명령과 단위마다 그것을 고른 path를 출력하고, 아무것도 고르지 않은 바뀐 path도 출력한다. coverage helper `packages/php/tests/coverage_cases.php`처럼 여러 기능이 쓰는 helper는 `helpers`에 자기 check와 함께 선언하고 어떤 입력에도 넣지 않는다. helper의 변경은 그 check(`scripts/features/check.mts --run --helper <id>`)만 실행하고, helper를 쓰는 모든 기능의 실행은 `make orm-check`가 맡는다. `contracts/features.json`이 바뀌면 `HEAD`와 항목이 다른 기능의 명령과 단위, 그리고 항목이 다른 helper를 고른다. 그 항목 밖의 변경은 `make orm-check`가 모든 기능을 실행하므로 아무것도 고르지 않는다. 고른 명령은 `scripts/features/check.mts --run --feature <id> --command <id>`로, 고른 단위는 `scripts/features/coverage.mts --feature <id> --part <part>`로 실행한다. 각각은 RUN, PASS나 FAIL과 경과 시간을 가진 단계 하나이고, 기한은 단계 안의 case마다 있다. 선언 검사는 입력이 없는 검증 명령, 추적되는 file을 맞추지 않는 입력, 입력으로 쓰인 helper를 실패시킨다. 또 `contracts/check-inputs.json`이 scope `owner`로 선언하고 입력이 바뀐 path를 맞추는 make target을 실행한다. `client-db-check`나 `feature-check`처럼 scope `suite`인 target은 `make orm-check`에서만 실행하고, scope가 없는 target이 있으면 선택이 실패한다. `node scripts/features/owners.mts --list [<paths>]`는 실행하지 않고 고른 것만 출력한다. `scripts/features/owners.test.mts`는 `make feature-unit-check`에서 실행한다.

## Catalog 연결 제외 항목 {#catalog-connection-exclusions}
recipe `contracts/fixtures/catalog_connection/catalog_connection.json`은 여섯 runtime이 공유하는 catalog 동작을 다룬다(SCH-6a, INT-117). 네이티브 테스트는 FCV-2가 한 runtime에 남기는 동작이거나 recipe로 표현할 수 없는 동작일 때만 남는다. 남은 동작은 이유와 함께 아래에 적는다.
- **표면과 패키징(FCV-2).** PHP와 PHP extension의 `Catalog`, `Model` 클래스와 메서드 표면, extension 로딩, build crate의 Rust 라이브러리 표면, commit·rollback·metadata·cleanup 실패, descriptor 변경, trigger 가시성을 만드는 fault 주입 더블. recipe는 실패를 주입할 수 없다.
- **recipe에서 제외.** TypeScript의 `precisionCase`는 recipe case `declared_temporal_cells`가 다루므로 네이티브 테스트가 없다.
- **PHP cause 형태(INT-109).** recipe case `descriptor_column_name`은 잘못된 열 이름을 가진 descriptor의 코드와 메시지를 모든 runtime에서 확인한다. 그 실패의 `previous` 예외는 PHP와 PHP 확장만 가진 형태이므로 `CatalogPageValidationTest`와 `CatalogConnectionSurfaceTest`가 확인한다. 라이브러리 `Catalog`가 PHP 클래스인지도 같은 surface이며 `CatalogPageValidationTest`가 확인한다.
- **codec.** 어떤 recipe case도 빈 `ordered_json` 텍스트를 decode하지 않으므로, codec recipe case가 이를 검사할 때까지 네이티브 검사를 남긴다.
