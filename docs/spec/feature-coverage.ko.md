# 기능 coverage 검증

- **FCV-1** `contracts/features.json`의 각 기능은 `coverage.kind`, 중복되지 않는 `coverage.cases`, `coverage.owners`, `coverage.dependents`를 선언한다. 데이터베이스를 읽거나 바꾸는 동작에는 `database`, 그 외에는 `independent`를 쓴다. 상태가 `pass` 또는 `partial`인 모든 client는 `packages/<runtime>` 아래에 `part`, `tests`, 필요한 각 데이터베이스(`mysql`, `postgres`, `sqlite`) 또는 `none` 한 칸의 언어별 테스트 명령을 선언한다. 각 사용 부분은 자기 디렉터리에 별도 사례와 테스트를 선언한다. 선언이 빠지거나 선언한 부분 밖의 경로이면 `make feature-check`가 실패한다.

- **FCV-2** 모든 orm 테스트는 하나의 spec에 있다. 둘 이상의 runtime이 가진 동작은 모든 runtime이 실행하는 recipe의 사례로 테스트한다. runtime은 다른 runtime에 없는 동작, 예를 들어 자기 binding과 packaging 표면, compile-fail fixture, PHP extension 적재에 대해서만, 또는 recipe 값이 담을 수 없는 입력, 예를 들어 JSON recipe가 쓸 수 없는 Unicode scalar 값의 열이 아닌 text에 대해서만 실제 테스트를 유지한다; 한 동작의 그런 실제 테스트는 하나의 parity unit이며, 그 입력을 담을 수 있는 각 runtime에 bind한다. P32의 harness 테스트는 parity unit이 아니다. recipe는 `$schema`가 recipe에서의 상대 경로로 `scripts/features/schema/recipe.schema.json`을 가리키는 parity suite(`config/parity.json`의 `suites`)의 JSON 파일이며, recipe는 이것으로 suite의 다른 파일과 구별되고, 그 schema가 key를 닫는다: `requirements`, `fixture`(`dbspec-set.json` document set, 데이터베이스가 없는 recipe에는 없다), `seed`, `cases`, 그리고 `schema`(`ir.validate` step이 검사하는 `.dbs` manifest, FCV-4)이며, 각 사례는 중복되지 않는 `id`, 자기 `requirements`, 선택적인 `seed`, 자기 `steps`를 가진다. `scripts/features/recipes.test.mts`는 `scripts/json/schema.mts`의 `checkJson`으로 ajv 8.20.0을 써서 모든 recipe를 schema로 검증하며, schema가 거부하는 recipe는 `make feature-unit-check`에서 실행되는 그 테스트를 실패시킨다. 모든 기능이 recipe가 되기 전까지 `contracts/features.json`의 검증 명령과 coverage 소유자는 FCV-1, FCV-5, FCV-6이 적은 대로 실행된다.
  - `schema-set-edited-generated-code`(DBS-120)는 FCV-2의 runtime 전용 항목으로 모든 runtime의 native에 남는다. 수정된 manifest의 generated code는 PHP에서는 파일을 load할 때, TypeScript와 Python에서는 model을 등록할 때, Go와 Rust에서는 entity의 요청을 plan할 때 실패하므로 여섯 runtime에 공통인 op이 없다.
  - `transaction-failure-rollback`와 `transaction-failure-savepoint-end`(INT-72, DIA-181, PLN-17)는 모든 runtime에서 FCV-2 driver 항목으로 native에 남는다: 그 결과는 열린 session에서 `ROLLBACK`, `RELEASE_LOCK`, local reset 또는 savepoint 종료 단계가 실패하거나 callback이 panic해야 나오고, 실제 데이터베이스에서 public 호출로는 그렇게 만들 수 없으므로 각 runtime이 자기 driver seam의 fake를 둔다. rollback fault, 끝난 session, 일찍 풀린 lock은 recipe `transactions`와 `utils`의 case이다.
  - `sqlite-row-lock-restoration`(INT-49)은 모든 runtime의 native에 남는다. 그 결과는 NOWAIT 설정이나 복원 중 `PRAGMA busy_timeout`이 실패해야 나오는데, 실제 database에서 공개 호출로는 일으킬 수 없다. 그래서 각 runtime이 자기 driver 쪽의 fake를 두며 recipe 값으로 적을 수 없다.
  - `php-extension-schema-utils-native`(INT-156a)는 FCV-2의 runtime 전용 항목으로 native에 남는다. PHP extension에만 있는 internal `SchemaUtils` class의 reflection을 읽기 때문이다.
  - `generator-takes-the-documents-only-from-the-set-file`(ORES-21, DBS-5, DBS-98)은 모든 runtime에서 native로 남는다. FCV-2의 runtime별 generator 진입점이며, generator에는 여섯 runtime이 공유하는 진입점이 없기 때문이다. Go `generator.Generate(Options)`는 runtime model을 받고, Rust `Builder::set(path).try_generate()`는 set file을 받으며, PHP `OrmGen::main`과 `OrmGen::run`, TypeScript `generateTypeScript(Manifest, ...)`, Python `generate_models(RuntimeModel, ...)`는 model 또는 명령줄을 받는다. 각 runtime은 이 규칙의 자기 test를 유지한다. Go `TestGoGenerationCommandRefusesTheRemovedDocumentFlags`, PHP `OrmGenCliTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, php-extension `OrmGenCliTestExtensionTest::testGenTakesTheDocumentsOnlyFromTheSetFile`, TypeScript `generate`, Python `test_the_removed_document_flags_are_usage_errors`, Rust `the_builder_takes_the_documents_only_from_the_set_file`.
  - `generator-check-reports-an-extra-generated-file-go`와 `generator-check-reports-an-extra-generated-file-php`(DBS-182, DBS-183)는 native로 남으며, FCV-2의 runtime 고유 생성기 진입점이다. `extra:` 줄은 Go와 PHP 파일의 생성 표지를 읽으며 다른 runtime은 이를 쓰지 않고, scan한 호출에서 실패하는 Go 검사는 이미 있는 출력을 그대로 둔다. set 오류, 파일 진단, `differs:`와 `missing:` 줄은 `generator` recipe의 case다.
  - `generated-field-types-follow-runtime-model`, `generated-field-types-follow-runtime-model-dbs-112`, `generated-decimal-field-uses-exact-text`, `generator-time-setter-takes-the-text-form`, `generated-typed-getter-public-column-api`와 `generated-nonnull-styled-setter-rejects-sql-null`은 모든 runtime에서 native로 남으며, FCV-2의 compile fixture다. 생성된 멤버와 그 타입은 언어의 source이고 그 언어의 compiler가 증명하므로 recipe 값으로 적을 수 없다(T334-3-5-1).
  - `dbspec-set-bench`(SCH-1)는 `generator-takes-the-documents-only-from-the-set-file`과 같은 이유로 모든 runtime에서 native로 남는다. 이 단위는 set 파일과 그 언어의 생성 출력으로 bench set을 읽고, `generator.generate`는 schema를 받는다.
  - `generated-external-model-reads-its-table`(DBS-110, DBS-173)는 모든 runtime에서 native로 남는다. 외부 텍스트를 담는 생성 schema 값은 그 언어의 소스이므로, 사용하는 외부 테이블의 모델이 자기 테이블을 읽는다는 것은 그 언어의 생성 모듈을 불러오거나 컴파일해 연결해야만 드러난다.
  - `generated-manifest-text-and-hash-match`(DBS-104, DBS-111, DBS-120)는 모든 runtime에서 native로 남는다. 언어의 생성된 module을 불러오고 manifest와 어긋나는 module을 거부하기 때문이다. `generator` recipe의 `generated-code-carries-the-manifest-hash` 사례가 모든 runtime에서 DBS-103의 hash를 검사한다.
  - `request-hook-params-are-read-only`(INT-78)는 모든 runtime에서 native로 남는다. 각 언어는 bind된 값 쓰기를 자기 형식, 곧 frozen array, tuple, 복사본, compiler 오류로 거부하며, `hook.install`의 동작은 매개변수를 읽고 더할 뿐이므로 어떤 recipe step도 그 쓰기를 시도할 수 없다.
  - `dynamic-vs-scanned-model-chain-dispatch`(PLN-40)는 모든 runtime에서 native로 남는다. recipe step은 scan이 쓴 이름(case `scanned-chain-methods-are-generated`)과 호출 하나의 결과만 보므로, 생성된 코드를 그것을 호출한 소비자와 함께 compile하거나, 정확한 signature를 읽거나, PHP나 Python 호출이 선언된 메서드를 탔는지 `__call`과 `__getattr__`을 탔는지 구분할 수 없다. 이 구분은 reflection만 보여 준다.
  - `native-public-package-entry`(INT-138)는 모든 runtime에서 native로 남는다. recipe step은 client를 자기 경로로 이미 import한 runner 안에서 돌므로, repository 밖 소비자가 native 형식으로 진입점을 찾는다는 사실을 어떤 step도 나타낼 수 없다.
  - `parameter-slot-validation-vectors`(PRT-67, DIA-31)는 모든 runtime에서 native로 남는다. 그 case는 date 객체 같은 runtime의 native host 값으로 JSON recipe 값이 쓸 수 없고, typed API가 compile 때 거부하는 값으로 recipe op이 넘길 수 없다. recipe가 쓸 수 있는 값은 모두 `tests/bind/messages.json`이 맡는다.
  - 생성 메서드를 호출하는 conformance 본문(`terminal_by`, `terminal_reuse`, `relation_empty`, `aes_values`, `hex_malformed`, `empty_reads`, `now_defaults`, `delete_recursive`, `affected_counts`)은 모든 runtime에서 native로 남는다. 생성 메서드는 언어의 source이고 recipe step은 일반 builder를 호출하기 때문이다. `conformance-generated-methods-check`는 recipe `conformance_verification`의 fixture와 seed에서 이 본문을 실행하고 출력을 같은 이름의 case expect와 비교하므로 두 경로가 어긋날 수 없다.
  - 고정 시계 본문 `clock_truncate_write`와 `clock_compare_six_digits`는 모든 runtime에서 native로 남는다. FixClock이 시험 진입점이기 때문이다(PRT-53). `conformance-fixed-clock-check`는 이 본문을 `tests/conformance/check/fixed_clock.json`과 비교하며, 이 파일은 client가 쓰는 곳의 정확한 시계를 적는다.
  - `static-model-chain-generation`(INT-27), `dynamic-model-chain-resolution`(INT-28), `dynamic-vs-scanned-model-chain-dispatch`(PLN-40), `dynamic-model-new-output-name-rejects-stored-column`(DSL-160)은 native로 남는다. 각각 정적 또는 동적 runtime 쪽 동작이며 반대쪽에는 그 호출이 없다. `generator-orders-sets-by-imports`(DSL-157)는 Go만의 것이다.
  - `conformance-errors-refusal`(DSL-10, DSL-19, DSL-47, DSL-67, DSL-96, DSL-98, DSL-123, PRT-14)는 거부를 버리는 사용에 대해 FCV-2 compile fixture로 Go, TypeScript, Rust에서 native로 남는다. Go `TestRefusalIsATypedError`, TypeScript `tsc accepts each chain of the errors vector as a promise and refuses it as rows`, Rust compiler fixture `refusal-*`이다. 실제로 도는 것은 recipe `conformance_verification`의 case `errors`이다.
  - `dsl-50-operator-value-shapes`와 `chain-null-on-a-non-null-column`(DSL-49, DSL-50)은 컴파일러가 거부하는 사용에 대해 Go, TypeScript, Rust에서 FCV-2의 compile-fail fixture로 native로 남는다. Go `TestChainArgumentTypes`, TypeScript `chain argument types`, Rust compiler fixture `dsl49-nonnull-null-e0277`과 `dsl50-ordering-list-e0277`이다. 실행되는 동작은 recipe `dsl`과 `dsl-dynamic`에 있다.
  - `statement-runner-non-text-statement`와 `statement-runner-frame-after-its-transaction-ended`(INT-150a, INT-150b)는 compiler가 거부하는 사용이므로 FCV-2에 따라 native로 남는다. 타입이 있는 Go와 Rust의 `run`은 텍스트가 아닌 statement를 받지 않고, Rust frame은 그것을 빌린 callback보다 오래 살 수 없다. 실행되는 동작은 recipe `statement_runner`에 있다.
  - `php-extension-failed-statement-closes-cursor`(CFG-6a)는 PHP extension에서 FCV-2 driver 항목으로 native로 남는다: 실패한 문장 뒤의 닫힌 cursor와 다시 쓰는 연결은 대역 PDO에서 세며, 이를 알리는 공개 호출이 없다.
  - `rust-postgres-bind-parse-cause`(PRT-79a)는 Rust에서, `php-extension-pgsql-adapter-statement-sqlstate`(PRT-79b)는 PHP extension에서 FCV-2 driver 항목으로 native로 남는다: 앞의 것은 비공개 bind 단계를 호출하고, 뒤의 것은 대역 adapter를 읽는다. `sqlite-locked-is-driver`(PLN-24)는 FCV-2 driver 항목으로 native로 남는다: SQLITE_LOCKED에는 recipe 연결이 잡지 않는 shared-cache lock이 필요하다.
  - `go-database-value-scalars`(INT-98a)는 Go에서 한 언어의 FCV-2 표면으로 native로 남는다: 공개 호출이 이 값으로 닿지 않는 비공개 decode 단계를 호출한다.
  - `statement-runner-python-active-frame`(INT-161)은 Python에서 FCV-2의 한 언어 표면으로 native로 남는다. `active_frame()`은 Python에서만 public이고, 다른 런타임에는 recipe op가 이름 붙일 호출이 없다.
  - `transaction-concurrent-use-and-flow-isolation`, `transaction-execution-flow-context`, `transaction-flow-overlap-rejected`, `handle-disposal-abort-or-unwind-rolls-back`, `handle-disposal-abandoned-query-cancels-and-releases`(PLN-18, DSL-121, DSL-122, INT-47, INT-67, CFG-9)는 모든 런타임에서 FCV-2의 언어 형태로 native로 남는다. 주제가 각 런타임의 flow나 disposal 형태(goroutine, fiber, thread, task; drop된 handle, 취소된 context, signal, close)이고, recipe의 step은 한 flow에서 실행되어 그중 어느 것도 적지 못한다. `utils-backend-waiting-for-lock`(INT-53)도 두 번째 flow이므로 native로 남는다. 기다리는 backend는 첫 flow가 쥔 행에서 막힌 문장을 필요로 하고, 그동안 첫 flow가 보고를 읽는다. recipe `utils`는 waiter가 없는 사례를 가진다.
  - `collection-parent-expansion-preserves-bare-dollar`(DSL-153)는 모든 runtime에서 FCV-2 driver 항목으로 native로 남는다: parent slot의 placeholder 번호 매기기는 generator가 쓰지 않는 statement를 받으므로 어떤 public op도 bare `$`를 줄 수 없다.
  - `plan-cache-in-list-shapes-share-ten-bucketed-keys`와 `page-cache-root-limit-values`(CPX-4, PRT-78)는 FCV-2의 비공개 상태 항목으로 모든 runtime에서 native로 남는다. plan cache가 드는 항목 수, 곧 값 1개에서 300개까지의 IN 목록에 최대 10개, 300 page에 1개는 연결 안의 수이며 어떤 공개 호출도 읽지 않는다. Go, PHP, PHP extension, Python은 항목 수를 읽고, TypeScript와 Rust는 PRT-78의 key인 서로 다른 shape key의 수를 읽는다. 그 shape의 공개 면은 case `core_in_list_padding`과 `page_statement_does_not_hold_its_values`가 맡는다.
  - `collection-composite-key-encoding`(PRT-35)는 FCV-2 driver 항목으로 모든 runtime에서 native로 남습니다. composite key의 encoded text와 구성 요소의 타입은 driver 행에서 읽히며, 여섯 runtime이 모두 가진 public 호출 중 구성 요소를 받거나 그 text를 돌려주는 것은 없습니다.
  - `group-row-driver-cell-forms`(INT-68, INT-90)는 모든 runtime에서 FCV-2의, recipe 값이 담을 수 없는 입력으로 native로 남는다. text나 float인 count와 반복된 열은 driver cell의 형태이고, listener의 답은 count가 JSON number이고 행이 JSON object이므로(PRT-69) 그중 어느 것도 담지 못한다. `collection-recipe`(`tests/collection/collection.json`)는 나머지 group row 동작을 모두 `ir.answer`로 담으며 새 op가 필요 없다. PHP의 `toArray` 선언 형태와 PHP extension의 iterator는 다른 runtime에 없는 FCV-2 binding surface로, parity 단위 없이 native 시험으로 남는다.
  - `connection-cancelled-transaction-session-state`(CFG-39)는 Go에서 native로 남는다. handle의 context는 Go에만 있고, 다른 runtime에는 그것으로 callback 도중 transaction을 취소하는 호출이 없다.
  - `connection-driver-from-dsn`(CFG-40)는 Go에서 native로 남는다. `DriverFromDSN`은 연결을 열지 않고 데이터베이스를 돌려주는 Go 고유 함수이며, recipe 형식의 어떤 op도 그것을 호출하지 않는다.
  - `connection-catalog-session-through-a-pooler`(CFG-41)는 Python에서 native로 남는다. `ORM_TEST_PGBOUNCER_SINGLE_DSN`의 server connection 하나에 두 번째 client가 필요한데, 그 DSN은 고정 데이터베이스에 닿고 recipe 사례는 case 데이터베이스에서 실행되기 때문이다.
  - `connection-sqlite-several-process-writers`(CFG-42)는 Go, Python, Rust에서 native로 남는다. 그 runtime의 recipe op `transaction.writers`는 test process 하나의 연결에서 실행되고, recipe step이 거기서 process를 시작하지 않기 때문이다. TypeScript, PHP, PHP extension은 사례 `sqlite_writers_commit_every_row`에서 실행하며, 그 op는 거기서 process를 시작한다.
  - `connection-sqlite-crashed-holder`(CFG-43)는 Go에서 native로 남는다. recipe step은 transaction 안에서 process를 끝낼 수 없고, Go 시험은 자기 binary에 다시 들어가 그렇게 한다.
  - `pool-idle-server-end`(INT-92)는 native로 남는다. recipe 사례는 자기 데이터베이스의 모든 runtime에서 실행되고 runtime별로 좁힐 수 없는데, 이 동작은 Go, TypeScript, Python, Rust의 pool에 속하고, PHP와 PHP extension은 pool이 없어 pool option을 거부하며 끝난 session을 `CONNECTION_LOST`로 보고하기 때문이다(CFG-38).
  - `connection-first-statement-lost`(CFG-38)는 이 동작이 PHP와 PHP extension에만 있으므로 두 runtime에서 native로 남는다. 두 runtime은 pool 없이 connection 하나를 두므로 첫 statement가 종료된 session을 만난다. 다른 runtime의 pool은 server가 종료한 idle connection을 버리고(INT-92, `pool-idle-server-end`), 다음 statement는 새 connection에서 성공한다.
  - `dbspec-introspect-silent-failure`(DIA-133a)는 PHP와 PHP extension에서, `dbspec-introspect-extension-method`(DIA-133b)는 PHP extension에서 native로 남는다. PDO connection의 error mode와 library의 method를 대신하는 method는 거기에만 있다. introspection의 다른 모든 동작은 recipe dbspec_introspect의 case다.

- **FCV-3** fixture가 있는 recipe는 데이터베이스마다 suite unit 하나, 즉 recipe 파일 하나 위의 `<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`이고, 사례는 `$.cases[*].id`이다. 데이터베이스가 없는 recipe는 suite unit 하나이다. 각 runtime은 각 unit을 자기 ecosystem 테스트 pattern의 entry 하나에 묶는다: Go는 `*_test.go` 파일의 `TestRecipe<Recipe><Database>`, PHP는 `*Test.php` class의 `test<Database>`, Rust는 libtest-mimic trial `<recipe>_<database>`, Node는 `<recipe>-<database>.test.mjs`, Python은 `test_<recipe>_<database>.py`이다. entry는 recipe와 데이터베이스를 주어 자기 runtime의 공유 recipe helper를 호출한다. helper는 command line, 자기 출력 형식, main이 없는 테스트 module이다. helper는 사례마다 자기 runtime의 case-database factory로 데이터베이스를 만들고, 자기 runtime의 public dbspec API(set 문서의 parse와 manifest)로 실행 시점에 fixture set의 Schema를 만들어 `utils().schema().install`로 설치하고, live catalog를 데이터베이스에 연결하고(Rust `CatalogConnection::connect`, Go `ConnectCatalog`, PHP `Catalog::connect`, TypeScript `connectCatalog`, Python `connect_catalog`) 그 current namespace를 읽고, `describe_table`이 읽은 metadata와 그 catalog의 `insert_row`로 recipe의 seed 행과 이어서 사례의 seed 행을 넣고, step을 차례로 실행하고, catalog를 닫는다. 실패한 seed 행은 사례를 실패시킨다. 실패한 step은 사례를 실패시키며 recipe, 사례, step 순번, 데이터베이스를 적는다. 데이터베이스가 없는 recipe는 데이터베이스 부분을 `None`으로 하여 unit을 묶는다: `TestRecipe<Recipe>None`, `testNone`, `<recipe>_none`, `<recipe>-none.test.mjs`, `test_<recipe>_none.py`이다. `fixture`가 `dbspec-set.json`이 아니라 `"none"`인 recipe는 fixture가 있는 recipe와 같이 database마다 suite unit 하나(`<recipe>-mysql`, `<recipe>-postgres`, `<recipe>-sqlite`)를 가지며, 그 사례는 빈 사례 database에서 실행되고 fixture를 설치하지 않는다. helper는 그 field를 읽고, 첫 op로 빈 database를 추정하지 않는다. MySQL만 필요한 사례를 가진 recipe(CFG-10의 소켓 사례)는 suite unit `<recipe>-mysql` 하나만 가지며, 그 unit은 MySQL을 실행하는 각 runtime에 bind한다. 그 unit의 각 사례는 그 bind마다 실행되고, FCV-4의 `expect`는 세 database key를 가지므로 그 step은 `expect`가 없다.
- **FCV-4** step은 `{"op": <name>, ...}`이다. op는 여섯 runtime(Go, PHP, PHP extension, TypeScript, Python, Rust) 모두가 가진 public API 호출 하나를 가리키고, 나머지 field는 그 호출의 인자이며, helper는 op를 그 호출에만 대응시킨다. op에 대응하는 호출이 없는 runtime은 `OP_UNKNOWN <op>`로 사례를 실패시킨다. 각 runtime의 loader는 어떤 사례도 실행하기 전에, recipe schema의 key table(recipe가 `$schema`로 지정하는 schema 옆의 `scripts/features/schema/recipe-keys.json`)이 담지 않은 file, case, step key와 op, 그리고 `$schema`가 없는 recipe를 그 이름과 함께 거부한다. step은 `"as": <name>`으로 결과를 묶을 수 있고, 같은 사례의 뒤 field는 `{"ref": "<name>"}` 또는 `{"ref": "<name>.<path>"}`로 그것을 읽는다. 경로(path)는 그 segment들을 `.`으로 이은 것이며, 각 segment는 member 이름이거나, array이면 0부터 세는 10진 index이다. 결과를 비교하는 op의 step은 `expect`를 가지며, 그 key는 fixture가 있는 recipe에서 정확히 그 step을 실행하는 database(`mysql`, `postgres`, `sqlite`, 또는 step의, 없으면 그 사례의 `only`가 이름 붙인 것들; FCV-10)이고 데이터베이스가 없는 recipe에서 정확히 `none`이다. 각 값은 `{"value": <value>}`, `docs/spec/errors.yaml`의 code를 가진 `{"error": <code>}`(그것을 선언한 op에서는 error 메시지가 끝나는 `message_suffix`, driver가 감싼 메시지가 담는 `message_holds`, driver의 error를 원인으로 지니는 error의 `driver_cause: true`, callback의 error를 지니는 ROLLBACK error의 `keeps_callback: true`를 더한다), 또는 아래에서 op가 선언하는 field이다. SQL을 담는 field는 문자열이거나 정확히 key `mysql`, `postgres`, `sqlite`를 가진 object이며, 데이터베이스의 기본 precision을 가진 시간처럼 데이터베이스가 형식을 정하는 인자 값도 그렇다. step, expect, seed 행의 값은 recipe wrapper이다: 부호 있는 또는 부호 없는 64-bit 정수는 `{"int": "<decimal>"}`, `{"text": ...}`, INT-103과 DBS-121 형식의 `{"date": ...}`, `{"time": ...}`, `{"datetime": ...}`, INT-97 형식의 `{"decimal": ...}`, byte마다 소문자 hex 두 자리인 `{"bytes_hex": ...}`, `{"bool": true}` 또는 `{"bool": false}`, parameter type을 가진 SQL NULL인 `{"null": <type>}`, 그리고 styled codec이 읽고 쓰는 COD-16의 공통 값 모델의 값으로서 SQL NULL이 아닌 그 null인 `{"nil": true}`(COD-20), 10진 또는 지수 text의 binary64 수인 `{"float": "<number>"}`, `{"array": [<value>, ...]}`, 그리고 member를 key와 value의 쌍으로 가진 `{"object": [["<key>", <value>], ...]}`이다. `{"sequence": {"from": <integer>, "count": <integer>}}`(`count`는 1 이상)는 `from`, `from + 1`, ..., `from + count - 1`의 정수 목록이며 각 값은 `int` wrapper이다. helper는 이를 인자의 목록으로 펼치므로, IN 목록 같은 긴 목록을 전부 적지 않아도 된다. array 값의 항목이 `sequence`이면 그 정수들을 그 위치에 펼쳐 넣는다. 두 float는 그 text가 같은 binary64 값을 가리킬 때 같다. `ordered_json` 값은 수를 그 text로, object member를 순서대로 비교하고(COD-16), 다른 style은 member 순서를 정의하지 않으므로 object를 그 쌍의 집합으로 비교한다. encode op가 쓴 cell은 그 byte로 비교하고 text cell은 UTF-8 byte로 비교하므로, 그 expect는 `{"value": {"bytes_hex": ...}}`이다. op는 다음과 같다:
  - `model.connect {pool_size, dsn?}`는 fixture의 generated model을 case 데이터베이스에 연결하고(Rust `model::connect`, Go `Connect`, PHP `Orm::connect`, TypeScript와 Python은 generated `connect`), `dsn`이 있으면 그 DSN이 이름한 데이터베이스에 연결하며(`case?<query>`는 그 parameter를 붙인 case DSN이고 `case-pooler`는 `ORM_TEST_PGBOUNCER_DSN`을 거친 case 데이터베이스이며, `statement_timeout_ms`가 있으면 그 statement 한도로 연결한다), `as`로 그 연결을 묶는다. 그 step은 `expect`가 없다. `dsn`은 `"case"`, `"case-socket"` 또는 step의 DSN 문자열이다. `"case-socket"`은 case 데이터베이스의 MySQL DSN에 Unix 소켓 `ORM_TEST_MYSQL_SOCKET`을 `socket` 매개변수로 붙인 것이다(CFG-10, CFG-19). 이 DSN을 쓰는 recipe는 suite unit `<recipe>-mysql` 하나뿐이다(FCV-3). 소켓 연결은 found-rows 개수를 켜므로(CFG-10), 자기 연결이 쓴 행을 가리키는 revision 보호 `model.update`는 그 행을 찾는다.

SQLite에서는 술어가 컴파일 단계에서 거부되므로 `{"error": "OPERATOR_NOT_ALLOWED"}`다(DIA-187). 각 expect는 FCV-10의 키를 가진다.
  - `query.search_chain {connection, model, mode, text}`는 `connection`에서 공개 getQuery로 mode의 생성된 fulltext method가 만드는 statement를 읽는다. `fulltext_boolean`은 `fulltextBooleanNameWithDescription`을, `fulltext`는 `fulltextNameWithDescription`을 각 런타임의 표기로 호출한다(DSL-32, DSL-33). expect는 MySQL과 PostgreSQL에서 `{"sql": <text>, "params": [<value>, ...]}`, SQLite에서 `{"error": "OPERATOR_NOT_ALLOWED"}`다(DIA-187).

  기능을 recipe로 옮기는 row는 필요한 op를 한 commit에서 이 목록, schema, 모든 runtime의 helper에 더한다.

- **FCV-5** `scripts/features/coverage.test.mts`의 테스트는 필요한 차원을 하나씩 바꾸고 만들어 낸 JSON 성공, 누락된 소유자, 사용자, 테스트 경로, client, 데이터베이스, 사례, 반복 실행, 상태 비교 또는 선언되지 않은 결과에서 실패를 요구한다. 주장한 모든 동작에 현재 실행 증거가 생길 때까지 `make feature-check`는 실패한다. 검사기 자체 테스트가 성공해도 client 동작의 완료를 주장하지 않는다.
- **FCV-6** `make feature-coverage`는 `make orm-check`처럼 모든 기능의 coverage를 한 번 실행하고, `make feature-check`는 그것을 모든 검증 명령과 함께 실행한다. `.runtime/servers/env`의 test 환경 아래에서 `node scripts/features/coverage.mts --feature <id>`는 그 기능의 coverage spec만 실행한다: 소유자와 사용자를 데이터베이스마다 두 번. `<id>`는 `scripts/features/check.mts --feature`처럼 `contracts/features.json`의 기능 `id`다. 없는 id는 아무것도 실행하지 않는 대신 고를 수 있는 id 목록과 함께 실패한다. 예를 들어 `node scripts/features/coverage.mts --feature dsn_connection`은 DSN 연결 기능만 실행한다. DSN 기능은 세 데이터베이스에서 다섯 client의 읽기 전용 소유 사례와 Go client와 Rust client 부분의 생성 모델 사용 사례를 실행한다. 검사기는 두 실행의 전후 데이터베이스 상태를 읽는다.


## Database 기능의 recipe화 {#database-recipes}

- **FCV-8** database 기능은 자기 commit에서 recipe가 된다. 그 commit은 recipe 파일을 `fixture`(`.dbs` 문서를 적는 `dbspec-set.json`), `seed`, `cases`와 함께 추가하고, 그 step들이 쓰는 op 각각을 FCV-4 목록, `scripts/features/schema/recipe.schema.json`, 여섯 runtime 각각의 recipe helper에 추가하며, FCV-3의 suite unit 세 개를 `config/parity.json`에 추가하여 여섯 runtime 모두 bind하고, `contracts/features.json`의 그 기능 소유자를 recipe로 향하게 하며, 그 기능의 손으로 쓴 coverage 테스트를 지워 어떤 동작도 두 번 테스트되지 않게 한다. recipe를 실행하는 make target은 `contracts/check-inputs.json`에 scope `owner`, runtime과 `databases`를 `needs`로, `inputs`에는 recipe에 맞는 경로를 적는다. `catalog-connection-check/<runtime>`이 그렇다. 선례는 `catalog_connection`(`contracts/fixtures/catalog_connection/catalog_connection.json`)이다.
- **FCV-9** recipe는 database를 feature 변수가 아니라 자기 run에서 받는다. target은 `databases`를 `needs`에 선언하므로 `scripts/check/run.mts`가 그 run의 database를 만들고, 그 run의 environment 파일을 `TEST_ENV`로 넘긴다(`make run-databases TARGETS=...`). recipe helper는 그 environment에서 서버 DSN `ORM_TEST_MYSQL_DSN`과 `ORM_TEST_POSTGRES_DSN`을 읽고, 관리 연결로만 쓴다. 사례마다 helper는 자기 runtime의 case-database factory(Go `testdb.New`, TypeScript `case-database.mjs`, Python `case_database`, PHP `with_case_database`, Rust `CaseDatabase::create`와 `packages/rust/case-database`)로 서버에 database 하나를 만들거나(SQLite는 자기 파일 하나), fixture를 설치하고, 사례가 끝나면 그것을 지운다.
- **FCV-10** database 기능은 `mysql`, `postgres`, `sqlite` 세 database 모두에서 실행된다. fixture가 있는 recipe는 database마다 suite unit 하나(FCV-3)를 가지며, 모든 expect는 정확히 그 step을 실행하는 database를 이름 붙인다(FCV-4). 그래서 사례가 실패하도록 기대된 database는 `{"error": <code>}`로 그렇다고 적고, 빠지지 않는다. step이나 사례의 `only`는 그것을 실행하는 database를 이름 붙이며, PostgreSQL의 알림(INT-91)처럼 거기에만 있는 문장이나 호출, 또는 그 database에만 있는 동작을 위한 것이다. database가 거부하는 호출은 `only`로 빼지 않고 그 거부로 적는다. recipe는 실행되지 않는 것을 말하지 않으므로 expect는 그 step을 실행하지 않는 database를 이름 붙이지 않으며, `scripts/features/recipes.test.mts`가 다른 이름 집합을 거부한다. `only`와 그 이유가 없으면 database 간 차이는 database마다의 결과로 적는다.
- **FCV-11** DSN이 없으면 사례는 실패하고 변수 이름을 밝히며, 건너뛰지 않는다. FCV-9의 각 factory는 `<VARIABLE> is required; run make orm-test-servers, which starts the databases and writes it`으로 실패한다. Go `testdb.New`, TypeScript `case-database.mjs`, Rust `packages/rust/case-database`, PHP `case_database.php`는 지금 그렇게 실패한다. Python `case_database`도 변수 이름을 밝히지만, 그 메시지(`statement_fault.py`의 `required_dsn`이 내는 `is required for the <dialect> statement fault cases`)는 FCV-11 문구가 아니므로 맞출 결함이다. 변수 이름을 밝히지 않거나 skip하는 factory는 FCV-11 결함이며 받아들일 skip이 아니다. make target 밖에서 recipe를 실행할 때 `ORM_TEST_MYSQL_DSN`이나 `ORM_TEST_POSTGRES_DSN`이 없어도 같은 실패가 난다.
- **FCV-12** feature 검사기는 각 runtime의 결과를 recipe의 사례 결과에서 사례 id로 읽는다. recipe의 owner는 자기 명령에 그것을 적는다: `{"runner", "test", "recipe"}`이고, Go와 PHP는 test method를 `symbol`로 적는다. recipe가 곧 그 owner들의 목록이다. manifest에는 사본이 없고, 읽을 때(`scripts/features/manifest.mts`) 그 database에서의 recipe 사례를 가져오며 `only`가 있는 사례는 다른 database에서 빠진다. manifest의 schema가 적어 둔 사본을 거부한다. feature의 모든 owner가 recipe owner이면 `coverage.cases`도 같은 방식으로 recipe에서 가져오고, `make feature-unit-check`의 `scripts/features/recipes.test.mts`가 그 목록의 사본을 거부한다. 검사기는 그 runtime의 test runner로 entry를 한 번 실행하고 `ORM_RECIPE_RESULTS`에 파일 하나를 지정한다. FCV-15의 각 recipe runner는 사례가 통과하면 그 파일에 `CASE <id> [<database>] PASS`를, database 없는 recipe면 `CASE <id> PASS`를 덧붙이고, 변수가 없으면 아무것도 쓰지 않는다. 결과는 entry의 종료 상태와 그 줄들이며, 여섯 runtime 모두 reader 하나로 읽는다. 줄이 없는 사례는 통과하지 않은 것이다. 독립 feature의 owner는 그 동작이 database 있는 recipe의 사례이면 그 database 하나를 `database`로 적는다. recipe owner는 `dsn_env`를 적지 않고, 사례마다 자기 database를 가지므로(FCV-9) 검사기는 그 database 상태를 읽지 않는다.
- **FCV-13** recipe의 seed 데이터는 recipe 파일에 속하며, run마다가 아니라 사례마다 설치되고, 공유 database에 담지 않는다. 사례마다 helper는 fixture set을 사례 database에 설치한 뒤, 파일 수준의 `seed`와 그다음 사례 자신의 `seed`를 recipe의 순서대로 `describe_table`이 읽는 metadata를 거쳐 `insert_row`로 넣는다(Go `insertSeed`, 그리고 TypeScript, Python, PHP, Rust도 같은 순서). seed 행 하나가 실패하면 사례가 실패한다. `seed.after`는 seed 행을 쓴 뒤 실행하는 `sql.exec` step 하나이며, 명시한 행이 움직이지 않는 PostgreSQL identity sequence처럼 그 행들이 남긴 것을 맞춘다.
- **FCV-14** runtime은 database 동작의 네이티브 테스트를, FCV-2가 그 동작을 runtime 고유로 적은 곳에서만 유지하고, 그 테스트 파일이 그 이유를 적는다. 다른 runtime이 가진 database 동작은 recipe 사례이며, 그 네이티브 테스트는 recipe를 더하는 commit에서 지운다. 네이티브 테스트가 유효한 이유를 가졌는지는 검토의 판단이며 검사가 아니다. 그런 test는 recipe처럼(FCV-9) 자기 case database를 쓴다. 그 command는 `dsn_env` 대신 `"case_database": true`를 적고, 둘을 함께 적으면 거부한다. checker는 그 항목에 bench database를 주지 않고 전후 상태를 읽지 않으며, 그래도 두 번 실행한다.
- **FCV-15** 각 runtime의 recipe runner는 하나다. Go `packages/go/internal/recipe`, TypeScript `packages/ts/tests/recipe.mjs`, Python `packages/python/tests/recipe.py`, PHP `packages/php/tests/Recipe.php`(PHP extension도 이것을 실행), Rust `packages/rust/tests/src/recipe.rs`이며, Rust의 trial binary는 runner가 이름을 알 수 없는 fixture의 생성 model을 위해 그 model의 dispatcher를 더한다. recipe suite unit의 binding은 그 파일을 자기 runtime의 runner에 넘기고 op를 구현하지 않는다. runner는 자기 목록의 전체 op 이름과 맞추어 dispatch하고, 목록에 없는 op는 `OP_UNKNOWN`으로 거부한다. recipe schema의 모든 op는 어떤 recipe의 step이므로, op가 없는 runtime은 그 recipe에서 실패한다. `make recipe-runners-check`가 이를 강제한다.

## Owner 검사 {#owner-checks}

- **FCV-7** `make owner-check`는 바뀐 file을 소유한 검사를 실행한다. 기본은 `HEAD`와 다른 file과 추적하지 않는 file이고, `PATHS="<paths>"`로 file을 줄 수 있다. `contracts/features.json`의 모든 검증 명령은 `inputs`를 선언하고, 모든 coverage 단위인 owner client(`owner/<language>`)와 사용 부분(`dependent/<id>`)은 `tests`와 선택적 `inputs`를 선언한다. `scripts/features/owners.mts`는 입력에 바뀐 file이 있거나 선언한 fixture data(JSON이나 dbspec file)가 그 file을 적는 명령과 단위를 고른다. 예를 들어 `contracts/fixtures/schema_definition.json`은 `contracts/fixtures/audit.dbs`를, `contracts/symbols/rust.json`은 Rust source를 적는다. 적힌 file이 다시 적는 file은 따라가지 않는다. 고른 명령과 단위마다 그것을 고른 path를 출력하고, 아무것도 고르지 않은 바뀐 path도 출력한다. coverage helper `packages/php/tests/coverage_cases.php`처럼 여러 기능이 쓰는 helper는 `helpers`에 자기 check와 함께 선언하고 어떤 입력에도 넣지 않는다. helper의 변경은 그 check(`scripts/features/check.mts --run --helper <id>`)만 실행하고, helper를 쓰는 모든 기능의 실행은 `make orm-check`가 맡는다. `contracts/features.json`이 바뀌면 `HEAD`와 항목이 다른 기능의 명령과 단위, 그리고 항목이 다른 helper를 고른다. 그 항목 밖의 변경은 `make orm-check`가 모든 기능을 실행하므로 아무것도 고르지 않는다. 고른 명령은 `scripts/features/check.mts --run --feature <id> --command <id>`로, 고른 단위는 `scripts/features/coverage.mts --feature <id> --part <part>`로 실행한다. 각각은 RUN, PASS나 FAIL과 경과 시간을 가진 단계 하나이고, 기한은 단계 안의 case마다 있다. 선언 검사는 입력이 없는 검증 명령, 추적되는 file을 맞추지 않는 입력, 입력으로 쓰인 helper를 실패시킨다. 또 `contracts/check-inputs.json`이 scope `owner`로 선언하고 입력이 바뀐 path를 맞추는 make target을 실행한다. `client-db-check`나 `feature-check`처럼 scope `suite`인 target은 `make orm-check`에서만 실행하고, scope가 없는 target이 있으면 선택이 실패한다. `node scripts/features/owners.mts --list [<paths>]`는 실행하지 않고 고른 것만 출력한다. `scripts/features/owners.test.mts`는 `make feature-unit-check`에서 실행한다.

## Catalog 연결 제외 항목 {#catalog-connection-exclusions}
recipe `contracts/fixtures/catalog_connection/catalog_connection.json`은 여섯 runtime이 공유하는 catalog 동작을 다룬다(SCH-6a, INT-117). 네이티브 테스트는 FCV-2가 한 runtime에 남기는 동작이거나 recipe로 표현할 수 없는 동작일 때만 남는다. 남은 동작은 이유와 함께 아래에 적는다.
- **표면과 패키징(FCV-2).** PHP와 PHP extension의 `Catalog`, `Model` 클래스와 메서드 표면, extension 로딩, build crate의 Rust 라이브러리 표면, commit·rollback·metadata·cleanup 실패, descriptor 변경, trigger 가시성을 만드는 fault 주입 더블. recipe는 실패를 주입할 수 없다.
- **recipe에서 제외.** TypeScript의 `precisionCase`는 recipe case `declared_temporal_cells`가 다루므로 네이티브 테스트가 없다.
- **PHP cause 형태(INT-109).** recipe case `descriptor_column_name`은 잘못된 열 이름을 가진 descriptor의 코드와 메시지를 모든 runtime에서 확인한다. 그 실패의 `previous` 예외는 PHP와 PHP 확장만 가진 형태이므로 `CatalogPageValidationTest`와 `CatalogConnectionSurfaceTest`가 확인한다. 라이브러리 `Catalog`가 PHP 클래스인지도 같은 surface이며 `CatalogPageValidationTest`가 확인한다.
- **codec.** 어떤 recipe case도 빈 `ordered_json` 텍스트를 decode하지 않으므로, codec recipe case가 이를 검사할 때까지 네이티브 검사를 남긴다.
