# Runtime connection

The clients take connection values as arguments and read no environment variable or secret store of their own. The client does not read a configuration file.

The DSN URI is the only database selector:

```text
mysql://user:password@host:3306/orm_example
mysql://user@localhost/orm_example?socket=/tmp/mysql.sock
postgres://user:password@host:5432/orm_example?sslmode=disable
postgres:///orm_example?host=/tmp
sqlite:///var/lib/orm_example.sqlite?_pragma=busy_timeout(5000)
markdown://127.0.0.1:4100/tracker?token=0123456789abcdef0123456789abcdef
```

- **CFG-1** The scheme selects MySQL, PostgreSQL, or SQLite. The client creates the matching native driver and opens its pool; schema loading and hash checks are internal. The scheme `markdown` selects the SQLite dialect on a markdown corpus that a flowmark server serves; its DSN and its server connections are in the [protocol](protocol.md#_5-markdown-connections) and what a corpus adds to SQLite is in the [dialects](dialects.md#markdown-corpus). A connection that the server refuses, such as over `max_user_connections`, fails with `DRIVER`, holding the server's message and with the native error as its cause, in every client; a TLS failure (CFG-16), a SQLite file and a time zone that the server does not know are `CONFIG`. Every client implements it; the Python client keeps one server connection for it.
- **CFG-2** Every connection reads and writes datetime values in UTC, whatever the server time zone ([dialects](dialects.md#date-and-time)): MySQL connections set `time_zone = '+00:00'`, PostgreSQL connections set `TimeZone` to `UTC`, and SQLite values and ORM value functions use UTC on the client. A value with an offset is written as its UTC wall clock and read back in UTC. The optional `timezone` parameter accepts only `UTC` or `+00:00`; any other value returns `CONFIG`.
- **CFG-3** Every MySQL connection sets the session `sql_mode` to `STRICT_ALL_TABLES,ONLY_FULL_GROUP_BY,NO_ZERO_DATE,NO_ZERO_IN_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` when it opens, after the driver's own setup, so a coercion, truncation or grouping result does not depend on the server's `sql_mode`, and modes that a driver adds (`PIPES_AS_CONCAT` from sqlx, `IGNORE_SPACE` from a client flag) are replaced; the connection reads `@@SESSION.sql_mode` as `ONLY_FULL_GROUP_BY,STRICT_ALL_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` (`mysql.session.sql_mode_set`, the case `mysql_session_settings` of `contracts/fixtures/dsn_connection`).
- **CFG-4** The connection configuration takes `poolSize`, the maximum open connections: Go `orm.Config{PoolSize: n}`, PHP `new Config(poolSize: n)`, TypeScript `{ poolSize: n }`, Rust `Db::connect(dsn, n, config)`, and Python `connect(dsn, {"poolSize": n})`. Zero or unset opens at most 10 connections in a client that keeps a pool, and a negative value returns `CONFIG`. A pool never opens more connections than its maximum; a statement or transaction that needs a connection while all of them are in use waits for one. The TypeScript SQLite driver holds one connection. PHP opens a connection per request: each `Db` opens one connection that closes with it, and no connection outlives the request. Pooling for PHP is done by PgBouncer or ProxySQL ([Connection poolers](#connection-poolers)). The PHP client keeps no pool of its own: a php-fpm worker serves one request at a time and shares no state with the next, a connection kept across requests carries the session state of one request into the next and multiplies the server connections by the workers, and a pooler shares a few server connections among all workers instead. `new Config(poolSize: n)` with n other than zero returns `CONFIG`, because a setting the client ignored would let a caller believe the connections are pooled when they are not. `stats()` reports `maxOpenConnections` 1, the one connection of the `Db`.
- **CFG-5** The connection configuration takes `poolIdleSize`, the maximum idle connections of the pool, and `poolLifetimeMs`, the lifetime of a pool connection in milliseconds: Go `orm.Config{PoolIdleSize: n, PoolLifetimeMs: ms}`, TypeScript `{ poolIdleSize: n, poolLifetimeMs: ms }`, Rust `Config { pool_idle_size: n, pool_lifetime_ms: ms, ..Default::default() }`, and Python `connect(dsn, {"poolIdleSize": n, "poolLifetimeMs": ms})`; PHP keeps no pool and refuses them, as the end of this item says. A connection released while the pool already keeps `poolIdleSize` idle connections is closed. A connection whose lifetime has passed is closed while it is idle or when it is released. Zero or unset `poolIdleSize` keeps up to the pool size of idle connections. Zero or unset `poolLifetimeMs` keeps connections without a lifetime in every client with a pool except Rust, which keeps the 30-minute lifetime of its pool. A negative value or an idle size above the pool size returns `CONFIG`; the Rust fields are unsigned. The TypeScript SQLite driver holds one connection and does not use these values. PHP returns `CONFIG` for any `poolIdleSize` or `poolLifetimeMs` other than zero, because it has no pool.
- **CFG-5a** Go and Rust and TypeScript and Python keep a pool of connections on MySQL and PostgreSQL, and `stats()` reports it: a transaction takes a connection of the pool for its length, so transactions beyond the pool size wait, and the open count never passes the pool size; a released connection beyond `poolIdleSize` closes. PHP and the PHP extension keep no pool (CFG-4), and the pool of SQLite differs by runtime, so the recipe `connection_pool` states these on the two servers.
- **CFG-5b** PHP and the PHP extension return `CONFIG` for any `poolSize`, `poolIdleSize` or `poolLifetimeMs` other than zero, and the message names PgBouncer and ProxySQL, since they keep no pool (CFG-4, CFG-5). The recipe `dsn_reject_php_pool` states this.
- **CFG-6** The connection configuration takes `statementTimeoutMs`, the bound of every statement of the connection: Go `orm.Config{StatementTimeoutMs: n}`, PHP `new Config(statementTimeoutMs: n)`, TypeScript `{ statementTimeoutMs: n }`, Rust `Config { statement_timeout_ms: n, ..Default::default() }`, and Python `connect(dsn, {"statementTimeoutMs": n})`. Zero or unset keeps the server default, and a negative value returns `CONFIG`. PostgreSQL bounds every statement with `statement_timeout`, which every client sends as a startup parameter of each server connection. MySQL bounds SELECT statements with `max_execution_time`; a write is bounded by the server lock wait timeout (`innodb_lock_wait_timeout`), not by this value. MariaDB bounds every statement with `max_statement_time`, and each connection sets the variable of its server (DIA-208). SQLite has no session timeout, so its bound is the DSN `busy_timeout`. A statement the bound stops returns `CANCELED`. A MySQL lock wait timeout (error 1205) is the expiry of that write bound, so it returns `CANCELED` too, in every client.
- **CFG-6a** PHP-extension package `polyspec/orm-php-ext` closes the cursor of a failed native statement, and the same connection runs the next statement.
- **CFG-7** The PHP client and the Python client set the session settings when a connection opens: PostgreSQL receives the time zone and `statement_timeout` as startup parameters, and MySQL runs `SET NAMES utf8mb4, time_zone = '+00:00', sql_mode = '<declared modes>'` as one init command; the statement timeout is the variable of the server that the connection reads after it opens (DIA-208), so the first connection sets it by a statement of its own after `SELECT VERSION()`, and a connection that opens again for the same `Db` takes it in its init command. A PHP request that ends inside a transaction, by `exit` or a fatal error, ends its connection with it, and the server rolls the transaction back and releases the named locks and session values of the connection.
- **CFG-8** The connection configuration takes `auditSource`, a function that returns the audit values of the current request, a map from column name to value of the audit record table, such as the account and the request id: Go `orm.Config{AuditSource: func(ctx context.Context) (map[string]any, error)}` (called with the transaction's context), PHP `new Config(auditSource: fn (): array => [...])`, TypeScript `{ auditSource: () => ({...}) }`, Rust `Config { audit_source: Some(Arc::new(|| Ok(vec![...]))), .. }`, and Python `connect(dsn, {"auditSource": lambda: {...}})`. A transaction with audit values calls it once and inserts the audit record with these values and its own ([usage](../operations/usage.md#audited-writes)); the ORM writes no audit value of its own, and an error of the source fails the transaction.
- **CFG-8a** The `github.com/polyspec/orm/packages/go` Go module calls the audit source with the context of the transaction, so the transaction of a `WithContext` handle hands its context to the source.
- **CFG-9** A flow cancels its statements with the cancellation primitive of its own language, on a connection handle. Go `db.WithContext(ctx)` and TypeScript `db.withSignal(signal)` return a handle on the same connection: models connect to the handle as they connect to the connection, transactions started on it carry the same cancellation, and cancelling the context or the signal ends the statement in flight with `CANCELED` while the connection stays usable. Python `db.with_future(future)` returns a handle whose active statement on a MySQL, PostgreSQL, or SQLite connection is cancelled when the supplied `asyncio.Future` is cancelled. Python SQL remains synchronous: run it with `asyncio.to_thread` so cancellation can be observed by the event loop; transaction cleanup is not cancelled, and the root connection remains reusable after rollback. In Rust, dropping the future of a statement cancels it; the checked-out connection is closed before it can return to the pool. PostgreSQL cancels the running statement, MySQL ends the running query, and the TypeScript SQLite driver runs a statement without yielding, so a signal there ends the next statement rather than the one in flight. PHP `$db->withCancellation($source)` returns a handle on the same logical connection. `$source->cancel()` ends every active statement started through a handle attached to that source with `CANCELED`. On SQLite a progress handler interrupts the virtual machine; on MySQL a control connection ends each active server connection attached to the source, the transaction is rolled back, and each root handle reconnects before its next statement. On PostgreSQL PHP requires both `pdo_pgsql` and `ext-pgsql`; it sends the protocol cancel request on the same physical connection, rolls back the interrupted transaction, and reuses the root connection. Transaction cleanup is not cancelled. On a markdown connection every client ends the statement in flight by closing its connection, and the server rolls back its transaction (PRT-71). The chain has no cancellation operation; the connection handle carries it. A handle is a separate value, so Go `db.Root()`, Python `db.root()`, and TypeScript `db.root()` return the connection it was derived from, and two handles of one connection compare equal.
- **CFG-10** A MySQL `socket` parameter connects through a Unix socket. The client enables the found-rows count that optimistic updates rely on. A login with a password succeeds over the socket in every client: MySQL counts a socket as a secure transport and reads the cleartext password in the full authentication of `caching_sha2_password`, which every client sends there. The case `socket_update_finds_its_row` of the recipe model_socket logs in with a password in the pooler lanes.
- **CFG-11** A SQLite path must be absolute. The client percent-decodes the path as UTF-8 before it opens the file: `sqlite:///var/lib/my%20data.sqlite` opens `/var/lib/my data.sqlite`, and `%25`, `%23` and `%3F` give a literal `%`, `#` and `?`. A `%` without two hexadecimal digits after it, a decoded NUL byte, and a decoded path that is not UTF-8 return `CONFIG`. The cases `sqlite_path_opens_the_percent_decoded_file` and `sqlite_invalid_path_is_config_and_creates_no_file` of the recipe `dsn_connection` hold them, and every client runs them. The client enables foreign keys. A write transaction begins with `BEGIN IMMEDIATE` and holds the write lock of the database from its start, so two write transactions run one after the other and neither fails when it writes after a read. A transaction with the `readOnly` option begins with `BEGIN` and takes no write lock. The client selects the begin statement, and a DSN with `_txlock` returns `CONFIG`.
- **CFG-12** A SQLite connection waits up to 5000 milliseconds for a lock that another connection holds. The six configured implementations—Go, PHP, PHP extension, TypeScript, Python, and Rust—use the DSN parameter `_pragma=busy_timeout(ms)` to set another duration. For example, `sqlite:///var/lib/orm_example.sqlite?_pragma=busy_timeout(10000)`; `busy_timeout(0)` does not wait, and a value that is not a whole number returns `CONFIG`. A lock that another connection still holds when the wait ends returns `CANCELED`. The transaction does not run again, because only `DEADLOCK` is retried. Every `_pragma=name(value)` parameter runs `PRAGMA name = value` on the connection. A DSN that returns `CONFIG` creates no file.
- **CFG-13** A SQLite read runs while another connection has a write transaction open and returns the rows committed before it. The clients keep the journal mode of the database file and do not require WAL. In the default rollback journal, a read that starts during the commit of a write waits for the commit within `busy_timeout`. `_pragma=journal_mode(WAL)` changes the file to WAL, in which a read does not wait for a commit; the mode stays in the file.
- **CFG-14** The `@polyspec/orm` SQLite driver, in TypeScript, waits for a lock synchronously and stops the event loop while it waits. A TypeScript process therefore opens one `Db` for a SQLite file; the transactions of that `Db` run one after the other, and several processes share the file through the lock wait.

Database credentials and AES keys must not be committed, written to runtime files, or included in logs. Pass them through the client connection options after resolving them from the deployment secret source.

## Lost connections {#lost-connections}

The server ends a connection when an administrator ends its session (`pg_terminate_backend`, `KILL`), when it restarts, and when the connection stays idle longer than its limit (PostgreSQL `idle_session_timeout`, and `idle_in_transaction_session_timeout` in a transaction, MySQL `wait_timeout`); a network failure breaks it. The next statement on that connection fails, and every client reports that failure with the code `CONNECTION_LOST`, whatever the driver and its message: MySQL errors 2006, 2013 and 4031, PostgreSQL SQLSTATE class 08 and 25P03, 57P01, 57P02 and 57P05, and the error of the driver for a connection that is no longer open (PHP pdo_pgsql reports it without a server SQLSTATE on a connection whose backend process id is 0, go-sql-driver `ErrInvalidConn`, `driver.ErrBadConn`, a broken socket in Rust, a fatal mysql2 error, a node-postgres connection that reported a connection error, a PyMySQL `InterfaceError` of a closed connection, and a psycopg error without a server SQLSTATE on a connection that psycopg marks closed). SQLite has no server connection.

- **CFG-15** Every client returns `CONNECTION_LOST` for the statement that failed so and does not send it again: the transaction or session state of the connection is gone.
- **CFG-38** PHP and the PHP extension hold one session on a connection, so a server that ended that session before its first statement fails the statement with `CONNECTION_LOST`, and the statement is sent once.
- **CFG-39** Go: a transaction whose context is canceled during its callback returns `CANCELED` alone, and the connection keeps no named lock, user variable or SQLite mode of that transaction.
- **CFG-40** Go: `DriverFromDSN` names the database of a DSN URI by its scheme and returns `CONFIG` for a DSN that is no URI.
- **CFG-41** A catalog session through a server connection of a transaction pooler reads a table whose column type changed while another client of that connection still holds the prepared statement of the same text.
- **CFG-42** Go and PHP and PHP extension and TypeScript and Python and Rust: several processes that open one SQLite file commit every write of their read-then-write transactions without transaction retries, since the lock between them is the file lock that CFG-12 waits for. Each write waits as long as the busy timeout of CFG-12; SQLite grants the lock to no waiter in turn, so the tests of this requirement open the file with `_pragma=busy_timeout(60000)`, and the load of the runner does not end a wait.
- **CFG-43** The `github.com/polyspec/orm/packages/go` module: a process that ends inside a write transaction on a SQLite file leaves no holder of the lock: the operating system releases the lock with the process, a connection that does not wait for a lock writes at once, and the uncommitted write is rolled back.

## DSN parameters and MySQL TLS

A MySQL DSN connects with TLS through one mode, which every client implements:

```text
mysql://user:password@db.example:3306/orm_example?ssl-mode=VERIFY_IDENTITY&ssl-ca=/etc/orm/mysql-ca.pem
```

- **CFG-16** `ssl-mode=VERIFY_IDENTITY` with `ssl-ca`, the absolute path of a PEM file of the certificate authority, connects with TLS that checks the server certificate against that authority and the host of the DSN against the certificate. A certificate that another authority signed or that names another host fails the connection with `CONFIG`, and the message holds `TLS connection failed`. The password then travels only inside TLS; the client requests no RSA public key of the server.
- **CFG-17** The host is a host name that the server certificate names, not an IP address, because the TypeScript driver checks an address host against the name `localhost`; every client returns `CONFIG` for an address with `ssl-mode`. The mode connects over TCP and does not accept `socket`.
- **CFG-18** Another value of `ssl-mode`, such as `VERIFY_CA` or `REQUIRED`, `ssl-mode` without `ssl-ca`, `ssl-ca` without `ssl-mode`, a relative `ssl-ca` path and an unreadable CA file return `CONFIG` in every client but Rust, whose parameters are below.
- **CFG-44** A MySQL DSN without `ssl-mode` connects without TLS in every client, also to a server that offers TLS. PyMySQL and sqlx would otherwise take TLS whenever the server offers it, with no check of its certificate, so the Python client passes `ssl_disabled` and the Rust client `ssl-mode=DISABLED` when the DSN names no `ssl-mode`; the Go, TypeScript and PHP drivers send no TLS on such a DSN. The case `plain_dsn_connects_without_tls` of the recipe dsn_connection reads an empty `Ssl_version` of the session on MySQL and MariaDB.
- **CFG-19** Go and Rust accept other parameters; every other client accepts only these parameters and returns `CONFIG` for another one: `timezone`, `socket`, `ssl-mode` and `ssl-ca` for MySQL; `timezone`, `host` and `sslmode` for PostgreSQL; `timezone`, `_pragma` and `_txlock`, which returns `CONFIG` itself, for SQLite.
- **CFG-20** The clients differ in the other parameters that they accept. The Go client passes another MySQL parameter to go-sql-driver/mysql, which sets a session variable or a driver option of that name, and another PostgreSQL parameter to pgx. The Rust client passes every parameter except `timezone` to sqlx, which also accepts other `ssl-mode` values such as `verify_ca`, in any case. A DSN that names only the parameters of this page behaves the same in every client.

## Primary and replicas

The ORM does not route statements between servers. Reads from replicas use one connection per server, one to the primary and one to each replica, and `connect` gives the model or row the connection that a statement uses:

| Language | Connections | Read through a replica | Write through the primary |
|---|---|---|---|
| PHP | `$master = \Polyspec\Orm\Tests\Model\connect($primaryDsn, $config);` `$slave1 = \Polyspec\Orm\Tests\Model\connect($replicaDsn, $config);` | `(new User)($slave1)->name($name)->get()` | `$row->connect($master)->setName($new)->update()` |
| Go | `master, err := model.Connect(primaryDSN, cfg)` `slave1, err := model.Connect(replicaDSN, cfg)` | `model.User().Connect(slave1).Name(name).Get()` | `row.Connect(master).SetName(next).Update()` |
| Rust | `let master = model::connect(&primary_dsn, n, cfg.clone()).await?;` `let slave1 = model::connect(&replica_dsn, n, cfg).await?;` | `User::new().connect(&slave1).name(name).get().await?` | `row.connect(&master).set_name(next).update(false).await?` |
| TypeScript | `const master = await connect(primaryDsn, options);` `const slave1 = await connect(replicaDsn, options);` | `new User().connect(slave1).name(name).get()` | `row.connect(master).setName(next).update()` |
| Python | `master = model.connect(primary_dsn, **options)` `slave1 = model.connect(replica_dsn, **options)` | `model.User().connect(slave1).name(name).get()` | `row.connect(master).set_name(new).update()` |

- **CFG-21** A model or a loaded row uses the connection it is connected to and no other. Inside a transaction of `master`, a model connected to `slave1` runs on `slave1` outside the transaction, and a model without `connect` runs in the transaction.
- **CFG-22** Each connection has its own pool, prepared statements, and session settings.
- **CFG-22a** Go and Rust and TypeScript and Python: `stats()` of a connection counts only the connections of its own pool on MySQL and PostgreSQL (CFG-5a).
- **CFG-23** A replica applies the changes of the primary after the primary commits them. A read that must see a write of the same request uses the primary connection; orm does not choose the connection itself.
- **CFG-24** A replica rejects a write: PostgreSQL returns SQLSTATE 25006 and a MySQL replica with `super_read_only` returns error 1290. The clients return `READ_ONLY` with the driver message, as they do for a write in a read-only transaction and for a write to a SQLite database opened read-only.
- **CFG-25** The schema tools and `utils().schema().install` run on the primary, and the replicas apply the schema through replication.
- **CFG-26** SQLite is single-node only. A SQLite database is a local file named by an absolute path, and the ORM supports no SQLite replica.

`make orm-test-servers` starts a replica of the MySQL primary and a standby of the PostgreSQL primary. These rules apply to all six configured implementations—Go, PHP, PHP extension, TypeScript, Python, and Rust; the PHP extension's full database verification remains open. The PostgreSQL standby streams through the physical replication slot `orm_replica`, so the primary keeps the WAL the standby has not received, also while it is stopped.

## Connection poolers {#connection-poolers}

A connection pooler stands between the client and one database server and shares a small number of server connections among many client connections. The shared pooler rules apply to all six configured implementations—Go, PHP, PHP extension, TypeScript, Python, and Rust. Clients work through PgBouncer in transaction mode for PostgreSQL and through ProxySQL for MySQL, used as poolers only: a client connects to the pooler with that server's DSN, and the pooler routes no statement to another server. `make client-pooler-check` exercises the configured database cases; it does not establish that PHP extension database coverage is complete.

PgBouncer settings:

- **CFG-27** `pool_mode`: `transaction`. A server connection serves one transaction of a client, or one statement outside a transaction, at a time.
- **CFG-28** `max_prepared_statements`: above 0 (PgBouncer default 200). The Go client, the Rust client, the TypeScript client and the Python client (psycopg with `prepare_threshold=0`) run statements as protocol-level named prepared statements; the PHP client sends each PostgreSQL statement with its binds as an unnamed statement. With 0, a statement prepared on one server connection is missing on the next and PgBouncer returns `prepared statement … already exists` or `does not exist`. PgBouncer keeps a named statement on the server connection under its text, and a Parse of a text that the server connection already holds never reaches the server. So a catalog session (SCH-6a), which runs after schema changes by design, sends `DEALLOCATE ALL` right after its `BEGIN` in every client that names statements: the transaction holds the server connection for the session, every statement of the session is parsed by the server after that point, and PgBouncer prepares again on that server connection what its other clients still use. `DEALLOCATE ALL` through PgBouncer needs version 1.22 or later. A statement from before a schema change, on a client connection or on a server connection that holds its text, fails in the same way on a direct connection and through PgBouncer: its result type changed (`0A000`, `cached plan must not change result type`), a parameter keeps its old type against the new column (`42883`, `42804`), or a value is read as that old type (`22P02`, `22003`, `22007`, `22008`). A statement outside a transaction that fails has changed nothing, so a statement that fails with one of these runs once more on one server connection, in one transaction that opens with `DEALLOCATE ALL`. The statement that runs again takes the parameter types that the server now infers, and a parameter whose type is now another is the value that PostgreSQL reads from its text, as every client but Rust sends it; the Rust client, whose driver binds every value in binary form, has the server read that text as the inferred type in the same transaction, so a text that the type does not read fails with the `DRIVER` error of PostgreSQL in every client (DIA-219). The cases `model_text_parameter_refused_after_schema_change`, `model_decimal_text_parameter_after_schema_change` and `model_numeric_text_parameter_refused_after_schema_change` of the recipe `parameter_chunking` write texts to a column changed to an integer, a date and a numeric type. A statement that failed for another reason fails the same way and that error reaches the caller. Inside a transaction of the caller the server has aborted the transaction, so the error reaches the caller as `DRIVER`; the PHP client names no statement, so this does not arise there.
- **CFG-29** `track_extra_parameters`: `statement_timeout`. Needed when a connection sets `statementTimeoutMs`. The clients send `statement_timeout` as a startup parameter; PgBouncer rejects a startup parameter it does not track, and sets a tracked one on every server connection it assigns to that client connection and on no other.

- **CFG-30** Outside a transaction the clients set no PostgreSQL session state other than the time zone, which every client sends as the startup parameter `TimeZone=UTC`; PgBouncer tracks `TimeZone` by default. Transaction options (`SET TRANSACTION`, `SET LOCAL statement_timeout`), `utils().setLocal` (`set_config(…, true)`), and `utils().lock` (`pg_advisory_xact_lock`) end with their transaction.
- **CFG-31** Cancellation of a statement through PgBouncer is best effort, not guaranteed. PgBouncer forwards the protocol cancel request of a client connection to the server connection that runs its statement, but that path is not reliable: PgBouncer's cancel race (BUG #14891) was fixed only in 1.18, and that fix has a hang side effect; in multi-process setups cancel requests were lost until peering arrived in 1.19; and SQLx 0.9 has no CancelRequest API, so the Rust client has no supported cancellation path through PgBouncer. TypeScript sends that request with the process id and secret key of its connection; PHP uses `ext-pgsql` to send the protocol cancel request through its PostgreSQL connection. A lost cancel leaves the statement running, so no caller may depend on the cancel reaching the server.
- **CFG-32** The `polyspec-orm` crate, the Rust client, does not send the startup parameter `extra_float_digits`; PostgreSQL 12 and later print float8 values exactly with the server default.
- **CFG-33** A violated foreign key, check or unique key is reported as `FOREIGN_KEY`, `CONSTRAINT` or `DUPLICATE_KEY`, with the native codes that [errors.yaml](errors.yaml) lists for each database, and the statement changes no row. This is the mapping beside the `1205` rule of CFG-6.
- **CFG-36** Go and PHP and the PHP extension and TypeScript and Python return `CONFIG` before they open a connection for each form that CFG-18 lists and for a negative `poolSize`, `poolIdleSize`, `poolLifetimeMs` or `statementTimeoutMs`; the configuration of Rust holds these values in an unsigned type.
- **CFG-37** PHP and the PHP extension and TypeScript and Python return `CONFIG` for a parameter that CFG-19 does not name; Go and Rust pass it to their drivers (CFG-20).

ProxySQL settings:

- **CFG-34** `mysql-threshold_resultset_size`: `65536`, not the default 4 MiB. Below this size ProxySQL buffers a result before it sends it to the client, and it pauses reading the backend when it has buffered 8 times this size. A worker thread of ProxySQL stays in the row reads of a result until one of these stops it, so with the default a result of short rows keeps the thread from recording its heartbeat, and the watchdog aborts the whole process after `restart_on_missing_heartbeats` (default 10) missed heartbeats, ending the connections of every client. The size also bounds two features: a result larger than it is not stored in the query cache, and a failed statement is not retried once its result has started to reach the client.
- **CFG-35** `mysql-kill_backend_connection_when_disconnect`: `true`, the default. A catalog read that its budget stops (INT-115) returns without reading the rest of the result and closes its connection. A statement that is sending rows then ends with its closed backend under either value; a statement that sends nothing, such as a long scan or `SLEEP`, runs to its end under `false` and is killed at once under `true`. A runtime that can close the socket of a stopped read closes it, with no wait, when its kill fails or it has none; a connection that the catalog closes holds its place in `max_user_connections` until the server ends that thread, which the server announces to no one, so a reopen that the limit refuses within 2 s of that close is tried again until those 2 s end (a timer, for want of any notice; within 40 ms measured). A connect that follows no close of that catalog fails at once. A budget stop that closed the connection attempts no rollback, and its error is `CATALOG_LIMIT` alone.

ProxySQL runs with its default multiplexing. ProxySQL keeps the `time_zone`, `sql_mode` and `max_execution_time` (on MariaDB `max_statement_time`) of each client connection and applies them on every server connection it uses for it. A statement that contains a user variable, `GET_LOCK`, or `CREATE TEMPORARY TABLE` makes ProxySQL keep that client connection on one server connection until it disconnects. On MySQL, `utils().setLocal` uses the user variable `` @`orm.<key>` `` and `utils().lock` uses `GET_LOCK`, so a connection that uses them is no longer multiplexed; results do not change.

Applying migration plans connects to the primary directly, not through a pooler: the apply holds the session-scoped MySQL `GET_LOCK` or PostgreSQL advisory lock ([plans](plans.md#apply)).
