# 코덱 — 컬럼 스타일의 읽기/쓰기 (S2)

- **COD-1** Go 데이터베이스 값 변환은 잘못된 형식, null, 범위 초과, 유한하지 않은 값, 지원하지 않는 값에 `CODEC_DECODE`를 반환한다. 모든 클라이언트에서 host 인코딩과 blind index는 host 단계 목록이 비었거나 값이 텍스트·바이트가 아니면 `CODEC_ENCODE`를 반환한다: host 단계는 텍스트의 UTF-8이나 받은 바이트를 받고 값을 그 종류대로 bind하므로, 정수·실수·bool은 평문이 아니다(`tests/codec/codec.json`의 case `host_values_by_kind`). SQL NULL은 host 단계를 SQL NULL로 지난다. `aes`, `hex`, `ip`가 아닌 style은 `serialize` 같은 codec style을 포함해 값이나 cell을 읽기 전에 `CODEC_UNSUPPORTED`를 반환하고, hex가 아닌 `hex` cell과 header, nonce, tag보다 짧은 `aes` cell은 `CODEC_DECODE`를 반환한다(case `host_stage_errors`). 생성 모델이 읽은 값을 그 타입으로 변환하지 못한 모델 컬럼은 변환의 code와, 변환 message 앞에 entity와 컬럼을 적은 message로 실패하며, 이 텍스트는 모든 클라이언트에서 같다: `<CODE>: <entity>.<column>: <message>`, COD-41의 형태이다. 변환 message는 모든 클라이언트에서 컬럼 타입마다 한 텍스트이며 host 타입도 값도 적지 않는다: `i16 cell is not an exact integer in its range`(`i32`, `i64`도 같다), `f64 cell is not a finite number`, `bool cell is not boolean`, `decimal cell is not a decimal of its precision and scale`, `date cell is not a date`(`datetime`, `time`도 같다), text가 아닌 셀에는 `varchar cell is not text`(`text`, `uuid`도 같다), bytes가 UTF-8이 아닌 셀에는 `text is not valid UTF-8`(COD-69), `bytes cell is not bytes`, `non-null column received SQL NULL`. 예를 들면 `CODEC_DECODE: typed_value.wide: i64 cell is not an exact integer in its range`이다. 행 조립은 오류를 호출자에게 반환하고 insert는 쓰기 전에 대입 필드를 검증한다. 빈 바이트 배열은 SQL NULL과 구분한다. scalar 집계 변환은 유효한 십진수를 가장 가까운 유한 binary64 값으로 받는다.

- **COD-2** `polyspec-orm` Python 패키지는 ORM 디코딩 전에 PyMySQL `DECIMAL`/`NEWDECIMAL` 및 psycopg `NUMERIC` 셀을 정확한 십진 텍스트로 등록한다. 생성된 `decimal(P,S)` 필드는 MySQL, PostgreSQL, SQLite에서 십진 문자열을 받고 소수부 자릿수가 정확히 `S`개인 십진 문자열을 반환한다. `P`는 1부터 18까지, `S`는 0부터 `P`까지이며 각 스키마 빌더는 이 범위 밖의 선언을 거부한다. 0으로 채운 뒤 전체 자릿수는 `P`개 이하이며 소수부 자릿수는 정확히 `S`개다. 이진 부동소수점 값은 decimal 필드 입력이 아니다. 잘못된 십진수, 초과한 정밀도·소수부 자릿수, 정확히 디코딩할 수 없는 데이터베이스 값은 쓰기에서 `CODEC_ENCODE`, 읽기에서 `CODEC_DECODE`로 실패한다. `CODEC_ENCODE`의 텍스트는 `decimal: <reason>`이고, 이유는 `invalid precision or scale`, `invalid text`, `fraction exceeds scale`, `value exceeds precision`, `value exceeds the scaled integer range` 중 하나다. 읽은 cell은 COD-1의 거부 `decimal cell is not a decimal of its precision and scale`이다. 둘 다 값을 적지 않는다(INT-163). SQL NULL은 구분한다. 이 필드의 정확한 값 기준은 scalar `sum`·`avg`의 유한 binary64 결과 기준을 바꾸지 않는다.

- **COD-3** 컬럼 스타일은 매니페스트 `styles: [...]`에 **쓰기 순서**로 기록된다(`gz_*` → `["serialize","gz"]`: 직렬화한 뒤 압축). 읽기는 역순.
  `aes`·`hex`·`ip`는 host stage이고 나머지는 실행기 codec이다. Go·PHP·Rust·TypeScript·Python은 같은 인증된 AES v2 형식과 정규화 값을 사용한다. 결정적 encoding은 모든 client에서 byte가 같다.

### Blind index

- **COD-4** `%% blind_index <table> <aes_column> <index_column>`은 AES column의 equality search column을 선언한다. 대상은 nullable 상태가 일치하고 single-column index로 선언된 `char(64)`/`string` 또는 `bytes` column이어야 한다. 여러 AES column이 같은 대상을 선언할 수 있다. request가 대상을 직접 할당하면 그 할당을 사용한다. 직접 할당하지 않은 대상은 할당된 AES source 하나만 계산할 수 있으며, 같은 대상을 계산하는 서로 다른 source를 할당하면 값과 관계없이 `IR_INVALID`이다. 이 규칙은 insert의 `set`과 `on_duplicate`에 각각 적용한다. insert와 update에서 runtime은 `secrets.blind_index`를 key로 사용한 lowercase HMAC-SHA256(plaintext)을 대상에 저장한다. AES column의 equality와 `IN` predicate는 대상 column을 사용하며 ciphertext를 비교하지 않는다. blind-index key는 AES key version과 분리되며 이 directive가 있으면 필수다.

### AES v2

- **COD-5** `aes`는 `ORM-AES2\0 || nonce || ciphertext || tag`를 저장한다. nonce는 12바이트 random 값이고 tag는 AES-256-GCM 인증 tag다. associated data는 `ORM-AES2\0`이다. AES key는 SHA-256(`polyspec/orm/aes-256-gcm/v2\0`와 설정 key bytes의 결합)이다. `aes_hex`는 AES 처리 후 uppercase hex를 적용한다.

- **COD-6** 모든 AES column은 같은 entity의 non-null integer `aes_key_version` column을 가진다. 새 write는 `secrets.aes_version`을 사용한다. read는 row에 저장된 version으로 `secrets.aes_keys[version]`을 선택한다. read의 각 node, 곧 root와 join한 각 row는 자기 row에 저장된 version을 쓰므로, 부모와 다른 version으로 저장된 join row도 자기 key로 decrypt된다. version이 없거나 인증에 실패하면 작업을 중단하며, 이 실패의 코드는 COD-44와 COD-47부터 COD-60까지가 정한다. runtime은 이전 ECB 형식을 decode하지 않는다.

### 암호화한 JSON 값 {#encrypted-json-value}

- **COD-7** `ordered_json aes` 단계를 가진 blob 컬럼은 AES v2로 암호화한 JSON 값을 저장한다. `ordered_json` 단계가 ordered-json 텍스트를 쓰고 `aes`가 그 텍스트를 암호화한다. 읽기는 셀을 복호화하고 모든 `ordered_json` 단계와 같이 텍스트의 ordered-json 값을 반환한다([값 모델](#value-model) 참고). 이 값은 멤버 순서, 숫자 텍스트, 빈 객체와 빈 배열의 구분을 유지하므로 `1.50`은 `1.50`으로 반환된다. 엔티티는 non-null integer `aes_key_version` 컬럼을 선언한다.

```text
dbspec 1 example

table service_config {
  seq i64 identity
  aes_key_version i32
  config bytes
  primary key (seq)
  settings {
    codec config ordered_json aes
    aes_version aes_key_version
  }
}
```

- **COD-8** 키는 연결 설정에서 받는다. Go `orm.Config`는 `AESKey`, `AESVersion`, `AESKeys`, PHP `Config`, TypeScript 연결 옵션, Python 연결 옵션은 `aesKey`, `aesVersion`, `aesKeys`, Rust `polyspec_orm::Config`는 `aes_key`, `aes_version`, `aes_keys`를 사용한다. 쓰기는 현재 version의 키 `AESKeys[AESVersion]`로 암호화하고 그 version을 `aes_key_version`에 기록한다. `AESKey`는 그 키이며 키 목록에 그 키가 있으면 생략할 수 있고, 그 키와 다른 `AESKey`는 연결을 `CONFIG`로 실패시킨다. 양수가 아닌 현재 version, 현재 version이 없는 키 목록, 양수가 아닌 version이나 빈 키를 담은 키 목록도 연결을 `CONFIG`로 실패시키며, 이 실패들은 어느 것도 database를 열지 않는다. 그 텍스트는 version을 적지 않는다(INT-163). 목록과 다른 키는 `aes key differs from the key list at the current version`, 양수가 아니거나 목록에 없는 현재 version은 `aes current version is not declared`, 잘못된 목록은 `aes key list holds an invalid version or an empty key`이다(COD-44). Go `AESVersion`의 zero value는 version이 없는 것이므로 1을 고른다. 읽기는 저장된 version의 키를 선택한다. `utils().aes().rotate(model, keyring)`는 version이 keyring의 현재 version과 다른 모든 행을 다시 암호화한다. `jsontext` 컬럼은 `ordered_json` 단계만 받으므로 암호화한 JSON 값은 항상 blob 컬럼이다. 감사 변경 행은 AES 컬럼을 평문이나 암호문이 아닌 `{"redacted": true, "present": true}`로 기록한다. 빈 AES 키는 암호화와 복호화에서, 빈 blind index 키는 색인을 계산할 때 모든 client에서 `CONFIG`로 실패한다. 유효하지 않은 ciphertext는 `CODEC_DECODE`로 실패하며 다른 키는 시도하지 않는다.

- **COD-9** `ordered_json` — 쓰기(값 → 저장 바이트): 공통 값 모델의 ordered-json 텍스트; 읽기(저장 바이트 → 값): ordered-json 파싱; 기준: tag `v0.0.9`의 ordered-json `0.0.9`; Go는 packages/go/go.mod가 요구하는 version(`v0.0.9`)의 module `github.com/polyspec/ordered-json/packages/go`를, Rust는 그 tag의 `packages/rust/Cargo.toml` package를 사용하고, PHP와 TypeScript는 version `0.0.9`를 선언하며 저장소 root의 composer.json과 package.json이 그것을 GitHub release `v0.0.9`의 Composer zip과 npm archive에서 받는다
- **COD-10** `serialize` — 쓰기(값 → 저장 바이트): PHP serialize; 읽기(저장 바이트 → 값): PHP unserialize; 기준: `serialize` / `unserialize`
- **COD-11** `base64` — 쓰기(값 → 저장 바이트): 앞 stage가 쓴 byte의 base64; 읽기(저장 바이트 → 값): base64_decode; 기준: `base64_encode` / `base64_decode`
- **COD-12** `gz` — 쓰기(값 → 저장 바이트): 앞 stage가 쓴 byte의 zlib, level 9; 읽기(저장 바이트 → 값): method가 deflate(RFC 1951)인 RFC 1950의 어떤 zlib stream이든 그 압축 level flag(`78 01`, `78 5e`, `78 9c`, `78 da`)와 block 종류(stored, fixed Huffman, dynamic Huffman)에 관계없이 zlib inflate; 기준: `gzcompress(…, 9)` / `gzuncompress`
- **COD-13** `yaml` — 쓰기(값 → 저장 바이트): YAML 1.2 문서; 읽기(저장 바이트 → 값): orm의 YAML reader(COD-74); 기준: 단일 문서와 공통 값 모델

### Stage 목록 {#stage-lists}

- **COD-14** 값을 byte로 바꾸는 것은 value stage(`ordered_json`, `serialize`, `yaml`)뿐이다. `base64`와 `gz`는 앞 stage가 쓴 byte를 변환할 뿐이므로 style `gz_*`는 목록 `['serialize','gz']`이고, `serialize`가 목록에 있어서 serialize한다. `['base64']`나 `['gz']`처럼 `base64`나 `gz`로 시작하는 목록은 어느 client에서도 serialize하지 않는다: 값은 string이고 stage는 그 UTF-8 text를 쓰며, 다른 값은 `CODEC_ENCODE`로 실패한다. SQL NULL은 SQL NULL로 남는다. 이런 목록을 읽으면 byte의 text가 되고, 올바른 UTF-8이 아닌 byte는 `CODEC_DECODE`로 실패한다. 빈 stage 목록은 string을 그대로 쓰고 cell을 그 text로 읽는다: 다른 값은 `CODEC_ENCODE`로, 올바른 UTF-8이 아닌 byte는 `CODEC_DECODE`로 실패한다(case `empty_stage_list`). 빈 cell은 `CODEC_DECODE`로 실패하지만 마지막 stage가 `base64`이거나 stage 목록이 비었으면 예외다: 그 encoder가 빈 text를 빈 cell로 쓰므로 `['base64']`나 `[]`로 저장한 `""`는 `""`로 읽히고, `['serialize','base64']`는 빈 cell을 `serialize` stage에서 거절한다. `ordered_json` cell은 JSON text이고 RFC 8259(8.1절)는 JSON text가 UTF-8이기를 요구하므로, 올바른 UTF-8이 아닌 cell은 `CODEC_DECODE`로 실패한다(case `ordered_json_text_is_utf8`). `tests/codec/codec.json`의 case `base64_text_*`, `gz_text_*`, `decode_base64_text_*`, `decode_gz_text_*`가 이 사례를 담는다.

## 값 모델 {#value-model}
- **COD-15** `ordered_json` 단계는 텍스트를 `jsontext` 컬럼에 저장한다. 이 컬럼은 세 데이터베이스에서 모두 텍스트이므로 저장한 텍스트를 적은 그대로 읽는다. `ordered_json aes` 단계는 암호화한 텍스트를 blob 컬럼에 저장한다([암호화한 JSON 값](#encrypted-json-value) 참고). 데이터베이스 안에서 질의하는 데이터는 컬럼이나 자식 테이블로 만들며, ORM에는 JSON 경로 조건과 JSON 인덱스가 없다.

- **COD-16** 스타일 컬럼의 타입은 "JSON형 값"이다: null · bool · 정수(i64) · 유한 실수(f64) · 문자열 · 리스트 · 문자열 키 맵. 유한하지 않은 실수(serialize의 `d:NAN;`, `d:INF;`, `d:-INF;` 등)는 값이 아니며 `CODEC_DECODE`를 반환한다. `ordered_json` 단계는 모든 클라이언트에서 ordered-json 값으로 읽으며, 이 값은 객체 멤버 순서와 숫자 텍스트를 보존하고 빈 객체와 빈 배열을 구분한다. 쓰기는 이 값을 받아 텍스트를 그대로 저장한다. ordered-json 값은 첫 `ordered_json` 단계만 쓴다: 다른 첫 단계(`serialize`, `yaml`, `gz`, `base64`) 아래에서는 모든 클라이언트에서 `CODEC_ENCODE`를 반환한다(`tests/codec/codec.json`의 case `ordered_json_value_stages`). 모든 클라이언트에서 모델의 JSON 출력은 각 ordered-json 값을 값 스타일 컬럼의 바깥 표현 안에 저장한 텍스트로 쓰며 멤버 순서와 숫자 텍스트를 바꾸지 않는다. 언어의 JSON 인코더가 저장한 텍스트를 쓸 수 없으면 클라이언트는 자체 메서드로 출력을 쓰고 인코더는 실패한다. PHP `json_encode`는 ordered-json 값을 가진 행에서 `CODEC_ENCODE`로 실패하고 `toJson()`이 출력을 쓴다. TypeScript `toJSON`은 저장한 멤버 순서로 값을 다시 만들고 각 스칼라를 저장한 텍스트의 `JSON.rawJSON`으로 반환한다. JavaScript가 `"1"` 같은 멤버 키의 순서를 바꾸거나 저장한 키 텍스트가 키의 `JSON.stringify`와 다르면 `CODEC_ENCODE`로 실패하며, `toJSONText()`는 모든 경우에 정확한 텍스트를 쓴다. Rust serde 직렬화는 출력을 serde_json raw value로 쓰며 serde_json serializer는 이를 그대로 쓴다. Python `json.dumps`는 모델을 인코딩할 수 없어 `TypeError`로 실패한다. 모델과 `Collection`의 `to_json_text()`가 출력을 쓰며, 멤버는 `to_array()`의 행 순서를 따르고 다른 값은 `JSON.stringify`가 쓰는 대로 쓰므로, 같은 행에 대해 TypeScript `toJSONText()`와 같은 텍스트를 쓴다. `bytes`나 유한하지 않은 수처럼 JSON으로 쓸 수 없는 값은 `CODEC_ENCODE`로 실패한다. 배열 출력은 표에 적었다. 다른 스타일은 공통 값 모델을 사용한다.
- **COD-62** Go는 i64 범위보다 큰 정수를 uint64로, Rust는 serde_json u64로, TypeScript는 bigint로, Python은 int로 담는다. 그런 정수를 `serialize`나 `yaml`로 쓰면 `CODEC_ENCODE`를 반환한다. 공통 value model은 i64 정수만 담기 때문이다(COD-16). PHP와 PHP 확장의 정수는 i64이고, PHP는 그보다 큰 정수 literal을 float로 읽으므로, 그런 정수를 담는 PHP 값은 없고 이 규칙에는 PHP case가 없다. recipe `tests/codec/codec-integer-beyond-i64.json`이 그 case를 담는다.
- **COD-63** Go는 bytes를 `[]byte`로, PHP와 PHP 확장은 `Bytes`로, TypeScript는 `Uint8Array`로, Python은 `bytes`로 담는다. bytes는 공통 value model의 값이 아니므로(COD-16), bytes 값이나 그것을 담은 list·map을 `ordered_json`, `serialize`, `yaml`로, 첫 `gz`나 `base64` 단계로, 또는 빈 stage 목록으로 쓰면 `CODEC_ENCODE`를 반환한다. Rust codec 쓰기의 값은 serde_json 값이고 serde_json 값은 bytes를 담지 않으므로, 이 규칙에는 Rust case가 없다. recipe `tests/codec/codec-bytes-value.json`이 그 case를 담는다.
- **COD-64** Go는 올바른 UTF-8이 아닌 text를 `string`으로, PHP와 PHP 확장은 `string`으로, TypeScript는 짝 없는 surrogate를 가진 text를 `string`으로, Python은 `str`로 담는다. 그런 text는 Unicode scalar 값의 열이 아니고 JSON text는 그 열이므로(RFC 8259, 8.1절), 그것을 `ordered_json`으로 쓰면 COD-70의 규칙 `text-unicode`인 `CODEC_ENCODE: json: the text is not a sequence of Unicode scalar values`를 반환한다. ## 사례
- **COD-30** ordered-json은 빈 객체와 빈 리스트를 구분한다. `{}`는 모든 client에서 파싱·인코딩·반복 왕복 후에도 객체로 유지되고, `[]`는 배열로 유지된다.
- **COD-31** Rust는 SQL NULL을 `Val::Null`로, 빈 텍스트를 `Val::Str("")`로 읽는다. 빈 텍스트를 `ordered_json` 단계로 디코딩하면 `CODEC_DECODE`를 반환한다.
- **COD-32** SQL NULL, JSON 리터럴 null, 조회하지 않은 값 스타일 컬럼은 저장값, getter, 행 배열, 모델 JSON 출력에서 구분한다. 조회하지 않은 컬럼을 요청하면 `COLUMN_UNSELECTED`를 반환한다.
- **COD-33** `ordered_json`은 `[]`, `{}`, `0`, `""`를 보존한다. 파싱 실패는 `CODEC_DECODE`를 반환한다.

- **COD-35** YAML 파싱·값 모델 오류는 `CODEC_DECODE`, YAML 인코딩 오류는 `CODEC_ENCODE`를 반환한다. 첫 위치가 아닌 value 단계(`ordered_json`, `serialize`, `yaml`)는 `CODEC_UNSUPPORTED`를 반환하며, COD-3의 어떤 단계도 아닌 style도 같다. 모든 클라이언트에서 쓰기와 읽기 모두, 값이나 cell을 읽기 전에 그렇다; `tests/codec/codec.json`의 case `encode_style_errors`가 둘을 담는다.
- **COD-36** 문자열 길이는 바이트 길이를 쓴다. 한 값의 `gz` 바이트는 COD-12의 zlib stream 안에서 구현마다 다를 수 있으므로, `gz`는 왕복한 값이 같음을 보장하고 모든 클라이언트는 다른 모든 클라이언트의 stream을 읽는다.

## 디코딩은 정확하다 {#decoding-is-exact}
- **COD-37** 저장 셀은 인코더의 출력이므로, 읽기는 모든 클라이언트와 모든 데이터베이스에서 인코더가 쓰는 형태의 셀만 디코딩한다. 인코더는 `base64`를 padding을 붙인 표준 알파벳으로, padding bit는 0으로, 공백이나 줄바꿈 없이 쓰고, `hex`는 대문자 hex 숫자로만 쓰며, 그 둘레에 어떤 문자도 쓰지 않는다. 그래서 `base64`나 `hex` 단계는 그 밖의 형태에서 `CODEC_DECODE`로 실패한다: 둘레나 안쪽의 모든 종류의 공백(space, 줄바꿈, form feed, NUL, U+001C 같은 information separator, byte order mark), 빠진 padding 문자, 0이 아닌 padding bit, 알파벳 밖의 문자. 어떤 클라이언트도 디코딩 전에 문자를 잘라 내거나 건너뛰지 않는다. 이유는 다음과 같다.

  - 둘 이상의 저장 형태에서 디코딩되는 값은 왕복하지 않는다. 다시 인코딩하면 다른 바이트를 쓰므로, 읽기가 저장 셀이 ORM이 쓰는 것과 다르다는 사실을 감춘다.
  - 언어마다 trim이 지우는 문자 집합이 다르다(예를 들어 Go와 Python은 form feed를, PHP는 NUL을, JavaScript는 byte order mark를 지운다). 그래서 너그러운 읽기는 클라이언트마다 다른 셀을 받는다. 정확한 읽기만이 모든 클라이언트가 똑같이 구현하는 규칙이다.
  - 클라이언트가 모든 `hex` 셀을 디코딩하므로 이 규칙은 모든 데이터베이스에서 성립한다. MySQL `UNHEX`는 홀수 길이 text를 받고 공백이 있는 셀에 NULL을 내므로, 어떤 dialect도 `hex`를 SQL에서 읽지 않는다. 어떤 dialect도 `hex`를 SQL에서 쓰지 않는다: 모든 데이터베이스에서 클라이언트 인코더가 대문자 text를 쓰고, 모든 dialect는 저장된 셀을 그대로 읽어 host 디코딩에 넘긴다.

- **COD-38** `ip` 인코더도 쓰기 쪽에서 같은 규칙을 지킨다: 모든 클라이언트에서 주소의 정확한 text만 pack하고, 그 둘레나 안의 공백(space, tab, 줄바꿈, form feed, NUL, no-break space)은 모두 `CODEC_ENCODE`로 실패한다. `ip` column의 조건 값도 조건을 만들 때 같은 방식으로 거부한다. SQL에서 인코딩하는 dialect는 그 값을 NULL로 읽기 때문이다. 어떤 클라이언트도 입력을 trim하지 않는다. trim하면 두 입력이 같은 바이트로 저장되고 저장 값이 입력으로 읽히지 않기 때문이다. `tests/codec/codec.json`의 case `ip_*`가 이 사례를 담는다. `%eth0` 같은 zone은 주소의 일부가 아니므로 `CODEC_ENCODE`로 실패한다. `ip`는 IPv4 주소를 4 byte로, IPv6 주소를 16 byte로 pack하며, IPv4-mapped 주소(`::ffff:a.b.c.d`)도 MySQL `INET6_ATON`처럼 16 byte로 pack한다(MySQL 8.4는 `::ffff:10.0.5.9`를 16 byte `00000000000000000000FFFF0A000509`로 pack한다). 읽기는 그 byte의 RFC 5952 정규형 text를 돌려주며, 이 text는 `INET6_NTOA`처럼 IPv4-mapped 주소를 `::ffff:`와 점 십진 표기로 쓴다(5절); 다른 길이의 cell은 `CODEC_DECODE`다(case `ip_packs_and_reads`와 `decode_ip_*`).

- **COD-69** 모델의 `varchar`나 `text` column은 모든 클라이언트와 모든 데이터베이스에서 셀이 올바른 UTF-8일 때만 그 셀을 text로 읽는다. 올바른 UTF-8이 아닌 저장 text는 `CODEC_DECODE`와 message `CODEC_DECODE: <entity>.<column>: text is not valid UTF-8`로 실패하며, 어떤 클라이언트도 그 bytes를 돌려주거나 바꾸지 않는다. 그런 text를 돌려주면 runtime마다 읽는 값이 달라진다. string이 어떤 runtime에서는 bytes를, 다른 runtime에서는 Unicode scalar 값만 담기 때문이다(COD-64). SQLite는 그런 text를 저장하고 flowmark는 그것을 `{"text": base64}`로 돌려주므로(PRT-67), 각 클라이언트는 거기서 그 bytes를 읽는다. Python과 Rust는 UTF-8이 아닌 SQLite text를 그 bytes로 읽고, node:sqlite가 잘못된 각 sequence를 U+FFFD로 바꾸는 TypeScript는 text에 U+FFFD가 있는 statement를 각 text를 BLOB으로 cast해 다시 읽고 응답 전체를 그 읽기에서 가져온다. catalog 읽기도 그렇게 한다(INT-153). MySQL `utf8mb4` column은 strict mode에서 그 쓰기를 거부하고(`Incorrect string value`) PostgreSQL `UTF8` 데이터베이스도 거부하므로(`invalid byte sequence for encoding "UTF8"`), 둘에는 그런 text가 저장되지 않는다. recipe `conformance_verification`의 case `text_not_utf8_refused`가 이 경우들을 검사한다. COD-1의 host decode는 bytes를 이유로 평문을 거부하지 않는다: UTF-8인 평문은 그 텍스트로, 그 밖의 평문은 그 bytes로 반환하며(Go와 PHP 문자열은 bytes를 담는다), column 변환이 그것을 읽고 `varchar`나 `text` column은 위와 같이 거부한다(`tests/codec/codec.json`의 case `host_refusals`).

- **COD-39** `hex`는 대문자 hex 숫자만 받는다. 모든 인코더가 대문자를 쓰므로 소문자는 `CODEC_DECODE`다. 길이가 홀수이거나 대문자 hex 숫자가 아닌 바이트가 있는 `hex` 셀은 모든 클라이언트에서 하나의 메시지 `hex: odd length or non-hex input`으로 실패한다. Go는 다른 클라이언트가 host 디코딩을 공개하듯(PHP `Codec::hostDecode`, TypeScript `hostDecode`, Rust `codec::host_decode`, Python `host_decode`) `orm.HostDecode(raw, styles, aesKey)`를 공개한다. `aes`가 없는 목록에는 key가 필요 없다.

## 벡터 (`tests/codec`)
- **COD-40** `tests/codec/codec.json`은 codec recipe이며(docs/spec/feature-coverage.md FCV-2), 모든 recipe처럼 손으로 관리하고 검토하는 데이터이다. 모든 클라이언트가 자기 recipe helper로 그것을 실행한다. 그 encode case는 값을 encode하고 cell을 다시 값으로 decode하며, style의 encoding이 결정적인 곳에서는 cell을 spec이 정한 바이트와 비교한다. 그 decode case는 spec이 쓰는 쪽에 허용하는 형식마다(COD-12의 zlib stream, COD-29의 YAML 형식, serialize의 float text) 고정 cell을 주며, 모든 클라이언트는 각 cell을 그 값이나 오류로 decode해야 한다. 그래서 한 클라이언트가 쓴 것을 모든 클라이언트가 읽는다. 데이터베이스 왕복은 `tests/conformance`의 `codec_roundtrip`이 검사한다. PHP 확장 `polyspec_orm`은 `Polyspec\\Orm\\Codec`을 직접 선언하고 C로 구현한다(`packages/php-ext/src/codec.c`, PHP 클라이언트 `Codec.php`의 이식). 그래서 확장 lane은 PHP 클라이언트가 아니라 확장의 codec으로 recipe를 실행한다.

## 생성 코드
- **COD-41** 읽기: 실행기가 위치형 행을 읽은 직후 `assemble.columns[].styles`에 따라 각 셀을 디코드한다. 단계가 거부한 셀은 읽기를 `CODEC_DECODE`로 실패시키며, 그 메시지는 단계의 메시지 앞에 셀을 읽는 노드(조인된 노드 포함)의 엔티티와 열을 적어 모든 클라이언트에서 같은 텍스트 `CODEC_DECODE: <entity>.<column>: <message>`가 된다. 예를 들어 `CODEC_DECODE: author.aes_hex_email: hex: odd length or non-hex input`이다(`contracts/fixtures/model_queries/model_queries.json`의 사례 `a_refused_row_ends_the_read_and_keeps_the_connection`). 키가 없을 때의 `CONFIG`처럼 다른 코드의 실패는 자기 메시지를 그대로 유지한다. 읽기와 쓰기에서 단계의 메시지는 값도, 단계가 읽고 쓰는 데 쓰는 library나 YAML reader의 텍스트도 적지 않는다(INT-163). library나 YAML reader(COD-74)가 거부한 stream이나 값은 단계 자신의 텍스트로 적는다. 읽기에서는 `gz: bad zlib stream`, `base64: bad input`, `json: the cell is not JSON`, `yaml: the stream does not parse`이고, 쓰기에서는 `gz: the compression failed`, `json: the value has no JSON text`, `yaml: the value has no YAML text`, `aes: the encryption failed`이다. 주소가 아닌 텍스트는 `ip: the text is not an address`, 길이가 다른 cell은 `ip: the cell is not 4 or 16 packed bytes`이다. 단계의 규칙 위반은 COD-70의 그 규칙 텍스트 하나로 적으며 위치를 적지 않고, 오류는 library의 실패나 YAML reader의 error를 cause로 남긴다(COD-71).
- **COD-42** 쓰기: `set<Col>(v)`는 선언된 스타일을 사용해 런타임 `setStyled`를 호출하고 인코딩된 바이트를 바인드한다.
- **COD-43** 스타일 컬럼의 술어는 비교하는 대상이 값의 결정적 함수여서 매개변수가 저장된 것과 같을 때에만 동등 비교(`eq`, `not_eq`, `in`, `not_in`)를 한다. 술어 값은 그 컬럼의 host stage(`aes`, `hex`, `ip`, COD-3)만 거치고, 쓰는 값만 인코딩하는 executor codec은 거치지 않는다. 따라서 모든 단계가 host stage인 컬럼은 동등 비교를 한다: `hex`와 `ip`는 저장된 셀을 비교하고, `aes` 단계를 가진 컬럼은 chain에서 `aes`의 위치와 관계없이 값 자체의 HMAC인 blind index([COD-4](#blind-index))를 비교하며 무작위 nonce의 암호문은 비교하지 않는다. 그런 컬럼에 blind index가 선언되지 않았으면 동등 비교는 `IR_INVALID`로 실패한다. `ordered_json aes`처럼 executor codec을 하나라도 가진 컬럼은 `isNull`과 `isNotNull`만 받는다. 그 저장 형태와 blind index는 인코딩된 텍스트에서 나오는데 술어 값은 그 텍스트가 아니기 때문이다. 모든 validator가 이 한 규칙을 적용한다(`ir.OpAllowed`와 그 대응; planner case `planner_ip_hex_eq`, `planner_hex_eq`, `planner_aes_hex_eq`, `planner_hex_aes_eq`, `planner_ordered_json_aes_eq`).
- **COD-44** Go, PHP, PHP extension, TypeScript, Python, Rust 여섯 declared implementation의 read 경로는 key version과 stored version에 대해 하나의 오류 contract를 따른다. 선언되지 않았거나, 비었거나, 잘못된 key version은 `CONFIG`이고, 양의 i32 정수가 아닌 stored version은 `CODEC_DECODE`이며, 0이나 NaN으로 강제 변환하지 않는다. keyring은 현재 version보다 key 목록을 먼저 검사하며, 그 텍스트는 version을 적지 않는다(INT-163). 1보다 작은 version이나 빈 key는 `aes key list holds an invalid version or an empty key`, 목록에 없는 현재 version은 `aes current version is not declared`, 읽기나 rotation이 필요로 하는데 목록에 없는 version은 `aes version is not declared`, 양의 i32 정수 밖의 stored version은 `aes version is not a positive 32-bit integer`이다. 이 규칙은 PHP extension native codec coverage가 완료됐다고 주장하지 않는다.
- **COD-45** TypeScript는 추가 열(INT-160)의 정수를 safe integer, 즉 크기가 2^53 - 1 이하일 때에만 JavaScript number로 읽으며, 그래야 정확하다; bigint와 정확히 그 숫자로만 된 문자열은 같은 한계로 변환된다. 소수, 유한하지 않은 number, boolean, 빈 문자열이나 숫자가 아닌 문자열, 그리고 더 큰 값은 `CODEC_DECODE`로 실패한다; SQL NULL은 null로 남는다.
- **COD-46** 실패한 conformance vector는 원래 error를 cause로 담아 그 error를 보고하며, write vector는 runner가 주는 transaction 안에서 그 본문을 실행한다.
- **COD-47** 구현된 rotation 경로는 COD-44의 key-version 및 stored-version 오류 코드와 텍스트를 사용한다. rotation이 거부하는 stored version은 `CODEC_DECODE: aes version is not a positive 32-bit integer`이며 entity와 컬럼을 적지 않는다. rotation은 model row를 읽지 않기 때문이고, 읽기는 그것을 적는다(COD-41). rotation에서 단계가 거부한 cell도 마찬가지로 단계의 메시지만 적는다. 예를 들어 `CODEC_DECODE: hex: odd length or non-hex input`이다. 이 규칙은 현재 모든 implementation이 rotation을 제공한다고 주장하지 않는다.
- **COD-48** version cell이 없는 read row는 `INTERNAL`이다. 저장된 바이트가 아니라 client 불변식이 깨진 것이다.
- **COD-49** 정수가 아닌 text인 stored version은 read 경로에서 `CODEC_DECODE`이며, 강제 변환하지 않는다.
- **COD-50** 0인 stored version은 read 경로에서 `CODEC_DECODE`다. 0은 key version이 아니다.
- **COD-51** i32 범위를 넘는 stored version은 read 경로에서 `CODEC_DECODE`다. 받아들이는 stored version은 양의 i32 정수다.
- **COD-52** 선언되지 않은 정수인 stored version은 `CONFIG`이며, 연결의 비밀이 없는 경우다.
- **COD-53** 앞자리 0의 유무와 관계없이 양의 정수인 text로 쓰인 stored version은 그 version으로 decode된다.
- **COD-54** rotation 경로에서 0인 stored version은 `CODEC_DECODE`다. read 경로와 같다.
- **COD-55** client가 선택한 AES column이 없는 rotation row는 `INTERNAL`이다. client 불변식이 깨진 것이다.
- **COD-56** AES column에 version column이 없는 read plan은 `INTERNAL`로 실패하며, version을 가정하지 않는다.
- **COD-57** stored version이 keyring에 없으면 `CONFIG`이며, 단일 key로 대신하지 않는다.
- **COD-58** NULL이 아닌 AES 값의 NULL stored version은 `CODEC_DECODE`다.
- **COD-59** NULL AES 값과 NULL version은 read 경로에서 NULL이다. version을 읽지도 검사하지도 않으며, 오류가 없다.
- **COD-60** rotation은 NULL AES cell을 그대로 둔다. version이 무엇이든 재암호화할 저장 바이트가 없기 때문이다.
- **COD-61** PHP-extension 패키지 `polyspec/orm-php-ext`는 model row와 그룹 값의 date 컬럼을 PHP 라이브러리와 같이 읽는다(COD-1). 실제 날짜의 텍스트 `YYYY-MM-DD`는 그 날짜로 읽고, `2026-1-1` 같은 다른 모든 저장 값은 COD-1의 `CODEC_DECODE` `OrmException` `<entity>.<column>: <type> cell is not a <type>`를 던지며, 이 메시지는 값을 적지 않는다. 모든 runtime이 실행하는 recipe `conformance_verification`의 case `invalid_stored_dates_sqlite`는 SQLite date 컬럼의 정수와 텍스트 `2026-1-1`을 row 읽기와 그룹 값에서 읽고, case `invalid_stored_cells_sqlite`는 어떤 date 형식도 읽지 않는 텍스트와 실제 날짜가 아닌 날을 읽는다.

## 단계의 거부 {#stage-refusals}

- **COD-70** codec 단계, host 단계, blind index는 아래 표의 규칙으로 입력을 거부한다. 각 규칙은 code 하나와 텍스트 하나를 가지며, Go, TypeScript, Python, PHP, PHP 확장, Rust에서 같다(INT-163). 텍스트는 값을 적지 않는다: cell이나 호출자의 값, 입력이 담은 숫자·tag·종류, host 타입, 위치를 적지 않는다. library나 YAML reader가 알려 준 line, column, offset은 COD-71이 남기는 cause에만 있고 텍스트에는 없다. 텍스트는 규칙이 선언된 style 목록에 관한 것일 때만 style을 적으며, 이는 COD-41이 entity와 column을 적는 것과 같다. 오류는 `<code>: <text>`이고, 모델 행의 읽기는 텍스트 앞에 entity와 column을 적는다(COD-41). 한 입력에 여러 규칙이 해당하면 단계가 먼저 만나는 규칙이 오류다: 값이나 cell보다 style 목록이 먼저이고, `yaml`의 parse보다 stream 규칙(`yaml-utf8`, `yaml-printable`)이 먼저이며, 값, cell, stream의 node와 byte는 그 순서대로이고 각 문서는 다음 문서보다 먼저다. node는 그것이 시작하는 곳에서, 그것이 담은 어떤 node보다 먼저 만난다: 먼저 anchor와 tag를 적힌 순서대로, 다음으로 그 단계의 중첩 규칙을, 그다음 node 자신의 규칙을 만난다. 그래서 sequence나 map인 map key는 그 안의 node보다 먼저 `yaml-key-collection`이며, key가 `.inf`와 `*y`보다 먼저 시작하므로 `[.inf]: c`와 `[*y]: c`도 그렇고, 257단계의 list나 map은 그 안의 node보다 먼저 그 중첩 규칙이다. key는 그 값보다 먼저 만나며, 반복된 key는 앞의 key를 반복하는 key에서 만난다(`yaml-duplicate`, `serialize-duplicate`). alias는 anchor가 stream에 있든 없든 그것이 있는 곳에서 만나므로, alias 앞 node의 규칙, 예컨대 앞선 tag, 반복된 key, 유한하지 않은 float가 오류이고 `yaml-alias`가 아니다(`tests/codec/codec.json`의 case `yaml_rules_before_an_undefined_alias`). 중첩 규칙(`json-depth`, `json-depth-read`, `serialize-depth`, `serialize-depth-write`, `yaml-depth`, `yaml-depth-write`)은 가장 바깥 것을 1단계로 하여 경로의 list와 map을 세며, block이든 flow든 YAML sequence나 mapping, serialize `a` field가 각각 한 단계다: 중첩된 list 256개, 그리고 중첩된 list 256개 안의 scalar는 256단계이고 모든 단계가 이를 읽고 쓰며, 257단계의 list나 map은 거부한다. 더 적은 단계를 거부하는 runtime은 없고, 더 많은 단계에서 stack, recursion 한도, library의 실패가 다른 오류로 단계를 떠나지 않는다(COD-71). 규칙은 모든 runtime에서 성립한다. 마지막 열은 그 값이 규칙에 이를 수 없는 runtime과 그 이유를 적으며, 어떤 입력도 이르지 못하는 규칙도 그 runtime이 그곳에서 반환하는 오류다. recipe 값이 이를 수 있는 규칙마다 전체 텍스트를 가진 case가 있다. 모든 runtime이 실행하는 `tests/codec/codec.json`에, 또는 그 입력을 값으로 담는 runtime의 recipe에 있다: `tests/codec/codec-bytes-value.json`(COD-63), `tests/codec/codec-integer-beyond-i64.json`(COD-62), `tests/codec/codec-non-finite-value.json`(유한하지 않은 float, FCV-4의 `f64` wrapper, Go, TypeScript, Python, PHP, PHP 확장), `tests/codec/codec-raw-text.json`(byte가 UTF-8이 아닌 문자열, `text_hex` wrapper, Go, PHP, PHP 확장, COD-64), `tests/codec/codec-lone-surrogate.json`(짝 없는 surrogate를 가진 문자열, `text_code_points` wrapper, TypeScript와 Python, COD-64), `tests/codec/codec-map-keys.json`(key가 문자열이 아닌 map, `map_entries` wrapper, Go와 Python), `tests/codec/codec-styled-unset.json`(SQL NULL도 값도 아닌 styled 값, `styled_unset` wrapper, Go와 Python), `tests/codec/codec-undefined-member.json`(undefined인 member, `undefined` wrapper, TypeScript), `tests/codec/codec-json-depth.json`(값 단계마다 encode와 decode의 중첩 규칙, 모든 runtime). 값의 형태가 없다는 이유로 recipe를 떠나는 규칙은 없다: 한 runtime이 담고 JSON이 담지 못하는 값은 그것을 담는 runtime만 실행하는 FCV-4의 wrapper다.

- **COD-71** COD-70의 규칙이 만나는 library나 host의 실패는 그 규칙의 orm 오류이며, library의 실패를 cause로 남긴다: Go `Cause`(`errors.Unwrap`), TypeScript `ErrorOptions`의 `cause`, Python `raise ... from`(`__cause__`), PHP와 PHP 확장 `getPrevious()`, Rust `source()`. 모든 runtime에서 실패가 library의 것인 규칙은 `gz-stream`, `gz-compress`, UTF-8인 cell의 `json-cell`, `json-depth-read`, `json-text`, `yaml-text`, `aes-encrypt`, `aes-auth`이고, 그 규칙의 recipe step은 모두 `library_cause: true`를 적는다(FCV-4). `yaml-parse`는 line과 column을 적는 YAML reader의 error(COD-80)를, `yaml-read-back`은 그 읽기의 error를 모든 runtime에서 cause로 남기며, 그 recipe step도 `library_cause: true`를 적는다. PHP `gzuncompress`와 `openssl_decrypt`가 `false`를 반환하는 것처럼 결과로만 실패를 알리는 library 호출은 library가 결과 곁에 알리는 것, 즉 호출의 경고, zlib의 메시지, OpenSSL 오류 queue를 담은 예외를 cause로 남기며, library가 더 알리는 것이 없으면 호출의 이름을 담는다. `base64-input`, UTF-8이 아닌 cell의 `json-cell`, `text-utf8`, `serialize-string-utf8`, `serialize-int`, `serialize-float`, `serialize-string-length`, `serialize-array-length`는 runtime이 library 호출로 찾을 때 cause를 남긴다. TypeScript, Python, PHP가 `base64-input`의 형식을 검사하듯 자체 검사로 찾는 runtime에는 남길 실패가 없으므로, 그 recipe step은 cause를 적지 않는다. library나 host의 예외는 codec 호출 밖으로 나가지 않는다: COD-70 경로의 `UnicodeDecodeError`, `TypeError`, Node `crypto` 오류, Rust panic은 그 규칙의 오류다. struct field를 규칙이 거부한 Go 값은 그 규칙의 오류이며 field를 적지 않는다.
- **COD-72** 언제나 먼저 걸리는 COD-70 규칙 뒤에 있는 codec 단계의 guard에는 어떤 입력도 이르지 않으므로 제거한다: Go, TypeScript, Python, Rust의 decode guard `style <style> after a decoded value`는 `style-first` 뒤에 있다. cell을 값으로 바꾸는 것은 값 단계뿐이고 `style-first`가 그 단계를 목록의 처음에 두며, decode는 그것을 마지막에 적용하기 때문이다. encode가 쓴 텍스트가 UTF-8인지 보는 TypeScript 검사(`the text is not valid UTF-8`)는 `text-unicode` 뒤에 있다. writer는 `text-unicode`를 통과한 문자열만 encode하고, Unicode scalar 값의 UTF-8은 올바른 UTF-8이기 때문이다. PHP 확장의 guard `ip: the packed address is not valid`는 `ip-cell` 뒤에 있다. `inet_ntop`은 4 byte나 16 byte라면 어떤 것이든 그 텍스트를 쓰기 때문이다. `yaml` 읽기 경로에는 library가 없으므로 그 위에 YAML library의 guard도 없다: COD-74의 reader는 그 문법이 담지 않는 것을 `yaml-parse`로 거부한다(COD-80).
- **COD-73** 값 스타일 컬럼의 setter와 styled 값의 `payload()`는 모든 runtime에서 자기만의 codec 텍스트를 적지 않는다. setter는 styled 값이 아닌 값을 `CODEC_ENCODE: <column> requires StyledValue`로, nullable이 아닌 컬럼의 SQL NULL을 `CODEC_ENCODE: <column> does not accept SQL NULL`로 거부하며(COD-20), 컬럼 이름을 적고 host 타입은 적지 않는다. 그 밖의 값은 host 단계를 뺀 컬럼의 codec 단계로 그 단계의 `codec.encode`처럼 인코딩하고, 값이 처음 만나는 COD-70 규칙의 오류 `<code>: <text>`(텍스트 앞에 아무것도 붙이지 않는다)로, 모델을 바꾸기 전에 호출에서 실패한다. 쓰기는 값을 다시 인코딩하므로, setter 뒤에 바뀐 값은 어떤 statement도 보내기 전에 그 오류로 쓰기에서 실패한다. `payload()`는 SQL NULL만 `CODEC_DECODE: SQL NULL has no styled value`로 거부하고 저장된 값을 검사 없이 반환한다. 그 값의 모든 인코딩이 그것을 검사하기 때문이다. `contracts/fixtures/styled_column_states.json`의 case `setter_json_nesting_beyond_256_levels`, `setter_serialize_nesting_beyond_256_levels`, `setter_yaml_nesting_beyond_256_levels`, `setter_json_nesting_of_256_levels`가 setter와 전체 텍스트인 case의 `message`를 지키며, 각 runtime의 runner는 그것을 setter가 반환한 오류의 메시지와 비교한다. 어떤 runtime의 값도 그 입력을 담을 수 없는 case는 `unreachable` 멤버에 그 runtime과 이유를 적고, 그 runtime의 runner는 setter에 넘길 때처럼 입력을 만들 수 없음을 확인한다. 첫 stage가 `ordered_json`인 Rust column은 ordered-json 값을 담는데, 이 값은 JSON text로 만들어지고 256 level까지만 담는다. 그래서 `setter_json_nesting_beyond_256_levels` case에는 Rust 입력이 없고, Rust runner는 그 입력을 만드는 일이 깊이 때문에 실패하는지 확인한다. 모델의 JSON 출력(COD-16, COD-26)은 codec 단계가 아니다: JSON이 쓰지 못하는 것을 자기 규칙으로 거부하므로, `payload()`가 검사 없이 반환한 값이 다른 값으로 쓰이는 일은 없다.

## YAML reader {#yaml-reader}

- **COD-74** `yaml` 단계는 모든 runtime에서 COD-74부터 COD-80이 정의하는 orm의 YAML reader로 cell을 읽는다: Go, TypeScript, Python, PHP, Rust는 각자의 언어로, PHP 확장은 C로 이를 구현하며, 모든 runtime이 실행하는 recipe `tests/codec/codec.json`이 이들을 같게 유지한다. 읽기 경로에서는 어떤 library도 parse하지 않는다. library는 쓰기만 하고(`docs/operations/packaging.md`), library가 쓴 모든 text는 reader가 다시 읽으므로(`yaml-read-back`), reader가 거부하는 text나 다른 값으로 읽히는 text를 쓰는 library는 그 규칙으로 쓰기에 실패하며 runtime 사이의 차이를 남기지 않는다. reader는 YAML 1.2.2의 production `l-yaml-stream` [211]이 담는 stream을, YAML 1.2.2 5장부터 9장의 production을 그것이 적은 그대로 써서(괄호 안의 번호는 그 번호의 production이다) 받고, 그 stream이 문서 하나를 담을 때만 받는다. reader는 그 문서의 값을 core schema(10.3.2)에 따라 COD-29의 값 모델로 돌려준다. 문법이 담는 형식은 COD-29, COD-66, COD-70의 규칙이 거부하지 않는 한 읽으며, COD-75부터 COD-80은 그렇다고 적고 그 이유를 적은 곳에서만 문법을 좁힌다. 문법이 담지 않고 COD-70의 다른 규칙이 다루지 않는 stream은 `yaml-parse`이다.
- **COD-75** stream과 그 문서.
  - 규칙 `yaml-utf8`과 `yaml-printable`은 reader가 읽기 전에 stream 전체에 대해 성립하며(COD-66, COD-70), reader는 stream을 시작할 수 있는 byte order mark 하나 뒤의 문자를 읽는다. cell은 UTF-8이므로(COD-29) UTF-16과 UTF-32(5.2)는 읽지 않는다.
  - 줄바꿈은 CR LF, CR, LF이다(`b-break` [28]). scalar 내용 안에서는 각각이 LF 하나이다. NEL(U+0085), U+2028, U+2029는 내용 문자이며 줄바꿈이 아니다(5.4). stream의 마지막 줄에는 줄바꿈이 없어도 된다.
  - comment는 `#`부터 그 줄 끝까지이다([75]부터 [79]). comment는 제 줄에 따로 있거나 공백 뒤에 온다. 다른 문자 뒤의 `#`은 plain scalar 안에서는 내용이고([130]) 그 밖의 곳, 예컨대 quoted scalar, flow indicator, block scalar header의 indicator 바로 뒤에서는 `yaml-parse`이다. scalar 내용 밖에서 공백만 있는 줄은 comment 줄이다(6.6). tab이 든 줄도 그렇다. 예를 들어 block scalar 내용 뒤의 tab 한 줄은 comment 줄이고 그 내용을 끝내므로 `|\n a\n\t\n`은 `a\n`이다.
  - 문서는 bare이거나 directives end marker `---`([203])로 시작한다. 그 줄에서 `---` 뒤에는 공백과 그 문서의 node나 comment가 올 수 있다. 문서는 document end marker `...`([204], [205])로 끝날 수 있으며, 그 줄에서 `...` 뒤에는 공백과 comment만 올 수 있다. 줄의 시작에 있고 뒤에 공백, 줄바꿈 또는 stream의 끝이 오는 `---`와 `...`는 marker이며 결코 내용이 아니다(`c-forbidden` [206]). `---x`, `---#x`, `...x`는 plain 내용이다. block collection은 첫 entry가 줄을 시작하므로 `---`의 줄에서 시작하지 않는다(`s-l+block-collection` [200]): `--- a: 1`과 `--- - a`는 `yaml-parse`이고, `--- [a]`, `--- "a"`, `--- |`는 그 줄에서 node를 시작한다. `---`만 있는 문서는 null을 담는다(COD-29).
  - 문자가 comment, 공백, 줄바꿈, document end marker뿐인 stream에는 문서가 없으며 `yaml-no-document`이다.
  - 두 번째 문서는 그것이 시작하는 곳에서 만나는 `yaml-documents`이다: 첫 directive, 그 `---`, 또는 `...` 뒤에서 comment 줄, 공백만 있는 줄, 또 다른 `...`의 일부가 아닌 첫 문자이다. reader는 그 문서를 전혀 읽지 않으므로 `a\n---\n[`는 `yaml-parse`가 아니라 `yaml-documents`이다.
  - 첫 문서 앞이나 `...` 뒤에서 `%`로 시작하는 줄은 directive이고([82]), directive 뒤에는 그 `---`가 온다(`l-directive-document` [209]). 문서 안에서 줄의 시작에 있는 `%`는 내용이므로(9.1.2) `a\n%b`는 `a %b`이다. `%YAML 1.2`는 한 문서에서 한 번 읽으며, 한 문서의 두 번째 `%YAML` directive는 `yaml-parse`이다(6.8.1). version이 `1.2`라는 text가 아닌 `%YAML` directive는 `1.1`, `1.3`, `1.02`, `01.2`처럼 모두 `yaml-parse`이다: YAML 1.2.2는 processor에게 `%YAML 1.1` 문서를 1.2로, 더 높은 minor version의 문서를 경고와 함께 읽으라고 하는데, 코덱에는 경고가 없으므로 reader는 stream이 적은 version이 주지 않는 값을 아무 알림 없이 돌려주게 된다. `%TAG` directive(6.8.2)는 그 문법대로, 한 문서에서 handle마다 많아야 한 번 읽고 그렇지 않으면 `yaml-parse`이며, 모든 tag가 `yaml-tag`이므로 어떤 값도 바꾸지 않는다. 그 밖의 directive(`ns-reserved-directive` [83])는 `yaml-parse`이다: YAML 1.2.2는 processor에게 이를 경고와 함께 무시하라고 하는데, 경고 없이 stream의 지시를 무시하는 것은 입력을 조용히 버리는 것이다.
- **COD-76** 들여쓰기와 block collection.
  - 들여쓰기는 공백(space)뿐이다(`s-indent` [63]). tab은 결코 들여쓰기가 아니다: 문법이 들여쓰기를 읽는 곳에서 tab은 들여쓰기를 끝내므로, tab 뒤에서 block node가 시작될 줄은 `yaml-parse`이다(6.1). 들여쓰기 뒤와 indicator `-`, `?`, `:` 뒤에서 tab은 공백처럼 구분하므로(`s-separate-in-line` [66]) `-\ta`는 `[a]`이고 `a:\tb`는 `{a: b}`이다. indicator의 줄에 있는 compact collection은 공백으로만 들여쓰므로(`s-l+block-indented` [185]) `-\t- a`는 `yaml-parse`이다. scalar 내용 안의 tab은 내용이다.
  - node는 그 부모보다 더 들여쓰며, 한 collection의 entry는 한 들여쓰기를 함께 쓴다(6.1). 문법이 entry를 읽는 곳에서 다른 들여쓰기의 줄은 `yaml-parse`이다. 문서의 node는 부모가 -1칸에 있으므로 0부터 어느 column에서든 시작한다(9.1.3).
  - block sequence([183]부터 [186])는 entry `-`들이며, 각 `-` 뒤에는 공백, tab, 줄바꿈 또는 stream의 끝이 온다. `-x`는 plain scalar `-x`이다. entry는 부모보다 몇 칸이든 더 들여쓰며, mapping key의 값인 sequence는 그 key의 들여쓰기에도 설 수 있다(`seq-space` [201]). sequence의 entry 안에서는 그럴 수 없다. entry는 그 줄이나 `-`보다 더 들여쓴 다음 줄들의 node, 그 줄의 compact sequence(`- - a`), 그 줄의 compact mapping(`- a: 1`, 다른 key는 `a`의 column에 선다), 또는 아무것도 없음, 곧 null을 담는다.
  - block mapping([187]부터 [195])은 implicit entry와 explicit entry를 담는다. implicit key([192]부터 [194])는 한 줄에 있다: plain, single-quoted, double-quoted scalar 또는 flow collection이며, 그 줄에서 뒤에 `:`와 공백, 줄바꿈 또는 stream의 끝이 온다. key는 그 첫 문자부터 `:`까지 많아야 1024 Unicode 문자이다([154], [155]). `:` 앞에서 여러 줄에 걸치거나 그보다 많은 문자인 node는 key가 아니다. block mapping에서 값은 quoted key 뒤라도 결코 `:`에 붙지 않는다: `"a":b`는 `yaml-parse`이다(8.2.2). 값은 key의 줄, key보다 더 들여쓴 다음 줄들, 또는 key의 들여쓰기에 있는 block sequence이며, 없으면 null이다. `: a`처럼 빈 key는 빈 plain scalar, 곧 null이며 `yaml-key-scalar`가 거부한다.
  - explicit entry([189]부터 [191])는 `?` 뒤에 key를, `?`의 들여쓰기에서 줄을 시작하는 `:` 뒤에 값을 담는다. 각각은 block-indented node(`s-l+block-indented` [185])로, indicator의 줄이나 다음 줄들의 node, 또는 그 줄의 compact collection이다. `:` 줄이 없는 entry의 값은 null이다. COD-66의 writer가 그런 key를 쓰며, `? a\n: - b`는 `{a: [b]}`이다. `? a: 1`, `? - a`, `? [a]`처럼 collection인 key는 `yaml-key-collection`이고, key가 compact mapping `{a: b}`인 `? a : b`도 그렇다.
  - block collection 안의 flow node(`s-l+flow-in-block` [197])는 첫 줄 뒤의 모든 줄에서, 닫는 괄호를 포함하여, 부모 block collection보다 더 들여쓴다: `a: [\n b\n]`는 `yaml-parse`이고 `a: [\n b\n ]`는 `{a: [b]}`이다. 문서의 node는 부모가 -1칸에 있으므로 `[\nb\n]`는 `[b]`이다.
- **COD-77** flow collection([137]부터 [161]).
  - flow sequence `[...]`와 flow mapping `{...}`는 중첩 규칙까지 서로 안에 중첩된다. entry는 `,`로 구분하며, 마지막 entry 뒤에 `,` 하나가 올 수 있다(7.4). `[,]`, `[a,,b]`, `{,}`처럼 앞에 entry가 없는 `,`는 `yaml-parse`이다. `[]`와 `{}`는 비어 있다.
  - flow collection은 여러 줄에 걸칠 수 있다: 공백, 줄바꿈, comment 줄이 token을 구분하며(`s-separate` [80]), 첫 줄 뒤의 각 줄은 COD-76이 적은 대로 들여쓴다. flow collection 안의 plain scalar는 `,`, `[`, `]`, `{`, `}`를 담지 않는다(`ns-plain-safe-in` [129]).
  - flow mapping의 entry는 key, `:`, 값이거나, 값이 null인 key 하나(`{a}`는 `{a: null}`), 값이 있는 빈 key(`{: a}`, null key, `yaml-key-scalar`), 또는 `?` 뒤의 explicit entry이다. flow mapping entry의 key는 그 scalar 형식이 허용하는 대로 여러 줄에 걸칠 수 있고([145]) 길이 제한이 없다. plain key 뒤의 `:` 뒤에는 공백, 줄바꿈, flow indicator 또는 collection의 끝이 오며([147]), 그렇지 않으면 `:`는 plain scalar의 일부이다: `{a:b}`는 `{"a:b": null}`이고 `{a: b}`는 `{a: b}`이다. quoted scalar나 flow collection인 key 뒤에서는 값이 `:`에 붙을 수 있다([148], [149]): `{"a":b}`는 `{a: b}`이다.
  - flow sequence의 entry `k: v`는 YAML 1.2.2가 읽는 대로 그 pair 하나의 map이며(`ns-flow-pair` [150]) 중첩 규칙의 한 level이다: `[a: 1, b]`는 `[{a: 1}, b]`이고, `[? a : 1]`은 `[{a: 1}]`이며, `[: a]`는 null key의 pair, 곧 `yaml-key-scalar`이다. 그 implicit key는 block mapping에서처럼 많아야 1024 문자의 한 줄이므로([152]부터 [155]) `[a\n b: c]`는 `yaml-parse`이다(Example 7.22).
- **COD-78** scalar.
  - plain scalar([126]부터 [135])는 indicator([22])가 아닌 문자로 시작하거나, 공백이 아니고 flow collection 안에서는 flow indicator도 아닌 문자가 뒤따르는 `-`, `?`, `:`로 시작한다. 공백이 뒤따르는 `:`, 공백 뒤의 `#`, 그리고 flow collection 안에서는 flow indicator를 담지 않으며, 양 끝의 공백은 그 일부가 아니다. implicit key가 아닌 값으로서 plain scalar는 다음 줄들로 이어질 수 있고, 각 줄은 부모보다 더 들여쓰며 COD-75의 marker가 아니다. 줄들은 접힌다: text가 있는 두 줄 사이의 줄바꿈은 공백 하나이고, 빈 줄 k개가 뒤따르는 줄바꿈은 line feed k개이며, 각 줄바꿈 둘레의 공백은 내용이 아니다(6.5). `@`와 `` ` ``(`c-reserved` [21])는 scalar를 시작하지 않으며 그곳에서 `yaml-parse`이다.
  - single-quoted scalar([117]부터 [125])의 escape는 `'`를 나타내는 `''` 하나이며, plain scalar처럼 줄을 접는다.
  - double-quoted scalar([107]부터 [116])의 escape는 정확히 5.7의 것이다: `\0`(U+0000), `\a`(U+0007), `\b`(U+0008), `\t`와 tab이 뒤따르는 `\`(U+0009), `\n`(U+000A), `\v`(U+000B), `\f`(U+000C), `\r`(U+000D), `\e`(U+001B), 공백이 뒤따르는 `\`(U+0020), `\"`, `\/`, `\\`, `\N`(U+0085), `\_`(U+00A0), `\L`(U+2028), `\P`(U+2029), 그리고 대소문자 어느 쪽이든 hex 숫자 2개, 4개, 8개가 뒤따르는 `\x`, `\u`, `\U`로, 그 수의 code point이다. 다른 문자나 그보다 적은 hex 숫자가 뒤따르는 `\`는 `yaml-parse`이며(Example 5.14), surrogate(U+D800부터 U+DFFF)나 U+10FFFF보다 큰 수의 escape도 그렇다: 둘 다 Unicode scalar value가 아니므로 값 모델의 어떤 문자열도 담지 못하고(COD-64), YAML 1.2.2는 두 `\u` escape를 한 문자로 읽지 않는다. 줄 끝의 `\`는 그 줄을 다음 줄에 공백 없이 잇고 `\` 앞의 공백을 남긴다(`s-double-escaped` [112]). 다른 줄들은 plain scalar처럼 접힌다.
  - implicit key인 quoted scalar는 한 줄이다([110], [121]).
  - block scalar([162]부터 [182])는 literal `|` 또는 folded `>`이다. 그 header는 많아야 하나의 indentation indicator `1`부터 `9`와 많아야 하나의 chomping indicator(`-` strip, `+` keep, 없으면 clip)를 어느 순서로든 담고, 그 뒤 줄바꿈 앞에는 공백과 comment가 오거나 아무것도 오지 않는다. header 뒤에는 comment 줄이 오지 않으며(6.6), 그 줄의 다른 것은 `yaml-parse`이다. 내용 들여쓰기는 node 부모의 들여쓰기에 indentation indicator를 더한 것이거나, indicator가 없으면 내용 중 비어 있지 않은 첫 줄의 공백 수이며, 이는 부모의 들여쓰기보다 크다(8.1.1.1). 문서의 node는 부모가 -1칸에 있으므로 `--- |1`은 내용을 0칸에서 읽고 `--- |`는 그 줄들을 column 0부터 읽는다. 비어 있지 않은 첫 줄보다 공백이 많은 앞쪽의 빈 줄은 `yaml-parse`이다(Example 8.3). 내용은 비어 있지 않고 내용 들여쓰기보다 덜 들여쓴 첫 줄에서 끝나며, 문법은 그 줄을 scalar 뒤에 오는 것으로 읽는다. 내용 뒤의 comment 줄은 내용 들여쓰기보다 덜 들여쓴다([169]).
  - literal scalar는 내용의 각 줄바꿈을 남긴다. folded scalar는 6.5대로 줄을 접는다: text가 공백 없이 시작하는 두 줄 사이에서 줄바꿈은 공백 하나이고 빈 줄 k개가 뒤따르는 줄바꿈은 line feed k개이다. text가 공백이나 tab으로 시작하는 더 들여쓴 줄의 앞이나 뒤의 줄바꿈은 남으며, 그 곁의 빈 줄도 각각 남는다([175]부터 [181]). chomping(8.1.1.2): strip은 마지막 줄바꿈과 뒤쪽의 빈 줄을 버리고, clip은 마지막 줄바꿈을 남기고 뒤쪽의 빈 줄을 버리며, keep은 둘 다 남긴다. stream의 끝은 마지막 줄바꿈을 대신하므로, 끝에 줄바꿈이 없는 `|\n a`는 어느 chomping에서든 `a`이며, 빈 줄만으로 된 scalar는 strip과 clip에서 빈 문자열이고 keep에서는 그 줄마다 line feed 하나이다(Example 8.6).
  - quoted scalar나 block scalar의 값은 무엇을 담든 그 문자열이다: `'true'`와 `"1"`은 문자열이다. 빈 node(`e-node` [106])는 빈 plain scalar, 곧 null이다.
- **COD-79** resolution과 값.
  - plain scalar는 core schema(10.3.2)에 따라, 쓰인 대소문자 그대로, 그 text 전체가 맞는 다음 중 첫 번째로 resolve된다: `null`, `Null`, `NULL`, `~`와 빈 scalar는 null, `true`, `True`, `TRUE`, `false`, `False`, `FALSE`는 bool, `[-+]?[0-9]+`는 10진 정수, `0o[0-7]+`는 8진 정수, `0x[0-9a-fA-F]+`는 16진 정수, `[-+]?(\.[0-9]+|[0-9]+(\.[0-9]*)?)([eE][-+]?[0-9]+)?`는 float, `[-+]?(\.inf|\.Inf|\.INF)`와 `\.nan|\.NaN|\.NAN`은 유한하지 않은 float로 `yaml-non-finite`이고, 그 밖의 text는 문자열이다. 그래서 `0b101`, `-0x1`, `1_000`, `tRuE`, `yes`, `.nAn`, `2014-12-31`은 문자열이다.
  - 정수는 그 숫자와 부호의 정확한 정수이며(`07`은 7, `-0`은 0), i64 범위 밖의 정수는 `yaml-int-range`이다. float는 그 10진 text의 정확한 값에 가장 가까운 binary64이며 동률이면 짝수 쪽이다. 무한대로 반올림되는 float는 `yaml-non-finite`이고, 0으로 반올림되는 float는 부호를 지닌다(`-1e-400`은 -0.0).
  - map key는 문자열이다. 정수로 resolve되는 plain key는 그 값의 10진 text이며(`0x1F`는 `31`, `07`은 `7`, `+3`은 `3`, `-0`은 `0`), i64 범위 밖이면 `yaml-int-range`이다. null, bool, float(유한하든 아니든)로 resolve되는 plain key는 `yaml-key-scalar`이고, quoted scalar나 block scalar인 key는 그 문자열이며, sequence나 map인 key는 `yaml-key-collection`이다. 한 map에서 문자열이 같은 두 key는 두 번째에서 만나는 `yaml-duplicate`이며(COD-29), `<<`는 보통의 key이다(COD-29).
  - map은 member가 stream의 순서대로 놓인 object이고, sequence는 그 순서의 list이다.
  - node가 시작할 수 있는 곳에서 `&`는 `yaml-anchor`, `!`는 `yaml-tag`, `*`는 `yaml-alias`이며, 뒤에 무엇이 오든 그 문자에서 만난다: reader는 anchor 이름, tag, alias 이름을 읽지 않으며, `%TAG` directive의 tag handle은 어떤 tag도 읽을 수 있게 하지 않는다. plain scalar 안에서 세 문자는 내용이다(`a&b`, `a!b`, `a*b`).
  - `yaml-depth`는 block이든 flow든 각 sequence와 map을, compact collection과 flow sequence의 single pair를 포함하여, 가장 바깥의 것을 level 1로 하여 하나씩 셈한다(COD-70).
- **COD-80** 오류의 순서와 cause. reader는 stream을 그 순서대로 한 번 읽고, 처음 만나는 오류를 돌려준다(COD-70):
  - `yaml-parse`는 지금까지 읽은 문자가 문법의 어떤 stream의 시작도 더는 아니게 되는 첫 문자, 또는 stream의 끝에서 만난다.
  - node의 규칙은 node가 시작하는 곳에서 COD-70의 순서로 만난다: 그 anchor나 tag, 그 중첩 규칙, 그다음 node의 규칙이다. 그래서 collection인 key는 그 안의 어떤 node보다 먼저 `yaml-key-collection`이다. level 257에 있는 collection key는 `yaml-key-collection`보다 먼저 `yaml-depth`이다. scalar 내용의 규칙(`yaml-int-range`, `yaml-non-finite`, `yaml-key-scalar`, `yaml-duplicate`)은 reader가 그 scalar를 다 읽은 뒤 그 시작에서 만나므로, 잘못된 escape처럼 scalar 안에서 문법을 벗어나는 stream은 먼저 `yaml-parse`이다.
  - block mapping이나 flow sequence의 node가 implicit key라는 것은 COD-76과 COD-77의 1024 문자 안에서 그 줄의 뒤에 오는 `:`로만 알 수 있다. reader는 그 `:`를 찾아 node 너머를 미리 읽으며, 미리 읽기가 stream이 문법을 벗어나는 자리를 만나는 node는 key가 아니므로, 그 안의 node들의 규칙을 그 `yaml-parse`보다 먼저 순서대로 만난다: `[.inf]: c`는 `yaml-key-collection`이고 `[.inf, @]: c`는 `yaml-non-finite`이다. 문법이 key를 요구하는 곳(block mapping의 첫 entry 다음 entry 등)에서 read ahead가 `:` 없이 끝나는 node도 같다. 그 node는 key가 아니므로, stream이 문법을 벗어나는 곳의 `yaml-parse`보다 먼저, 그 node와 그 안의 node의 규칙을 key가 아닌 node의 규칙으로 만난다. 그래서 `a: 1\n.inf\n`과 `a: 1\n[.inf]\n`은 `yaml-non-finite`이다. flow mapping에서 entry를 시작하는 모든 node는 그 key이며, 시작하는 곳에서 그것이 정해진다.
  - `yaml-parse`의 cause(COD-71)는 stream이 문법을 벗어나는 자리의 line과 column을 적는 reader의 error이며, 둘 다 1부터 세고 column은 Unicode 문자로 세며 byte order mark는 세지 않는다. 오류의 텍스트는 위치를 적지 않는 `yaml: the stream does not parse`이며(COD-70), 어떤 runtime도 그 cause를 다른 runtime의 것과 비교하지 않는다.
