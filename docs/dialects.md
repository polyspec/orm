# SQL dialects

A SQL dialect is the SQL syntax and execution rule set for one database system. In this project, `mysql`, `postgres`, and `sqlite` select identifier quoting, placeholders, type mapping, write syntax, and supported SQL functions. The planner asks the selected SQL dialect for every database-specific part; the IR and plan format do not change.
Executors still see the same plan shape: steps, bind slots, assemble.

Executor consequences: a `$n` renumbering step when expanding relation IN lists on
PostgreSQL, host-side AES/inet codecs where the table says "client-side", one DSN/driver per database
(Go: `pgx` stdlib / `modernc.org/sqlite`; Rust: sqlx features; PHP: `pdo_pgsql` / `pdo_sqlite`).

**Go driver packages.** `clients/go/orm` links MySQL only. A program that opens PostgreSQL or SQLite
imports the matching package for its side effect, as it would a `database/sql` driver:

```go
import (
    _ "github.com/polyspec/orm/clients/go/orm/pg"      // driver "postgres"
    _ "github.com/polyspec/orm/clients/go/orm/sqlite"  // driver "sqlite"
)
```

Without it `orm.Open` returns `CONFIG` naming the import. The split keeps a MySQL-only binary at
4.6MB instead of 11MB and avoids SQLite's package init (it parses `/etc/services`). Rust does the
same with sqlx features, PHP with the PDO extension that is installed.

## Rules that keep the three databases identical
- `UPDATE` always assigns the entity's updated timestamp explicitly (`updated_ts = CURRENT_TIMESTAMP(6)` on MySQL, `CURRENT_TIMESTAMP` on PostgreSQL, an executor-bound microsecond text on SQLite via a `now` bind slot; soft deletion assigns its column the same way) — MySQL's `ON UPDATE` has no counterpart elsewhere and optimistic locking relies on it.
- `plus`/`minus` reference the column table-qualified (`"author"."read_count" + $9`): inside `ON CONFLICT DO UPDATE` a bare name is ambiguous on PostgreSQL.
- `?` in raw fragments (`raw`, `setRaw<Col>`, `addRawColumn<Alias>`) is rewritten to the dialect placeholder in bind order; the count must equal the binds (`IR_INVALID` otherwise). Fragments are otherwise raw SQL: write them portably (`LENGTH(x)`, `TRUE`/`FALSE`, not `DAYOFMONTH` or `= 0` against booleans).
- SQLite datetimes are text with six fraction digits (`YYYY-MM-DD HH:MM:SS.ffffff`) in UTC; the executor binds `time` values in that form and supplies the clock for omitted `default now` columns on insert, so a value read back compares equal. A string compared with or assigned to a datetime column is written in the same form: `YYYY-MM-DD[ T]HH:MM:SS[.f]` gets six fraction digits, and a string with `Z` or `±HH:MM` is converted to UTC. A date column takes `YYYY-MM-DD`. Any other string returns `CODEC_ENCODE`.
- A `decimal(P,S)` column uses MySQL `DECIMAL(P,S)`, PostgreSQL `NUMERIC(P,S)`, and SQLite `DECIMALINT(P,S)`. SQLite stores the exact value as a signed integer multiplied by 10^S; the executor converts this integer to the generated model's fixed-scale decimal string on read. The declaration requires `1 ≤ P ≤ 18` and `0 ≤ S ≤ P`, so the scaled value fits a signed 64-bit integer. The manifest records `scale: 0` explicitly for an integral decimal. Invalid text, excess digits, scale loss, and an incompatible stored cell fail with `CODEC_ENCODE` or `CODEC_DECODE`.
- A `jsontext` column is text on every dialect: `text` on PostgreSQL, `LONGTEXT` on MySQL, and TEXT on SQLite. The stored text is returned as written, so member order, duplicate keys, and an empty object against an empty array survive. The ORM has no JSON path conditions and no JSON indexes; data queried inside the database is modeled as columns or a child table.
- A `uuid` column is a native `uuid` on PostgreSQL, `char(36)` on MySQL, and TEXT on SQLite; clients bind uuid values as text.
- MySQL writes a literal default of a TEXT, BLOB, JSON, or geometry column in the expression form `DEFAULT ('value')`, which needs MySQL 8.0.13 or later; import reads it back as the literal.
- Booleans: PostgreSQL `boolean`, MySQL `BOOLEAN`/`TINYINT(1)` with numeric `0`/`1` defaults, and SQLite INTEGER 0/1 (read back as bool by column type); bind bools, not integers, in fragments/raw.
- CHECK expressions are rendered unchanged on PostgreSQL and SQLite. MySQL wraps the declared expression in an explicit boolean comparison because MySQL rejects predicate-valued `CASE` expressions as CHECK definitions; `NULL` remains `UNKNOWN` and therefore retains standard CHECK semantics. MySQL CHECK names are physically prefixed with the table name, `ck_<table>_<name>`, because MySQL scopes them to the database rather than the table; import removes the prefix and returns the logical MMD name. Generated constraint and index names are deterministically shortened to the engine's identifier limit with a hash suffix when required.
- `bind_slots[].col_type` is the dbspec type of the value a placeholder takes: the type of the column it is compared with or assigned to (a value that host styles encode is the stored value, so it has the column's type), the input type of a SQL-side style function (`HEX` takes `bytes`, `INET6_ATON` takes `text`), the result type of a compared column function, `i32` or `f64` for the interval of a relative time function, `text` for a secret, the column's type for a config value or an audit key, and `datetime` for a `now` slot. A `parent` slot carries `key_types`, the types of the compared key columns. Every slot except a placeholder inside a raw fragment has a type, and a slot without one is `IR_INVALID`. On PostgreSQL the Rust client binds each value as the PostgreSQL type of its slot's dbspec type and asks the server for no parameter or column information; a raw fragment placeholder takes the type of its value. Executors normalize SQLite time values and convert typed points to `POINT(x y)` before binding.
- aes/hex/ip host stages: `bind_slots[].host_styles` names the stages the executor applies to a bound value; `columns[].styles` carries them on read. AES uses the `ORM-AES2\0` authenticated ciphertext format, a random 12-byte nonce, AES-256-GCM, and the versioned key derivation defined in `docs/codec.md`.
- An entity with AES columns declares its key version column with the `aes_version` setting. A read selects that column once: the selected column when the request selects it, otherwise a hidden column; the key comes from the configured key versions using the stored version. A missing key or invalid ciphertext fails with `CONFIG` or `CODEC_DECODE`; the current key is never tried for an older version.
- Bench databases: `scripts/bench-db.sh` recreates the databases named by `BENCH_MYSQL_DSN`, `BENCH_POSTGRES_DSN` and `BENCH_SQLITE_DSN`, installs `schema/bench.dbs` through `go run ./bench/install`, runs `bench/sql/seed.mysql.sql`, `bench/sql/seed.pg.sql` or `bench/sql/seed.sqlite.sql`, and `go run ./bench/seedaes` fills the AES and blind-index columns using the authenticated host format.
- Conformance: `tests/conformance/vectors.postgres.json` / `vectors.sqlite.json` are recorded per dialect; every vector's **result** is identical to MySQL except `get_query`, whose result is the dialect's own SQL text.

## Schema definitions

This section records how MySQL, PostgreSQL and SQLite define, enforce and report schema objects, and decides for each feature whether the neutral schema language dbspec supports it. A feature is supported only when (1) dbspec has one common definition for it, (2) that definition renders with the same meaning on MySQL, PostgreSQL and SQLite, and (3) introspection restores the same definition from the catalog without hidden markers. A behavior generated from a setting, such as a CHECK or trigger that the renderer writes, is restored only when the catalog text equals the output of the declared renderer version.

Every fact cites the IDs of the shared probes in `tests/dialects` (`make dialect-facts-check`). A probe runs DDL, DML and catalog queries in its own disposable database, schema or file and fails when the database behaves differently. `render.*` probes check a proposed rendering. Facts without a probe ID cite the official manual. Each row ends with **Decision:**; **T8.1 review** marks a definition this record does not decide.

Notation: "renderer CHECK" is a CHECK constraint that the renderer writes for a type or setting; T8.1 fixes its exact text and name, and introspection accepts it only when the catalog text equals the renderer output for that server.

SQLite STRICT tables enforce storage classes but accept only `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB` and `ANY` as type names (`sqlite.strict.enforces_types`, `sqlite.strict.type_names_limited`). A STRICT table therefore cannot keep `varchar(n)` or `DECIMALINT(p,s)` in its catalog, and the length or scale would not be restorable. **Decision:** SQLite tables are not STRICT; the declared type name carries the neutral type and renderer CHECKs enforce it.

Time zone decision (owner: local date-time with a UTC connection rule):

- **Definition.** `datetime(p)` is a wall-clock date-time without a time zone. The runtime rule is that every connection reads and writes it in UTC: clients set MySQL `time_zone='+00:00'` and PostgreSQL `TimeZone='UTC'` on each connection, convert a value with an offset to UTC before binding, and never send an offset literal. SQLite stores the UTC text form that clients write.
- **Reasons.** The type is restored exactly from every catalog; the range 0001-01-01 to 9999-12-31 is accepted on all three databases (`mysql.datetime.range`, `postgres.timestamp.range`); under the UTC rule the clock functions agree: MySQL `NOW(6)` equals `UTC_TIMESTAMP(6)` (`mysql.render.datetime_utc_session`), PostgreSQL `CURRENT_TIMESTAMP` cast to `timestamp` equals `now() AT TIME ZONE 'UTC'` (`postgres.render.timestamp_utc_session`), and SQLite `'now'` is UTC (`sqlite.datetime.now_is_utc`). An offset literal would be converted by MySQL and dropped by PostgreSQL (`mysql.datetime.offset_literal_converted`, `postgres.timestamp.ignores_offset`), which is why clients never send one.
- **Consequences.** The database does not enforce the UTC rule: a writer outside the ORM whose session uses another time zone stores a different wall clock without an error, and raw SQL must follow the same rule. Instants with a time zone are unsupported, so the 1970 to 2038 limit of MySQL `TIMESTAMP` (`mysql.timestamp.range_2038`) never applies. The rejected alternatives were instants limited to that range on every database, and a rendering of MySQL `DATETIME` with PostgreSQL `timestamptz`, which introspection cannot restore.
- **Existing columns.** dbspec introspection reports a PostgreSQL `timestamptz` column as unsupported, so it is converted before the schema is introspected: `ALTER TABLE … ALTER COLUMN c TYPE timestamp(p) USING c AT TIME ZONE 'UTC'` keeps the UTC wall clock of each instant (`postgres.render.timestamptz_conversion`). A MySQL `TIMESTAMP` column converts to `DATETIME(p)` with `MODIFY` in a `+00:00` session (`mysql.render.timestamp_conversion`). There is no compatibility mapping: introspection reports a remaining `timestamptz` or `TIMESTAMP` column as unsupported.

| Trigger | A `BEFORE UPDATE` row trigger can assign `NEW` and fires when no value changes | A `BEFORE UPDATE` row trigger with a function can assign `NEW` and fires when no value changes | `NEW` cannot be assigned; an `AFTER UPDATE` trigger runs a separate `UPDATE` and fires when no value changes | `mysql.trigger.new_assignable`, `mysql.trigger.update_fires_when_unchanged`, `postgres.trigger.update_fires_when_unchanged`, `sqlite.trigger.new_read_only` | **Decision:** no trigger is rendered for stamping; see below | Not applicable |

Update-time stamping decision (owner: executor stamping):

- **Definition.** Update-time stamping is an ORM mapping setting of a table column. The executor assigns the column explicitly on every `UPDATE` it plans, with the UTC statement time. Nothing physical is created: no trigger, no `ON UPDATE` clause and no default change. The setting belongs to `manifestHash`, not to `schemaHash`, and introspection neither reads nor produces it.
- **Reasons.** The executor writes the same value on the three databases, and the column definition stays an ordinary `datetime(p)` that introspection restores exactly. MySQL `ON UPDATE CURRENT_TIMESTAMP` stays unsupported: it exists on MySQL only and skips an update that changes no value (`mysql.on_update.skipped_when_unchanged`), unlike the executor.
- **Consequences.** Raw SQL and writers outside the ORM do not stamp the column. Trigger stamping was rejected: it needs MySQL `SUPER` or `log_bin_trust_function_creators=ON` (`mysql.trigger.binlog_privilege_1419`), a PostgreSQL function object, and a second write per row on SQLite (`sqlite.trigger.new_read_only`).

Audit context options. The audit triggers read the audit of the unit of work that the client sets inside the transaction:

- **PostgreSQL** `set_config('<setting>', id, true)` is local to the transaction; after `COMMIT` the setting reads as an empty string in the same session and NULL in a session that never set it (`postgres.context.set_config_local`).
- **MySQL** user variables are session-scoped and survive `COMMIT` (`mysql.context.user_variable_session_scope`); a pooled connection keeps the value unless the client clears it.
- **SQLite** has no session variable. A trigger of a main table can be created over a `TEMP` table but fails when it fires (`sqlite.context.temp_table_not_visible`); a row in a main table is visible to every connection after `COMMIT` (`sqlite.context.main_table_shared`).

The options are (1) these per-database mechanisms with the rule that the client sets the id inside the transaction and clears it at the end of the transaction on MySQL and SQLite, or (2) an audit column written by the executor in each audited row, which changes the table definition.

**Decision:** neither channel. The audited row carries its own audit column with the key of an audit record, which the transaction inserts and the executor writes on every `INSERT` and `UPDATE`, so a row trigger reads the changing audit record from `NEW` and the previous one from `OLD` on every database. Generated triggers copy the row column by column into a history table instead of serializing it as JSON, and an audited table deletes only through its soft delete column, because `OLD` of a physical `DELETE` names the previous audit record rather than the deleting one. The session variable, the transaction setting and the `orm__context` table are not used. The definition is in [dbspec](dbspec.md#audit).

## Rendered statements

The renderer turns a dbspec document set into the statements of one dialect; an invalid set returns its diagnostics instead ([manifest and hashes](dbspec.md#manifest-and-hashes)). `tests/dbspec/ddl.json` lists the exact statements for every rendered form and is the normative text; this section states the rules behind it. Every vector of that file is applied to MySQL 8.4, PostgreSQL 17 and SQLite by `make dbspec-ddl-check`.

### Statements and their order

- Documents are rendered in `use` order (a used document before the document that uses it, ties by document name), and the tables of a document in document order. A used table is rendered once, by its own document.
- Every identifier is quoted: MySQL backticks, PostgreSQL and SQLite double quotes. Keywords are upper case and every statement is one line without a final semicolon.
- For each table: one `CREATE TABLE`; on SQLite then one `CREATE UNIQUE INDEX` per unique key; then one `CREATE INDEX` per index, in name order.
- After every table: on MySQL and PostgreSQL one `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY` per foreign key, tables in order and keys in name order; SQLite writes foreign keys inside `CREATE TABLE`, where a later table may be referenced.
- Last, the triggers of `immutable` and `audit`, tables in order; a PostgreSQL trigger follows the `CREATE FUNCTION` it executes.

### Inside `CREATE TABLE`

The parts come in this order: columns in declared order; the primary key; on MySQL and PostgreSQL the unique keys as named `UNIQUE` constraints in name order; on SQLite the foreign keys in name order; the renderer CHECKs in column order; the declared checks in name order. MySQL ends the statement with `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_bin`.

A column is written as its name, its type, `NOT NULL` or `NULL`, then its default:

| dbspec | MySQL | PostgreSQL | SQLite |
| --- | --- | --- | --- |
| `i16`, `i32`, `i64` | `SMALLINT`, `INT`, `BIGINT` | `smallint`, `integer`, `bigint` | `smallint`, `integer`, `bigint` |
| `bool` | `tinyint(1)` | `boolean` | `BOOLEAN` |
| `decimal(p,s)` | `DECIMAL(p,s)` | `numeric(p,s)` | `DECIMALINT(p,s)` |
| `f64` | `DOUBLE` | `double precision` | `REAL` |
| `varchar(n)` | `varchar(n) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin` | `varchar(n) COLLATE "C"` | `varchar(n)` |
| `text` | `LONGTEXT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin` | `text COLLATE "C"` | `TEXT` |
| `bytes` | `LONGBLOB` | `bytea` | `BLOB` |
| `uuid` | `char(36) CHARACTER SET ascii COLLATE ascii_bin` | `uuid` | `TEXT` |
| `date` | `DATE` | `date` | `DATE` |
| `time(p)` | `TIME(p)` | `time(p)` | `TIME` |
| `datetime(p)` | `DATETIME(p)` | `timestamp(p)` | `DATETIME` |

- **Identity.** MySQL `BIGINT NOT NULL AUTO_INCREMENT` with `PRIMARY KEY` at table level; PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL` with `PRIMARY KEY` at table level; SQLite `INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT` on the column and no table-level primary key.
- **Defaults.** A literal default is written in the dialect form of the literal (below). `default now` is MySQL `CURRENT_TIMESTAMP(p)`, PostgreSQL `statement_timestamp()`, and SQLite the UTC text with exactly p fraction digits: `strftime('%Y-%m-%d %H:%M:%S', 'now')` for p = 0, `substr(strftime('%Y-%m-%d %H:%M:%f', 'now'), 1, 20 + p)` for p ≤ 3, and `(strftime('%Y-%m-%d %H:%M:%f', 'now') || '0…')` with p − 3 zeros for p > 3, each in parentheses.
- **Literals.** Integers, `f64` and strings are written as in the document; a MySQL string doubles every backslash, because MySQL reads a backslash as an escape. `true` and `false` are `1` and `0` on MySQL and SQLite and `TRUE` and `FALSE` on PostgreSQL. A SQLite decimal literal is the integer value × 10^s: `7.50` of `decimal(13,2)` is `750`.
- **Keys.** `PRIMARY KEY (…)` lists the key columns; PostgreSQL keeps its default name `<table>_pkey`. A unique key is `CONSTRAINT <name> UNIQUE (…)` on MySQL and PostgreSQL and `CREATE UNIQUE INDEX <name> ON <table> (…)` on SQLite, whose catalog then reports the name. An index column is followed by `DESC` when it is descending.
- **Foreign keys.** `CONSTRAINT <name> FOREIGN KEY (…) REFERENCES <table> (…) ON DELETE <action> ON UPDATE <action>` with `RESTRICT`, `CASCADE` or `SET NULL`.
- **Checks.** A declared check is `CONSTRAINT <name> CHECK (<predicate>)`: column names quoted, `and`, `or`, `not`, `in`, `between`, `is null` and `is not null` in upper case, literals in the dialect form, parentheses as written.

### Renderer CHECKs

A renderer CHECK enforces a type the dialect does not enforce. It is named `<table>$<column>`; a dbspec name cannot contain `$`, so it never meets a declared name. One CHECK per column holds every condition of the column's type:

| dbspec | MySQL | PostgreSQL | SQLite |
| --- | --- | --- | --- |
| `i16`, `i32` | | | `typeof(c) IN ('integer', 'null') AND c BETWEEN <min> AND <max>` |
| `i64` (not identity) | | | `typeof(c) IN ('integer', 'null')` |
| `bool` | `c IN (0, 1)` | | `c IN (0, 1)` |
| `decimal(p,s)` | | | `typeof(c) IN ('integer', 'null') AND c BETWEEN -(10^p − 1) AND 10^p − 1` |
| `f64` | | | `typeof(c) IN ('real', 'null')` |
| `varchar(n)` | | | `length(c) <= n` |
| `uuid` | `REGEXP_LIKE(c, '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$', 'c')` | | `c GLOB` 36 character classes |
| `date` | | | `c IS date(c)` |
| `time(0)` | `c >= '00:00:00' AND c < '24:00:00'` | `c < '24:00:00'` | `c IS time(c) AND c < '24:00:00'` |
| `time(p)`, p > 0 | as `time(0)` | as `time(0)` | `length(c) = 9 + p AND substr(c, 1, 8) IS time(substr(c, 1, 8)) AND substr(c, 1, 8) < '24:00:00' AND substr(c, 9, 1) = '.' AND substr(c, 10) GLOB` p digit classes |
| `datetime(0)` | | | `length(c) = 19 AND c IS datetime(c) AND substr(c, 12, 2) < '24'` |
| `datetime(p)`, p > 0 | | | `length(c) = 20 + p AND substr(c, 1, 19) IS datetime(substr(c, 1, 19)) AND substr(c, 12, 2) < '24' AND substr(c, 20, 1) = '.' AND substr(c, 21) GLOB` p digit classes |

The SQLite `f64` CHECK has no probe in the schema definitions above: a REAL column converts integers and numeric text to real values and keeps other text, which this CHECK rejects (`sqlite.ddl.types_and_defaults`). PostgreSQL reads the input hour 24 of a `timestamp` as midnight of the next day, so `'2026-01-01 24:00:00'` stores `2026-01-02 00:00:00`, a valid date-time, while MySQL rejects that input (1292) and SQLite its renderer CHECK; no PostgreSQL CHECK applies, because the stored values are the same set (`postgres.ddl.types_and_defaults`). Clients never send hour 24.

### Triggers

A generated trigger is named `<table>$<event>`: `immutable_update`, `immutable_delete`, `audit_insert`, `audit_update` and `audit_delete`. A PostgreSQL trigger executes a function of the same name that the renderer owns. A rejection raises the message `table <table> is immutable` or `table <table> deletes through its soft delete column`: MySQL `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '…'`, PostgreSQL `RAISE EXCEPTION '…'`, SQLite `SELECT RAISE(ABORT, '…')`.

- `immutable`: `BEFORE UPDATE` and `BEFORE DELETE` row triggers that reject.
- `audit`: an `AFTER INSERT` row trigger inserts into the history table the action `'insert'`, a NULL previous audit record and the `NEW` value of every recorded column; an `AFTER UPDATE` row trigger inserts `'update'`, `OLD.<audit column>` and the `NEW` value of every recorded column; a `BEFORE DELETE` row trigger rejects. The insert names the action, previous and recorded columns in that order, the recorded columns in table column order, and leaves the history key to its identity ([audit](dbspec.md#audit)).
- A MySQL trigger body is the single statement; a PostgreSQL function body is `BEGIN … RETURN NULL; END` in `LANGUAGE plpgsql` (a `BEFORE` rejection never returns); a SQLite body is `BEGIN …; END`.

## Introspection

Introspection reads the current database (MySQL), the current schema (PostgreSQL) or the `main` database (SQLite) of a connection and returns one dbspec document, named by the caller, and the list of objects it cannot read. Every query reads all tables at once, so their number does not depend on the table count. `make dbspec-introspect-check` renders and applies every vector of `tests/dbspec/ddl.json` and every schema document, introspects the database, and requires the schema text of the result to equal the schema text of the source with its tables in name order and no unsupported object. It also runs `tests/dbspec/introspect.json`: each case renders its documents and runs its statements in an empty database of its dialect, with `{schema}` in a statement replaced by the name of that database or schema (a PostgreSQL case may create a second schema `{schema}_b`, which is dropped with it), then expects the introspected document in canonical form and the unsupported objects as `[kind, table, name]`; reasons are not compared. `make dbspec-introspect-<client>-check` runs the same round trips and cases through the PHP, TypeScript and Rust clients. `make dbspec-introspect-compare-check` applies a 20-table document of the stress shape (`make dbspec-introspect-compare-bench`, part of `make bench`: the 2000-table stress document with the release Rust runner) to each dialect, runs the four runners of `tests/dbspec/introspect` on it, and requires equal outputs (the canonical document, then a line `! kind<TAB>table<TAB>name` per unsupported object), the source schema text, no unsupported object, and each introspection within 5 seconds.

### Document

- Tables come in name order, columns in catalog position, constraints and indexes by name; a document holds no diagram and no comment.
- Every table and column whose name begins with `dbspec$` is left out and not reported: the plan history table `dbspec$plans`, the hidden tables and columns of a plan and the SQLite work table ([plans](plans.md#steps)).
- Only the settings that render in the database are read: `immutable` and `audit`, recognized from their triggers. The manifest settings live only in documents; a tool that synchronizes keeps them from the document it compares.

### Types and columns

| Catalog | MySQL `COLUMN_TYPE` | PostgreSQL `format_type` | SQLite declared type | dbspec |
| --- | --- | --- | --- | --- |
| 16, 32, 64-bit integer | `smallint`, `int`, `bigint` | `smallint`, `integer`, `bigint` | `smallint`, `integer`, `bigint` with its renderer CHECK | `i16`, `i32`, `i64` |
| boolean | `tinyint(1)` with its renderer CHECK | `boolean` | `BOOLEAN` with its renderer CHECK | `bool` |
| decimal | `decimal(p,s)` | `numeric(p,s)` | `DECIMALINT(p,s)` with its renderer CHECK | `decimal(p,s)` |
| float | `double` | `double precision` | `REAL` with its renderer CHECK | `f64` |
| bounded text | `varchar(n)` in `utf8mb4_0900_bin` | `character varying(n)` with collation `C` | `varchar(n)` with its renderer CHECK | `varchar(n)` |
| text | `longtext` in `utf8mb4_0900_bin` | `text` with collation `C` | `TEXT` without CHECK | `text` |
| bytes | `longblob` | `bytea` | `BLOB` | `bytes` |
| uuid | `char(36)` in `ascii_bin` with its renderer CHECK | `uuid` | `TEXT` with its renderer CHECK | `uuid` |
| date | `date` | `date` | `DATE` with its renderer CHECK | `date` |
| time of day | `time` or `time(p)` with its renderer CHECK | `time(p) without time zone` with its renderer CHECK | `TIME` with the renderer CHECK of one p | `time(p)` |
| date-time | `datetime` or `datetime(p)` | `timestamp(p) without time zone` | `DATETIME` with the renderer CHECK of one p | `datetime(p)` |

MySQL writes precision 0 without parentheses (`time`, `datetime`). A column whose type, collation or character set is not in this table, a MySQL `tinyint(1)`, `char(36)` or `time` column without its renderer CHECK, and a SQLite column whose CHECK is not the renderer output of one dbspec type are reported as unsupported.

- **Null.** `IS_NULLABLE`, `attnotnull` and `pragma_table_xinfo.notnull` give `null`.
- **Identity.** A single-column `bigint` primary key with MySQL `EXTRA` `auto_increment`, PostgreSQL `attidentity` `d`, or SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` is `identity`; PostgreSQL `attidentity` `a` (`ALWAYS`) is unsupported.
- **Defaults.** A literal default is read in the column's canonical default form: MySQL `COLUMN_DEFAULT` is the unescaped value (a string, a number, `1` or `0` for `bool`); PostgreSQL `pg_get_expr` gives a literal with a cast, such as `'-5'::integer`, `'a''b'::character varying` or `'2026-01-01'::date`, whose cast is removed; SQLite `dflt_value` is the rendered literal, a scaled integer for a decimal. A clock default is `default now` when it equals the renderer output: MySQL `CURRENT_TIMESTAMP` or `CURRENT_TIMESTAMP(p)` with `DEFAULT_GENERATED`, PostgreSQL `statement_timestamp()`, SQLite the `strftime` expression of that precision. Any other expression is unsupported.

### Keys, indexes and foreign keys

- The primary key keeps its column order. A MySQL `UNIQUE` index, a PostgreSQL `UNIQUE` constraint and a SQLite unique index whose origin is `c` are unique keys; any other index is an index, with `DESC` read from `COLLATION`, `indoption` or `pragma_index_xinfo.desc`.
- A prefix, partial, expression or full-text index, a PostgreSQL unique index without its constraint, a SQLite `sqlite_autoindex` other than the primary key, and an index whose name contains `$` are unsupported.
- A foreign key reads its name, columns, referenced table and columns and both actions; `NO ACTION`, `SET DEFAULT`, a deferrable key, `MATCH FULL` and a PostgreSQL key whose referenced table is in another schema are unsupported. SQLite foreign key names come from the `CREATE TABLE` text in `sqlite_master`.

### Checks

A check named `<table>$<column>` is a renderer CHECK. It must equal the catalog form of the renderer output for the column's type: MySQL `` (`c` in (0,1)) `` for `bool`, `` regexp_like(`c`,_utf8mb4\'^…$\',_utf8mb4\'c\') `` for `uuid`, `` ((`c` >= _utf8mb4\'00:00:00\') and (`c` < _utf8mb4\'24:00:00\')) `` for `time(p)`; PostgreSQL `CHECK ((c < '24:00:00'::time without time zone))` with the column name as `quote_ident` writes it; SQLite the rendered text itself. MySQL writes `CHECK_CLAUSE` again on every `ALTER TABLE` of the table, giving the uuid pattern an `_ascii` introducer and the time literals none (`mysql.check.alter_rewrites_introducers`), and writes a time literal that meets a `time(p)` column with `p` zero fraction digits (`mysql.check.alter_writes_time_precision`), so a MySQL clause is compared with its character set introducers and the zero fractions of its time literals removed; the literals of these templates are ASCII and a zero fraction keeps the value, so the comparison keeps their meaning. A renderer CHECK that differs, and a name with `$` that is no renderer CHECK, are unsupported.

Every other check is read into a predicate of [dbspec](dbspec.md#checks) and written in canonical form:

- **MySQL** `CHECK_CLAUSE`: fully parenthesized, lower-case keywords, backquoted columns, `in (a,b)` without spaces, a negative number as `-(n)`, and a string as `_utf8mb4` followed by the MySQL string literal, whose text is escaped a second time (`\'` and `\\` in the clause).
- **PostgreSQL** `pg_get_constraintdef`: `CHECK (…)` around a fully parenthesized expression, columns quoted only where `quote_ident` needs it, casts on literals and columns (`'x'::text`, `(s)::text`, `'-1.50'::numeric`, `(1.5)::double precision`), `= ANY (ARRAY[…])` for `in` and `<> ALL (ARRAY[…])` for `not in`, and a time or date-time literal without trailing zero fractions.
- **SQLite**: the text inside `CHECK (…)` of the `CREATE TABLE` statement, which is the rendered text; a decimal literal is the scaled integer.

A literal is read as the value of the column it meets and written in its canonical default form, so `'2100-01-01 00:00:00'` of a `datetime(6)` column becomes `'2100-01-01 00:00:00.000000'` and `1` of a `bool` column `true`. A check that does not read as a predicate, or whose predicate breaks a dbspec rule, is unsupported.

### Triggers

The triggers named `<table>$immutable_update` and `<table>$immutable_delete`, or `<table>$audit_insert`, `<table>$audit_update` and `<table>$audit_delete`, give the `immutable` or `audit` setting when every one of them equals the renderer output: MySQL timing, event and `ACTION_STATEMENT`; PostgreSQL `pg_get_triggerdef` with the schema prefix of the table removed and the `prosrc` of its function; SQLite the `CREATE TRIGGER` text. The `audit` parameters are read from the insert statement of `audit_insert` and the `OLD` column of `audit_update` before the comparison: the insert names the action, previous and recorded columns, the recorded columns include the audit column, and the columns of the table that it does not name become the `exclude` list in column order, as the schema text writes it; the audit record table is the target of the one foreign key of the audit column. A set that is incomplete or differs, and every other trigger, are unsupported.

### Unsupported objects

Each unsupported object is reported with its kind, its table and name where it has them, and the reason; the document leaves it out. The list is ordered by table, kind and name, and objects without a table come first. The kinds are `column`, `index`, `unique`, `foreign_key`, `check`, `trigger` (one per set for an `immutable` or `audit` setting that does not parse), `view`, `routine`, `sequence`, `event`, `partition` (a MySQL or PostgreSQL partitioned table and a PostgreSQL partition) and `table` (a SQLite `WITHOUT ROWID` or virtual table, and a table without a primary key).

An object that refers to a left-out object is reported and left out too: an index or a key on an unsupported column, a foreign key to a table that is left out, a check that names an unsupported column. The introspected document is parsed, and each object on a line that the parse rejects is reported with the diagnostic as its reason and left out, until the document parses. When the parse rejects a table, the table is left out with all its objects, and objects of that table rejected by the same parse are not reported apart from it. Each object is reported once, also a foreign key whose catalog rows are one per column.

SQLite reads table items from the `CREATE TABLE` text. A column definition is read when it is the renderer form: the quoted name, the declared type, `NULL` or `NOT NULL`, and the default if there is one; a column with any other clause (`CHECK`, `REFERENCES`, `UNIQUE`, `COLLATE`, …) is unsupported. A `CHECK`, `UNIQUE` or `FOREIGN KEY` item that is not the renderer form is reported with that kind and its constraint name, an empty name when it has none; the automatic index of a `UNIQUE` item or clause is not reported apart from it. A primary key item of another form, and any other item, leave the table out.
