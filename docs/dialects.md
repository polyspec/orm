# SQL dialects

A SQL dialect is the SQL syntax and execution rule set for one database system. In this project, `mysql`, `postgres`, and `sqlite` select identifier quoting, placeholders, type mapping, write syntax, and supported SQL functions. The planner asks the selected SQL dialect for every database-specific part; the IR and plan format do not change.
Executors still see the same plan shape: steps, bind slots, assemble.

Executor consequences: a `$n` renumbering step when expanding relation IN lists on
PostgreSQL, host-side AES/inet codecs where the table says "client-side", one DSN/driver per database
(Go: `pgx` stdlib / `modernc.org/sqlite`; Rust: sqlx features; PHP: `pdo_pgsql` / `pdo_sqlite`).

**Go driver packages.** `clients/go/orm` links MySQL only. A program that opens PostgreSQL or SQLite
imports the matching package for its side effect, as it would a `database/sql` driver:

```go
import (
    _ "github.com/polyspec/orm/clients/go/orm/pg"      // driver "postgres"
    _ "github.com/polyspec/orm/clients/go/orm/sqlite"  // driver "sqlite"
)
```

Without it `orm.Open` returns `CONFIG` naming the import. The split keeps a MySQL-only binary at
4.6MB instead of 11MB and avoids SQLite's package init (it parses `/etc/services`). Rust does the
same with sqlx features, PHP with the PDO extension that is installed.

## Rules that keep the three databases identical
- `UPDATE` always assigns the entity's updated timestamp explicitly (`updated_ts = CURRENT_TIMESTAMP(6)` on MySQL, `CURRENT_TIMESTAMP` on PostgreSQL, an executor-bound microsecond text on SQLite via a `now` bind slot) — MySQL's `ON UPDATE` has no counterpart elsewhere and optimistic locking relies on it.
- `plus`/`minus` reference the column table-qualified (`"author"."read_count" + $9`): inside `ON CONFLICT DO UPDATE` a bare name is ambiguous on PostgreSQL.
- `?` in raw fragments (`raw`, `setRaw<Col>`, `addRawColumn<Alias>`) is rewritten to the dialect placeholder in bind order; the count must equal the binds (`IR_INVALID` otherwise). Fragments are otherwise raw SQL: write them portably (`LENGTH(x)`, `TRUE`/`FALSE`, not `DAYOFMONTH` or `= 0` against booleans).
- SQLite datetimes are text with six fraction digits (`YYYY-MM-DD HH:MM:SS.ffffff`) in the connection time zone; the executor binds `time` values in that form and supplies the clock for `=now` columns on insert, so a value read back compares equal. A string compared with or assigned to a datetime column is written in the same form: `YYYY-MM-DD[ T]HH:MM:SS[.f]` gets six fraction digits, and a string with `Z` or `±HH:MM` is converted to the connection time zone. A date column takes `YYYY-MM-DD`. Any other string returns `CODEC_ENCODE`.
- A `decimal(P,S)` column uses MySQL `DECIMAL(P,S)`, PostgreSQL `NUMERIC(P,S)`, and SQLite `DECIMALINT(P,S)`. SQLite stores the exact value as a signed integer multiplied by 10^S; the executor converts this integer to the generated model's fixed-scale decimal string on read. The declaration requires `1 ≤ P ≤ 18` and `0 ≤ S ≤ P`, so the scaled value fits a signed 64-bit integer. The manifest records `scale: 0` explicitly for an integral decimal. Invalid text, excess digits, scale loss, and an incompatible stored cell fail with `CODEC_ENCODE` or `CODEC_DECODE`.
- A `jsontext` column is text on every dialect: `text` on PostgreSQL, `LONGTEXT` on MySQL, and TEXT on SQLite. The stored text is returned as written, so member order, duplicate keys, and an empty object against an empty array survive. The ORM has no JSON path conditions and no JSON indexes; data queried inside the database is modeled as columns or a child table.
- A `uuid` column is a native `uuid` on PostgreSQL, `char(36)` on MySQL, and TEXT on SQLite; clients bind uuid values as text.
- MySQL writes a literal default of a TEXT, BLOB, JSON, or geometry column in the expression form `DEFAULT ('value')`, which needs MySQL 8.0.13 or later; import reads it back as the literal.
- Booleans: PostgreSQL `boolean`, MySQL `BOOLEAN`/`TINYINT(1)` with numeric `0`/`1` defaults, and SQLite INTEGER 0/1 (read back as bool by column type); bind bools, not integers, in fragments/raw.
- CHECK expressions are rendered unchanged on PostgreSQL and SQLite. MySQL wraps the declared expression in an explicit boolean comparison because MySQL rejects predicate-valued `CASE` expressions as CHECK definitions; `NULL` remains `UNKNOWN` and therefore retains standard CHECK semantics. MySQL CHECK names are physically prefixed with the table name, `ck_<table>_<name>`, because MySQL scopes them to the database rather than the table; import removes the prefix and returns the logical MMD name. Generated constraint and index names are deterministically shortened to the engine's identifier limit with a hash suffix when required.
- `bind_slots[].col_type` names a `date`, `time`, `datetime`, or `point` target. Executors normalize SQLite time values and convert typed points to `POINT(x y)` before binding.
- aes/hex/ip host stages: `bind_slots[].host_styles` names the stages the executor applies to a bound value; `columns[].styles` carries them on read. AES uses the `ORM-AES2\0` authenticated ciphertext format, a random 12-byte nonce, AES-256-GCM, and the versioned key derivation defined in `docs/codec.md`.
- `aes_key_version` is required for AES columns. Reads select the key from the configured key versions using that stored version. A missing key or invalid ciphertext fails with `CONFIG` or `CODEC_DECODE`; the current key is never tried for an older version.
- Seeds: `bench/sql/seed.mysql.sql`, `bench/sql/seed.pg.sql`, and `bench/sql/seed.sqlite.sql`, then `go run ./bench/seedaes` fills the AES and blind-index columns using the authenticated host format.
- Conformance: `tests/conformance/vectors.postgres.json` / `vectors.sqlite.json` are recorded per dialect; every vector's **result** is identical to MySQL except `get_query`, whose result is the dialect's own SQL text.

## Schema definitions

This section records how MySQL, PostgreSQL and SQLite define, enforce and report schema objects, and decides for each feature whether the neutral schema language dbspec supports it. A feature is supported only when (1) dbspec has one common definition for it, (2) that definition renders with the same meaning on MySQL, PostgreSQL and SQLite, and (3) introspection restores the same definition from the catalog without hidden markers. A behavior generated from a setting, such as a CHECK or trigger that the renderer writes, is restored only when the catalog text equals the output of the declared renderer version.

Every fact cites the IDs of the shared probes in `tests/dialects` (`make dialect-facts-check`). A probe runs DDL, DML and catalog queries in its own disposable database, schema or file and fails when the database behaves differently. `render.*` probes check a proposed rendering. Facts without a probe ID cite the official manual. Each row ends with **Decision:**; **T8.1 review** marks a definition this record does not decide.

Notation: "renderer CHECK" is a CHECK constraint that the renderer writes for a type or setting; T8.1 fixes its exact text and name, and introspection accepts it only when the catalog text equals the renderer output for that server.

SQLite STRICT tables enforce storage classes but accept only `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB` and `ANY` as type names (`sqlite.strict.enforces_types`, `sqlite.strict.type_names_limited`). A STRICT table therefore cannot keep `varchar(n)` or `DECIMALINT(p,s)` in its catalog, and the length or scale would not be restorable. **Decision:** SQLite tables are not STRICT; the declared type name carries the neutral type and renderer CHECKs enforce it.

Time zone decision (owner: local date-time with a UTC connection rule):

- **Definition.** `datetime(p)` is a wall-clock date-time without a time zone. The runtime rule is that every connection reads and writes it in UTC: clients set MySQL `time_zone='+00:00'` and PostgreSQL `TimeZone='UTC'` on each connection, convert a value with an offset to UTC before binding, and never send an offset literal. SQLite stores the UTC text form that clients write.
- **Reasons.** The type is restored exactly from every catalog; the range 0001-01-01 to 9999-12-31 is accepted on all three databases (`mysql.datetime.range`, `postgres.timestamp.range`); under the UTC rule the clock functions agree: MySQL `NOW(6)` equals `UTC_TIMESTAMP(6)` (`mysql.render.datetime_utc_session`), PostgreSQL `CURRENT_TIMESTAMP` cast to `timestamp` equals `now() AT TIME ZONE 'UTC'` (`postgres.render.timestamp_utc_session`), and SQLite `'now'` is UTC (`sqlite.datetime.now_is_utc`). An offset literal would be converted by MySQL and dropped by PostgreSQL (`mysql.datetime.offset_literal_converted`, `postgres.timestamp.ignores_offset`), which is why clients never send one.
- **Consequences.** The database does not enforce the UTC rule: a writer outside the ORM whose session uses another time zone stores a different wall clock without an error, and raw SQL must follow the same rule. Instants with a time zone are unsupported, so the 1970 to 2038 limit of MySQL `TIMESTAMP` (`mysql.timestamp.range_2038`) never applies. The rejected alternatives were instants limited to that range on every database, and the current `ormgen` rendering of MySQL `DATETIME` with PostgreSQL `timestamptz`, which introspection cannot restore.
- **Existing columns.** dbspec introspection reports a PostgreSQL `timestamptz` column as unsupported, so it is converted before the schema is introspected: `ALTER TABLE … ALTER COLUMN c TYPE timestamp(p) USING c AT TIME ZONE 'UTC'` keeps the UTC wall clock of each instant (`postgres.render.timestamptz_conversion`). A MySQL `TIMESTAMP` column converts to `DATETIME(p)` with `MODIFY` in a `+00:00` session (`mysql.render.timestamp_conversion`). There is no compatibility mapping: introspection reports a remaining `timestamptz` or `TIMESTAMP` column as unsupported.

| Feature | MySQL 8.4 | PostgreSQL 17 | SQLite | Probes | Decision and neutral rendering | Introspection |
|---|---|---|---|---|---|---|
| Column clause | `ON UPDATE CURRENT_TIMESTAMP` fires when another column changes, not when no value changes, and an explicit value wins | No such clause (42601) | No such clause | `mysql.on_update.fires_on_change`, `mysql.on_update.skipped_when_unchanged`, `mysql.on_update.explicit_value_kept`, `postgres.on_update.unsupported`, `sqlite.on_update.unsupported` | **Decision:** the column clause is unsupported: it exists on MySQL only | MySQL `EXTRA` `on update …` reported as unsupported |
| Trigger | A `BEFORE UPDATE` row trigger can assign `NEW` and fires when no value changes | A `BEFORE UPDATE` row trigger with a function can assign `NEW` and fires when no value changes | `NEW` cannot be assigned; an `AFTER UPDATE` trigger runs a separate `UPDATE` and fires when no value changes | `mysql.trigger.new_assignable`, `mysql.trigger.update_fires_when_unchanged`, `postgres.trigger.update_fires_when_unchanged`, `sqlite.trigger.new_read_only` | **Decision:** no trigger is rendered for stamping; see below | Not applicable |

Update-time stamping decision (owner: executor stamping):

- **Definition.** Update-time stamping is an ORM mapping setting of a table column. The executor assigns the column explicitly on every `UPDATE` it plans, with the UTC statement time. Nothing physical is created: no trigger, no `ON UPDATE` clause and no default change. The setting belongs to `manifestHash`, not to `schemaHash`, and introspection neither reads nor produces it.
- **Reasons.** The executor writes the same value on the three databases, and the column definition stays an ordinary `datetime(p)` that introspection restores exactly. MySQL `ON UPDATE CURRENT_TIMESTAMP` stays unsupported: it exists on MySQL only and skips an update that changes no value (`mysql.on_update.skipped_when_unchanged`), unlike the executor.
- **Consequences.** Raw SQL and writers outside the ORM do not stamp the column. Trigger stamping was rejected: it needs MySQL `SUPER` or `log_bin_trust_function_creators=ON` (`mysql.trigger.binlog_privilege_1419`), a PostgreSQL function object, and a second write per row on SQLite (`sqlite.trigger.new_read_only`).

Audit context options. The audit triggers read an operation id that the client sets inside the transaction:

- **PostgreSQL** `set_config('<setting>', id, true)` is local to the transaction; after `COMMIT` the setting reads as an empty string in the same session and NULL in a session that never set it (`postgres.context.set_config_local`).
- **MySQL** user variables are session-scoped and survive `COMMIT` (`mysql.context.user_variable_session_scope`); a pooled connection keeps the value unless the client clears it.
- **SQLite** has no session variable. A trigger of a main table can be created over a `TEMP` table but fails when it fires (`sqlite.context.temp_table_not_visible`); a row in a main table is visible to every connection after `COMMIT` (`sqlite.context.main_table_shared`).

The options are (1) these per-database mechanisms with the rule that the client sets the id inside the transaction and clears it at the end of the transaction on MySQL and SQLite, or (2) an operation column written by the executor in each audited row, which changes the table definition.

**T8.1 review.** One common definition exists for the ORM: an audited write requires an operation id that the executor sets inside the transaction and that no other transaction can read. The three mechanisms give that meaning only through the executor, so they are not just an implementation detail: MySQL keeps the variable for the session, so the meaning depends on the executor clearing it after every `COMMIT` and `ROLLBACK` (the Go client ignores the result of that clear, `clients/go/orm/utils.go:152`), and a raw SQL writer on the same connection can still pass the trigger with a stale id; SQLite needs the ORM-owned main table `orm__context`, a physical object outside the dbspec definition. T8.1 decides between option 1 with these limits stated as part of the definition and option 2.
